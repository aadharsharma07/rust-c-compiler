# Lesson 14.1 — Why Registers Matter
**Part:** 3 — Build the Compiler · **Unit:** 14 — Register Allocation · **Type:** Learning · **Est. time:** 2–3 h · **Tests:** none
**Prerequisites:** lessons 13.1–13.6; 6.2 (registers and memory); 6.4 (caller- and callee-saved registers)

## Overview
Before building a register allocator, you need a clear picture of what it is trying to achieve: why values in
registers beat values in stack slots, which registers `rcc` may hand out, what makes a value impossible to keep in a
register, and what happens when there aren't enough. This lesson builds that vocabulary and has you measure the gap
between your compiler and `clang` on real code.

## The lesson

### Where `rcc` is today
Since 9.3, every pseudoregister gets its own stack slot, and the fix-up pass patches instructions that end up with two
memory operands by routing one through `%r10`. For
```c
int f(int a, int b) { int c = a + b; return c * 2; }
```
your output looks something like:
```
    movl  %edi, -4(%rbp)       # copy parameter a to its slot
    movl  %esi, -8(%rbp)       # copy parameter b to its slot
    movl  -4(%rbp), %r10d      # tmp.0 = a      (fix-up: memory -> memory)
    movl  %r10d, -12(%rbp)
    movl  -8(%rbp), %r10d      # tmp.0 += b
    addl  %r10d, -12(%rbp)
    movl  -12(%rbp), %r10d     # c = tmp.0
    movl  %r10d, -16(%rbp)
    ...                        # and so on for c * 2 and the return
```
Every value makes a round trip to memory. If instead `a`, `b` and `c` lived in registers, the body could be:
```
    movl  %edi, %eax
    addl  %esi, %eax
    imull $2, %eax
```
That's roughly what a simple register allocator produces. (`clang -O1` does even better with a single `lea`;
look on Godbolt.)

Python has the same "everything in memory" shape. Run `python3 -c "import dis; dis.dis(lambda a, b: (a + b) * 2)"`:
CPython's bytecode loads `a` and `b` from the frame's array of locals (`LOAD_FAST`) onto an evaluation stack, operates,
and stores back. CPython is an interpreter and accepts that cost; a compiler doesn't have to.

### Why memory costs more
A register is inside the CPU core and is read in the same cycle an instruction executes. A stack slot is in memory;
even when it is in the fastest cache (L1), a load takes several cycles, and a store followed by a load of the same slot
creates a dependency the CPU must track. Memory operands also make instructions longer, and the fix-up pass adds extra
instructions. Fewer instructions, shorter instructions and fewer memory dependencies all add up to faster code. But
instruction count is a proxy, not the goal: always measure, and always check the output is still correct.

### Which registers can `rcc` allocate?
x86-64 has 16 general-purpose registers. Four are off-limits:
- `%rsp` and `%rbp` hold the stack frame.
- `%r10` and `%r11` are the fix-up pass's scratch registers. Values that don't get a register still go to memory and
  still need fix-ups, so these two must stay free.

That leaves **12** allocatable registers: `ax, bx, cx, dx, di, si, r8, r9, r12, r13, r14, r15`. If you implemented
`double` in Unit 12, floating-point values use a separate set: `xmm0`–`xmm13`, keeping `xmm14`/`xmm15` as scratch.
Integer and floating-point values are allocated separately and never compete for the same registers.

### Caller-saved and callee-saved, revisited
Recall from 6.4 and 11.3:
- **Caller-saved** (`ax, cx, dx, di, si, r8, r9`, plus `r10, r11` and all `xmm` registers): any `call` may overwrite
  them. A value that must survive a call can't sit in one of these.
- **Callee-saved** (`bx, r12–r15`, plus `rbp`): a function that uses one must save it on entry and restore it before
  returning. Using one costs a `push`/`pop` pair per function, but the value survives calls.

So, of the 12 allocatable registers, 7 are caller-saved (free to use, but wiped by calls) and 5 are callee-saved
(cost a save and restore, but safe across calls).

### Live ranges and interference
A value is **live** at a point if it holds something that may still be read later (you computed exactly this for
dead-store elimination in 13.6). Its **live range** is the set of program points where it is live. Two values whose
live ranges overlap **interfere**: they need different registers. Two values that are never live at the same time can
share one register, one after the other.
```
                   live after this line
    a = 1          {a}
    b = 2          {a, b}     <- a and b are live together: they interfere
    c = a + b      {c}        <- a and b are read here for the last time
    return c * 2   {}
```
Here `c` can reuse `a`'s register, because `a` is dead from the moment `c` is written.

### Register pressure and spilling
**Register pressure** at a point is the number of values live there. If the pressure ever exceeds 12, at least one
value must stay in memory at that point: it is **spilled**. A good allocator spills the value that is cheapest to keep in
memory: one used rarely, not a loop counter read on every iteration.

### What can never go in a register
- **Static variables** (11.4): they live at a fixed address in `.data`/`.bss` and other functions may read them.
- **Address-taken variables** (12.5): if the program computes `&x`, then `x` must have an address, and registers don't.
- **Aggregates** (arrays and structs, 12.6 and 12.9): too large, and accessed by address.
These keep going to memory exactly as now. Everything else is a **candidate** for a register.

### Registers with fixed jobs
Some instructions use specific registers whether you like it or not: `idiv` and `cdq` use `%eax` and `%edx`; the
return value goes in `%eax`; arguments go in `%edi`, `%esi`... An allocator must know these facts, or it will put a
value in `%edx` right before a `cdq` overwrites it. Lesson 14.2 handles this by making hard registers part of the graph.

### The allocator in one sentence
Give each candidate pseudo a register so that no two interfering pseudos share one, and spill the ones that don't fit.
That is **graph colouring** (14.3) on an **interference graph** (14.2). The analogy: scheduling exams so that no student
has two at once, with 12 time slots. Exams are pseudos, "shares a student" is interference, time slots are registers.

## Check your understanding
1. Why does your compiler need `%r10` at all? What would break if the allocator gave a pseudo `%r10`?
2. A value is live across a call to `putchar`. Which registers may hold it, and what does each choice cost?
3. What is the register pressure just before `return a + b + c` if `a`, `b`, `c` are all live there?
4. Why is spilling a value used once better than spilling a loop counter?
5. Why can't static and address-taken variables live in registers?
6. Why is minimising instruction count not the same as minimising run time?

## Common pitfalls
- Planning to allocate `%r10`/`%r11`, then discovering fix-ups clobber them.
- Forgetting that `%rax`, `%rdx` (and `%rcx`, if you did shifts) have fixed jobs in some instructions.
- Treating callee-saved registers as free: each one used adds save/restore code.
- Comparing instruction counts without checking that the programs still print the same output.
