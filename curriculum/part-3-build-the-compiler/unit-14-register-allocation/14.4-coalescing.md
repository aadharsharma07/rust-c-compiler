# Lesson 14.4 — Coalescing
**Part:** 3 — Build the Compiler · **Unit:** 14 — Register Allocation · **Type:** Builds coalescing · **Est. time:** 8–12 h · **Tests:** ch. 20
**Prerequisites:** lessons 14.1–14.3

## Overview
Your allocator now assigns registers, but the output is still full of `mov`s between them: parameters copied out of
`%edi`, results moved into `%eax`, temporaries copied into variables. **Coalescing** merges the two sides of such a
`mov` into one graph node before colouring, so they are guaranteed the same register and the `mov` disappears. The
catch is that careless merging can make the graph harder to colour, so you implement *conservative* coalescing, which
only merges when it can prove no harm is done.

## The lesson

### Why there are so many moves
Look at your output for any function. TACKY introduced a temporary for every intermediate result, codegen copies each
parameter from its argument register into a pseudo (11.3), every `return` moves a value into `%eax`, and every call
moves arguments into `%edi`, `%esi`... After 14.3, some of these become `mov %reg, %reg` by luck and get deleted, but
most survive because colouring chose different registers for the two sides. If `mov a, c` ends up with `a` and `c` in
the same register, the move is a no-op. Coalescing forces that outcome rather than hoping for it.

### Merging two nodes
To **coalesce** `a` and `c` means to replace both nodes with a single node `ac` whose neighbours are the union of their
neighbours, then rename every `a` and `c` in the instructions to the merged name. After colouring, both get the same
register and the `mov a, c` becomes `mov %r, %r`, which is deleted.

**When it is legal.** Only if `a` and `c` do **not** interfere. Thanks to the `mov` exception in 14.2, the move itself
never creates an edge between its own source and destination, so many move pairs qualify. Never merge two hard
registers (they are different registers). If one side is a hard register, the merged node **is** that hard register:
merging pseudo `c` into `%eax` simply means "`c` lives in `%eax`".

### When it is unwise: aggressive coalescing
The merged node has more neighbours than either original, and a node's degree is exactly what decides colourability.
Take this graph, which is a path and needs only 2 colours:
```
a — c — d — b          colouring: a=0, c=1, d=0, b=1
```
Suppose the code contains `mov a, b`. `a` and `b` don't interfere, so merging is legal. But the result is:
```
ab — c, ab — d, c — d   (a triangle: needs 3 colours)
```
With *k* = 2, a value now has to spill. You traded a one-cycle `mov` for memory traffic on every use. **Aggressive**
coalescing (merge every legal pair) can do this; **conservative** coalescing tests first.

### The Briggs test (for any pair)
Merge `a` and `b` only if the merged node would have **fewer than *k* neighbours of significant degree**, where a
neighbour has *significant degree* if its degree is ≥ *k*. Count each neighbour's degree **after** the merge: a node
adjacent to both `a` and `b` loses one edge, because its two edges become one.

Why this is safe: during simplify (14.3), every neighbour with degree < *k* will be removed. Afterwards, the merged node
has fewer than *k* neighbours left, so it can be removed too. The merged node is no harder to colour than before.

Applied to the triangle example: `ab`'s neighbours are `c` and `d`, each with degree 2 after the merge. With *k* = 2,
both are significant, and 2 is not < 2, so Briggs **refuses** the merge. Exactly right.

### The George test (pseudo into hard register)
Merge pseudo `a` into hard register `r` only if **every neighbour `t` of `a` either already interferes with `r`, or has
degree < *k***. Why it is safe: neighbours that already interfere with `r` gain no new constraint, and low-degree
neighbours will be simplified away whatever happens. So merging adds nothing that could block colouring.

Why a second test? Hard-register nodes have enormous neighbour lists (every other hard register, plus every pseudo live
across a write to them), so Briggs almost always fails for them. George looks only at the pseudo's neighbours. A common
policy: Briggs for pseudo–pseudo pairs, George for pseudo–hard-register pairs.

### Worked example (k = 12)
The program from 14.2:
```
1: movl $1, a
2: movl $2, b
3: movl a, c
4: addl b, c
5: movl c, %eax
6: ret
```
Graph: `a — b`, `b — c`, and the 12 hard registers all connected to each other.
- **`mov a, c` (line 3).** `a` and `c` don't interfere. Merged node `ac` has one neighbour, `b`, of degree 1: no
  significant neighbours, 0 < 12, so Briggs merges. Graph: `ac — b`.
- **`mov c, %eax` (line 5).** `c` is now `ac`. `ac` and `ax` don't interfere. George: `ac`'s only neighbour `b` has degree
  1 < 12, so merge `ac` into `ax`. Graph: `ax — b`.
- **Rename and delete self-moves.** `a` and `c` become `%eax`; line 3 becomes `movl %eax, %eax` (deleted), and so does line 5:
```
movl $1, %eax
movl $2, b
addl b, %eax
ret
```
Rebuild liveness and the graph. No more move pairs to merge, so colour: `b` interferes with `ax` and gets some other
register, say `%ecx`. Six instructions became four, with no stack traffic at all.

### Tracking merges: union-find
After several merges you need to answer "what is `a` called now?" quickly, for chains like `a → c → %eax`. A
**union-find** (or *disjoint-set*) structure does this: each name points to a parent, and following parents leads to the
group's **representative**. `find(x)` follows the chain (and, with *path compression*, re-points every visited name
straight at the representative so later lookups are instant); `union(x, y)` makes one representative point at the
other. When a hard register is involved, it must always be the representative. In Python terms it is a `dict` of
parent pointers plus a tiny loop.

### Iterating
Merging changes liveness and degrees, which can enable or block other merges. The loop, per function:
```
repeat:
    build liveness and the interference graph
    for each mov whose source and destination are both nodes:
        if they don't interfere and the conservative test passes: merge (update the graph's adjacency as you go)
    if nothing merged: break
    rename every operand to its representative; delete mov x, x
then: spill costs -> colour -> rewrite -> pseudo replacement -> fix-up   (as in 14.3)
```
Updating the graph in place after each merge keeps later tests in the same round accurate; rebuilding from scratch
between rounds keeps everything honest, because the in-place updates are only approximate after renaming.

## Build

**Practice first (paper).**
1. Find a graph and a `mov` where Briggs refuses but George (with one side a hard register) accepts.
2. Run the worked example's coalescing yourself, then add a line `movl %edi, a` at the top (with `a`'s first write
   removed) and redo it. What happens to `a`?

**Spec.** Input: one function's assembly and interference graph. Output: the function with merged names renamed and
self-moves deleted, ready for colouring.
- **Coalescing pass:** considers each `mov` with a node on both sides; skips pairs that interfere, pairs of two hard
  registers, and pairs failing the conservative test. After each merge, updates the graph: union of neighbour sets,
  neighbours re-pointed at the representative, degrees adjusted. Records merges in a union-find or rename map.
- **Rename pass:** rewrites every operand to its representative and deletes `mov`s whose source equals destination.
- **Driver loop:** as above, then the 14.3 pipeline.
- **Correctness conditions:** merged nodes never interfere; hard registers keep their identity; behaviour is unchanged;
  no new spills compared with running without coalescing, in normal cases.
- **Edge cases:** a `mov` from a constant or memory (never a candidate); an existing `mov a, a`; chains of moves
  (`a → b → c → %eax`); parameters copied from argument registers; merged nodes that spill anyway; never merge across
  register classes (integer with `xmm`).

**Suggested order.** Briggs and George as small pure functions with unit tests on hand-built graphs → union-find →
one round of coalescing plus rename → the full loop → run chapter 20 and compare your output with and without coalescing.

## Check your understanding
1. Why can't two interfering nodes be coalesced?
2. In the Briggs test, why do neighbours with degree < *k* not count?
3. Why does George work well for hard registers when Briggs mostly fails?
4. After a round of merges, which names must be renamed, and which `mov`s disappear?
5. Why rebuild liveness between rounds instead of trusting the incrementally updated graph forever?

## Common pitfalls
- Forgetting the "neighbour of both" adjustment in Briggs, making the test wrongly pessimistic (or, counted the other way, unsafe).
- Making a pseudo the representative of a merge with a hard register, losing the register's identity.
- Leaving stale edges that still point at a merged-away node.
- Coalescing across register classes.
- Looping forever because renaming wasn't applied before rebuilding, so the same pair is "merged" every round.
