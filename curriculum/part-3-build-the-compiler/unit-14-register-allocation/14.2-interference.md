# Lesson 14.2 — Interference
**Part:** 3 — Build the Compiler · **Unit:** 14 — Register Allocation · **Type:** Builds interference graph · **Est. time:** 6–8 h · **Tests:** ch. 20
**Prerequisites:** lessons 14.1; 13.3 (control-flow graphs), 13.4 (dataflow analysis), 13.6 (liveness)

## Overview
You build the data structure a register allocator works on: the **interference graph**, with one node per value that
might get a register and an edge between any two values that must not share one. To build it you run liveness analysis
over *assembly* instructions, which means knowing exactly which registers every instruction reads and writes,
including the ones it uses silently. Nothing in your output changes yet; this lesson is about getting the graph right.

## The lesson

### What "interfere" means precisely
14.1 said two values interfere if they are live at the same time. The precise rule compilers use is slightly
different: **`d` interferes with `l` if an instruction writes `d` at a point where `l` is live afterwards** (and `l` is
not simply a copy of the same value). Why phrase it via writes? A register only changes when something writes it. If
`d` is written while `l` is still needed, then putting both in one register would destroy `l`. If two values are live
together but neither is ever written while the other is live, they always hold the same value and could share.

### Nodes: values and hard registers
The graph has two kinds of node:
- **Every allocatable hard register** (the 12 from 14.1). These are *pre-coloured*: each already "is" a register. All
  of them interfere with each other, so each gets a distinct colour in 14.3.
- **Every candidate pseudo**: a pseudoregister that is not static, not address-taken (never the source of a
  `lea`/`GetAddress`), and not an array or struct. Other pseudos keep going to memory as before.

Why include hard registers? Because instructions already use them: `%edi` holds an argument, `%eax` is written by
`idiv` and `call`, `%edx` by `cdq`. If a pseudo is live while `cdq` writes `%edx`, the pseudo must not be given `%edx`.
Making `%edx` a node with an edge to that pseudo expresses the constraint in the same language as everything else.

If you implemented `double`, build a **separate** graph for `xmm` registers and `double` pseudos. The two classes never
interfere with each other and are coloured independently.

### Reads and writes of every instruction
Liveness needs, for each instruction, the registers and candidate pseudos it **reads** and **writes**. Memory operands
aren't nodes, but registers *inside* an address are reads (the `%rax` in `8(%rax)` is read, even if the instruction
writes to that memory).

| Instruction | Reads | Writes |
|---|---|---|
| `mov src, dst` (and sign/zero-extending moves, conversions) | src | dst |
| `add/sub/imul/and/or/xor src, dst` | src, dst | dst |
| `neg/not dst` | dst | dst |
| `cmp a, b` | a, b | (nothing) |
| `setCC dst` | dst (conservative; see pitfalls) | dst |
| `cdq` / `cqo` | ax | dx |
| `idiv op` / `div op` | op, ax, dx | ax, dx |
| shifts by `%cl` (if you did them) | operand, cx | operand |
| `lea src, dst` | registers in the src address | dst |
| `push op` | op | (nothing) |
| `call f` | the argument registers this call actually uses | every caller-saved register |
| `ret`, jumps, labels | (nothing; `ret` is handled at the exit) | (nothing) |

Two entries deserve explanation. `call` **writes** every caller-saved register because, as far as this function knows,
the callee may overwrite all of them. It **reads** only the argument registers this particular call uses: if `f` takes
two arguments, only `%edi` and `%esi` carry meaning; claiming it reads all six would make unrelated values look live.
Your backend symbol table can tell you each function's parameter registers.

### Liveness over assembly
This is the same backward analysis you built in 13.6, run on a CFG of **assembly** basic blocks (labels start blocks;
`jmp`, `jCC` and `ret` end them). The transfer function for one instruction is
```
live_before = (live_after − writes) ∪ reads
```
and at a block's end, `live_out` is the union of its successors' `live_in`. The boundary condition at `Exit`: the
return-value register is live, `ax` for a function returning an integer (`xmm0` for `double`; for struct returns, the
registers 12.9 uses). For a `void` function, nothing is live at exit. If your 13.4 framework is generic over the
instruction type, reuse it; if it isn't, this is the moment to make it so rather than copying it.

### The interference rule
For each instruction, for each node `d` it **writes**, for each node `l` live **after** it, add the edge `d — l`, unless:
- `l` is `d` itself, or
- the instruction is `mov src, d` and `l` is `src`.

The `mov` exception matters: after `mov a, c`, `a` and `c` hold the *same* value, so sharing a register is harmless,
and if they do share, the `mov` becomes `mov %reg, %reg` and can be deleted. Lesson 14.4 exploits this deliberately.
Edges are symmetric: always add both directions.

### Worked example
```
                        live after
1: movl $1, a           {a}
2: movl $2, b           {a, b}
3: movl a, c            {b, c}
4: addl b, c            {c}
5: movl c, %eax         {ax}
6: ret                  (Exit: {ax})
```
Work backwards from `{ax}` at the exit. Line 5 writes `ax`, reads `c`: live before is `{c}`. Line 4 writes and reads
`c`, reads `b`: `{b, c}`. Line 3 writes `c`, reads `a`: `{a, b}`. And so on.

Now the edges. Line 1 writes `a`; live after is `{a}`: nothing new. Line 2 writes `b` while `a` is live: **`a — b`**.
Line 3 writes `c` while `b` is live: **`b — c`** (`a` is the `mov` source, and not live after anyway). Line 4 writes `c`;
only `c` is live: nothing. Line 5 writes `ax`; only `ax` is live: nothing. The pseudo part of the graph:
```
a: b        b: a, c        c: b
```
plus the 12 hard registers, all connected to each other. `a` and `c` don't interfere, so they can share a register.

### A pseudo live across a call
```
movl $5, x         # x is read after the call
call f             # writes ax, cx, dx, di, si, r8, r9 (and r10, r11) while x is live
movl %eax, y
addl x, y
```
The `call` writes every caller-saved register while `x` is live, so `x` gets an edge to each allocatable caller-saved
register. The only colours left for `x` are callee-saved registers (or a spill). That is exactly the rule from 14.1,
falling out of the graph automatically.

## Build

**Practice first (paper, ~30 min).** Compute live-after sets and the interference graph for:
```
movl %edi, x
movl $10, y
cmpl y, x
jl   L1
movl x, %eax
ret
L1:
movl y, %eax
ret
```
(Hint: two blocks follow the `jl`; live-after at the `jl` is the union of both successors' live-in.)

**Spec.** Input: one function's assembly (with pseudos), plus the backend symbol table. Output: an interference graph.
No change to emitted code.
- **Reads/writes helper:** maps one instruction to the set of nodes read and written, covering every instruction your
  back end emits, including the implicit operands in the table.
- **Assembly CFG and liveness:** reuse the Unit 13 framework; boundary at `Exit` is the return-value register(s).
- **Graph:** one node per allocatable hard register and per candidate pseudo. Each node stores its set of neighbours,
  plus empty slots for a spill cost and a colour (filled in 14.3). A node ID is either a hard register or a pseudo name.
- **Candidate filter:** exclude statics, address-taken variables and aggregates, using the backend symbol table.
- **Debug output:** a flag or test helper that prints the graph as adjacency lists (or Graphviz `dot`).

**Suggested order.**
1. The reads/writes helper with a unit test per instruction kind.
2. Liveness over assembly; test on the worked example's live-after sets.
3. Graph construction; test the worked example and the call example.
4. Run on a real chapter 20 program and read the printed graph for sanity.

## Check your understanding
1. Why does `mov a, c` not make `a` and `c` interfere, while `add a, c` would?
2. Why must hard registers be nodes in the graph instead of being handled separately?
3. Which pseudos are not nodes, and why can't they live in registers?
4. What does `idiv` read and write, and what goes wrong if you forget `dx`?
5. Why does a `call` read only the argument registers it uses? What would happen if it read all six?

## Common pitfalls
- Missing implicit operands (`cdq`, `idiv`, `call`, shifts), producing allocations that silently clobber `ax`/`dx`/`cx`.
- `setCC` writes only the low byte of its operand. Treating it as also *reading* the operand is the conservative,
  always-correct choice.
- Adding edges in one direction only.
- Applying the `mov` exception to other instructions (including extending moves, which change the value).
- Treating static or address-taken variables as candidates.
