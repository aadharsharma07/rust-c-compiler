# Lesson 9.5 — Arithmetic in Assembly
**Part:** 3 — Build the Compiler · **Unit:** 9 — Expressions and an IR · **Type:** Builds arithmetic codegen · **Est. time:** 3–5 h · **Tests:** ch. 3
**Prerequisites:** lessons 9.3, 9.4; 6.1 (sign extension); 6.3 (x86-64 instructions)

## Overview
The parser now builds `Binary` nodes; this lesson takes them all the way to machine code. You'll add
a `Binary` instruction to TACKY, then learn how x86-64 really does arithmetic: two-operand
instructions that overwrite one input, and a division instruction with fixed registers and a
setup step. Each new instruction comes with its own operand rules, so the fix-up pass from 9.3
grows. At the end, chapter 3 passes.

## The lesson

### TACKY gets a binary instruction
```
instruction     = Return(val) | Unary(unary_operator, val src, val dst)
                | Binary(binary_operator, val src1, val src2, val dst)
binary_operator = Add | Subtract | Multiply | Divide | Remainder
```
Translation follows the same rule as unary (9.2): translate the left operand (giving `v1`), then
the right (giving `v2`), make a fresh temporary `dst`, emit `Binary(op, v1, v2, dst)`, return `dst`.

`return 1 + 2 * 3;` becomes:
```
tmp.0 = 2 * 3
tmp.1 = 1 + tmp.0
return tmp.1
```
A note on order: C doesn't specify whether the left or right operand is evaluated first (in
Python, it's always left first). Left-to-right is a legal choice, and the simplest. It won't matter
until expressions have side effects in Unit 10.

### Two-operand arithmetic
Most x86-64 arithmetic instructions take two operands and **overwrite the second** (AT&T order is
source, destination; recall 6.3). The destination is both an input and the output:
```
addl  %ecx, %eax        # eax = eax + ecx
subl  $3, -4(%rbp)      # mem = mem - 3          (source subtracted FROM destination)
imull %ecx, %eax        # eax = eax * ecx
```
Python analogy: these are augmented assignments. `addl %ecx, %eax` is `eax += ecx`; `subl $3, x`
is `x -= 3`. So a three-address `dst = src1 op src2` becomes "copy, then augment":
```
Binary(op, src1, src2, dst)   →   Mov(src1, dst)
                                  Binary(op, src2, dst)      # dst op= src2
```
Check it on subtraction: `dst = 5 - 3` → `dst = 5`, then `dst -= 3` → 2. Correct. Swapping the
operands gives `dst = 3; dst -= 5` → −2, a very common bug.

### Division: fixed registers and `cdq`
Division is the odd one out. `idivl x` (signed integer divide) takes a single operand, the
divisor. The dividend is implicit: it's the **64-bit** value formed by `%edx` (high 32 bits) and
`%eax` (low 32 bits), written `%edx:%eax`. After it runs, the **quotient** is in `%eax` and the
**remainder** in `%edx`. One instruction gives you both `/` and `%`.

Since our dividend is a 32-bit value in `%eax`, the high half `%edx` must hold its correct
**sign extension** (6.1): all zeros if `%eax` is non-negative, all ones if negative. The `cdq`
instruction ("convert doubleword to quadword") does exactly that. Skip it and whatever happens to
be in `%edx` becomes part of the dividend: you'd divide some huge number instead.

```
 before cdq:   %edx = ????????     %eax = FFFFFFF9   (-7)
 after cdq:    %edx = FFFFFFFF     %eax = FFFFFFF9   (%edx:%eax = -7 as 64 bits)
 idivl (2):    %eax = FFFFFFFD (-3, quotient)   %edx = FFFFFFFF (-1, remainder)
```
C division truncates toward zero, so `-7 / 2 == -3` and `-7 % 2 == -1`. (Python's `//` rounds
down, giving `-4` and `1`. Don't use Python to check expected values for negative operands.)

### Lowering table
New assembly AST pieces: `Binary(binary_operator, operand, operand)`, `Idiv(operand)`, `Cdq`;
the operator enum `Add | Sub | Mult`; registers `DX` and `R11` join `AX` and `R10`.

| TACKY | Assembly AST |
|---|---|
| `Binary(Add/Subtract/Multiply, a, b, dst)` | `Mov(a, dst)`, `Binary(op, b, dst)` |
| `Binary(Divide, a, b, dst)` | `Mov(a, Reg AX)`, `Cdq`, `Idiv(b)`, `Mov(Reg AX, dst)` |
| `Binary(Remainder, a, b, dst)` | `Mov(a, Reg AX)`, `Cdq`, `Idiv(b)`, `Mov(Reg DX, dst)` |

### Operand rules and fix-ups
Each instruction has its own rules about which operand kinds are legal. Your fix-up pass learns:

| Illegal form | Why | Fix |
|---|---|---|
| `idivl $3` | `idiv` can't take an immediate | `movl $3, %r10d` · `idivl %r10d` |
| `addl -4(%rbp), -8(%rbp)` (also `subl`) | two memory operands | `movl -4(%rbp), %r10d` · `addl %r10d, -8(%rbp)` |
| `imull $3, -8(%rbp)` | `imul` can't write to memory | `movl -8(%rbp), %r11d` · `imull $3, %r11d` · `movl %r11d, -8(%rbp)` |
| `movl -4(%rbp), -8(%rbp)` | two memory operands (from 9.3) | via `%r10d` |

The convention: `%r10d` patches up *sources*, `%r11d` patches up *destinations*. Keeping them
separate means one rewritten sequence never needs the same scratch register for two jobs at once.
Immediate sources are fine for `add`, `sub` and `imul` (`addl $1, -8(%rbp)` is legal).

Pseudo replacement (9.3) must now visit the operands of `Binary` and `Idiv` too.

### Worked example: `return 10 / 3 - 1;`
TACKY: `tmp.0 = 10 / 3`, `tmp.1 = tmp.0 - 1`, `return tmp.1`. After all three back-end passes
(8 bytes reserved, prologue and epilogue omitted):
```
	movl	$10, %eax          # Mov(10, AX)
	cdq                        # sign-extend into %edx
	movl	$3, %r10d          # fix-up: idiv can't take $3
	idivl	%r10d              # eax = 3, edx = 1
	movl	%eax, -4(%rbp)     # tmp.0 = quotient
	movl	-4(%rbp), %r10d    # Mov(tmp.0, tmp.1), split by fix-up
	movl	%r10d, -8(%rbp)
	subl	$1, -8(%rbp)       # tmp.1 -= 1
	movl	-8(%rbp), %eax     # return tmp.1
```
Exit status: 2.

### Optional: bitwise operators
If you did the `--bitwise` extension in 9.4: `&`, `|`, `^` lower like `add` to `andl`, `orl`,
`xorl`, with the same fix-ups. Shifts `<<` and `>>` become `sall` and `sarl` (arithmetic shift
right, which keeps the sign of a signed `int`). Their shift count must be an immediate or the
register `%cl`, so you'd add `CX` and a fix-up that moves the count there. Precedences: `<<` `>>`
40, `&` 25, `^` 20, `|` 15.

## Build
1. **TACKY.** Add `Binary` and its operator enum; translate AST `Binary` nodes, left operand first.
2. **Assembly AST.** Add `Binary`, `Idiv`, `Cdq`, the operator enum and the `DX` and `R11` registers.
3. **Instruction selection.** Implement the lowering table.
4. **Pseudo replacement.** Visit the new instructions' operands.
5. **Fix-up.** Add the three new rules. Write one unit test per rule.
6. **Emitter.** `addl`, `subl`, `imull`, `idivl`, `cdq`; `%edx`, `%r11d`.
7. **End-to-end checks.** Compile and run small programs and compare exit codes: `10 / 3 - 1` → 2,
   `7 % 3` → 1, `2 * (3 + 4)` → 14, `-7 / 2` → −3 (shown by the shell as 253, since exit statuses are
   one unsigned byte).
8. **Run the suite.** `./test_compiler ./target/debug/rcc --chapter 3`, plus `--stage tacky` and
   `--stage codegen` (and `--bitwise` if you did the extension).

## Check your understanding
1. Why does `Mov(src1, dst); Binary(Sub, src2, dst)` compute `src1 - src2` and not `src2 - src1`?
2. What's in `%edx` before `cdq`, and what goes wrong for `-7 / 2` if you skip it?
3. Why doesn't `idiv` need a destination operand? Where do `/` and `%` each find their result?
4. Write the fully fixed-up assembly for `return 7 % 3;`.
5. Which instructions in this lesson can't take an immediate operand, and which can't write to memory?

## Common pitfalls
- Swapping operands for `sub`: `5 - 3` comes out as −2.
- Forgetting `cdq`: division works for small positive numbers and fails mysteriously otherwise.
- Reading the remainder from `%eax` (it's in `%edx`).
- Forgetting to update pseudo replacement for the new instructions, so the emitter meets a `Pseudo`.
- Applying the `imul` rule to `add`/`sub`, or the other way round: each instruction has its own rule.
