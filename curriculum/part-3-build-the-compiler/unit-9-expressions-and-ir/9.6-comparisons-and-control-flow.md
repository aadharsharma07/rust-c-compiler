# Lesson 9.6 — Comparisons and Control Flow
**Part:** 3 — Build the Compiler · **Unit:** 9 — Expressions and an IR · **Type:** Builds relational + logical ops · **Est. time:** 6–8 h · **Tests:** ch. 4
**Prerequisites:** lessons 9.4, 9.5; 6.2 (flags); 6.3 (jumps)

## Overview
Chapter 4 adds the comparisons `== != < <= > >=` and the logical operators `!`, `&&` and `||`.
Comparisons teach you how the CPU *decides* (flags, `cmp`, `setcc`); `&&` and `||` force your IR to
gain **labels and jumps**, because they must sometimes skip evaluating their right operand. Those
jumps are exactly what `if` and loops will be made of in Unit 10, so this lesson is where control
flow enters your compiler.

## The lesson

### What C's comparisons and logical operators produce
C has no boolean type here: comparisons produce an `int`, exactly **1** for true or **0** for false.
`!x` is 1 if `x` is 0, else 0. `a && b` is 1 if both are non-zero; `a || b` is 1 if either is. In
Python, `3 and 5` evaluates to `5`; in C, `3 && 5` is `1`.

`&&` and `||` **short-circuit**, like Python's `and`/`or`: if the left operand already decides the
answer, the right operand is *not evaluated at all*. So `0 && (1 / 0)` is 0, and never divides by
zero. This is a promise about *what runs*, not just about the value.

### Lexing and parsing
Nine new tokens: `!`, `&&`, `||`, `==`, `!=`, `<`, `>`, `<=`, `>=`. Longest match matters again: `<=`
must not lex as `<` `=`, and `!=` must not lex as `!` `=`. `!` is a unary operator, parsed in the
factor parser next to `-` and `~`. The others go into the precedence table:

| Operators | Precedence |
|---|---|
| `*` `/` `%` | 50 |
| `+` `-` | 45 |
| `<` `<=` `>` `>=` | 35 |
| `==` `!=` | 30 |
| `&&` | 10 |
| `||` | 5 |

All are left-associative, so your climbing loop needs no change at all, just new table rows. That
payoff is why you built it that way in 9.4.

### How the CPU compares: flags, `cmp`, `setcc`, `jcc`
Recall from 6.2 that the CPU has a **flags register**: single bits set as side effects of
arithmetic, such as ZF (the result was zero), SF (the result was negative), OF (signed overflow)
and CF (unsigned carry). Three instruction families use them:

- **`cmpl b, a`** computes `a - b`, throws the result away, and sets the flags. Mind the AT&T
  order: the *second* operand is the left side of the comparison.
- **`setCC dst`** writes 1 to a **one-byte** destination if condition `CC` holds, else 0.
- **`jCC label`** jumps to `label` if condition `CC` holds; otherwise falls through to the next
  instruction. **`jmp label`** jumps unconditionally.

The condition codes for signed integers, after `cmpl b, a`:

| C | CC | holds when |
|---|---|---|
| `a == b` | `e` | ZF set (difference was 0) |
| `a != b` | `ne` | ZF clear |
| `a < b` | `l` | SF ≠ OF |
| `a <= b` | `le` | ZF set, or SF ≠ OF |
| `a > b` | `g` | ZF clear and SF = OF |
| `a >= b` | `ge` | SF = OF |

You don't need to memorise the flag logic, just the pairing: `cmp b, a` then `setl` means `a < b`.

### `setcc` writes a single byte
`setl` can only write one byte, either a byte register like `%al` (the lowest 8 bits of `%eax`) or
one byte of memory. Our results are 4-byte `int`s, so the destination must first be zeroed:
```
	movl	$0, -4(%rbp)    # all 4 bytes = 0
	setl	-4(%rbp)        # lowest byte = 0 or 1
```
x86-64 is **little-endian**: the lowest-addressed byte of an `int` is its least significant byte.
So writing 1 into the byte at `-4(%rbp)` makes the whole 4-byte value 1. The zeroing `mov` can sit
*between* `cmp` and `setcc` because `mov` never changes the flags. (A `xor`-based zeroing would
clobber them, which is why we don't use it here.)

Byte register names: `%al` for `AX`, `%dl` for `DX`, `%r10b` for `R10`, `%r11b` for `R11`.

### Short-circuiting needs jumps in TACKY
`a && b` can't be a TACKY `Binary` instruction, because a `Binary` evaluates both operands before it
runs. Instead, TACKY gets plain control flow:
```
instruction = ... | Copy(val src, val dst) | Jump(identifier target)
            | JumpIfZero(val condition, identifier target)
            | JumpIfNotZero(val condition, identifier target)
            | Label(identifier)
```
plus `Not` as a unary operator and `Equal | NotEqual | LessThan | LessOrEqual | GreaterThan |
GreaterOrEqual` as binary operators. `e1 && e2` translates to:
```
<instructions for e1, result v1>
JumpIfZero(v1, and_false.0)          # left is 0: skip e2 entirely
<instructions for e2, result v2>
JumpIfZero(v2, and_false.0)
Copy(1, result)
Jump(and_end.1)
Label(and_false.0)
Copy(0, result)
Label(and_end.1)                     # result holds 0 or 1
```
`e1 || e2` is the mirror image: `JumpIfNotZero` to a "true" label, `Copy(0, result)` on the
fall-through path and `Copy(1, result)` at the label. Notice that the instructions for `e2` sit
*after* a jump that can skip them; that's the short-circuit.

**Labels must be unique** across the whole program, just like temporaries: two `&&`s mustn't both
define `and_false`. Generate them from a counter, with a `.` in the name (it can't appear in a C
identifier, so labels can't clash with C names). Sharing one counter for temporaries and labels is
simplest.

### Lowering to assembly
New assembly AST instructions: `Cmp(operand, operand)`, `Jmp(label)`, `JmpCC(cond_code, label)`,
`SetCC(cond_code, operand)`, `Label(identifier)`, with a condition-code enum `E | NE | L | LE | G | GE`.

| TACKY | Assembly AST |
|---|---|
| `Binary(LessThan, a, b, dst)` (and the other five) | `Cmp(b, a)`, `Mov(Imm 0, dst)`, `SetCC(L, dst)` |
| `Unary(Not, src, dst)` | `Cmp(Imm 0, src)`, `Mov(Imm 0, dst)`, `SetCC(E, dst)` |
| `JumpIfZero(v, t)` | `Cmp(Imm 0, v)`, `JmpCC(E, t)` |
| `JumpIfNotZero(v, t)` | `Cmp(Imm 0, v)`, `JmpCC(NE, t)` |
| `Jump(t)` / `Label(t)` / `Copy(s, d)` | `Jmp(t)` / `Label(t)` / `Mov(s, d)` |

`cmp` has two operand rules for the fix-up pass. Both operands in memory: move the first into
`%r10d`. Second operand an immediate (e.g. `cmpl $0, $5`, from `!5`): `cmp` can't compare *into*
a constant, so move it into `%r11d` first.

### Worked example: `return 2 < 3;`
TACKY: `tmp.0 = 2 < 3`, `return tmp.0`. Selection gives `Cmp(Imm 3, Imm 2)`, which fix-up repairs:
```
	movl	$2, %r11d       # fix-up: cmp's second operand can't be an immediate
	cmpl	$3, %r11d       # computes 2 - 3; sets SF (negative), OF clear
	movl	$0, -4(%rbp)
	setl	-4(%rbp)        # SF != OF, so "less": writes 1
	movl	-4(%rbp), %eax  # exit status 1
```

### Emitting labels
Compiler-made labels should be **local labels**, which the assembler doesn't export as symbols.
On Linux they start with `.L`; on macOS with `L` (and no `_`: the underscore is for C-visible
symbols like `_main`). So `Label("and_false.0")` is emitted as `.Land_false.0:` on Linux and
`Land_false.0:` on macOS, and `JmpCC(E, "and_false.0")` as `je .Land_false.0` or `je Land_false.0`.

## Common pitfalls
- Swapping `cmp` operands, which silently turns `<` into `>`.
- `setl %eax`: `setcc` needs a byte operand (`%al`); and forgetting the zeroing `mov` leaves garbage in the upper bytes.
- Evaluating both sides of `&&`/`||` eagerly; later chapters' tests with side effects will catch it.
- Emitting labels with a `_` prefix or without `.L`/`L`, so they become global symbols.
- Lexing `<=` as `<` then `=`, or `!=` as `!` then `=`.
