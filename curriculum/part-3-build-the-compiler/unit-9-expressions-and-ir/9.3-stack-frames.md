# Lesson 9.3 — Stack Frames and Fix-ups
**Part:** 3 — Build the Compiler · **Unit:** 9 — Expressions and an IR · **Type:** Builds pseudoregister + fix-up passes · **Est. time:** 5–8 h · **Tests:** ch. 2
**Prerequisites:** lessons 8.4, 8.5, 9.2; 6.3 (reading assembly); 6.4 (the stack)

## Overview
TACKY has as many temporaries as it likes; the CPU has sixteen registers. This lesson rebuilds
the back end around TACKY as a short **pipeline of passes**: instruction selection (TACKY →
assembly with placeholder operands), pseudoregister replacement (placeholders → stack slots) and
instruction fix-up (make every instruction legal). You'll also give every function a proper stack
frame. At the end, chapter 2 programs compile and run.

## The lesson

### Recap: the stack frame
From 6.4: the **stack** is a region of memory that grows *downwards*, towards lower addresses.
`%rsp` (the stack pointer) holds the address of the current top, the lowest in-use byte. Each
running function gets a **stack frame**, and `%rbp` (the base pointer) marks its base so local
data can be found at fixed offsets from it.

A function sets up its frame with a **prologue**:
```
	pushq	%rbp          # save the caller's base pointer on the stack (rsp -= 8)
	movq	%rsp, %rbp    # our frame's base is the current top
	subq	$8, %rsp      # reserve 8 bytes for our temporaries
```
and tears it down with an **epilogue** just before returning:
```
	movq	%rbp, %rsp    # drop everything we reserved
	popq	%rbp          # restore the caller's base pointer (rsp += 8)
	ret                   # pop the return address and jump to it
```
These use the `q` (quadword, 8-byte) forms because addresses are 64 bits. Picture the frame after
the prologue, with two 4-byte slots:
```
higher addresses
  ┌──────────────────────┐
  │ return address       │  8(%rbp)    pushed by the caller's `call`
  ├──────────────────────┤
  │ caller's saved %rbp  │  0(%rbp)  ← %rbp points here
  ├──────────────────────┤
  │ tmp.0                │ -4(%rbp)
  │ tmp.1                │ -8(%rbp)  ← %rsp points here
  └──────────────────────┘
lower addresses
```
Our data lives at **negative** offsets from `%rbp`. Writing to `0(%rbp)` or `4(%rbp)` would
overwrite the saved `%rbp`, and the epilogue's `popq` would then restore garbage.

### Pseudoregisters: pretend first, decide later
The simplest correct way to store unlimited temporaries is to give each one its own 4-byte stack
slot (an `int` is 4 bytes). Unit 14 replaces this with real register allocation; for now, slow and
correct wins.

Rather than choosing slots while translating instructions, split the work in two. First, translate
each TACKY `Var("tmp.0")` into an abstract operand `Pseudo("tmp.0")`, a **pseudoregister**: "some
storage location, to be decided". Then a separate pass walks the instructions and swaps every
pseudo for a real `Stack(offset)`. The translator stays simple, and when Unit 14 arrives, only the
second pass changes.

### Selecting instructions for unary operators
x86-64 has `negl` (negate in place) and `notl` (flip all bits in place). Both take one operand and
overwrite it. TACKY's `Unary(op, src, dst)` has separate source and destination, so it becomes a
copy and then an in-place operation:
```
TACKY Unary(Negate, src, dst)   →   Mov(src, dst)   then  Unary(Neg, dst)
TACKY Return(val)               →   Mov(val, Reg(AX))  then  Ret
```

### The assembly AST grows
```
program        = Program(function_definition)
function_definition = Function(identifier name, instruction* instructions)
instruction    = Mov(operand src, operand dst) | Unary(unary_operator, operand)
               | AllocateStack(int) | Ret
unary_operator = Neg | Not
operand        = Imm(int) | Reg(reg) | Pseudo(identifier) | Stack(int)
reg            = AX | R10
```
Unit 8's dataless `Register` becomes `Reg(reg)` because you now need more than one register.
`AllocateStack(n)` will be emitted as `subq $n, %rsp`.

### Pass 2: replacing pseudoregisters
Walk every instruction and every operand in it. Keep a map from pseudo name to offset. The first
time you meet a name, give it the next slot (`-4`, then `-8`, `-12`, …) and remember it; every later
occurrence of the same name reuses that slot. At the end, the total bytes used is what the frame
must reserve. A `HashMap` (3.4) with the entry API fits naturally.

### Pass 3: fixing up illegal instructions
x86-64 has rules about operands that our neat model ignores. The first one bites immediately: an
instruction can have **at most one memory operand**. `movl -4(%rbp), -8(%rbp)` doesn't exist;
the assembler rejects it. The fix is to route the value through a register we reserve for this:
```
movl -4(%rbp), -8(%rbp)     ✗   becomes    movl -4(%rbp), %r10d
                                           movl %r10d, -8(%rbp)
```
`%r10d` is the 32-bit view of `%r10`, a register that nothing else in our code uses yet, so it's
safe as scratch. The fix-up pass also inserts `AllocateStack(total_bytes)` as the function's first
instruction, now that pass 2 has told it how many bytes there are.

Why three passes instead of one clever one? Each pass has one job and one invariant you can
test in isolation. Units 12–14 add many more rules; small passes keep them manageable.

### Where the prologue and epilogue come from
The emitter (8.5) prints the prologue right after the function's label. Every `Ret` instruction is
printed as the three-line epilogue. That way a function with several `return`s (Unit 10) gets a
correct epilogue at each one, with no extra bookkeeping.

### Worked example: `return ~(-2);`
TACKY from 9.2 is `tmp.0 = Negate 2`, `tmp.1 = Complement tmp.0`, `return tmp.1`.
```
1. instruction selection      2. pseudos → stack            3. fix-up (+ emission)
Mov(Imm 2, Pseudo tmp.0)      movl $2, -4(%rbp)             pushq %rbp            (prologue)
Unary(Neg, Pseudo tmp.0)      negl -4(%rbp)                 movq  %rsp, %rbp
Mov(Pseudo tmp.0,             movl -4(%rbp), -8(%rbp)  ✗    subq  $8, %rsp        (AllocateStack 8)
    Pseudo tmp.1)                                           movl  $2, -4(%rbp)
Unary(Not, Pseudo tmp.1)      notl -8(%rbp)                 negl  -4(%rbp)
Mov(Pseudo tmp.1, Reg AX)     movl -8(%rbp), %eax           movl  -4(%rbp), %r10d
Ret                           ret                           movl  %r10d, -8(%rbp)
                                                            notl  -8(%rbp)
                                                            movl  -8(%rbp), %eax
                                                            movq  %rbp, %rsp      (epilogue)
                                                            popq  %rbp
                                                            ret
```
Column 2 is written as assembly for readability; it's still the assembly AST. On macOS the label
is `_main`; on Linux add the `.note.GNU-stack` section line from 8.5. The program exits with 1.

(Stack sizes: this course allocates exactly the bytes it needs for now. Unit 11 rounds the frame
up to a multiple of 16, which the calling convention requires once functions call each other.)

## Build
1. **Assembly AST.** Extend it as above.
2. **Instruction selection.** Rewrite the code generator to take TACKY instead of the AST, producing
   `Pseudo` operands for every TACKY `Var`. Chapter 1 programs now go through TACKY too, so delete
   the old AST→assembly path.
3. **Pseudo replacement.** A pass that replaces every `Pseudo` with `Stack`, one slot per distinct
   name, and reports the bytes used. Unit test: the worked example gives column 2.
4. **Fix-up.** A pass that inserts `AllocateStack` first and splits any `Mov` whose operands are
   both `Stack`. Unit test: column 2 gives column 3, minus prologue and epilogue.
5. **Emitter.** Prologue after the label; `Ret` → epilogue; `Stack(n)` → `n(%rbp)`; `Reg(AX)` →
   `%eax`; `Reg(R10)` → `%r10d`; `Neg` → `negl`; `Not` → `notl`; `AllocateStack(n)` → `subq $n, %rsp`.
   The emitter must never see a `Pseudo`; make that case an internal error.
6. **Driver.** `--codegen` now stops after fix-up.
7. **Run the suite.** `./test_compiler ./target/debug/rcc --chapter 2`, plus `--stage codegen`.

## Check your understanding
1. Why does the first slot live at `-4(%rbp)` and not `0(%rbp)`? What's stored at `0(%rbp)` and `8(%rbp)`?
2. What do `pushq %rbp` and `popq %rbp` each do to `%rsp`?
3. Your pseudo-replacement pass sees `tmp.0` twice. How does it know to reuse the same slot?
4. Why separate "replace pseudos" from "fix up"? What would merging them cost when Unit 14 arrives?
5. How many bytes does `return -(-(-(-1)));` reserve? Count the temporaries.
6. Why does `Ret` carry the epilogue instead of the function as a whole?

## Common pitfalls
- Giving a pseudo a fresh slot every time it appears, instead of once per name.
- Using `movl` in the prologue/epilogue: addresses are 64-bit, so `pushq`, `movq`, `popq`.
- Getting the offset sign wrong (`4(%rbp)` instead of `-4(%rbp)`): the program returns into nowhere.
- Allocating stack space during instruction selection, before you know how many slots exist.
- Emitting a bare `ret` without the epilogue: `%rsp` still points at your temporaries, so `ret` pops one of them as the return address and jumps into garbage.
