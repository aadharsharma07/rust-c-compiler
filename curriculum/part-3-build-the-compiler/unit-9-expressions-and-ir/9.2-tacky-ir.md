# Lesson 9.2 — The TACKY IR
**Part:** 3 — Build the Compiler · **Unit:** 9 — Expressions and an IR · **Type:** Builds TACKY + AST→TACKY · **Est. time:** 5–7 h · **Tests:** ch. 2
**Prerequisites:** lesson 9.1; 5.5 (intermediate representations, three-address code)

## Overview
In lesson 5.5 you met three-address code on paper and saw CPython's bytecode as an IR. Now you
build one. **TACKY** is the intermediate representation the rest of this course compiles through:
a flat list of simple instructions where every intermediate result has a name. You'll define its
data types, write the pass that flattens the AST into it, and add a `--tacky` stage flag. Every
later unit extends this pass, so its shape matters more than its size.

## The lesson

### The gap between a tree and a list
Your AST is a **tree**: `~(-2)` is a node inside a node. Assembly is a **flat list**: each
instruction does one small thing, in order, and results live in named places (registers or memory).
Turning one into the other involves two separate problems:

1. **Structure.** Which operation happens first? Where does each intermediate result go? (Later:
   how do `if` and loops become jumps?)
2. **Machine details.** Which registers exist? Which instruction forms are legal? Where on the
   stack does each value live?

Solving both at once, in one pass, gets tangled quickly. An **intermediate representation** (IR)
splits them: AST → IR solves *structure*, IR → assembly solves *machine details*. The IR is also
where the optimiser of Unit 13 works, because it's free of both C syntax and x86-64 quirks.

You've seen this already: CPython compiles your Python source into bytecode (5.5, `dis`) rather
than interpreting the tree directly. Same idea, different target.

### Three-address code, recapped
In **three-address code** every instruction has at most one operator and at most three "addresses"
(two inputs, one output): `dst = src1 op src2`, or `dst = op src`. Operands are only ever
*simple*: a constant or a name. Never a nested expression. When an expression needs an
intermediate result, the IR invents a fresh name for it: a **temporary**.

Python analogy: imagine rewriting `y = -(~x)` so that every line does exactly one operation:
```python
t0 = ~x
t1 = -t0
y = t1
```
That's three-address code. Your compiler does this rewrite automatically.

### TACKY's types (chapter 2 version)
Described in the same notation as the AST:
```
program             = Program(function_definition)
function_definition = Function(identifier name, instruction* body)
instruction         = Return(val) | Unary(unary_operator, val src, val dst)
val                 = Constant(int) | Var(identifier)
unary_operator      = Complement | Negate
```
`instruction*` means "a list of instructions" (a `Vec`). A `val` is the simple operand: a constant
or a named variable. In chapter 2 every `Var` is a temporary the compiler made up; in Unit 10, C's
own variables become `Var`s too. Notice that nothing here is recursive: an instruction contains
`val`s, and a `val` never contains an instruction. That flatness is the whole point.

It's worth making TACKY's `unary_operator` a separate type from the AST's, even though today they
look identical. Each stage then evolves on its own (TACKY gains `Not` in 9.6; the AST gains things
TACKY never sees), and the conversion between them is a tiny function.

### Flattening: the translation rule
Translating an expression means: *emit the instructions that compute it, and give back the `val`
that names its result.* The recursion goes:

- **`Constant(n)`** → emit nothing; the result is `Constant(n)`. A constant is already simple.
- **`Unary(op, inner)`** → first translate `inner` (which emits its instructions and gives back
  `src`); then make a fresh temporary `dst`; emit `Unary(op, src, dst)`; the result is `Var(dst)`.

A `Return(exp)` statement translates `exp` to get `v`, then emits `Return(v)`.

Because the inner expression is translated *before* the outer instruction is emitted, the tree is
visited in **post-order** (children before parent), which is exactly the order the operations
must run in.

### Worked example
`return ~(-2);` has the AST `Return(Unary(Complement, Unary(Negate, Constant(2))))`.
```
translate Return:
  translate Unary(Complement, …):
    translate Unary(Negate, Constant 2):
      translate Constant 2          → emits nothing, gives Constant(2)
      fresh temp tmp.0; emit  Unary(Negate, Constant(2), Var(tmp.0))
      gives Var(tmp.0)
    fresh temp tmp.1; emit  Unary(Complement, Var(tmp.0), Var(tmp.1))
    gives Var(tmp.1)
  emit Return(Var(tmp.1))
```
Resulting TACKY, written one instruction per line:
```
tmp.0 = Negate 2
tmp.1 = Complement tmp.0
return tmp.1
```
And `return 5;` becomes just `return 5`, with no temporaries at all.

### Fresh names and where the counter lives
Every temporary needs a name that is unique across the whole program. A counter that increases on
every request does the job: `tmp.0`, `tmp.1`, … The `.` matters: it can't appear in a C
identifier, so when Unit 10 adds user variables, a user's `tmp0` can never clash with one of yours.

The counter is **state** that changes during the translation and is shared by every recursive
call. In Python you might keep it as an attribute on a translator object. In Rust the same shape
works: a struct that owns the counter, with methods taking `&mut self` (recall 3.1 and 2.3). Avoid
a global mutable variable: Rust makes those `unsafe` for good reason, and you don't need one.

A small borrowing note. Two `&mut` uses of the same thing can't overlap, but they can follow each
other. Getting a fresh name on one line and pushing an instruction on the next is always fine;
nesting one call inside the other's arguments sometimes trips the borrow checker. When it does,
introduce a local variable.

### Where the instructions go
The translator needs somewhere to put emitted instructions. Two common designs: pass a `&mut Vec`
of instructions down through the recursion, or keep the `Vec` inside the translator struct.
Either is fine. What matters is that an expression's translation *appends* to the list and
*returns* its `val`.

### The `--tacky` stage
The driver (8.1) has stage flags that stop the pipeline early. Add `--tacky`, which runs lex →
parse → TACKY generation, then exits 0 without writing any files. The test suite's
`--stage tacky` calls it. In the stage order it sits between `--parse` and `--codegen`.

## Common pitfalls
- Emitting the outer instruction before translating the inner expression (wrong order).
- Making a temporary for every constant: wasteful, and it makes later passes noisier.
- A `static mut` counter. Thread a struct through instead.
- Reusing the AST's types inside TACKY "to save time", then having to untangle them when the stages diverge.
- Forgetting to add `--tacky` to argument parsing, so the test suite reports "unknown flag".
