# Lesson 9.1 — Unary Operators
**Part:** 3 — Build the Compiler · **Unit:** 9 — Expressions and an IR · **Type:** Builds unary `-`, `~` · **Est. time:** 2–3 h · **Tests:** ch. 2
**Prerequisites:** lessons 8.1–8.5 (chapter 1 passing); 6.1 (two's complement); 5.3 (grammars, recursive descent)

## Overview
Your compiler can return a constant. In this lesson the front end learns its first operators: `-`
(negation) and `~` (bitwise complement), which can nest without limit: `-~-(-2)`. That makes the
expression grammar recursive for the first time, so your AST becomes a real tree and your parser
calls itself. The back end can't compile these yet (lessons 9.2 and 9.3 do that), so this lesson
ends at a passing `--stage parse`.

## The lesson

### What the two operators mean
A **unary operator** takes one operand; a binary operator (lesson 9.4) takes two. C's `int` is a
32-bit two's-complement integer (recall 6.1), and both operators work on its bits:

- **Negation** `-x`: the arithmetic negative. In two's complement you get it by flipping every bit
  and adding 1. `-2` is `0xFFFFFFFE`.
- **Bitwise complement** `~x`: flip every bit and *don't* add 1. `~0` is `0xFFFFFFFF`, which is `-1`.

Putting those together gives a handy identity: `~x == -x - 1` for every `int`. Worked example:
```
  2  = 0000 0000 ... 0000 0010   (0x00000002)
 -2  = 1111 1111 ... 1111 1110   (0xFFFFFFFE)   flip all bits of 2, add 1
~(-2)= 0000 0000 ... 0000 0001   (0x00000001)   flip all bits of -2
```
So `return ~(-2);` exits with status 1.

Python has both operators with the same meaning, but Python integers never overflow. In C, `-x`
overflows for exactly one value: `-2147483648` has no positive partner in 32 bits, so
`-(-2147483648)` is **undefined behaviour** (UB). UB means the C standard places no requirement
at all on what happens; the test suite simply never does it, and neither should your tests.

(In Rust, bitwise complement on integers is spelled `!`, not `~`: `!0i32 == -1`. You'll want that
when writing expected values in unit tests.)

### New tokens, and why `--` is one of them
The lexer needs three new tokens: `-` (hyphen), `~` (tilde) and `--` (decrement). We aren't
implementing decrement, so why lex it? Because of the **longest-match rule** from 5.2: at each
position, the lexer takes the longest string that forms a valid token. C defines `--`, so the
characters `--2` must lex as `--` then `2`, never as `-` `-` `2`. If your lexer only knew `-`,
it would accept `return --2;` as "negate negate 2", a different program from what the C standard
says. With `--` as its own token, the parser sees `Decrement` where an expression should start,
finds no grammar rule that accepts it, and rejects the program. Nothing special to write.

Compare: `- -2` (with a space) and `-(-2)` are fine, because whitespace and `(` separate the
two hyphens into two tokens. Both mean negation of negation, which is 2.

### The grammar becomes recursive
Recall the BNF notation from 5.3. The expression rule now reads:
```
<exp>   ::= <int> | <unop> <exp> | "(" <exp> ")"
<unop>  ::= "-" | "~"
```
`<unop> <exp>` mentions `<exp>` inside its own definition: an expression can contain an
expression. That is what lets operators nest. Parentheses are also new; they just **group**, so
`(2)` means the same as `2`.

### The AST becomes a tree
Using the same notation for the AST as in Unit 8 (each line is a type; `|` separates the
alternatives, which become Rust enum variants):
```
exp            = Constant(int) | Unary(unary_operator, exp)
unary_operator = Complement | Negate
```
Two things to notice. First, there's no node for parentheses. They exist only to steer the parser;
once the tree is built, its shape already records the grouping, so a `Paren` node would carry no
information. Second, `Unary` contains an `exp`, so the type is **recursive**. As you saw in lesson
4.4 (Part 1), a Rust type that contains itself directly would need infinite size, so the inner
expression goes behind a `Box` (a pointer to a heap allocation, which has a fixed size).

Worked example, `return ~(-2);`:
```
Tokens: Return  Tilde  OpenParen  Hyphen  Constant(2)  CloseParen  Semicolon

AST:    Return
          └── Unary(Complement)
                └── Unary(Negate)
                      └── Constant(2)
```

### Parsing it: peek and dispatch
The heart of recursive descent (5.3, and your calculator parser in 7.2) is: look at the next token
*without consuming it*, and let it choose which rule applies. For `<exp>`:

| Next token | Action |
|---|---|
| a constant | consume it; return `Constant(n)` |
| `-` or `~` | consume it; parse an `<exp>` (a recursive call); wrap it in `Unary` |
| `(` | consume it; parse an `<exp>`; expect and consume `)`; return the inner expression unchanged |
| anything else | syntax error |

Trace on `~(-2)`: see `~` → consume, recurse. See `(` → consume, recurse. See `-` → consume,
recurse. See `2` → return `Constant(2)`. Wrap: `Unary(Negate, Constant 2)`. Back in the `(` case,
expect `)` → found. Back in the `~` case, wrap: `Unary(Complement, …)`. The call stack of your
parser mirrors the shape of the tree.

### What happens to the rest of the compiler
Adding a variant to the expression enum makes every exhaustive `match` on it fail to compile:
the assembly generator from 8.4 doesn't know what to do with `Unary`. That's Rust helping you
find every place that needs updating. For now, make the generator return a clear "not supported
yet" error for `Unary` (or use the `todo!()` macro, which panics with a message). Lesson 9.2
inserts an IR between the parser and the back end, and 9.3 rewrites the back end around it.

## Build
You are extending the lexer, the AST and the parser. Chapter 1 must keep passing throughout.

1. **Lexer.** Add `Hyphen`, `Tilde` and `Decrement` tokens. Make sure `--` wins over `-` by longest
   match. Unit tests: `-`, `~`, `--`, `--2` (two tokens), `- -2` (three tokens), `-~2`.
2. **AST.** Add the unary-operator enum and a unary variant on the expression type holding an
   operator and a boxed operand. Make your debug printing show nested unary nodes readably.
3. **Parser.** Rewrite the expression function as peek-and-dispatch over the four cases above.
   It must reject, with a parse error (non-zero exit, no panic):
   - `return --2;` (decrement token where an expression starts);
   - `return -;` (operator with no operand);
   - `return (2;` and `return 2);` (unbalanced parentheses);
   - `return 2-;` and `return 2 3;` (there are no binary operators yet, so nothing may follow the operand).
4. **Codegen placeholder.** Return a "not yet supported" error for `Unary` so the program still compiles.
5. **Unit tests.** ASTs for `~(-2)`, `-(-2)`, `-~2`, `((5))` (which must be just `Constant(5)`);
   rejection of `--2`.
6. **Run the suite.** `./test_compiler ./target/debug/rcc --chapter 2 --stage lex`, then
   `--stage parse`. (`--chapter N` also reruns earlier chapters' tests at that stage.)

## Check your understanding
1. Why is `return --2;` rejected but `return -(-2);` accepted? Which stage rejects the first, and what does it see?
2. What is `~5` as a decimal `int`? Show the bits, then check it with the identity `~x == -x - 1`.
3. Why must the expression parser be recursive now, when in chapter 1 it wasn't?
4. Why don't parentheses appear in the AST? What node does your parser return for `(2)`?
5. What would go wrong with a recursive enum that held its child directly instead of in a `Box`?

## Common pitfalls
- Lexing `--` as two `-` tokens, so `--2` is wrongly accepted.
- Adding a `Paren` AST node; every later pass then has to skip over it.
- Consuming the token before deciding which case applies, so the error case loses the token it should report.
- Putting a catch-all `_ =>` arm in a `match` on expressions; it silently swallows every variant you add later.
- Forgetting to re-run chapter 1 after the change.
