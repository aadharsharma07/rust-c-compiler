# Lesson 9.4 — Precedence Climbing
**Part:** 3 — Build the Compiler · **Unit:** 9 — Expressions and an IR · **Type:** Builds binary-expression parser · **Est. time:** 4–6 h · **Tests:** ch. 3
**Prerequisites:** lesson 9.1; 5.3 (precedence, associativity, left recursion); 7.2 (calculator parser)

## Overview
Chapter 3 adds the binary operators `+ - * / %`. Parsing them correctly means getting
**precedence** (`*` before `+`) and **associativity** (`10 - 4 - 3` is `(10 - 4) - 3`) right. In
the calculator (7.2) you did that with one function per precedence level. Here you learn
**precedence climbing**: one loop driven by a table of numbers, which stays small as C's operator
list grows from 5 to over 15. This lesson is parser-only; 9.5 compiles the result.

## The lesson

### Precedence and associativity change the tree
Recall from 5.3: **precedence** says which operator binds tighter; **associativity** says how to
group operators of equal precedence. Both are about the *shape of the tree*, and the shape decides
the answer:
```
1 + 2 * 3           10 - 4 - 3                 10 - 4 - 3 (wrong!)
     +                    -                          -
    / \                  / \                        / \
   1   *                -   3                     10   -
      / \              / \                            / \
     2   3           10   4                          4   3
   = 7                 = 3                         = 9
```
All five operators in this lesson are **left-associative**, like in Python: equal-precedence
operators group from the left. `*`, `/` and `%` bind tighter than `+` and `-`.

### Why the obvious grammar doesn't work
The natural way to write the grammar is:
```
<exp>    ::= <factor> | <exp> <binop> <exp>
<factor> ::= <int> | <unop> <factor> | "(" <exp> ")"
<binop>  ::= "-" | "+" | "*" | "/" | "%"
```
It has two problems (both from 5.3). It's **ambiguous**: `1 - 2 - 3` matches it in two ways,
producing both trees above, and the grammar doesn't say which is right. And it's **left
recursive**: a recursive-descent function for `<exp>` would start by calling itself for the
left `<exp>`, without consuming a token, forever.

The calculator fixed both by writing one rule per level (`expr` for `+ -`, `term` for `* /`,
`factor` for the rest), with loops instead of left recursion. That's correct, but C has about
ten precedence levels by the end of this course. Ten near-identical functions is a lot of
copy-paste.

### Factors
Notice the split in the grammar: a **factor** is anything that can be an operand of a binary
operator without parentheses: a constant, a unary operator applied to a factor, or a parenthesised
expression. Your expression parser from 9.1 becomes the factor parser, with one change: unary
operators now apply to a *factor*, not to a whole expression. That makes `-2 + 3` mean
`(-2) + 3`, as C requires, instead of `-(2 + 3)`.

### Precedence climbing
Give every binary operator a number. Higher binds tighter:

| Operators | Precedence |
|---|---|
| `*` `/` `%` | 50 |
| `+` `-` | 45 |

The gaps leave room: 9.6 adds comparisons and logical operators below 45, Unit 10 adds assignment
right at the bottom, and the optional bitwise operators slot in between.

The algorithm is one function, "parse an expression with **minimum precedence** `min`", which
only accepts operators at least that strong:

1. Parse a factor. Call it `left`.
2. Peek at the next token. If it's a binary operator whose precedence `p` is **at least** `min`,
   consume it; otherwise stop and return `left`.
3. Parse the right operand by calling the same function with minimum **`p + 1`**.
4. Combine: `left` becomes `Binary(op, left, right)`. Go back to step 2.

The top level (`parse_exp(0)` in the trace below) starts at minimum 0, which accepts every operator.

Why `p + 1`? When parsing the right operand of a `-` (45), the recursive call may only take
operators *stronger* than 45. So in `10 - 4 - 3`, the right operand of the first `-` stops at `4`
when it meets the second `-` (45 is not ≥ 46). Control returns to the outer loop, which builds
`10 - 4` and *then* consumes the second `-`, making `(10 - 4) - 3`. That's left associativity. If
you passed `p` instead, the right operand would swallow `4 - 3`, giving the wrong tree above.
(Right-associative operators do exactly that on purpose; you'll use it for `=` in 10.1.)

### A full trace: `1 - 2 * 3 - 4`
```
parse_exp(0)
  left = 1
  see '-' (45 >= 0): consume; right = parse_exp(46)
  │  left = 2
  │  see '*' (50 >= 46): consume; right = parse_exp(51)
  │  │  left = 3; see '-' (45 < 51): stop; return 3
  │  left = (2 * 3)
  │  see '-' (45 < 46): stop; return (2 * 3)
  left = (1 - (2 * 3))
  see '-' (45 >= 0): consume; right = parse_exp(46)
  │  left = 4; end of expression: return 4
  left = ((1 - (2 * 3)) - 4)
  see ';' (not an operator): stop
result: Binary(Subtract, Binary(Subtract, 1, Binary(Multiply, 2, 3)), 4)
```
Read it slowly with a pencil: the call depth rises for stronger operators and falls back for weaker
ones, which is where the name "climbing" comes from.

### One `-` token, two meanings
The lexer emits the same `Hyphen` token for `-2` and for `5 - 2`. It doesn't need to know which is
which, because the *parser* knows where it is: at the start of a factor, `-` is negation; in the
loop, after a complete operand, it's subtraction. Context decides, so the lexer stays simple.

### AST additions
```
exp             = Constant(int) | Unary(unary_operator, exp) | Binary(binary_operator, exp, exp)
binary_operator = Add | Subtract | Multiply | Divide | Remainder
```
A small helper that maps a token to "its precedence, or none if it's not a binary operator"
keeps the loop readable. Returning an `Option` (3.3) expresses "or none" exactly.

## Common pitfalls
- Using `p` instead of `p + 1`, making everything right-associative.
- Unary operators applying to a whole expression, so `-2 + 3` parses as `-(2 + 3)`.
- Consuming the operator token before checking its precedence, then losing it when the loop exits.
- Splitting `-` into separate "unary minus" and "binary minus" tokens in the lexer.
- Forgetting that `--chapter 3` reruns chapters 1–2 too; a broken factor parser shows up there.
