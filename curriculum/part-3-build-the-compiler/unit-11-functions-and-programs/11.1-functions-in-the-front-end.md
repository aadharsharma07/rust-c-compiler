# Lesson 11.1 — Functions in the Front End
**Part:** 3 — Build the Compiler · **Unit:** 11 — Functions and Whole Programs · **Type:** Builds function decls/calls · **Est. time:** 4–6 h · **Tests:** ch. 9
**Prerequisites:** lessons 10.1–10.5 (chapters 1–8 pass); 5.4 (scopes and symbol tables)

## Overview
You teach the lexer, parser, identifier resolver and TACKY generator about functions: declaring them, defining them,
giving them parameters and calling them. The new idea is **linkage**: some names must keep exactly the same spelling
everywhere, because they refer to one shared thing. Code generation for calls waits until 11.3, so this lesson ends at
the `--tacky` stage.

## The lesson

### Declarations and definitions
In Python, `def add(a, b): ...` creates the function at the moment that line *runs*. You can call `add` from
another function written earlier in the file, because by the time the call executes, the `def` has run. C works
differently: the compiler reads the file once, top to bottom, and must know what `add` is **at the point where it
sees the call**. So C separates two things:

```c
int add(int a, int b);                    /* declaration (a "prototype"): no body, ends in ';' */
int add(int a, int b) { return a + b; }   /* definition: has a body */
```

Reading the C syntax: `int` before the name is the **return type**; the parenthesised list holds the
**parameters**, each written as a type followed by a name; `(void)` means "takes no parameters". A **declaration**
is a promise: "a function called `add`, taking two `int`s and returning an `int`, exists somewhere, maybe in this
file, maybe in another one, maybe in the C library." A **definition** is a declaration that also supplies the body.
A function can be declared many times but defined only once in the whole program.

Modern C (C17, the standard this course follows) has no "implicit declarations": calling a function the compiler
hasn't seen declared is an error. That is why real C files start with lines like `int putchar(int c);`.
(`int f();` with empty parentheses means "parameters unspecified" in C17; this course and the tests only use
`(void)` or a named list.)

### The grammar
```
<program>              ::= { <function-declaration> }
<declaration>          ::= <variable-declaration> | <function-declaration>
<function-declaration> ::= "int" <identifier> "(" <param-list> ")" ( <block> | ";" )
<param-list>           ::= "void" | "int" <identifier> { "," "int" <identifier> }
<factor>               ::= <int> | <identifier> | ... | <identifier> "(" [ <argument-list> ] ")"
<argument-list>        ::= <exp> { "," <exp> }
```
Three things changed. A program is now a *list* of function declarations. A block item can declare a function as
well as a variable. And a factor can be a **call**: a name followed by a parenthesised, comma-separated list of
argument expressions. Each argument is a full expression (assignment included). C has a "comma operator", but this
course doesn't support it, so inside a call a `,` always separates arguments.

### Telling the cases apart: lookahead
After reading `int x`, your parser can't yet tell which of these it is looking at:
```c
int x;            int x = 1;            int x(void);            int x(void) { return 1; }
```
It has to peek at the **next** token: `(` means function, anything else means variable. Then, for a function,
`;` after the `)` means declaration and `{` means definition. In an expression, the same trick distinguishes a
variable `foo` from a call `foo(...)`: an identifier followed by `(` is a call. This is *lookahead*: deciding which
grammar rule applies by inspecting tokens you haven't consumed yet (recall recursive descent from 5.3).

### Where functions may appear
Declaring a function inside a block is legal, and the declaration is visible only in that block:
```c
int main(void) {
    int helper(int n);      /* legal: block-scope declaration */
    return helper(3);
}
```
*Defining* a function inside another function is **not** legal C (unlike Python's nested `def`). Your parser may
happily parse it; some later check must reject it.

### Linkage: which names must not be renamed
Recall from 10.2 that the resolver gives every local variable a unique name (`x` becomes `x.0`), so that later passes
never confuse two different variables that happen to share a spelling. Functions are different. Every declaration of
`add`, in any scope and in any file, refers to **the same function**. If the resolver renamed one of them to
`add.3`, the call would no longer match the definition, or the linker would look for a symbol that doesn't exist.

This property is called **linkage**: a name with linkage refers to the same entity wherever it is declared; a name
with **no linkage** (an ordinary local variable) refers to a separate entity in each declaration. For now, every
function has linkage and every variable has none. (11.4 refines this into internal and external linkage.)

So each entry in your resolver's scope map gains one more fact: *does this name have linkage?* That fact drives two rules:
- A name with linkage is recorded under its **own** name; a name without linkage gets a fresh unique name, as before.
- Redeclaring a name in the **same** scope is an error *unless both* the old and the new declaration have linkage.
  `int f(void); int f(void);` is fine (two promises about the same function). `int x; int f(void);` in one block is
  an error. `int f(void);` in a block then `int f;` in the same block is an error.

### Parameters and their scope
Parameters behave like local variables declared at the very start of the function body, **in the same scope** as the
body's outermost block. So:
```c
int f(int a) { int a = 1; return a; }       /* error: 'a' declared twice in one scope */
int g(int a) { { int a = 1; } return a; }   /* fine: the inner 'a' is in a nested block */
```
Parameters are renamed like locals (`a` becomes `a.0`). Parameter names in a pure declaration are also resolved, only so
that duplicates like `int h(int a, int a);` are caught; nothing uses them afterwards.

### A worked example
```c
int add(int a, int b);
int main(void) { return add(1, 2); }
int add(int a, int b) { return a + b; }
```
After resolution (sketch):
```
Program([
  FunDecl("add",  params ["a.0", "b.1"], body: none),
  FunDecl("main", params [],             body: [ Return(Call("add", [Constant 1, Constant 2])) ]),
  FunDecl("add",  params ["a.2", "b.3"], body: [ Return(Binary(Add, Var "a.2", Var "b.3")) ]) ])
```
`add` kept its name; parameters were renamed. In TACKY, a program is now a list of *function definitions*;
prototypes produce nothing. A new instruction `FunCall(name, args, dst)` calls a function with already-evaluated
argument values and stores the result in `dst`:
```
Function main():        FunCall("add", [1, 2], tmp.4)   Return(tmp.4)   Return(0)
Function add(a.2, b.3): Binary(Add, a.2, b.3, tmp.5)    Return(tmp.5)   Return(0)
```
Notice that arguments are evaluated into plain values **before** the call. For `f(g(1), 2)` TACKY first emits
`FunCall("g", [1], tmp.0)` and only then `FunCall("f", [tmp.0, 2], tmp.1)`. That ordering will matter in 11.3.
(The trailing `Return(0)` you already add to `main` is harmless in other functions; keeping it everywhere is simplest.)

### Comparing with Python
Python's `ast` module shows the same shapes. Run `python3 -c "import ast; print(ast.dump(ast.parse('f(g(1), 2)'), indent=2))"`
and you'll see a `Call` node with a `func` and a list of `args`, one of which is itself a `Call`. Your C AST call node is
the same idea, except the callee in C is always a plain name.

## Build

**Practice first (paper, ~30 min).**
1. For each of `int x;`, `int x = 1;`, `int x(void);`, `int x(int a) { return a; }`, `x(1, y = 2)`, write the token
   at which your parser commits to a rule.
2. Resolve this program by hand, writing each renamed identifier and noting which declarations are errors:
   `int f(int a); int main(void) { int f = 2; { int f(void); return f(); } }`.
3. Write the TACKY for `return f(g(1), h(2, 3));`.

**Spec.** Inputs: a C file using the grammar above. Outputs: with `--parse`, an AST or a parse error; with
`--validate`, a resolved AST or a resolution error; with `--tacky`, TACKY or an error. All errors exit non-zero.
- **Lexer:** add the `,` token.
- **AST:** a program is a list of function declarations. A function declaration holds a name, a list of parameter
  names, and an *optional* body (absent for a prototype). A declaration (in a block) is now either a variable
  declaration or a function declaration. Expressions gain a call node: a function name plus a list of argument expressions.
- **Parser:** implement the grammar, including block-scope function declarations.
- **Resolver:** each map entry records the new name and whether it has linkage. Functions keep their names;
  parameters get unique names in the body's scope; arguments are resolved in the caller's current scope.
- **TACKY:** each function carries its parameter names; add `FunCall(name, args, dst)`; prototypes emit nothing.
- **Must reject (parse):** `int f(int a, );`, `int f(void) int x;`, `f(1, 2` (unclosed call), `int f(void, int a)`,
  `int f(int a int b);`. Unnamed parameters such as `int f(int);` are legal C but outside this grammar: decide what you
  do and write it down.
- **Must reject (resolution):** calling an undeclared function; using a call as an assignment target (`f() = 1`);
  duplicate parameter names; a parameter redeclared in the body's outermost block; a function definition nested in
  another function; a variable and a function with the same name in the same block.
- **Must accept:** recursion; a call before the definition when a prototype came first; nested calls `f(g(1), 2)`;
  a block-scope function declaration that shadows an outer variable.

**Suggested order.**
1. Lexer and AST changes. Let `cargo build` list every place that no longer compiles and fix them one by one.
2. Parse function definitions with parameter lists, then prototypes, then calls. Run `--chapter 9 --stage parse`.
3. Add the linkage flag to the resolver, then parameter scoping, then the nested-definition check.
4. TACKY generation for calls and parameters. Inspect the output of `--tacky` on a few test programs.
5. Unit tests: one per "must reject" item, plus the worked example's resolved names.

## Check your understanding
1. Why must the resolver leave `add` alone but rename `a` and `b`?
2. Why is `int f(void); int f(void);` legal in one scope while `int x; int x;` in one block is not?
3. Is `int foo(void) { int foo = 3; return foo; }` legal? Which `foo` does the `return` read, and why?
4. Why do parameters share a scope with the body's outermost block rather than living in an enclosing scope?
5. Why does TACKY evaluate every argument before the `FunCall` instead of interleaving argument setup with evaluation?

## Common pitfalls
- Renaming function names, which then don't match across declarations, across files, or with libc's `putchar`.
- Putting parameters in a scope *outside* the body, so `int f(int a) { int a; }` is wrongly accepted.
- Accepting nested function definitions because "it parsed".
- Resolving call arguments in the wrong scope, or forgetting to resolve them at all.
- Peeking only one token ahead and mis-parsing `int x(void);` as a variable declaration.
