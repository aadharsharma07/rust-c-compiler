# Lesson 11.2 — Type Checking Basics
**Part:** 3 — Build the Compiler · **Unit:** 11 — Functions and Whole Programs · **Type:** Builds type checker · **Est. time:** 5–7 h · **Tests:** ch. 9
**Prerequisites:** lesson 11.1; 5.4 (semantic analysis, symbol tables)

## Overview
You add a new semantic-analysis pass, the **type checker**, and the data structure it fills in, the **symbol table**.
It catches mistakes such as calling a function with the wrong number of arguments or calling a variable. The symbol
table outlives the pass: code generation reads it in 11.3 and 11.4, and Unit 12 grows it into a full type system.

## The lesson

### What a type checker is for
In Python, this program starts running and fails only when the bad line executes:
```python
def f(a, b): return a + b
print("hello")
f(1)        # TypeError: f() missing 1 required positional argument: 'b'
```
Python checks at **run time** because it has no other choice: `f` could be reassigned to anything before the call.
C checks at **compile time**: every function's parameter list is fixed by its declaration, so the compiler can reject
`f(1)` before the program exists. The pass that does this is the **type checker**. A **type** is a description of
what kind of value something is and what you may do with it. Right now there are only two kinds of thing:
- `int`: variables and parameters;
- "function taking *n* `int` parameters and returning `int`".

That seems almost too simple to need a pass, but the structure you build now carries `long`, `double`, pointers and
structs in Unit 12. Design for that growth.

### Why not do this in the resolver?
The resolver (10.2, 11.1) answers *"which declaration does this name refer to?"* using **scoped** maps: a map is
created when a block opens and thrown away when it closes. Type checking answers a different question, *"is this use
consistent with everything declared about this thing?"*, and needs information that survives the end of a block.
Consider:
```c
int f(int a);
int main(void) {
    int f(void);       /* a second declaration of the same function, inside a block */
    return f();
}
```
Both declarations of `f` have linkage, so they name **one** function. They disagree (one parameter vs. none), so the
program is invalid. A scoped map can't see this: the file-scope entry and the block-scope entry live in different
maps. A single, program-wide table can.

### The symbol table, and why it can be flat
A **symbol table** maps each name to what the compiler knows about it. It can be a plain flat map (Python: one `dict`),
not a stack of scopes, because of what the resolver already guaranteed: every local variable now has a unique name
(`x.0`, `x.1`...), and every name with linkage refers to the same entity everywhere. So no two different things share
a key. Each entry holds:
- the **type**: `int`, or function-with-*n*-parameters;
- **attributes**: for a function, whether it has been **defined** yet. (11.4 adds linkage and initial values.)

Represent the type as an enum with an `Int` case and a `Function` case that records the parameter count today and
will record parameter and return *types* in Unit 12.

### The rules
Walk the resolved AST and apply these:

**A function declaration `f`.**
1. If `f` is already in the table, its stored type must equal the new one (same parameter count). Otherwise:
   *incompatible declarations*. If it is stored as `int` (a variable), that is also an error.
2. If the old entry says *defined* and this declaration has a body: *function defined more than once*.
3. Store `defined = old_defined || this_has_body`. (Never just overwrite: a prototype that comes *after* the
   definition must not erase the fact that the function was defined.)
4. If there is a body: add each parameter to the table as `int`, then check the body.

**A local variable declaration.** Add it as `int`; check its initializer, if any.

**A call `f(args)`.** Look up `f`. If its type is `int`: *variable used as a function*. If the argument count
differs from the parameter count: *wrong number of arguments*. Then check every argument, since arguments may contain
their own bad calls.

**A variable use `x`.** If `x`'s type is a function: *function used as a variable* (`return f;`, `f + 1`, `f = 3`).

Everything else (statements, other expressions) just recurses into its children.

### A worked example
```c
int sq(int x);
int main(void) { int sq_val = sq(3); return sq_val; }
int sq(int x) { return x * x; }
```
After resolution and type checking, the table holds:
```
sq       -> Function(params: 1), defined: true
x.0      -> Int          (parameter of the prototype; harmless to record)
sq_val.1 -> Int
x.2      -> Int
```
Trace: the prototype adds `sq` (defined: false). In `main`, the call `sq(3)` finds a 1-parameter function and one
argument: fine. The definition matches the stored type, was not defined before, so `defined` becomes true.

Programs this pass rejects:
```c
int f(int a, int b); int main(void) { return f(1); }   /* wrong number of arguments */
int f(void); int f(int a);                              /* incompatible declarations */
int f(void) { return 1; } int f(void) { return 2; }     /* defined twice */
int main(void) { int x = 3; return x(); }               /* variable used as a function */
int f(void); int main(void) { int f = 1; return f(); }  /* the local 'f' shadows the function */
```
The last one is worth tracing: the resolver maps the inner `f` to `f.0` (a variable, no linkage), so the call becomes
`f.0()`, and the type checker finds that `f.0` is an `int`.

### Which pass catches which error?
| Error | Caught by |
|---|---|
| Syntax: `int f(int a, );` | parser |
| Undeclared function or variable, duplicate declaration in one scope | resolver |
| Wrong argument count, incompatible declarations, defined twice, wrong kind of thing | type checker |

### Keeping the table
The type checker returns both the (unchanged) program and the table. Don't drop the table at the end of `--validate`:
in 11.3 the code generator asks it "is this function defined in this file?" and in 11.4 "is this variable static?".

## Build

**Practice first (paper, ~20 min).** For each program in the rejection list above, write the table entries that
exist at the moment the error is found. Then invent one program where a variable and a function legally share a source
name, and show its table.

**Spec.** Input: the resolved (and loop-labelled) AST. Output: the same AST plus a symbol table, or a type error with a
clear message and non-zero exit. The pass runs as part of `--validate`, after resolution and loop labelling.
- **Type representation:** an enum with `Int` and a function case recording the parameter count, deriving equality
  so two types can be compared directly.
- **Symbol table:** a map from name to an entry holding the type and a "defined" flag for functions. It is created by
  this pass and handed on to TACKY generation and codegen.
- **Errors:** incompatible function declarations; function defined more than once; variable used as a function;
  function used as a variable; wrong number of arguments.
- **Must reject:** all of chapter 9's invalid-type programs, including conflicts across scopes and the shadowing case above.
- **Must accept:** repeated identical prototypes; a prototype after the definition; calls nested in arguments; a local
  variable shadowing a function name when the function is not called in that scope; recursion.

**Suggested order.**
1. Define the type enum and the entry struct; write the empty pass and plug it into the driver.
2. Function declarations (rules 1–4), then variable declarations.
3. Calls and variable uses.
4. Change the driver so the table flows from `--validate` into the later stages.
5. Unit tests: one per error kind, plus "prototype after definition keeps `defined: true`".

A borrow-checker classic awaits: you can't keep the reference returned by looking up an entry alive while you insert
into the same map. Copy out the small facts you need (the old type, the old flag) first, then insert.

## Check your understanding
1. Why can't the resolver's scoped maps detect `int f(int a);` conflicting with a block-scope `int f(void);`?
2. Why is a flat table safe for local variables? Which guarantee of the previous pass makes it so?
3. What does `defined = old_defined || has_body` protect against? Give the program that breaks if you overwrite.
4. Which pass rejects calling an undeclared function, and which rejects calling with the wrong number of arguments? Why that split?
5. How would you change the function type so it extends to `long` and pointer parameters in Unit 12?

## Common pitfalls
- Overwriting a function's entry when a prototype follows its definition, losing the "defined" flag.
- Forgetting to check call arguments, which may themselves contain bad calls.
- Comparing only that a function was declared before, not that its *type* matches.
- Folding type checking into the resolver and then fighting scope-limited maps.
- Discarding the symbol table after `--validate`; 11.3 and 11.4 need it.
