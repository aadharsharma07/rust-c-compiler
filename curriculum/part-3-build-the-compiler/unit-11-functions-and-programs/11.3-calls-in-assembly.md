## Overview
You turn TACKY's `FunCall` and function parameters into real x86-64 assembly that follows the System V calling

call `putchar` from the C library and be linked with object files built by `clang`: your programs print text.

## The lesson

### Recap: the System V calling convention (from 6.4)
A **calling convention** is the agreement between a caller and a callee about where arguments go, where the result
comes back, and which registers survive a call. Your code must follow the one used on x86-64 Linux and macOS, called
**System V AMD64**, because the other side of a call (libc, the test suite's `clang`-compiled files) follows it too.
The parts you need:

| `int` argument | 1 | 2 | 3 | 4 | 5 | 6 | 7+ |
|---|---|---|---|---|---|---|---|
| goes in | `%edi` | `%esi` | `%edx` | `%ecx` | `%r8d` | `%r9d` | the stack |

(`%edi` is the low 32 bits of the 64-bit `%rdi`, and so on.) Stack arguments are pushed **right to left**, so the
7th argument ends up at the lowest address, right on top of the stack when `call` runs. Each one takes 8 bytes, even an
`int`. The **caller** removes them afterwards. The `int` result comes back in `%eax`.

`%rsp` must be a multiple of 16 **at the moment `call` executes**. `call` pushes an 8-byte return address, the callee's
`pushq %rbp` pushes 8 more, and after `movq %rsp, %rbp` the callee is aligned again, provided it subtracts a multiple of
16 for its locals. Here is the stack inside a callee after its prologue, for a call with 8 arguments:
```
 higher addresses
 +-----------------------+
 | arg 8                 |  24(%rbp)
 | arg 7                 |  16(%rbp)   (was 0(%rsp) just before `call`)
 | return address        |   8(%rbp)   (pushed by `call`)
 | caller's saved %rbp   |   0(%rbp)   <- %rbp
 | callee's locals ...   |  -4(%rbp), -8(%rbp), ...
 +-----------------------+  <- %rsp
 lower addresses (the stack grows downward)
```
Registers `%rax %rcx %rdx %rsi %rdi %r8–%r11` are **caller-saved**: any call may overwrite them. `%rbx %rbp %rsp
%r12–%r15` are **callee-saved**: a function that changes them must restore them. Right now `rcc` keeps every value in a
stack slot and uses registers only briefly inside one instruction sequence, so nothing is ever live in a register
across a `call`. That's why you can ignore saving for now. Unit 14 can't.

### New assembly constructs
To express calls, the assembly AST (from 8.4 and 9.3) needs:
- **Registers** `DI`, `SI`, `DX`, `CX`, `R8`, `R9`, alongside the `AX`, `DX`, `R10`, `R11` you already have.
- **`Push(operand)`**: `pushq` decrements `%rsp` by 8 and stores 8 bytes there.
- **`Call(name)`**: `call` pushes the return address and jumps to the function.
- **Stack deallocation**, the mirror of the allocation you already emit: `addq $n, %rsp`.
- **Positive stack offsets**: `Stack(16)`, `Stack(24)`... now appear, meaning the caller's stack arguments.
- A program becomes a **list of functions**, each with its own instructions and its own frame size.

### The callee side: copying parameters in
At the start of each function, copy every parameter into its own pseudoregister. For parameter *i* (counting from 0):
- if *i* < 6: `Mov(Reg(argument register i), Pseudo(param))`;
- otherwise: `Mov(Stack(16 + 8 × (i − 6)), Pseudo(param))`.

After those moves, a parameter is just another pseudoregister, and the rest of your back end (pseudo replacement,
fix-ups) needs no change. A copy from `Stack(16)` into a stack slot is a memory-to-memory move, which your existing
fix-up pass already splits through `%r10d`.

### The caller side: lowering `FunCall(f, args, dst)`
Let *n* be the number of arguments and *k* = max(0, *n* − 6) the number of stack arguments.
1. **Padding.** If *k* is odd, allocate 8 bytes (`subq $8, %rsp`). Your frame keeps `%rsp` 16-aligned; pushing an odd
   number of 8-byte values would leave it 8 off at the `call`.
2. **Register arguments.** Move the first six arguments into `DI, SI, DX, CX, R8, R9` in order.
3. **Stack arguments, in reverse order** (last argument first). If the operand is an immediate or a register, `Push` it.
   If it is in memory, first `Mov` it into `AX`, then `Push(Reg(AX))`. Why not push the stack slot directly? `pushq`
   always reads 8 bytes, and only 4 of those belong to your `int`. (`%rax` is safe as scratch here: it holds nothing
   live, and the call will overwrite it anyway.)
4. **`Call(f)`**, then deallocate `8 × k + padding` bytes if that is non-zero.
5. **Result:** `Mov(Reg(AX), dst)`.

Recall from 11.1 that TACKY evaluates every argument *before* the `FunCall`. That is what makes step 2 safe: for
`f(g(1), 2)` the call to `g` is completely finished, its result stored in a temporary, before anything is put in `%edi`
for `f`. If argument evaluation could run in the middle of setting up registers, a nested call would clobber them.

### Frames per function
Pseudo replacement is now done **per function**, with a fresh pseudo-to-offset map and its own total size. Round each
function's size up to a multiple of 16 so the alignment reasoning above holds.

### Worked example: seven arguments
`int r = f(1, 2, 3, 4, 5, 6, 7);` in a function whose frame is a multiple of 16 (macOS names):
```
    subq  $8, %rsp           # k = 1 stack argument (odd): pad
    movl  $1, %edi
    movl  $2, %esi
    movl  $3, %edx
    movl  $4, %ecx
    movl  $5, %r8d
    movl  $6, %r9d
    pushq $7                 # argument 7
    call  _f
    addq  $16, %rsp          # 8 bytes of argument + 8 bytes of padding
    movl  %eax, -4(%rbp)     # r (well, a temporary that is then copied to r)
```
At `call`, `%rsp` = frame-aligned − 8 − 8 = a multiple of 16. Inside `f`, parameter 7 is at `16(%rbp)`.

### Worked example: printing
```c
int putchar(int c);
int twice(int x) { return x + x; }
int main(void) { putchar(twice(33)); return 0; }   /* prints "B" (ASCII 66) */
```
macOS output, abbreviated:
```
    .globl _twice
_twice:
    pushq %rbp
    movq  %rsp, %rbp
    subq  $16, %rsp
    movl  %edi, -4(%rbp)        # x.0 <- parameter 1
    movl  -4(%rbp), %r10d
    movl  %r10d, -8(%rbp)       # tmp.1 = x.0
    movl  -4(%rbp), %r10d
    addl  %r10d, -8(%rbp)       # tmp.1 += x.0
    movl  -8(%rbp), %eax
    movq  %rbp, %rsp
    popq  %rbp
    ret

    .globl _main
_main:
    pushq %rbp
    movq  %rsp, %rbp
    subq  $16, %rsp
    movl  $33, %edi
    call  _twice
    movl  %eax, -4(%rbp)        # tmp.2
    movl  -4(%rbp), %edi
    call  _putchar              # Linux: call putchar@PLT
    movl  %eax, -8(%rbp)        # tmp.3 (unused)
    ...
```

### Emission and symbols
- Every function gets `.globl name` so the linker can see it from other files.
- **macOS** prefixes every symbol with `_`: `_twice:`, `call _putchar`.
- **Linux** has no prefix. A call to a function **not defined in this file** is written `call putchar@PLT`: the
  linker routes it through the *Procedure Linkage Table*, a small jump table that finds the function in a shared
  library at load time. Calls to functions defined in this file are plain `call twice`. The symbol table's *defined*
  flag (11.2) tells you which. macOS has no `@PLT` syntax.
- Register names depend on operand size: `movl %edi, -4(%rbp)` but `pushq %rax` (there is no 32-bit push in 64-bit
  mode). Your emitter needs 4-byte and 8-byte names for every register.

### The `-c` flag
From chapter 9, the test suite compiles some files with `rcc` and others with the system compiler, then links them
together. `rcc -c foo.c` must stop after assembling and produce `foo.o` (no linking). Without `-c`, link as before:
`clang`/`gcc` adds libc automatically, which is how `putchar` is found (recall the linker from 6.5).

## Build

**Practice first.**
1. On [Godbolt](https://godbolt.org) (x86-64 clang, `-O0`), compile a function with 8 `int` parameters and a caller
   that passes 8 constants. Annotate every instruction of the call and the callee's parameter reads.
2. On paper, draw the stack for `main` calling `f(1..9)` at the `call` instruction and after `f`'s prologue, with
   offsets from both `%rsp` and `%rbp`.
3. Compute padding and deallocation for 0, 1, 6, 7, 8 and 11 arguments.

**Spec.** Input: TACKY with functions, parameters and `FunCall`, plus the symbol table. Output: assembly text, an object
file (`-c`), or an executable.
- **TACKY → assembly:** parameter copy-in; `FunCall` lowering exactly as above; per-function pseudo replacement with
  16-byte rounding.
- **Fix-up:** memory-to-memory moves involving positive `Stack` offsets are handled; `Push` of an immediate or register
  needs no fix-up.
- **Emitter:** `.globl` per function; 4- and 8-byte register names; `_` prefix on macOS; `@PLT` on Linux only for
  functions not defined in this file.
- **Driver:** `-c` produces an object file and skips linking; all existing stage flags still work. An assembler or
  linker failure exits non-zero.
- **Must handle:** 0–6 register arguments; more than 6 with odd and even stack counts; recursion (`fib`); mutual
  recursion through prototypes; calls as arguments; calling `putchar`; a function defined in one file and called from another.

**Suggested order.**
1. Extend the assembly AST and emitter (registers, push, call, deallocation, list of functions).
2. Callee side: parameter copy-in. Test with a function that just returns its first parameter, called from a C file
   compiled by `clang` (`rcc -c lib.c`, then link).
3. Caller side with ≤ 6 arguments, then stack arguments and padding.
4. Platform symbol rules, then `-c`.
5. Write small C programs with a known output (7, 8 and 9 arguments; `putchar` loops) and check them by running.

## Check your understanding
1. Why is each parameter copied out of its register into a pseudoregister at the start of the function?
2. Why are stack arguments pushed in reverse order, and why is the padding allocated *before* pushing?
3. Why is `%rax` a safe scratch register for pushing an argument from memory?
4. How does the emitter decide between `call f` and `call f@PLT` on Linux? What changes on macOS?
5. Where does the callee read its 9th parameter, and what goes wrong if two functions share one pseudo-to-offset map?

## Common pitfalls
- Forgetting to deallocate after the call, or deallocating the pushed bytes but not the padding.
- Emitting `pushl` or a 4-byte register name with `push`; it must be `pushq %rax`.
- Reading the first stack parameter from `8(%rbp)` (that's the return address); it is at `16(%rbp)`.
- Not rounding each frame to 16, so calls into libc crash only sometimes.
- Missing `_` on macOS, or emitting `@PLT` on macOS.
- Resetting the temporary/label counter per function, so two functions emit the same label.
