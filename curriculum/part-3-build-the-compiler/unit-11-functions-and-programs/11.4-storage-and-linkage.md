# Lesson 11.4 — Storage and Linkage
**Part:** 3 — Build the Compiler · **Unit:** 11 — Functions and Whole Programs · **Type:** Builds globals/static/extern · **Est. time:** 8–12 h · **Tests:** ch. 10
**Prerequisites:** lessons 11.3; 6.5 (object files, symbols, linking)

## Overview
You add variables that live outside functions (**globals**), `static` variables that keep their value between calls,
and the `extern` and `static` keywords that control which files can see a name. This means separating three properties
every identifier has (scope, linkage and storage duration), extending the symbol table, and emitting data in `.data`
and `.bss` sections. At the end of this lesson `rcc` is a real compiler for an `int`-only subset of C.

## The lesson

### Three independent properties
Python blurs these together; C keeps them apart, and you need all three.
- **Scope**: where in the source the name is *visible*. File scope (declared outside any function, visible to the end
  of the file) or block scope (visible to the end of its block). You've handled scope since 10.4.
- **Linkage**: whether declarations in different places refer to the *same* entity. **External**: the same entity
  across all files of the program. **Internal**: the same entity within this file only. **None**: each declaration is
  its own entity. (11.1 had only "functions have linkage, variables don't".)
- **Storage duration**: how long the object *exists*. **Automatic**: created when its block is entered, gone when
  it exits; lives in the stack frame. **Static**: exists for the whole run of the program; lives at a fixed address in
  the executable's data area, and is initialized **once**, before `main` starts.

The Python analogy: a module-level variable in `counter.py` is like a C global (exists for the whole run, visible to
other modules that import it). A name starting with `_` is "private by convention"; C's `static` at file scope makes it
private *for real*, because the linker never sees it. A function's local variable is automatic. Python has no
direct equivalent of a `static` local; the closest is a default argument or attribute that persists between calls.

### The specifiers
A declaration now starts with a list of **specifiers** in any order: exactly one `int`, and at most one storage class,
`static` or `extern`. `static int x;` and `int static x;` mean the same. Parameters and the first clause of a `for`
loop may not have a storage class.

| Declaration | Linkage | Storage duration |
|---|---|---|
| file scope, no storage class | external | static |
| file scope, `static` | internal | static |
| `extern` (file or block scope) | that of a visible earlier declaration, else external | static |
| block scope, no storage class | none | automatic |
| block scope, `static` | none | static |

Functions always have static storage duration. `static` on a function gives internal linkage; no specifier or
`extern` gives external. A block-scope `static` *function* declaration is illegal.

### Rules for file-scope variables
These belong in the type checker, which now records more per symbol.
- The initializer must be a **constant** (`int x = 3;`, not `int x = y + 1;`): the value is baked into the executable
  file, so it must be known at compile time.
- Each declaration has an **initial-value kind**: *initial(n)* if it has an initializer; *tentative* if it has none
  and no `extern`; *no initializer* if it is `extern` without an initializer. A **tentative definition** is C's way of
  saying "define this, unless a real definition turns up": `int x;` at file scope.
- Merging two declarations of the same name: two *initial*s is a **conflicting definitions** error; otherwise
  *initial* beats *tentative*, which beats *no initializer*. So `int x; int x = 3; int x;` is legal and `x` is 3.
- If only tentative definitions exist, the variable is defined and initialized to 0.
- Linkage must agree: `static int x; int x;` is an error (internal then external). `static int x; extern int x;` is
  fine, because `extern` adopts the earlier declaration's internal linkage.
- A variable and a function may not share a file-scope name.

### Rules at block scope
- `extern int x;` inside a function refers to the file-scope (or other-file) `x`. It has linkage, so the resolver must
  **not** rename it, and it conflicts with a no-linkage `x` declared in the same block. It may not have an initializer.
- `static int n = 3;` inside a function has no linkage, so it is renamed like any local (`n.0`), but it has static
  storage: it is initialized **once, at load time**, not every time the function runs. Its initializer must be a
  constant (default 0). This is why it can count calls.

### Code generation for static storage
**TACKY.** A TACKY program now holds two kinds of top-level item: functions (each gaining a `global` flag, meaning
"external linkage") and **`StaticVariable(name, global, initial value)`**. Generate the static variables from the
symbol table, not from the AST: *initial(n)* emits with n, *tentative* emits with 0, *no initializer* emits nothing
(another file defines it). Declarations of `static` and `extern` locals produce **no** instructions: their
initialization isn't a run-time action.

**Assembly.** A pseudo whose symbol has static storage is replaced by a new **`Data(name)`** operand instead of a stack
slot. `Data` is memory, so every fix-up rule for `Stack` applies to it too (no memory-to-memory `mov`, no memory
operand for `idiv`, etc.).

**RIP-relative addressing.** `Data(name)` is emitted as `name(%rip)`. `%rip` is the *instruction pointer*, the address
of the next instruction. Writing `x(%rip)` asks the assembler and linker to encode "the distance from here to `x`"
rather than `x`'s absolute address. Because the distance stays the same wherever the program is loaded in memory, the
code is **position-independent**, which macOS requires and modern Linux prefers.

**Sections.** An object file is divided into **sections** (recall 6.5): `.text` for code, `.data` for initialized
data, and `.bss` for data that starts as all zeros. `.bss` takes no bytes in the file; the loader just reserves zeroed
memory. So zero-initialized statics go in `.bss`, others in `.data`. Only symbols with external linkage get `.globl`.

### A worked example
```c
static int counter = 5;
int total;
int bump(void) { static int calls; calls = calls + 1; counter = counter + 1; return calls; }
```
Symbol table: `counter` (internal, initial 5); `total` (external, tentative); `calls.0` (no linkage, static
storage, tentative so 0); `bump` (external function, defined). macOS output (Linux: drop the `_`):
```
    .globl _total
    .bss
    .balign 4
_total:
    .zero 4
    .data
    .balign 4
_counter:                         # no .globl: internal linkage
    .long 5
    .bss
    .balign 4
_calls.0:
    .zero 4
    .globl _bump
    .text
_bump:
    pushq %rbp
    movq  %rsp, %rbp
    subq  $16, %rsp
    movl  _calls.0(%rip), %r10d   # fix-up: memory -> memory
    movl  %r10d, -4(%rbp)         # tmp.1 = calls.0
    addl  $1, -4(%rbp)
    movl  -4(%rbp), %r10d
    movl  %r10d, _calls.0(%rip)   # calls.0 = tmp.1
    ...
```
`.balign 4` aligns the next address to 4 bytes; `.long 5` emits a 4-byte value; `.zero 4` emits 4 zero bytes. Real
compilers may print `.comm` or `.zerofill` instead (compare on Godbolt), but these simple directives assemble on both
platforms.

### What the linker does with all this
If two files each define `static int helper(void)`, each file has its own private `helper`, and nothing clashes. If
two files each contain `int g = 1;`, the linker sees two external definitions of `g` and fails with a duplicate-symbol
error. If one file has `extern int g;` and no file defines `g`, the link fails with an undefined symbol.

## Build

**Practice first (paper).**
1. Fill in scope, linkage and storage duration for: file-scope `static int a;`, block-scope `static int b;`,
   block-scope `extern int c;`, a parameter.
2. Merge the declarations `int x; extern int x; int x = 4;` step by step and say what gets emitted.
3. On Godbolt, compile the worked example with `clang -O0` and match each directive to the one above.

**Spec.** Inputs: C files with file-scope declarations and storage-class specifiers. Outputs: as before, plus data
sections; `-c` objects must link with `clang`-built objects.
- **Parser:** specifier lists (exactly one `int`, at most one storage class); variable declarations at file scope;
  reject storage classes on parameters and in a `for` initializer.
- **Resolver:** file-scope names keep their spelling; a block-scope `extern` keeps its spelling and has linkage; a
  same-block conflict between a name with linkage and one without is an error.
- **Type checker / symbol table:** per-entry attributes: function (defined, global), static (initial-value kind,
  global), local (automatic). Apply every rule above.
- **TACKY:** `global` on functions; `StaticVariable` items generated from the table; nothing emitted for `static` or
  `extern` local declarations.
- **Assembly:** `Data(name)` operand; pseudo replacement consults the table; fix-up treats `Data` as memory; emitter
  prints `.globl` only for global symbols, switches `.data`/`.bss`/`.text`, and writes `.balign 4`, `.long n`/`.zero 4`
  and `name(%rip)`.
- **Must reject:** `static extern int x;`; `int int x;`; `static x;` (no type); `int f(static int a)`; `for (static int
  i = 0; ...)`; non-constant file-scope or static-local initializers; `extern int x = 1;` in a block; a block-scope
  `static int f(void);`; `int x; static int x;`; two initialized definitions; a variable and a function with the same
  file-scope name; an `extern` in a block conflicting with a local in the same block; `extern int f;` where `f` is a function.
- **Edge cases:** `extern int x = 3;` at file scope (a legal definition); a tentative definition followed by a real
  one; static locals with the same source name in two functions; a global defined in another file; recursion using a static counter.

**Suggested order.** Parser → resolver → symbol-table attributes and rules → TACKY → `Data` operand and fix-ups →
emitter. Run `--chapter 10 --stage parse`, then `validate`, then the full chapter. Emit statics in a deterministic
order (for example sorted by name): Rust's `HashMap` iteration order is unspecified, and unstable output makes debugging painful.

## Common pitfalls
- Emitting a TACKY copy for a static local's initializer, which resets it on every call.
- Forgetting `.text` before a function after emitting data, so code lands in `.data` or `.bss`.
- Marking internal-linkage variables `.globl`, causing duplicate-symbol link errors across files.
- Emitting storage for an `extern` declaration with no initializer (multiple-definition errors).
- Not treating `Data` operands as memory in the fix-up pass (`idiv`, `cmp`, memory-to-memory `mov`).
