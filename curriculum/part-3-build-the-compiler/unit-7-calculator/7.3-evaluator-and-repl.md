# Lesson 7.3 — Evaluator and REPL
**Part:** 3 — Build the Compiler · **Unit:** 7 — Warm-up, a Calculator · **Type:** Builds evaluator + REPL · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 4.1, 4.6, 7.2

## Overview
You finish the calculator: an evaluator that walks the AST and computes its value with C-like integer rules, one error
type that carries failures from every stage to the user, a `Display` pretty-printer for the tree, and a REPL
(read–eval–print loop) to drive it all. You also split the crate into modules that mirror the phases of a compiler.
The result is a complete miniature language implementation, laid out the way `rcc` will be.

## The lesson

### Evaluation is a post-order tree walk
To evaluate a node, first evaluate its children, then combine their values. That is a **post-order** traversal (children
before parent), and it falls naturally out of a recursive function with one `match` arm per kind of node:

- a literal evaluates to its value;
- a negation evaluates its child, then negates the result;
- a binary node evaluates its left child, then its right child, then applies the operator.

For `Sub(Mul(2, Add(3, 4)), Neg(1))` the visits go:

```
Sub ──► Mul ──► 2                     → 2
          └──► Add ──► 3, 4           → 7
        Mul(2, 7)                     → 14
    └──► Neg ──► 1                    → -1
Sub(14, -1)                           → 15
```

The function takes the tree by reference (`&Expr`): evaluating should not consume the tree, because you may want to
print it too. This is the same shape as the compiler passes you will write later. A pass that turns the C AST into
assembly (lesson 8.4) is "evaluation" that produces instructions instead of numbers.

### Integer semantics: be like C, not like Python
Your calculator follows C's rules for 64-bit signed integers, because your compiler will have to.

**Division truncates toward zero.** In C (and in Rust's `/` on integers), `-7 / 2` is `-3`: the exact answer `-3.5`
is cut toward zero. Python's `//` *floors* instead: `-7 // 2` is `-4`. If you have Python habits, this is the one to
unlearn. Rust's `/` already does the C thing, so you just need to not "fix" it.

**Overflow is an error you must detect.** Python integers never overflow. Rust's `i64` does, and plain operators panic
in debug builds and wrap in release builds. Use the checked methods (`checked_add`, `checked_sub`, `checked_mul`,
`checked_div`, `checked_neg`), which return `None` instead of misbehaving, and turn `None` into an evaluation error.

**Three sneaky cases:**

| Input | Why it fails | Detected by |
|---|---|---|
| `4 / 0` | division by zero | `checked_div` returns `None` |
| `9223372036854775807 + 1` | result exceeds `i64::MAX` | `checked_add` returns `None` |
| `(-9223372036854775807 - 1) / -1`, i.e. `i64::MIN / -1` | the true answer, 2⁶³, does not fit in an `i64` | `checked_div` returns `None` |

The last one surprises people: dividing can overflow, because two's complement (lesson 6.1) has one more negative
number than positive. `checked_div` covers both division by zero and this case, but your error message should say
which one happened, so check for a zero divisor first.

### One error type for the whole pipeline
Each stage has its own error type: `LexError`, `ParseError`, and now an `EvalError` (division by zero, overflow).
The REPL wants to run all three and report "whatever went wrong". The idiomatic design is a top-level enum with one
variant wrapping each stage's error, plus a `From` implementation for each (lesson 3.3). With `From` in place, the `?`
operator converts automatically, so a function that runs lex → parse → eval reads as three lines, each ending in `?`.

### Modules mirror phases
A compiler is a pipeline of phases, and its code should be too. Give each phase its own module with a narrow public
surface:

```
src/
  lib.rs      declares the modules below (mod lexer; mod parser; …) and re-exports what main needs
  token.rs    token kinds + Token                        (or keep these inside lexer.rs)
  lexer.rs    pub fn: &str        → Result<Vec<Token>, LexError>
  ast.rs      Expr, BinOp, constructor helpers, Display
  parser.rs   pub fn: tokens      → Result<Expr, ParseError>
  eval.rs     pub fn: &Expr       → Result<i64, EvalError>
  error.rs    the top-level error enum + From impls     (or errors live in their stage's module)
  main.rs     only the REPL
```

Recall from lesson 4.6: `mod lexer;` tells `rustc` to load `src/lexer.rs`; everything is private to its module unless
marked `pub`; `crate::ast::Expr` names an item from anywhere in the crate. Putting the modules in a library (`lib.rs`)
and keeping `main.rs` as a thin binary means tests in `tests/` can use the library too.

**What to make `pub`:** the one entry function per phase, and the types callers need to hold or match on (tokens, the
AST, error types). The parser struct and its helper methods (peek, expect, parse_term, …) stay private: they are how
the parser works, not what it offers. A small surface means you can rewrite the inside of a phase without touching
anything else. Making everything `pub` "to get it compiling" throws that away.

**Dependencies flow one way:** the parser uses the lexer's tokens and the AST; the evaluator uses the AST; `main` uses
everything. Nothing points backwards (the lexer never imports the parser). `rcc` will have the same arrows, just more
boxes: lexer → parser → semantic passes → IR → assembly → emitter.

### A `Display` pretty-printer for the AST
`Debug` output (`{:?}`) is for developers and can be derived. `Display` (`{}`) is for humans, and you write it yourself
(lesson 4.1). Implementing it for `Expr` gives you `println!("{}", expr)` and `.to_string()` for free.

A **fully parenthesised** printer makes the tree's shape visible: wrap every binary node in parentheses with spaces
around the operator, and print negation as `(-x)`. For `2 * (3 + 4) - -1`:

```
((2 * (3 + 4)) - (-1))
```

The implementation is recursive: printing a binary node writes `(`, then the left child **with `{}`** (which recursively
calls your `Display`), the operator, the right child, and `)`. Implement `Display` for the operator enum too, so that
part is just another `{}`.

This printer has a property worth testing: **round-tripping**. Parse a string, print the AST, parse the printed text
again: you must get the *same* AST. The test is cheap and catches bugs in both the parser and the printer. (A
printer that leaves out redundant parentheses, printing `2 * (3 + 4) - -1` back exactly, must know precedence. That
is a good stretch goal.)

Write `Display` for your errors as well. Offsets are 0-based byte positions; humans count columns from 1. Convert in
one place, the error's `Display`, so the rest of the code never has to think about it:

```
error: unexpected character '$' at column 3
```

### The REPL
A REPL is a loop: print a prompt, read a line, process it, print the result, repeat. In Python, `input("> ")` does
the first two steps. In Rust you do them by hand, and three details matter:

- **Flushing.** `print!` (without `ln`) writes into a buffer; the terminal may not show `> ` until a newline. Call
  `flush()` on stdout after printing the prompt.
- **End of input.** `read_line` returns `Ok(0)` (zero bytes read) at end of file: when the user presses Ctrl-D, or
  when input piped in from `echo` runs out. That is the signal to exit. An *empty line* is different: it returns
  `Ok(1)` (just the `\n`). Confusing the two gives an infinite loop at EOF.
- **The buffer appends.** `read_line` adds to the `String` you pass it. Clear it at the top of each iteration, or
  create a fresh one.

Errors are printed and the loop continues; a calculator that quits on a typo is no fun. Send results to **stdout** and
errors to **stderr** (`eprintln!`): then `echo "6*7" | calc > out.txt` captures only answers. Your compiler follows the
same convention.

The session the spec expects:

```
> 1 + 2 * 3
7
> :ast (1+2)*3
((1 + 2) * 3)
> 2 $ 3
error: unexpected character '$' at column 3
> 4 / 0
error: division by zero
> (Ctrl-D)
```

## Build
1. **Evaluator.** In `eval.rs`, define `EvalError` (division by zero, overflow) and a public function from `&Expr` to
   `Result<i64, EvalError>`, using checked arithmetic throughout. Test it on hand-built ASTs (not via the parser), so
   an evaluator test can only fail because of the evaluator.
2. **Top-level error.** Define an enum wrapping the three stage errors, with a `From` impl for each, and a function
   that runs lex → parse → eval with `?`.
3. **Modules.** Move code into the layout above (your names may differ), declared from `lib.rs`. Move each phase's
   tests into that module's `#[cfg(test)]` block. Shrink each module's `pub` surface to the minimum, and fix what
   breaks.
4. **`Display`.** Implement it for the operator enum, the AST (fully parenthesised), each error type (1-based column,
   human wording) and optionally tokens (their lexeme).
5. **REPL.** `main.rs` contains only the loop: prompt `> ` and flush; read a line; exit with status 0 on EOF or
   `:quit`; skip blank lines; `:ast <expr>` prints the parsed AST with `Display` instead of evaluating; otherwise print
   the value. Errors print as `error: …` on stderr and the loop continues.
6. **Tests:** evaluator tests for precedence results (`1+2*3` → 7), truncation (`-7/2` → -3, `7/-2` → -3), division by
   zero, `i64::MAX + 1`, `i64::MIN / -1` (built as an AST) and negating `i64::MIN`; `Display` tests for the AST and
   each error; a round-trip test over at least five expressions. Optional: one integration test in `tests/` that uses
   only `pub` items.
7. Check that piping works: `echo "6*7" | cargo run -q` prints `42` (a prompt in the output is acceptable).

## Common pitfalls
- Using `+`, `-`, `*`, `/` directly on `i64` in the evaluator: debug panics, release garbage.
- Reaching for Python's floor division semantics and "correcting" Rust's truncation.
- Calling `{:?}` on children inside your `Display` impl, mixing two formats in one output.
- Forgetting to flush, so the prompt appears after the user's input.
- Treating `Ok(0)` from `read_line` as a blank line and spinning forever at EOF; or not clearing the buffer.
- Making everything `pub`, or letting modules import each other in a circle.
