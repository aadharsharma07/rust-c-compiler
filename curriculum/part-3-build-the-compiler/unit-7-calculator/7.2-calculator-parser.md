# Lesson 7.2 — Calculator parser
**Part:** 3 — Build the Compiler · **Unit:** 7 — Warm-up, a Calculator · **Type:** Builds recursive-descent parser + AST · **Est. time:** 5–8 h · **Tests:** none
**Prerequisites:** lessons 4.4, 5.3, 5.4, 7.1

## Overview
You turn the calculator's grammar into Rust: a recursive enum for the abstract syntax tree (AST), and a
recursive-descent parser that reads the tokens from lesson 7.1 and builds that tree, or explains precisely why it
can't. In lesson 5.3 you ran recursive descent on paper; here you design the parser's state, its helper methods and
its errors. This is the heart of every front end, including the C parser you start in lesson 8.3.

## The lesson

### The grammar, recalled
From lesson 5.3, in EBNF (`{ … }` means "zero or more times", `|` means "or", quoted things are tokens):

```
<expr>    ::= <term>  { ("+" | "-") <term> }
<term>    ::= <unary> { ("*" | "/") <unary> }
<unary>   ::= "-" <unary> | <primary>
<primary> ::= <number> | "(" <expr> ")"
```

Three facts are encoded here, and your parser inherits all three:

- **Precedence by levels.** Each rule only calls rules *below* it, so the lower the rule, the tighter it binds. `*` is
  handled in `<term>`, below `<expr>`, so `1 + 2 * 3` groups the `2 * 3` before the `+` ever sees it. Unary minus is
  lower still, so `-2 * 3` means `(-2) * 3`.
- **Left associativity by loops.** `{ ("+" | "-") <term> }` is a loop, and (as you'll see) each pass of the loop makes
  everything parsed so far the *left* child of a new node. So `1 - 2 - 3` means `(1 - 2) - 3`.
- **Parentheses restart at the top.** `<primary>` can contain a whole `<expr>`, which is how `(1 + 2) * 3` overrides
  precedence.

### Why not the "natural" left-recursive rule
You might want to write `<expr> ::= <expr> "-" <term> | <term>`. It describes left associativity perfectly, but
translated into a function, `parse_expr` would begin by calling `parse_expr`, which begins by calling `parse_expr`…
without consuming a token, forever, until the stack overflows. That is **left recursion**, and recursive descent
cannot handle it. The `{ … }` loop form describes the same language and the same grouping without the problem.

### Designing the AST
The AST (lesson 5.4) keeps meaning and drops syntax: there is no node for parentheses, because the tree's *shape*
already says what was grouped. The calculator needs three kinds of expression:

- an integer literal (carrying an `i64`);
- a unary negation, with one child expression;
- a binary operation: an operator and two child expressions.

In Python you might write three small classes, or use tuples like `("bin", "+", left, right)`. In Rust, this is a
**recursive enum** (lesson 4.4). The children must be boxed: an expression that *directly* contained two expressions
would need infinite size, since each of those could contain two more. A `Box` is a fixed-size pointer to a value on
the heap, so the enum has a known size:

```
   Binary(Sub, ●, ●)                     the enum value: tag + operator + two pointers
              |  \
              v   v   (heap)
   Binary(Mul, ●, ●)     Neg(●)
              |  \           \
            Num 2  Binary(Add, ●, ●)   Num 1
                              |  \
                            Num 3  Num 4
```

Make the operator a **separate small enum** (`Add`, `Sub`, `Mul`, `Div`) rather than one variant per operator
(`Add(left, right)`, `Sub(left, right)`, …). With a separate enum, the parser builds every binary node the same way,
and the evaluator (lesson 7.3) and printer handle "a binary node" once, then dispatch on the operator. Derive `Debug`,
`Clone` and `PartialEq` on both enums so tests can compare whole trees.

Tests that build expected trees by hand get verbose fast (all those `Box::new` calls). Small helper constructor
functions, such as "make a binary node from an operator and two expressions", keep them readable.

### The parser's state
A recursive-descent parser needs very little state: the token list and a **cursor** (the index of the next unread
token). Put both in a struct, and write the grammar functions as methods taking `&mut self`, because they advance the
cursor. Three small helper methods do almost all the token handling:

- **peek**: return the current token without advancing. It returns an `Option`, because the cursor may be past the end.
- **advance**: return the current token and move the cursor forward.
- **expect** *kind*: if the current token has this kind, advance past it; otherwise return an error saying what was
  expected and what was found. You will use this for the closing `)`.

Why an index rather than an iterator? An index makes "where am I?" trivial (useful for errors) and lets you peek as
far ahead as you like. A peekable iterator also works for this grammar. Both are fine; the index is easier to debug.

A borrow-checker note: if peek returns a *reference* into the token vector, you can't call a `&mut self` method while
holding it, because that would mean a shared and a mutable borrow alive at once (lesson 2.3). This is exactly why you
made tokens `Copy` in lesson 7.1: peek can return a copy, and the problem disappears.

### One function per rule
Each non-terminal becomes one method that returns `Result<Expr, ParseError>`:

- **parse_primary**: peek. A `Number` → advance and return a literal. A `(` → advance, call parse_expr, then expect `)`
  and return the inner expression (no node for the parentheses). Anything else, or nothing → error.
- **parse_unary**: if the next token is `-`, advance, call parse_unary *recursively* and wrap the result in a negation.
  Otherwise, delegate to parse_primary. (Recursion here is fine: a token was consumed before recursing.)
- **parse_term**: call parse_unary to get a `left`. Then loop: while the next token is `*` or `/`, advance, call
  parse_unary for a `right`, and replace `left` with a new binary node built from `left`, the operator and `right`.
  When the next token is anything else, stop and return `left`.
- **parse_expr**: the same shape as parse_term, one level up, with `+`/`-` and parse_term.

Finally, a public entry point creates the parser, calls parse_expr, and then **checks that every token was used**.

### Watching left associativity happen: `1 - 2 - 3`
Inside parse_expr (each term is just a number here):

| Step | Action | `left` afterwards |
|---|---|---|
| 1 | parse_term reads `1` | `Num 1` |
| 2 | sees `-`, advances; parse_term reads `2` | `Sub(Num 1, Num 2)` |
| 3 | sees `-`, advances; parse_term reads `3` | `Sub(Sub(Num 1, Num 2), Num 3)` |
| 4 | sees end of input, stops | returned |

The tree leans left, so it evaluates to `(1 - 2) - 3 = -4`. If you mistakenly put the *new* term on the left, you get
`3 - (...)`-style nonsense; if you recurse instead of looping, you get `1 - (2 - 3) = 2`. Both are classic bugs.

### A full trace: `2 * (3 + 4) - -1`
Tokens: `2 * ( 3 + 4 ) - - 1`. Indentation shows the call stack, which mirrors the tree being built:

```
expr
  term
    unary → primary: Number 2                     left = 2
    sees *  → unary → primary: sees (
                expr
                  term → unary → primary: 3       left = 3
                  sees + → term → … → 4           left = Add(3, 4)
                  sees ) : not + or -, return
              expect ) ✓                          right = Add(3, 4)
    left = Mul(2, Add(3, 4)); sees - : not * or /, return
  sees - → term
    unary: sees -  → unary → primary: Number 1    Neg(1)
  left = Sub(Mul(2, Add(3, 4)), Neg(1))
  end of input: return
```

Value: `14 - (-1) = 15`. Note how the second `-` was a binary operator (parse_expr saw it after a complete term) and
the third was a negation (parse_unary saw it where an operand was required). Position in the grammar, not the
token, decides.

### Parse errors
A parser must reject three different situations, and a good error says which:

- **Unexpected token**: `1 + * 2`. parse_unary finds `*` where an operand must start. Report what was found, its
  offset, and ideally what was expected ("a number, `-` or `(`").
- **Unexpected end of input**: `(1 + 2`. expect `)` finds nothing. There is no token, so there is no offset from a token;
  use the input length, or simply say "end of input".
- **Trailing input**: `1 2`. parse_expr happily parses `1` and returns, leaving `2` unread. Only the final "all tokens
  used?" check catches it. Forgetting that check is the most common parser bug of all.

Design `ParseError` as an enum with those variants, each carrying what its message needs (token kind and offset).
Indexing the token vector past the end with `tokens[i]` panics; use `get(i)`, which returns an `Option`, and turn
`None` into the end-of-input error.

Keep the parser's job narrow: it builds the tree and **does not evaluate**. Computing values while parsing is tempting
for a calculator, but your compiler will never do it, and keeping the AST as the interface lets lesson 7.3 add an
evaluator and a printer without touching the parser.

## Build
Continue the `calc` crate.

1. **AST types.** Define the operator enum (`Add`, `Sub`, `Mul`, `Div`) and the expression enum (literal, negation with
   one boxed child, binary with an operator and two boxed children). Derive `Debug, Clone, PartialEq`. Write small
   constructor helpers for tests.
2. **Error type.** Define `ParseError` with variants for an unexpected token (kind, offset, optionally a description of
   what was expected), unexpected end of input, and trailing input (kind and offset of the first leftover token).
3. **Parser struct.** Holds the tokens (owned, or a slice) and a cursor. Write peek, advance and expect, and test
   expect on its own.
4. **Grammar methods, bottom-up.** Write parse_primary for numbers only and test it; add parentheses (with parse_expr
   temporarily just calling parse_primary); then parse_unary; then parse_term; then the real parse_expr. Run the tests
   after every step.
5. **Entry point.** A public function: tokens in, `Result<Expr, ParseError>` out, including the trailing-input check.
6. **Update `main`** to lex, then parse, and print the `{:#?}` (pretty `Debug`) form of the AST or the first error.
7. **Tests (at least 12), comparing whole ASTs:** a single number; `1+2*3` (the `*` is deeper); `(1+2)*3`; `1-2-3` and
   `8/4/2` (left-leaning); `-3`; `- -1`; `-2*3` (negation inside the multiplication); `((((5))))`; and each error:
   `1 + * 2`, `(1 + 2`, `1 2`, `)`, and empty input.

## Check your understanding
1. To add `%` with the same precedence as `*`, which grammar rule and which parser method change? Why only those?
2. Write the left-recursive rule for subtraction and explain, in terms of your methods, what happens if you translate
   it directly.
3. Draw the AST your parser builds for `8 / 4 / 2` and for `-(1 - 2) * 3`.
4. How does your parser know that `1 2` is an error, when parse_expr succeeds on `1`?
5. In `5 - -5`, how does the parser decide that the first `-` is subtraction and the second is negation?
6. Why are the children of your AST nodes boxed? What would `rustc` say if they weren't?

## Common pitfalls
- Translating a left-recursive rule into a method, causing a stack overflow.
- Building right-leaning trees in the loop (or recursing instead of looping), so `1-2-3` gives `2`.
- Forgetting the final "all tokens consumed" check, so `1 2` quietly returns `1`.
- Indexing past the end of the token list and panicking instead of reporting end of input.
- Returning a placeholder node on error instead of an `Err`, which causes baffling failures later.
- Evaluating inside the parser instead of returning a tree.
