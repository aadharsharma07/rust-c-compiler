# Lesson 12.4 — Floating point
**Part:** 3 — Build the Compiler · **Unit:** 12 — A Real Type System · **Type:** Builds `double` · **Est. time:** 12–18 h · **Tests:** ch. 13
**Prerequisites:** lessons 12.1–12.3; 6.1 (binary); 6.4 and 11.3 (calling convention)

## Overview
C's `double` is the same 64-bit floating-point format as a Python `float`. Compiling it is a big step, because the CPU
handles floating point with a *separate* set of registers and instructions, and the calling convention passes doubles
separately from integers. You will also meet the strangest value in computing, NaN, and make comparisons treat it
correctly.

## The lesson

### What `double` is, seen from Python
Good news: you already use doubles. Every Python `float` is an IEEE 754 *binary64* value, which is exactly C's `double`.
So `0.1 + 0.2 != 0.3` in C for the same reason as in Python. Use Python to look at the bits:

```python
>>> import struct
>>> struct.pack('>d', 2.0).hex()     # big-endian bytes of 2.0
'4000000000000000'
>>> (0.1).hex()                      # exact binary value: 0.1 is not representable
'0x1.999999999999ap-4'
```

A double has 1 sign bit, an 11-bit exponent (stored with a bias of 1023) and a 52-bit fraction: value
= (−1)^sign × 1.fraction × 2^(exponent−1023). `2.0` is sign 0, exponent 1024, fraction 0, giving `0x4000000000000000`.
Two special cases matter to a compiler:
- `-0.0` (`0x8000000000000000`) is a different bit pattern from `0.0`, yet `0.0 == -0.0` is true.
- **NaN** ("not a number", e.g. `0.0/0.0`) compares unequal to everything, even itself: `x != x` is true for NaN.

In C you write `double d = 1.5;`. Floating constants look like `1.0`, `1.`, `.5`, `1e10`, `2.5e-3`. The compiler must round
each one to the nearest double **at compile time**, the same way Python's `float("0.1")` does.

### A second register file
Integer registers (`%rax` …) cannot do floating-point arithmetic. x86-64 has sixteen 128-bit **SSE registers**,
`%xmm0`–`%xmm15`; scalar double operations use their low 64 bits. The instructions have an `sd` suffix ("scalar double"):

| Operation | Instruction | Notes |
|---|---|---|
| move | `movsd` | register↔register, register↔memory (not memory→memory) |
| `+ - * /` | `addsd`, `subsd`, `mulsd`, `divsd` | destination must be an `xmm` register |
| negate | `xorpd mask, %xmmN` | flip the sign bit with a mask holding `-0.0` |
| compare | `comisd` | sets flags (see NaN below) |
| int → double | `cvtsi2sdl` / `cvtsi2sdq` | source not an immediate; destination `xmm` |
| double → int | `cvttsd2sil` / `cvttsd2siq` | truncates toward zero; destination a general register |

Reserve `%xmm14` and `%xmm15` as fix-up scratch registers, the way you use `%r10`/`%r11`.

### Constants live in memory
No SSE instruction takes an immediate. So every double constant becomes a labelled 8-byte value in read-only data, and
instructions read it with RIP-relative addressing (as you did for globals in 11.4). Emit the exact bits with `.quad`, so
no decimal round trip can change the value:

```asm
# Linux                              # macOS
    .section .rodata                     .literal8
    .balign 8                            .balign 8
.Lconst.0:                           Lconst.0:
    .quad 4611686018427387904            .quad 4611686018427387904   # 2.0
```

These are *local* labels: `.L` prefix on Linux, `L` on macOS, and no `_` prefix even on macOS. Equal constants can share
one label. The negation mask must be 16-byte aligned (`.literal16` on macOS, `.balign 16` on Linux), because `xorpd`
with a memory operand reads 16 bytes and faults if they are misaligned.

### Worked example

```c
double half(double x) { return x / 2.0; }
```

```
half(x):
    tmp.0 = x / 2.0
    Return(tmp.0)
```

```asm
    movsd   %xmm0, -8(%rbp)          # x arrives in %xmm0
    movsd   -8(%rbp), %xmm14
    movsd   %xmm14, -16(%rbp)        # tmp.0 = x   (mem→mem fix-up)
    movsd   -16(%rbp), %xmm15
    divsd   Lconst.0(%rip), %xmm15   # SSE arithmetic needs a register destination
    movsd   %xmm15, -16(%rbp)
    movsd   -16(%rbp), %xmm0         # a double is returned in %xmm0
```

### Conversions between integers and doubles
`cvtsi2sd` and `cvttsd2si` (the extra `t` means *truncate*, like Python's `int(2.9) == 2`) only understand **signed**
integers. Unsigned types need extra steps:
- `unsigned int` → double: zero-extend to 64 bits (12.3), then `cvtsi2sdq`; every 32-bit unsigned value fits in a signed long.
- double → `unsigned int`: `cvttsd2siq` into a 64-bit register, then keep the low 32 bits.
- `unsigned long` → double: if the value is non-negative as a signed number, `cvtsi2sdq` directly. Otherwise halve it with
  `shrq $1`, OR the lost lowest bit back in (so rounding stays correct), convert, then `addsd` the result to itself.
- double → `unsigned long`: if the value is below 2⁶³ (compare with `comisd`), `cvttsd2siq` directly. Otherwise subtract
  2⁶³ as a double, convert, then add 2⁶³ back as an integer (a 64-bit immediate, so it goes through a register).

In TACKY, give these their own instructions: `IntToDouble`, `UIntToDouble`, `DoubleToInt`, `DoubleToUInt`. The common type
rule gains one line: **if either operand is `double`, the common type is `double`**.

### The calling convention for doubles
Extending 6.4 and 11.3: the first eight double arguments go in `%xmm0`–`%xmm7`, counted **separately** from the integer
argument registers `%rdi, %rsi, %rdx, %rcx, %r8, %r9`. Leftover arguments of either kind go on the stack, in their original
order relative to each other. A double is returned in `%xmm0`. All `xmm` registers are caller-saved.

```c
double f(int a, double b, long c, double d);  /* a→%edi  b→%xmm0  c→%rsi  d→%xmm1 */
```

You cannot `pushq` an `xmm` register. To pass a double from a register on the stack, `subq $8, %rsp` and
`movsd %xmmN, (%rsp)`; a double already in memory can be pushed with `pushq` like any 8-byte value.

### Comparisons and NaN
`comisd %xmm1, %xmm0` compares `%xmm0` with `%xmm1` and sets flags like an unsigned compare: greater → ZF, PF, CF all
clear; less → CF=1; equal → ZF=1. If either value is NaN the result is **unordered**, which sets ZF=PF=CF=1. Read naively,
`setb` would say "NaN < x is true" and `sete` would say "NaN == NaN is true". NaN-safe lowering:
- `a > b` → `seta`; `a >= b` → `setae` (both false when unordered, as required).
- `a < b` → compute `b > a` (swap operands, then `seta`); likewise `a <= b` → swapped `setae`.
- `a == b` → `sete` AND `setnp` (equal and not unordered); `a != b` → `setne` OR `setp`.
- Truthiness (`if (d)`, `!d`, `&&`, `||`): compare against `0.0` (zero a register with `xorpd %xmmN, %xmmN`) and treat
  unordered as *true*, because NaN is not zero.

The suite keeps its NaN tests behind an extra-credit flag (check `./test_compiler --help`). Do them anyway.

### Rust notes
`f64` is neither `Eq` nor `Hash` (because of NaN), so deriving `Eq` on an enum that holds an `f64` fails.
`f64::to_bits` gives an exact `u64` that is hashable and distinguishes `-0.0` from `0.0`:

```rust
assert_ne!(0.0_f64.to_bits(), (-0.0_f64).to_bits());
```

`str::parse::<f64>` rounds correctly, as C requires. Rust's float-to-int `as` saturates, while x86 returns `0x80000000`;
C calls out-of-range conversions undefined, so rely on neither.

## Build
1. **Lexer.** Floating constants: `1.0`, `1.`, `.5`, `1e10`, `1E-3`, `2.5e+2`. Reject `1.0.0`, `1e`, `1.e+`, `2._`, and a
   constant followed directly by a letter or `.`.
2. **Parser and types.** The `double` keyword (not combinable with `long`, `signed`, `unsigned` or `int`); a `Double` type;
   double constants and static initial values.
3. **Type checker.** The new common-type rule. Reject `%` and `~` on doubles (and bitwise/shift operators if you did that
   extra credit). Convert static initialisers between doubles and integers at compile time, truncating toward zero.
4. **TACKY.** The four conversion instructions; casts choose among them by source and target type.
5. **Assembly.** A `Double` assembly type; `Cvtsi2sd`, `Cvttsd2si`; SSE binary ops including `xorpd`; `Cmp` on doubles
   emits `comisd`; parity condition codes `P`/`NP`; `xmm` registers; a table of static constants keyed by (bits, alignment).
6. **Calls.** Classify each argument and parameter as integer or SSE; copy parameters in from `xmm` registers and the
   stack; read return values from `%xmm0` or `%rax` by return type.
7. **Fix-ups.** SSE arithmetic and `comisd` need a register destination (`%xmm15`); `cvttsd2si` needs a register
   destination (`%r11`); `cvtsi2sd` needs a non-immediate source and a register destination; no memory→memory `movsd`.
8. **Emitter.** Linux and macOS constant sections and local labels, as shown above.
9. **Test these yourself:** mixed `int`/`double` argument lists with more than eight doubles; `(unsigned long) 1e19`;
   `(double) 18446744073709551615ul`; `-0.0`; `if (0.0/0.0)`. Then run `--chapter 13`, with and without the NaN flag.

## Common pitfalls
- Numbering integer and SSE argument registers with one shared counter.
- `comisd` operand order: AT&T `comisd %xmm1, %xmm0` compares `%xmm0` *with* `%xmm1`.
- Emitting doubles as decimal text, so values round-trip through a string. `.quad` with the bits is exact.
- Truthiness tests after `comisd` that ignore the parity flag, so `if (nan)` is skipped.
- Using `.align` on macOS, or giving `double` stack slots 4-byte alignment.
