# Lesson 12.3 — `unsigned`
**Part:** 3 — Build the Compiler · **Unit:** 12 — A Real Type System · **Type:** Builds `unsigned` · **Est. time:** 8–12 h · **Tests:** ch. 12
**Prerequisites:** lessons 12.1–12.2; 6.1 (two's complement, zero extension); 6.2 (flags); 9.6 (comparisons)

## Overview
C has unsigned integer types, which read the same bits as non-negative numbers only. This lesson adds `unsigned int` and
`unsigned long`. You will find that most instructions do not care about signedness at all, and learn exactly which four
kinds of operation do. That knowledge is the heart of the lesson: once you have it, the code changes are small and precise.

## The lesson

### What `unsigned` is, seen from Python
Python has no unsigned integers: `-1` is just `-1`. But you have met the idea whenever you masked a number:

```python
>>> -1 & 0xFFFFFFFF        # the 32 bits of -1, read as a non-negative number
4294967295
>>> (4294967295 + 1) & 0xFFFFFFFF   # unsigned arithmetic wraps around
0
```

A C `unsigned int` is 32 bits read this way: its range is 0 … 2³²−1 (0 … 4,294,967,295). An `unsigned long` is 64 bits,
0 … 2⁶⁴−1. You write them as `unsigned int` (or just `unsigned`) and `unsigned long` (or `long unsigned`, `unsigned long int`).
Constants take a `u`/`U` suffix: `10u` is an `unsigned int`, `10ul` (or `10LU`, in any order and case) an `unsigned long`.
There is also a `signed` keyword: `signed int` is just `int`, and `signed long` is `long`.

Unlike signed overflow, unsigned arithmetic is fully defined: it **wraps modulo 2ⁿ**, exactly like the masked Python above.
Programmers use unsigned types for sizes, bit patterns and anything that cannot be negative.

### Same bits, different meaning
The 32-bit pattern `0xFFFFFFFF` is `-1` as an `int` and `4294967295` as an `unsigned int`. A key fact from 6.1: two's
complement was designed so that **addition, subtraction and the low half of multiplication produce identical bits** for
both readings. Check it: `0xFFFFFFFF + 1` wraps to `0` in 32 bits, which is right for both `-1 + 1` and
`4294967295 + 1` (mod 2³²). So `addl`, `subl`, `imull` and `movl` work unchanged, and so does truncation. Only four kinds of
operation differ:
1. **comparison** (`<`, `<=`, `>`, `>=`; equality does not care),
2. **division and remainder**,
3. **widening** to a larger type,
4. **conversion to and from floating point** (lesson 12.4).

### 1. Comparisons read different flags
Recall from 6.2 and 9.6 that `cmp` subtracts and sets flags, and `setCC` reads them. Signed conditions (`l`, `le`, `g`,
`ge`) read the sign and overflow flags. Unsigned conditions read the **carry flag** (CF, set when an unsigned subtraction
borrows) and the zero flag: `b` ("below", <), `be` (≤), `a` ("above", >), `ae` (≥). With AT&T order, `cmpl %ebx, %eax`
computes `eax - ebx`, so `setb` afterwards means "eax < ebx, as unsigned numbers".

```c
int lt(unsigned int a, unsigned int b) { return a < b; }
```

```asm
    movl    -8(%rbp), %r10d       # b       (cmp can't have two memory operands)
    cmpl    %r10d, -4(%rbp)       # computes a - b
    movl    $0, -12(%rbp)
    setb    -12(%rbp)             # 1 if a < b, unsigned
```

If `a` = `0xFFFFFFFF` and `b` = `1`, signed `setl` would say true (−1 < 1) while `setb` says false (4294967295 < 1 is false).

### 2. Division uses `div`, with a zeroed high half
`idiv` is signed. Its unsigned twin is `div`, which divides `%edx:%eax` (or `%rdx:%rax`) the same way, but expects the high
half to be **zero**, not a copy of the sign bit:

```asm
    movl    -4(%rbp), %eax
    movl    $0, %edx              # zero-extend the dividend: no cdq here
    divl    -8(%rbp)              # quotient → %eax, remainder → %edx
```

### 3. Widening uses zero extension
Widening an unsigned value fills the new high bits with **zeros** (6.1), because the value is never negative. x86-64 makes
this cheap: **any write to a 32-bit register zeroes the upper 32 bits of the full 64-bit register**. So `movl src, %r11d`
followed by `movq %r11, dst` is a complete 32→64-bit zero extension. (There is no `movzlq` instruction; this is why.)
Model it as a TACKY `ZeroExtend(src, dst)` and an assembly `MovZeroExtend`, which the fix-up pass lowers to those moves.

### Which conversion instruction?
The **source** type decides how to widen: a signed source is sign-extended and an unsigned source is zero-extended,
whatever the target. Same-size conversions (`int` ↔ `unsigned int`, `long` ↔ `unsigned long`) keep the bits: plain `Copy`.
Narrowing is always `Truncate`. Examples: `(unsigned long) -1` sign-extends (source is signed) to `0xFFFF…FFFF`, which is
18446744073709551615; `(long) 4294967295u` zero-extends to 4294967295.

### The common type, now with signedness
Extend 12.1's rule: if the types are equal, use that type; if they have the **same size, the unsigned one wins**;
otherwise the **larger one wins**. This produces some famous surprises:
- `-1 < 0u` → `-1` becomes `unsigned int` 4294967295, so the result is `0` (false!).
- `-1L < 0u` → `0u` becomes `long` (larger), so the result is `1`.
- `-1 < 0ul` → `-1` becomes `unsigned long`, so the result is `0`.

### Integer promotions (preparing for `char`)
Before arithmetic, C converts any type *narrower* than `int` to `int`. You have no such types yet, but `char` arrives in
12.7. Find the single place in your checker where operands are converted to a common type: that is where promotion goes.

### Constant typing
`u` makes a constant unsigned. A `u` constant that does not fit in 32 bits becomes `unsigned long`. An unsuffixed decimal
constant is `int` or else `long` and never becomes unsigned. `18446744073709551615ul` is valid even though it does not fit
in an `i64`, so store constants in a way that can hold it.

### Rust notes
Rust's `as` between signed and unsigned keeps the bits, just like C: `-1_i32 as u32` is `4294967295`, and `-1_i32 as u64`
sign-extends first. For compile-time folding of static initialisers use `wrapping_*` methods or `as`, because plain `+`
panics on overflow in debug builds. Write a tiny `#[test]` for every conversion you rely on.

## Build
1. **Lexer.** Add `unsigned` and `signed`. Accept suffixes `u`, `U`, `l`, `L` in either order (`10ul`, `10LU`); reject
   `10uu`, `10lul` and similar.
2. **Parser.** Specifier lists with signedness: `unsigned`, `unsigned int`, `long unsigned`, `signed long int`. Reject
   `signed unsigned` and repeated `signed`/`unsigned`.
3. **Types.** Add `UInt` and `ULong`. Constants and static initial values gain unsigned forms.
4. **Type checker.** The new common-type rule; constant typing; compile-time conversion of static initialisers between all
   four integer types (wrap, truncate or extend exactly as C does).
5. **TACKY.** Add `ZeroExtend`. Casts choose `SignExtend`, `ZeroExtend`, `Truncate` or `Copy` from source and target types.
6. **Assembly.** Add `Div`, unsigned condition codes `A`, `AE`, `B`, `BE`, and `MovZeroExtend`. Choose condition codes
   from the comparison's **operand** type, and `Div` vs `Idiv` from the division's operand type.
7. **Fix-ups.** `div` cannot take an immediate operand (same as `idiv`); lower `MovZeroExtend` to a `movl` (plus a `movq`
   when the destination is memory).
8. **Test these yourself:** `4294967295u + 1u == 0`; `(unsigned long) -1`; dividing large unsigned values whose top bit is
   set; `unsigned` parameters passed on the stack; `static unsigned long x = 18446744073709551615ul;`.
9. **Unit-test** your compile-time integer conversions for all 16 source/target pairs, then run `--chapter 12`.

## Common pitfalls
- Choosing sign vs. zero extension from the *target* type instead of the *source* type.
- Choosing condition codes from the comparison's *result* type (always `int`) instead of its *operand* type.
- Emitting `cdq` before `div`: correct for small values, wrong when the top bit is set.
- Range-checking an unsigned constant as if it were signed, so `18446744073709551615ul` is rejected.
- Looking for a 32→64-bit `movz` instruction. There is none: a `movl` into a register *is* the zero extension.
