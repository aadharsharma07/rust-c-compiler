# Lesson 12.8 — Memory
**Part:** 3 — Build the Compiler · **Unit:** 12 — A Real Type System · **Type:** Builds `void`, `sizeof`, `malloc` · **Est. time:** 5–8 h · **Tests:** ch. 17
**Prerequisites:** lessons 12.1–12.7; 2.1 (stack and heap); 6.4 and 11.3 (calls)

## Overview
This lesson gives your compiled programs access to the heap. You add `void` (the "no value" type and the generic pointer
`void *`), `sizeof` (the size of a type, computed by the compiler), and enough of both to call `malloc`, `calloc` and
`free` from the C library. Along the way you meet *incomplete* types, which structs will need in 12.9.

## The lesson

### Heap memory, seen from Python
In Python you never ask for memory. `[0] * 1000` allocates a list on the heap, and the reference-counting garbage
collector frees it when the last reference disappears. Rust (lesson 2.1) also frees automatically, when the owner goes
out of scope. C does neither. You ask the C library for a block of bytes and must give it back yourself:

```c
void *malloc(unsigned long size);   /* returns the address of `size` fresh, uninitialised bytes */
void *calloc(unsigned long n, unsigned long size);  /* n*size bytes, all zero */
void free(void *ptr);               /* gives the block back; ptr must not be used afterwards */
```

Our compiler has no preprocessor, so programs cannot `#include <stdlib.h>`; the tests declare these functions themselves,
as above. Forgetting `free` leaks memory; using a block after `free` is undefined behaviour. None of this is the
compiler's business: to `rcc`, `malloc` is just an ordinary function call. What the compiler needs are the *types* that
make these declarations legal: `void`, `void *` and `unsigned long` sizes.

### `void`: the type with no values
`void` means "no value". It plays three roles:
- **Return type:** `void f(void)` returns nothing, like a Python function without a `return` (which returns `None`, but in
  C there is no value at all). In a `void` function, `return;` has no expression and `return expr;` is an error, even if
  `expr` is itself `void`. In a non-`void` function, `return;` is an error.
- **Expression type:** a call to a `void` function, or a cast to void like `(void) e`, has type `void`. Such an expression
  may only appear as an expression statement, the operand of a cast to `void`, both branches of `?:`, or the first or third
  clause of a `for` header. Using it where a value is needed (`int x = f();`, `if (f())`, `f() + 1`, `!f()`) is an error.
- **Parameter list:** `(void)` means "no parameters", as you have done since Unit 8. A parameter of type `void` is an error.

### Complete and incomplete types
A type is **complete** when the compiler knows its size. `void` has no size, so it is **incomplete**, and nothing can make
it complete. Therefore you cannot declare a `void` variable, make an array of `void`, dereference a `void *`, or do
pointer arithmetic on one (GCC allows `void *` arithmetic as an extension; standard C does not, and neither should you).
In 12.9, `struct s;` adds incomplete types that *can* be completed later.

### `void *`: the generic pointer
`malloc` cannot know what you will store in the block, so it returns `void *`, "a pointer to something". A `void *`
converts implicitly **to and from** any other object pointer type, in assignments, arguments, returns and initialisers.
So `int *p = malloc(8);` needs no cast, whereas `int *p = (long *) q;` is still an error. For `==`, `!=` and `?:`, if one
side is `void *` and the other another object pointer, the common type is `void *`.

### `sizeof`: sizes computed at compile time
`sizeof (type)` and `sizeof expr` give the size in bytes, as an `unsigned long` constant (`size_t` on x86-64 Linux and
macOS). Compare Python's `ctypes.sizeof(ctypes.c_int)`, which is 4. (Python's `sys.getsizeof` is different: it includes
object overhead.) The operand is type-checked but **never evaluated**, and an array operand does **not** decay:

```c
int a[10]; int x = 1;
sizeof a;         /* 40, not 8: no decay */
sizeof (x = 5);   /* 4, and x is still 1: not evaluated */
sizeof x + 1;     /* (sizeof x) + 1 == 5: sizeof is a unary operator */
```

Parsing: after `sizeof (`, look at the next token. A type specifier means a type name; anything else means a parenthesised
expression. So `sizeof (int) * 2` is `(sizeof(int)) * 2`, and `sizeof (x) * 2` parses the same way. `sizeof` on `void`,
a function, or any incomplete type is an error. Sizes of arrays multiply through: `sizeof (char[3][5])` is 15.

### Worked example

```c
void *malloc(unsigned long size);
void free(void *ptr);

int main(void) {
    int *a = malloc(4 * sizeof(int));
    a[3] = 42;
    int r = a[3];
    free(a);
    return r;
}
```

TACKY for the first line. The checker converted `4` to `unsigned long` (the common type with `sizeof`'s result) and the
returned `void *` to `int *`:

```
tmp.0 = SignExtend(4)          # int → unsigned long: signed source, so sign-extend (12.3)
tmp.1 = tmp.0 * 4UL            # sizeof(int) became the constant 4UL
tmp.2 = malloc(tmp.1)
a = tmp.2                      # void * → int *: same bits, a plain copy
```

The call is ordinary System V (6.4): the size goes in `%rdi`, the result comes back in `%rax`. On Linux it is
`call malloc@PLT`, on macOS `call _malloc`. The block lives on the heap, outside your stack frame:

```
 stack frame of main                  heap
┌──────────────┐                     ┌────┬────┬────┬────┐
│ a: 0x5000 ───┼────────────────────▶│    │    │    │ 42 │  16 bytes from malloc
│ r: 42        │                     └────┴────┴────┴────┘
└──────────────┘                     0x5000         0x500c
```

`free(a)` is a call whose return type is `void`, so the TACKY call has **no destination** and codegen must not read
`%rax` afterwards. Make the call's destination optional.

### Rust notes
Predicates such as `is_complete`, `is_scalar`, `is_arithmetic` belong as methods in an `impl` block on your `Type`; write
them once, unit-test them, and use them everywhere. An optional return expression and an optional call destination are
both `Option`s: prefer `if let` and `map` to `unwrap`. Computing the size of nested arrays is a natural recursive method.

## Build
1. **Lexer and parser.** The `void` and `sizeof` keywords; `void` as a type specifier (alone only); `sizeof` as a unary
   operator with two forms; `return` with an optional expression; `(void)` parameter lists still mean "none".
2. **Types.** Add `Void`, plus the predicates: complete, scalar, arithmetic, pointer to a complete type.
3. **Type checker.** All the `void` rules above; `void *` conversions and common pointer type. Reject dereferencing or
   subscripting `void *`, arithmetic on `void *`, `sizeof` on incomplete or function types, arrays of incomplete element
   type, and `void` variables. Controlling expressions of `if`, loops, `?:`, `!`, `&&`, `||` must be scalar. `sizeof`
   does not decay its operand.
4. **TACKY.** `sizeof` lowers to an `unsigned long` constant; `return;` lowers to a `Return` with no value; a call's
   destination is optional; a cast to `void` evaluates its operand and discards the result.
5. **Codegen.** A `void` function's return does not touch `%rax`; a call without a destination skips the result copy.
6. **Test these yourself:** a `void` function that falls off the end; `?:` with two `void` branches as a statement; comparing
   a `void *` with an `int *`; `calloc` returning zeroed memory; storing `double`s in `malloc`ed memory through a `double *`.
7. **Write a small program** that builds a linked list or a growable array with `malloc`, frees it, and is compiled by `rcc`.
8. **Run** `./test_compiler ./target/debug/rcc --chapter 17`.

## Common pitfalls
- Evaluating the operand of `sizeof`, so `sizeof (x = 5)` changes `x` or `sizeof f()` calls `f`.
- Decaying an array operand of `sizeof`, so `sizeof a` gives 8.
- Accepting `void *` arithmetic because it "works" with a scale of 1.
- Typing `sizeof` as `int`; it is `unsigned long`, which changes the conversions around it.
- Dropping a `void` call that is used as an expression statement: it still has to run.
