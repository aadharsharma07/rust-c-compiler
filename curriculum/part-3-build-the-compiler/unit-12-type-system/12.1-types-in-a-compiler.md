# Lesson 12.1 — Types in a compiler
**Part:** 3 — Build the Compiler · **Unit:** 12 — A Real Type System · **Type:** Builds `Type` + typed AST · **Est. time:** 4–6 h · **Tests:** ch. 11 (front end only: `--stage validate`)
**Prerequisites:** lessons 11.1–11.4 (a compiler passing chapters 1–10); 5.4 (semantic analysis); 6.1 (numbers in binary)

## Overview
Your compiler has assumed that every value is a 32-bit `int`. In this lesson you give it a real notion of *type*: a
recursive `Type`, an AST in which every expression is annotated with its type, and a type checker that makes every
implicit conversion explicit. You do this for C's second integer type, `long`, but only in the front end. Lesson 12.2
then teaches the back end to generate 64-bit code. Every later lesson in this unit adds to the machinery you build here.

## The lesson

### What `int` and `long` are, seen from Python
In Python an integer has no size limit. `2**100` just works, because a Python `int` is an object that grows as many
digits as it needs. C does not work this way. A C integer type is a **fixed number of bits**, chosen so that the value fits
in a machine register and arithmetic is a single instruction.

- `int` is 32 bits on every platform this course targets. Recall from 6.1 that 32-bit two's complement holds
  −2³¹ … 2³¹−1, that is −2,147,483,648 … 2,147,483,647.
- `long` is 64 bits on x86-64 Linux and macOS (−2⁶³ … 2⁶³−1). (On 64-bit Windows `long` is still 32 bits. We follow
  System V, so for us `long` is 64.) You can also write it `long int`; the two mean the same thing.

```c
int  small = 2147483647;      /* the largest int */
long big   = 4294967296L;     /* 2**32: too big for int, fine for long; the L suffix asks for a long constant */
long x     = small;           /* int value widened to long: still 2147483647 */
int  y     = big;             /* long narrowed to int: keeps the low 32 bits, giving 0 */
```

The last line shows the price of fixed sizes. Python would never silently lose bits; C does, by design. When a signed
`int` computation goes out of range (`2147483647 + 1`), C says the behaviour is **undefined**: the language makes no
promise at all, and a compiler may assume it never happens. In practice our compiler emits whatever the hardware does
(wrap around), but correct C programs must never rely on it. The tests never depend on undefined behaviour.

### What a type means to a compiler
To a programmer a type is a kind of value. To a compiler it is a bundle of facts that decide what code to emit:
- **Size**: how many bytes a value occupies (4 for `int`, 8 for `long`). This picks `movl` vs `movq`.
- **Alignment**: which addresses a value may start at (lesson 12.2 needs this for stack slots).
- **Legal operations**: which operators accept it (later, `~` is illegal on a `double`, `*` on a pointer).
- **Interpretation of bits**: signed or unsigned (12.3), integer or floating point (12.4).

So `a + b` is `addl` when both are `int` and `addq` when both are `long`. The type checker's job is to work out the type
of every expression *before* code generation, so that the back end never has to guess.

### The `Type` representation
Your compiler needs data that describes types. Right now you need three kinds: `Int`, `Long`, and a function type that
holds a list of parameter types and a return type. Later lessons add `UInt`, `ULong`, `Double`, `Pointer(T)`,
`Array(T, n)`, three `char` types, `Void` and `Structure(tag)`. Because `Pointer(T)` will contain another type, `Type` is
a recursive enum, exactly like the expression trees you built in Part 1 (lesson 4.4). Design it to grow: you will add a
variant in nearly every lesson.

### Python does implicit conversions too, just later
In Python, `1 + 2.5` gives `3.5`. Behind the scenes, `int.__add__` cannot handle a float, so Python falls back to
`float.__radd__`, which converts the `1` to `1.0` first. That conversion happens **at run time**, every time the line runs,
by inspecting the objects. C makes the same kind of decision **at compile time**, once, from the declared types. The type
checker decides "this `int` must become a `long` here", and the back end emits one instruction to do it.

### Annotating the AST
After type checking, every expression node carries its type. Two common designs:
1. An optional type field on every expression node, filled in by the checker.
2. A separate "typed" expression tree that the checker produces from the untyped one.

Option 1 is less code. Option 2 lets the Rust compiler prove that later passes never see an untyped node. Both work.
Pick one and explain the choice in your journal.

### Implicit conversions become explicit casts
A **cast** is an explicit conversion written by the programmer: `(long) x` means "convert `x` to `long`". C also converts
values *without* being asked, in many places. The type checker inserts a `Cast` node at each of these places, so after
this pass every conversion is visible in the tree, and TACKY generation only has to lower `Cast` nodes. Example:

```c
long f(int a, long b) {
    return a + b;
}
```

After type checking (types in brackets):

```
Return(
  Binary(Add,
    Cast(Long, Var a [Int]) [Long],
    Var b [Long]
  ) [Long]
)
```

`a` was an `int`, but it is added to a `long`, so the checker wrapped it in a cast. The sum is already a `long`, which
matches the return type, so `return` needs no cast here.

### The usual arithmetic conversions
When a binary operator gets operands of different types, C first converts both to a **common type**. With only `int`
and `long`, the rule is simple: if both types are equal, that is the common type; otherwise it is `long`. Lesson 12.3
extends the rule for signedness and 12.4 for `double`.
- `+ - * / %`: both operands are converted to the common type, and the result has the common type.
- `< <= > >= == !=`: both operands are converted to the common type, but the **result is always `int`** (0 or 1).
- `&& || !`: operands are tested for truth (no common type needed) and the result is `int`.

### Conversion "as if by assignment"
Some places convert to a fixed *target* type, even if that narrows `long` to `int`:
- assignment `x = e` converts `e` to the type of `x` (and the assignment expression has `x`'s type);
- an initialiser `int x = e;` converts `e` to `int`;
- a function argument is converted to the parameter type from the declaration;
- `return e;` converts `e` to the function's return type.

### Parsing type names and casts
A type is now written as a *list of specifier keywords*, in any order: `long`, `long int` and `int long` all mean `long`;
`int` alone means `int`. Storage-class keywords (`static`, `extern`) may be mixed into the list too, as in Unit 11.
A cast looks like `(` *type* `)` *expression*. The parser tells it apart from a parenthesised expression `(x)` by looking
at the token after `(`: a type keyword means a cast. A cast binds like a unary operator, so `(long) a + b` is
`((long) a) + b`.

### Typed constants
Constants have types too:
- `100` is `int`. `100L` or `100l` is `long`.
- An unsuffixed constant too big for `int`, such as `2147483648`, is `long`.
- A constant too big even for `long` is an error.
- `-2147483648` is *not* one constant: it is unary minus applied to `2147483648`, which is a `long`.

### Static initialisers are converted by the compiler
In `static int x = 4294967297L;` (that is 2³² + 1) no code ever runs to convert the value: it is written straight into
the data section. So the *compiler* must do the conversion: keep the low 32 bits, giving `1`. Recall from 11.4 that static
and global variables must have constant initialisers; now those constants need converting to the variable's type.

### Redeclarations must match exactly
In Unit 11 you checked that a function's redeclarations had the same number of parameters. Now types must be identical:
`int f(int a);` followed by `int f(long a) { … }` is an error, and so is `int x;` then `long x;` at file scope.

### Rust notes
Derive `Debug, Clone, PartialEq, Eq` on `Type` from the start. Avoid `_ =>` catch-alls when matching on it: then adding
`UInt` in 12.3 makes `rustc` list every place that must handle it. For constants, know which conversion you mean:

```rust
let fits = i32::try_from(4_294_967_297_i64).is_ok(); // false: checks the range
let wrapped = 4_294_967_297_i64 as i32;              // 1: C-style wrap
```

## Build
1. **Lexer.** Add the `long` keyword and long constants with an `l`/`L` suffix. Reject malformed suffixes such as `1LL`,
   `1lL` and `1L2`, and keep rejecting a constant that runs straight into an identifier character (`1Lx`).
2. **Type.** Define a `Type` with `Int`, `Long` and a function type (parameter types plus return type). Define a constant
   value type that holds either a 32-bit or a 64-bit integer. The AST's constant node now stores one of these.
3. **Parser: specifiers.** Parse a list of specifiers in declarations, parameters and for-loop headers. Turn the type
   keywords into a `Type`. Reject an empty list, duplicates (`int int`, `long long`, `long int long`) and the storage-class
   errors from Unit 11.
4. **Parser: casts.** Add a `Cast(target type, expression)` expression at unary precedence.
5. **Constant typing.** Decide each constant's type (in the parser or the checker): `int` if unsuffixed and it fits in
   32 bits, otherwise `long`; an error if it does not fit in 64 bits.
6. **Symbol table.** Entries now store a full `Type`. Static variables store a typed initial value (int or long).
7. **Type checker.** Annotate every expression with its type. Apply the common-type rule to binary operators, and insert a
   `Cast` wherever an operand's type differs from the type it must have. Choose one rule ("cast only when the types
   differ" is simplest) and apply it everywhere. Handle assignment, initialisers, arguments and `return` "as if by
   assignment". Check that redeclarations have identical types. Convert static initialisers at compile time.
8. **Leave the back end alone.** TACKY generation and codegen can treat everything as `int` for now (or refuse `long`).
   Chapters 1–10 must still pass end to end.
9. **Tests.** Write unit tests for the checker: the typed tree of `1L + 2`, of an `int` passed to a `long` parameter, of
   `return x;` in a `long` function, and of `static int x = 4294967297L;`.
10. **Run** `./test_compiler ./target/debug/rcc --chapter 11 --stage validate`, then the full `--chapter 10`.

## Check your understanding
1. Why is the type of `a < b` always `int`, even when `a` and `b` are `long`? What happens to the operands?
2. List four places, apart from binary operators, where C converts a value implicitly.
3. What do later passes gain because the checker turns conversions into explicit `Cast` nodes?
4. Why must `static long x = 2147483648;` be converted by the compiler, while a local `long x = 2147483648;` need not be?
5. How does your parser tell `(long) x` from `(x)` using one token of lookahead?
6. A Python programmer writes `int big = 3000000000;`. What actually ends up in `big`, and why does C allow it?

## Common pitfalls
- Forgetting that the *operands* of `<` are converted to the common type while the *result* is `int`.
- Giving `2147483648` type `int`, or lexing `-2147483648` as a single constant.
- Comparing function types by parameter count only: `int f(int)` and `int f(long)` conflict.
- Annotating an assignment with the right-hand side's type instead of the left-hand side's.
- Inserting casts inconsistently (sometimes always, sometimes only when types differ), which confuses later passes.
