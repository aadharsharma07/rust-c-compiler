# Lesson 12.2 — `long`
**Part:** 3 — Build the Compiler · **Unit:** 12 — A Real Type System · **Type:** Builds `long` · **Est. time:** 10–14 h · **Tests:** ch. 11
**Prerequisites:** lesson 12.1; 6.1 (two's complement, sign extension); 6.4 (calling convention); 9.3 (fix-ups); 11.3–11.4

## Overview
Lesson 12.1 taught the front end what a `long` is. Now the back end must generate correct 64-bit code for it: widening
and narrowing between `int` and `long`, sizing every instruction, handling 64-bit constants that most instructions cannot
encode, and laying out a stack frame with values of different sizes. You also build a *backend symbol table*, which every
later lesson relies on. When you finish, chapter 11 passes end to end.

## The lesson

### Widening: sign extension
Recall from 6.1 that two's complement stores a negative number with its top bit set, and that widening a signed value
means **copying the sign bit into all the new high bits**. In Python you can watch it with masks:

```python
>>> hex(-1 & 0xFFFFFFFF)            # -1 as a 32-bit pattern
'0xffffffff'
>>> hex(-1 & 0xFFFFFFFFFFFFFFFF)    # -1 as a 64-bit pattern: the extra 32 bits are all 1s
'0xffffffffffffffff'
>>> hex(5 & 0xFFFFFFFFFFFFFFFF)     # a positive value gets 0s on top
'0x5'
```

Converting an `int` to a `long` must preserve the value, so `-1` must become `0xFFFFFFFFFFFFFFFF`, not
`0x00000000FFFFFFFF` (which is 4,294,967,295). x86-64 has an instruction for exactly this: `movslq src, %reg`
("move sign-extended, long to quad"). Its source may be a register or memory, but its **destination must be a register**.

### Narrowing: truncation
Converting a `long` to an `int` keeps the low 32 bits and throws the rest away. x86-64 is little-endian: the low 4 bytes
of an 8-byte value sit at its *lowest* address, and `%eax` names the low 32 bits of `%rax`. So truncation needs no special
instruction: a `movl` that reads the source as 4 bytes already takes the low half.

### Two new TACKY instructions
`Cast` nodes from 12.1 lower to one of three things:
- `SignExtend(src, dst)` for `int` → `long`;
- `Truncate(src, dst)` for `long` → `int`;
- a plain `Copy` when the source and target types are the same.

TACKY generation also creates temporaries, and the back end now needs to know each temporary's size. So whenever you make
a temporary, add it to the symbol table with its type (the type of the expression it holds).

### Every instruction gets a size
In the assembly AST, give `Mov`, `Unary`, `Binary`, `Cmp`, `Idiv` and `Push` an **assembly type**: `Longword` (4 bytes,
suffix `l`) or `Quadword` (8 bytes, suffix `q`). The emitter picks the suffix and register names from it:

| 64-bit | 32-bit | | 64-bit | 32-bit |
|---|---|---|---|---|
| `%rax` | `%eax` | | `%r8` | `%r8d` |
| `%rdx` | `%edx` | | `%r9` | `%r9d` |
| `%rcx` | `%ecx` | | `%r10` | `%r10d` |
| `%rdi` | `%edi` | | `%r11` | `%r11d` |
| `%rsi` | `%esi` | | `%rsp` | (always 64) |

Division widens its dividend differently by size. Recall from 9.5 that `idivl` divides `%edx:%eax`, and `cdq` fills `%edx`
with copies of `%eax`'s sign bit. For `idivq`, the dividend is `%rdx:%rax` and the sign-filling instruction is `cqo`.

### Worked example

```c
long add(int a, long b) { return a + b; }
```

TACKY, then assembly after pseudoregister replacement and fix-ups:

```
add(a, b):
    tmp.0 = SignExtend(a)
    tmp.1 = tmp.0 + b
    Return(tmp.1)
```

```asm
    movl    %edi, -4(%rbp)        # a: 4 bytes, arrives in %edi (6.4)
    movq    %rsi, -16(%rbp)       # b: 8 bytes, must start at a multiple of 8
    movslq  -4(%rbp), %r11        # fix-up: movslq needs a register destination…
    movq    %r11, -24(%rbp)       # …so go through %r11 into tmp.0
    movq    -24(%rbp), %r10
    movq    %r10, -32(%rbp)       # tmp.1 = tmp.0   (mem→mem fix-up via %r10)
    movq    -16(%rbp), %r10
    addq    %r10, -32(%rbp)       # tmp.1 += b
    movq    -32(%rbp), %rax       # a long is returned in all of %rax
```

The stack frame, with `%rbp` at the top:

```
 -4(%rbp)  ┌────────────┐  a      (4 bytes, 4-aligned)
 -8(%rbp)  ├────────────┤  unused (4 bytes of padding)
-16(%rbp)  ├────────────┤  b      (8 bytes, 8-aligned)
-24(%rbp)  ├────────────┤  tmp.0
-32(%rbp)  └────────────┘  tmp.1   → frame size 32 (rounded up to a multiple of 16)
```

The gap at `-8` exists because `b` must sit at an address that is a multiple of 8. Misaligned accesses still work on
x86-64, but they are slower, and the System V ABI requires natural alignment.

### 64-bit immediates
An **immediate** is a constant written inside an instruction (`$5`). Almost every x86-64 instruction can encode at most a
32-bit immediate, which the CPU sign-extends to 64 bits. So `addq $4294967296, %rax` simply cannot be encoded, and the
assembler rejects it. There is one exception: moving a 64-bit immediate into a **register**, `movabsq $4294967296, %r10`.
(GNU and Apple `as` also accept `movq $big, %r10` and pick the `movabs` encoding for you.)

So your fix-up pass gets a new rule: for any quadword instruction whose immediate is outside the `i32` range (`add`,
`sub`, `imul`, `cmp`, `push`, and `mov` to memory), first move the immediate into `%r10`, then use `%r10`. A related case
is `Truncate` of a big constant: `movl $4294967299, …` makes the assembler warn, so emit the low 32 bits (`$3`) instead.

### The backend symbol table
Pseudoregister replacement now needs each variable's size and alignment to hand out stack slots, and the emitter still
needs to know whether a function is defined in this file (for `@PLT` on Linux). Build a **backend symbol table** once,
after TACKY generation, that maps each name to either:
- an object entry: its assembly type (`Longword` or `Quadword`) and whether it is static; or
- a function entry: whether it is defined in this file.

Later passes only look things up in it. Keeping the front-end table (C types) and the backend table (assembly types)
separate means codegen never needs to understand C types.

### Static data
A `static long` goes in `.data` with `.balign 8` and `.quad 5`, or in `.bss` with `.zero 8` if it is zero. A `static int`
keeps `.balign 4` and `.long 5`. Use `.balign n` (align to `n` bytes) rather than `.align n`: on macOS `.align n` means
2ⁿ bytes, so `.align 8` would ask for 256-byte alignment.

### Arguments on the stack
Recall from 6.4 and 11.3 that arguments after the sixth are pushed, and `pushq` always pushes 8 bytes. Pushing a `long`
from memory is fine. Pushing an `int` *from memory* would read 4 bytes past the variable, possibly from an unmapped page.
So for a longword memory operand, move it into `%eax` first and `pushq %rax`. The upper half is garbage, but the callee
only reads the low 4 bytes.

### Rust notes
Adding an assembly type to `Mov` breaks every `match` that destructures it: read the errors as a to-do list. An assembly
type with no data can derive `Copy`, so you can pass it around by value. Store constants as `i64` once they reach the back
end, and test immediates with `i32::try_from`.

## Build
1. **TACKY.** Add `SignExtend` and `Truncate`. Constants carry int or long values. Lower each `Cast` by comparing source
   and target types. Give every temporary a symbol-table entry with its type. Static variables carry their type and a
   typed initial value.
2. **Assembly AST.** Add an assembly type to `Mov`, `Unary`, `Binary`, `Cmp`, `Idiv`, `Push`. Add `Movsx` (emitted as
   `movslq`), and `Cdq` with a type (emitted `cdq` or `cqo`). Static variables carry an alignment.
3. **Codegen.** Choose each instruction's type from its operands' types. Function parameters and return values use the
   right size: a `long` comes back in `%rax`, read with `movq`.
4. **Backend symbol table.** Build it from the front-end table after TACKY generation.
5. **Pseudoregister replacement.** Allocate 4- or 8-byte slots with the right alignment; round the frame up to 16.
6. **Fix-ups.** One clearly named rule per constraint: `movslq` with a memory destination or an immediate source;
   out-of-range quadword immediates via `%r10`; `imulq` with a memory destination; `push` of a longword memory operand;
   truncated `movl` immediates; plus every existing rule applied at both sizes.
7. **Emitter.** Suffixes, 32/64-bit register names, `.quad`, `.balign`, `cqo`.
8. **Test these yourself:** `long` parameters past the sixth; a `long` result used as an `int`; `static long x = 2147483648;`;
   `long` comparisons with `cmpq`; `-2147483648L`; `9223372036854775807L`; division of negative `long`s.
9. **Run** `./test_compiler ./target/debug/rcc --chapter 11`.

## Common pitfalls
- Emitting `movslq` with a stack destination, or with an immediate source.
- Aligning every slot to 4 bytes, so `long`s straddle 8-byte boundaries.
- Reading a `long` return value with `movl`, or passing a `long` argument in `%edi` instead of `%rdi`.
- Leaving `cdq` before `idivq`: the result is wrong only for negative or large values, so it is easy to miss.
- Not recording temporaries' types, then guessing their size in codegen.
- Using `.align` instead of `.balign`, which breaks on macOS.
