# Lesson 12.6 — Arrays
**Part:** 3 — Build the Compiler · **Unit:** 12 — A Real Type System · **Type:** Builds arrays · **Est. time:** 10–14 h · **Tests:** ch. 15
**Prerequisites:** lessons 12.1–12.5; 2.4 (slices in Rust)

## Overview
A C array is a fixed-size block of identical values laid out back to back in memory, very different from a Python list.
This lesson adds array types, the rule that makes arrays turn into pointers almost everywhere ("decay"), pointer
arithmetic and subscripts, and compound initialisers like `{1, 2, 3}`. It is also your first *aggregate* type: a value
too big for a register, which the back end must handle as a block of bytes.

## The lesson

### What a C array is, seen from Python
A Python list is an object holding a length and a growable array of *references* to other objects, which can be of any
type and live anywhere on the heap. A C array is much simpler:
- a **fixed** number of elements, decided at compile time (`int a[3];` holds exactly three `int`s, forever);
- all of **one type**, stored **contiguously**, with no references and no header;
- **no stored length** and **no bounds checks**: `a[5]` on a 3-element array silently reads whatever is next in memory
  (undefined behaviour), where Python would raise `IndexError`.

```c
int a[3] = {10, 20, 30};
a[1] = 25;              /* subscript: element 1 */
int m[2][3];            /* a 2-D array: 2 rows, each an array of 3 ints */
```

Memory for `a`, starting at a made-up address 0x1000 (each `int` is 4 bytes):

```
 0x1000   0x1004   0x1008
┌────────┬────────┬────────┐
│   10   │   25   │   30   │      12 bytes, nothing else
└────────┴────────┴────────┘
  a[0]     a[1]     a[2]
```

The closest Python relatives are `array.array('i', …)` and `bytes`, which also store raw values contiguously. A Rust
array `[i32; 3]` (Part 1) has exactly this layout too. `m[2][3]` is "an array of 2 arrays of 3 ints": 24 bytes, with row 0
first, then row 1 (row-major order). `m[1][2]` is at byte offset 1×12 + 2×4 = 20.

### Array types and declarators
The type is `Array(element type, n)`, with size n × size(element). The declarator suffix `[n]` binds like a function's
`(params)`: tighter than a prefix `*`. So `int *a[3]` is an array of 3 pointers to `int`, while `int (*a)[3]` is a
pointer to an array of 3 `int`s. The size must be a positive integer constant. In `int m[2][3]`, the innermost type is
`int[3]` and `m` is an array of 2 of those: get this order wrong and your layout is transposed.

### Decay: arrays become pointers
In C, an expression of array type is almost never used as an array. It is automatically converted to a **pointer to its
first element**. If `a` is `int[3]`, then in `int *p = a;` or `f(a)` the value used is `&a[0]`, of type `int *`. This is
**array-to-pointer decay**. It does not happen in a few places: the operand of `&` (so `&a` is a pointer to the *whole*
array, type `int (*)[3]`), the operand of `sizeof` (12.8), and a string literal initialising a `char` array (12.7).

Do decay in the type checker: wrap every array-typed expression in an implicit address-of node, except in those places.
A consequence: you cannot assign to an array (`a = b` is an error), and a function parameter declared as `int a[3]` is
silently *adjusted* to `int *a`. A function cannot return an array.

### Subscripts are pointer arithmetic
`a[i]` is defined as `*(a + i)`. After decay, one operand is a pointer and the other an integer, so even `2[a]` is legal C.
Pointer arithmetic is **scaled**: `p + i` advances by i × sizeof(element) *bytes*, so it lands on element `i`. The rules:
- `ptr + int`, `int + ptr`, `ptr - int` → pointer type. Convert the integer to `long` first (addresses are 64-bit).
- `ptr - ptr` (same type) → `long`: the byte difference divided by the element size, i.e. the number of elements apart.
- `<`, `<=`, `>`, `>=` on two pointers of the same type → unsigned comparison.

### Worked example

```c
int main(void) {
    int a[3] = {1, 2, 3};
    long i = 2;
    return a[i];
}
```

```
CopyToOffset(1, a, 0)
CopyToOffset(2, a, 4)
CopyToOffset(3, a, 8)
i = 2L
tmp.0 = GetAddress(a)           # decay: the address of a[0]
tmp.1 = AddPtr(tmp.0, i, 4)     # pointer, index, scale (element size)
tmp.2 = Load(tmp.1)
Return(tmp.2)
```

```asm
    movl    $1, -12(%rbp)           # a occupies -12..-1
    movl    $2, -8(%rbp)
    movl    $3, -4(%rbp)
    movq    $2, -24(%rbp)           # i (8-aligned, so it skips to -24)
    leaq    -12(%rbp), %r11
    movq    %r11, -32(%rbp)         # tmp.0
    movq    -32(%rbp), %rax
    movq    -24(%rbp), %rdx
    leaq    (%rax,%rdx,4), %r11     # address = rax + rdx*4
    movq    %r11, -40(%rbp)         # tmp.1
    movq    -40(%rbp), %rax
    movl    (%rax), %r10d           # Load
    movl    %r10d, -44(%rbp)        # tmp.2
    movl    -44(%rbp), %eax
```

`(%rax,%rdx,4)` is an **indexed** memory operand: base + index × scale. The scale may only be 1, 2, 4 or 8. For other
element sizes (a 12-byte `int[3]` row) multiply the index first with `imulq $12, %rdx`, then use scale 1. A constant index
can fold into a displacement: `leaq 8(%rax), %r11`.

### Aggregates in the back end
An array is not a scalar, so it cannot live in a pseudoregister with a fixed width. Give the assembly AST a byte-array
assembly type (a size and an alignment) and a `PseudoMem(name, offset)` operand meaning "byte `offset` inside aggregate
`name`"; pseudoregister replacement turns it into a `Memory(BP, …)` slot. TACKY gets `CopyToOffset(src, dst, offset)`,
which writes a scalar into an aggregate at a byte offset. System V rule: an array variable of **16 bytes or more** is
16-byte aligned, on the stack and in static storage. Smaller arrays use their element's alignment.

### Initialisers
A compound initialiser lists elements in order, and nested braces initialise sub-arrays: `int m[2][3] = {{1, 2, 3},
{4, 5, 6}};`. Missing trailing elements are zero; too many elements is an error. A trailing comma is allowed. In a
function, lower each scalar to a `CopyToOffset` (including the zeros). For `static int a[4] = {1, 2};` emit `.long 1`,
`.long 2`, `.zero 8`; an all-zero static array can go in `.bss`.

### Rust notes
A nested initialiser is a tree of single values and lists; walking it alongside the target type is recursion over two
matched enums. `zip`, `enumerate` and `chain` express "each element with its offset" without index arithmetic. Use
`checked_mul` when computing sizes of huge arrays.

## Build
1. **Parser.** `[constant]` declarator suffixes (also in abstract declarators); postfix `[expr]` subscripts at the highest
   precedence; compound initialisers `{…}` with an optional trailing comma.
2. **Types.** `Array(element, size)`. Adjust array parameters to pointers. Reject arrays as return types and casts *to* arrays.
3. **Type checker.** Decay; subscript, pointer `+`/`-` and relational rules; reject a non-constant, zero or negative size,
   a compound initialiser for a scalar, a scalar initialiser for an array, too many elements, and assignment to an array.
   Static initialisers become a list of values plus zero-fill entries.
4. **TACKY.** `AddPtr(ptr, index, scale, dst)` and `CopyToOffset(src, dst, offset)`. `ptr - ptr` becomes a `Subtract` then a
   `Divide` by the element size.
5. **Assembly.** `Indexed` operand, `PseudoMem`, the byte-array assembly type, `lea` for `AddPtr`, `.zero n` in static data.
   The backend symbol table records size and alignment of aggregates.
6. **Fix-ups.** Never use `%r10`/`%r11` as the base or index of an `Indexed` operand that a fix-up might clobber.
7. **Parser unit tests** for at least five tricky declarators (`int *a[3]`, `int (*a)[3]`, `int a[2][3]`, `int *(*x)[4]`, a cast).
8. **Test these yourself:** `a[i][j]`; `int (*row)[3] = m;`; `p[-1]`; arrays as arguments; static and `extern` arrays; arrays
   of `double` and of pointers. Then run `--chapter 15`.

## Common pitfalls
- Getting the declarator order wrong, so `int a[2][3]` becomes 3 arrays of 2.
- Decaying the operand of `&`, which makes `&a` a pointer to `int` instead of a pointer to an array.
- Scaling by the size of the *pointer* (8) instead of the size of the *element*.
- Treating `CopyToOffset` offsets as element indices rather than bytes.
- Forgetting to divide `ptr - ptr` by the element size, or typing it as a pointer.
