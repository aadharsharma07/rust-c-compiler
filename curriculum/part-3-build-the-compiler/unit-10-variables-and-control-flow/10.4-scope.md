# Lesson 10.4 — Scope
**Part:** 3 — Build the Compiler · **Unit:** 10 — Variables, Scope and Control Flow · **Type:** Builds compound statements · **Est. time:** 4–6 h · **Tests:** ch. 7
**Prerequisites:** lesson 10.3; 5.4 (scopes and symbol tables)

## Overview
Chapter 7 adds **compound statements**: blocks `{ … }` that group several block items into one
statement and open a new **scope**. Variables declared inside a block are invisible outside it, and an
inner block may declare a name that already exists outside, hiding (**shadowing**) the outer one.
All of this is handled in variable resolution; thanks to the renaming you did in 10.2, TACKY and
the back end don't change at all.

## The lesson

### Blocks and scope, compared with Python
In Python, scope belongs to *functions*: a variable assigned inside an `if` or a `for` is still
visible after it. C is stricter. Every pair of braces opens a **block scope**: a name declared in a
block is visible from the end of its declaration to the closing `}` of that block, and nowhere
else.
```c
int main(void) {
    int x = 1;
    {
        int x = 2;      /* a new x: shadows the outer one inside this block */
        x = x + 10;     /* the inner x becomes 12 */
    }
    return x;           /* the outer x again: returns 1 */
}
```
While the inner `x` is in scope, the outer `x` is **hidden** but still exists, holding 1. When the
block ends, the outer one is visible again. Two declarations of the same name in the *same* block
are still an error (10.2's duplicate-declaration check).

Scope (where a name can be *seen*) is separate from **lifetime** (when the storage *exists*). C
says a block's variables live only while the block runs; in our compiler every variable just gets
its own stack slot for the whole function, which is a legal way to implement that.

### Grammar
```
<block>     ::= "{" { <block-item> } "}"
<statement> ::= ... | <block>
<function>  ::= "int" <identifier> "(" "void" ")" <block>
```
The function body is now just a block. And since a block is a statement, it can be the branch of an
`if`: `if (a) { int b = 1; return b; }` is now legal, even though `if (a) int b = 1;` is not.

AST: a `Block` holds a list of block items; a new statement variant `Compound(Block)`; the function
body becomes a `Block`. `Block` contains statements and a statement can contain a `Block`, so the
types are mutually recursive (the `Vec` inside provides the indirection, so no extra `Box` is needed).

### Resolution with scopes: the problem
The 10.2 map answers one question: "what does this name mean right now?" Scopes add a second
question for declarations: "was this name declared in the *current* block?" Only that case is a
duplicate. Shadowing an outer name is fine. So each map entry now records two things:
```
user name  →  (unique name, declared in current block?)
```

### Design 1: copy the map on entry
1. **Entering a block:** make a *copy* of the current map, with every entry's "current block" flag
   set to false. Resolve the block's items using the copy.
2. **Declaration:** error only if the name exists **and** its flag is true. Otherwise insert
   (replacing any outer entry) with a fresh unique name and the flag true.
3. **Leaving the block:** throw the copy away. The outer map was never touched, so it's already correct.

Trace the example above:
```
after `int x = 1;`        outer map:  {x → (x.0, current)}
enter block (copy):       inner map:  {x → (x.0, outer)}
`int x = 2;`              inner map:  {x → (x.1, current)}     not a duplicate: flag was false
`x = x + 10;`             both x's resolve to x.1
leave block               back to outer map: {x → (x.0, current)}
`return x;`               resolves to x.0
```
Resolved AST:
```
Declaration(x.0, Constant 1)
Compound([ Declaration(x.1, Constant 2),
           Expression(Assignment(Var x.1, Binary(Add, Var x.1, Constant 10))) ])
Return(Var x.0)
```
In Python terms: entering a block is `inner = {k: (v, False) for k, (v, _) in outer.items()}`.
In Rust, this is a `clone` (2.2) and then a mutable pass over the values. The pass takes the outer
map by shared reference and owns its copy, which matches who changes what.

### Design 2: a stack of maps
Keep a `Vec` of maps, one per open block. **Entering** pushes an empty map; **leaving** pops it. A
**declaration** checks only the top map for duplicates and inserts there. A **lookup** searches
from the top (innermost) map downwards and takes the first hit. No copying, and the "current
block" flag is implicit (it's whatever is in the top map). The cost: you must pop on *every* exit
from a block, including early returns via `?` when an error occurs. (If an error aborts the whole
pass anyway, a stale stack does no harm, but it's a trap if you ever recover from errors.)

Both designs pass every test. Copy-on-entry is simpler and obviously correct; the stack avoids
copying. For programs the size of our tests, the copying cost is irrelevant. Pick one and be able to
defend it.

### Why TACKY doesn't change
After resolution, the inner and outer `x` are `x.1` and `x.0`: different names, so different TACKY
variables, so different stack slots. A compound statement lowers to its items' instructions, one
after another. There's no "enter scope" instruction, because scope is purely a compile-time idea in
our compiler. This is the guarantee 10.2's renaming bought you.

### A subtle case
```c
int x = 1;
{ int x = x + 1; }
```
The inner `x` comes into scope *before* its initializer (10.2), so the initializer reads the new,
uninitialized inner `x`, not the outer one. That compiles (it's undefined behaviour at run time).
Your design handles it automatically if declarations insert before resolving the initializer.

## Build
1. **AST.** `Block`, `Compound(Block)`, function body as a `Block`.
2. **Parser.** `{` starts a compound statement wherever a statement is allowed; the function body
   uses the same block parser.
3. **Resolution.** Choose a design; implement scoped maps with the duplicate rule above. The
   function body is a block like any other.
4. **TACKY.** Lower `Compound` by lowering its items in order.
5. **Must reject:** duplicate declarations in the same block (including the function body's top
   level), using a variable after its block ended (`{ int a = 1; } return a;`), unbalanced braces,
   an undeclared variable inside a nested block.
6. **Must accept:** shadowing at any depth, empty blocks `{}`, blocks as `if`/`else` branches, the
   same name declared in two sibling blocks, reading an outer variable in a block before the block
   declares its own copy.
7. **Unit tests.** Resolved AST for the example; one test per rejection.
8. **Run the suite.** `./test_compiler ./target/debug/rcc --chapter 7`.

## Common pitfalls
- Mutating the outer map on entry, so a shadowing name stays overwritten after the block ends.
- Copying the map but forgetting to clear the flags, which rejects all shadowing.
- Treating the function body specially and skipping its duplicate check.
- A stack design that searches outermost-first, picking the shadowed variable.
- Mapping inner names back to the *source* name, so two different `x`s share a stack slot.
