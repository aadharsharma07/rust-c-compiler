# Lesson 10.3 — Conditionals
**Part:** 3 — Build the Compiler · **Unit:** 10 — Variables, Scope and Control Flow · **Type:** Builds `if`/`else`, `?:` · **Est. time:** 3–5 h · **Tests:** ch. 6
**Prerequisites:** lesson 10.2; 9.6 (TACKY jumps and labels)

## Overview
Chapter 6 adds C's two ways of choosing: the `if` statement and the conditional expression
`c ? a : b`. You'll meet a classic grammar ambiguity (the "dangling else") and see why your parser
already resolves it correctly, extend the precedence climber with a three-operand operator, and
lower both constructs to the jumps and labels from 9.6. No new TACKY instructions and no back-end
changes: that's the payoff of building short-circuiting properly.

## The lesson

### `if` in C, compared with Python
```c
if (a > 3)
    b = 1;
else
    b = 2;
```
C syntax notes: the condition must be in parentheses, there's no colon, and each branch is a single
**statement** (indentation means nothing to C). There's no `elif`: `else if (…)` is just an `else`
whose statement happens to be another `if`. The condition is any expression; zero means false,
anything else means true, like Python's truthiness for integers.

Braces `{ … }` group several statements into one; they arrive in 10.4. So in chapter 6, every
branch is exactly one statement.

### Grammar
```
<statement> ::= "return" <exp> ";" | <exp> ";" | ";"
              | "if" "(" <exp> ")" <statement> [ "else" <statement> ]
<exp>       ::= <factor> | <exp> <binop> <exp> | <exp> "?" <exp> ":" <exp>
```
The branches are `<statement>`, not `<block-item>`, so `if (a) int b = 1;` is a parse error, as
10.1 promised. (A declaration as the only thing in a branch would be useless anyway: the name would
go out of scope immediately.)

### The dangling else
Look at `if (a) if (b) x = 1; else x = 2;`. Which `if` owns the `else`? The grammar allows both:
```
reading 1 (C's rule)              reading 2
if (a)                            if (a)
    if (b) x = 1;                     if (b) x = 1;
    else   x = 2;                 else x = 2;
```
C resolves it by rule: an `else` belongs to the **nearest** unmatched `if`, reading 1.

A recursive-descent parser does this automatically. Parsing the outer `if`, it parses its
then-branch, which is the inner `if`. The inner `if` parses `x = 1;`, then peeks, sees `else`,
and takes it greedily for itself. By the time control returns to the outer `if`, the `else` is
gone. There's nothing to implement; you only need to be able to explain why it works.

### The conditional operator `?:`
`c ? a : b` evaluates `c`; if it's non-zero, the whole expression is `a`, otherwise `b`. It's
Python's `a if c else b` with the parts in a different order. Like `&&`, it must evaluate **only
one** of its branches: `x ? (y = 1) : (y = 2)` assigns once.

Its precedence is just above assignment (give it 3), and it's **right-associative**:
`a ? b : c ? d : e` means `a ? b : (c ? d : e)`, which reads like an `else if` chain.

In the precedence climber, treat `?` as a binary operator with one twist. When you see `?`:
1. Consume it, then parse the **middle** operand as a complete expression, with minimum precedence
   0, and expect `:`. The middle sits between two delimiters, like the inside of parentheses, so
   anything can go there, even an assignment.
2. Parse the **right** operand with minimum precedence equal to `?:`'s own (3), not 3 + 1. That's
   what makes it right-associative, as with `=` in 10.1.
3. Combine all three into a `Conditional` node.

Consequences worth checking: `a ? b = 1 : 2` is legal (the middle is a full expression);
`a = 1 ? 2 : 3` assigns 2 to `a` (assignment is weaker than `?:`); and `1 ? 2 : 3 = 4` parses as
`1 ? 2 : (3 = 4)`, which resolution then rejects as an invalid lvalue.

### AST additions
```
statement = ... | If(exp condition, statement then, statement? else)
exp       = ... | Conditional(exp condition, exp then, exp else)
```
`statement?` is an `Option` holding a boxed statement. Variable resolution just recurses into the
new nodes; there are no new rules.

### Lowering to TACKY
No new instructions. An `if` with an `else`:
```
<instructions for condition, result c>
JumpIfZero(c, else.N)
<instructions for then-branch>
Jump(end.M)
Label(else.N)
<instructions for else-branch>
Label(end.M)
```
Without an `else`, it's shorter: `JumpIfZero(c, end.M)`, the then-branch, `Label(end.M)`.

A conditional expression has the same shape, but it produces a value. Each branch translates its
expression and `Copy`s the result into **one shared** fresh temporary, which is the value of the
whole expression. Both paths must write the same place, because the code after `end` doesn't know
which path ran.

### Worked example
```c
int main(void) { int a = 5; return a > 3 ? 10 : 20; }
```
TACKY (names after resolution; the exact numbers depend on your counter):
```
a.0 = 5
tmp.1 = a.0 > 3
JumpIfZero(tmp.1, cond_else.2)
tmp.4 = 10
Jump(cond_end.3)
Label(cond_else.2)
tmp.4 = 20
Label(cond_end.3)
return tmp.4
```
And the core of the assembly (macOS label style; Linux uses `.L`):
```
	movl	$5, -4(%rbp)
	cmpl	$3, -4(%rbp)       # a.0 - 3
	movl	$0, -8(%rbp)
	setg	-8(%rbp)           # tmp.1 = a.0 > 3
	cmpl	$0, -8(%rbp)
	je	Lcond_else.2
	movl	$10, -12(%rbp)
	jmp	Lcond_end.3
Lcond_else.2:
	movl	$20, -12(%rbp)
Lcond_end.3:
	movl	-12(%rbp), %eax    # exit status 10
```

## Build
1. **Lexer.** Keywords `if` and `else`; tokens `?` and `:`.
2. **AST.** The `If` statement with an optional else branch; the `Conditional` expression.
3. **Parser.** The `if` statement; `?` in the precedence table at 3 with the middle-operand rule.
4. **Resolution.** Recurse into the new nodes.
5. **TACKY.** The two lowerings, with labels from your shared generator.
6. **Must reject:** `if a return 1;` (no parentheses), `if (a) int b = 2;`, a lone `else`, `a ? b;`,
   `a : b;`, and (semantically) `1 ? 2 : 3 = 4` and undeclared variables inside branches.
7. **Must accept:** nested ternaries, `else if` chains, assignments inside branches and in the middle
   of `?:`, an `if` whose branches both `return`, `if (a) ; else ;`.
8. **Unit tests.** Trees for the dangling-else example and for `a ? b : c ? d : e`; TACKY for the worked example.
9. **Run the suite.** `./test_compiler ./target/debug/rcc --chapter 6`. (The chapter's `--goto` extra
   credit is lesson 10.6.)

## Check your understanding
1. Draw both trees for `if (a) if (b) x = 1; else x = 2;`. Which does your parser build, and which code decides it?
2. Why is the middle operand of `?:` parsed at minimum 0, but the right operand isn't?
3. Why do both branches of `?:` copy into the *same* temporary? What breaks if each uses its own?
4. How does `a = b ? c : d` parse, and why?
5. Write the TACKY skeleton for `if (c) s;` with no `else`.

## Common pitfalls
- Parsing the middle of `?:` at the operator's own precedence, so `a ? b = 1 : 2` fails to parse.
- Reusing fixed label names for every `if`: the assembler reports a symbol defined twice.
- With no `else`, jumping to an `else` label that's never emitted, or forgetting the `end` label.
- Evaluating both branches of `?:` and then choosing: side effects happen twice.
- Accepting a declaration as an `if` branch.
