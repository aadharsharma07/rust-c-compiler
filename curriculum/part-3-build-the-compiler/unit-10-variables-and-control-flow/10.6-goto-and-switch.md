## Overview
Two more C control-flow statements, both tested as extra credit. `goto` jumps to a named label
anywhere in the function; `switch` jumps to one of several `case` labels depending on a value. Both
are easy to lower, because TACKY already has jumps and labels. The interesting parts are semantic:
labels follow a different scoping rule from variables, and `switch` changes what `break` means.

## The lesson

### `goto` and labelled statements
```c
int main(void) {
    int a = 0;
    goto skip;          /* jump forward */
    a = 5;              /* never runs */
skip:
    return a;           /* returns 0 */
}
```
A **labelled statement** is an identifier, a colon, then a statement: `skip: return a;`. `goto skip;`
transfers control there. Python has no equivalent (its `break`/`continue` are restricted forms of
the same idea).

Grammar:
```
<statement> ::= ... | "goto" <identifier> ";" | <identifier> ":" <statement>
```
Telling `skip: …` from an expression statement like `skip = 1;` needs **two** tokens of lookahead:
an identifier followed by `:` is a label. Make sure your parser can peek two tokens ahead.

### Labels follow different rules from variables
- **Function scope.** A label is visible throughout its whole function, *including before* its
  definition: forward `goto`s are normal. Blocks don't limit it.
- **Separate namespace.** Labels and variables never clash: `int a; a: a = 1;` is legal. So labels
  need their own table, not your variable map.
- **A label must label a statement.** In C17, `end: }` and `lbl: int x = 1;` are errors (a
  declaration isn't a statement, 10.1). Use `end: ;` (a null statement) instead.

Because of forward references, you can't check a `goto` when you meet it: the label may come later.
So label resolution collects first, then checks. Walk the function body collecting every label
definition into a set (a second definition of the same name is a **duplicate label** error) and every
`goto` target into a list; then check each target against the set (missing means **undefined label**).

Also **rename** labels uniquely (e.g. by prefixing them, or with your shared counter), so a user's
`loop.0` or `end` can never clash with your generated labels. In Unit 11, two functions may both
have a label `end`, which renaming also handles.

Lowering: `Goto(l)` becomes `Jump(l)`; `Labeled(l, s)` becomes `Label(l)` followed by `s`.

### `switch`: a computed jump
```c
switch (x) {
    case 1:  y = 10;        /* no break: falls through! */
    case 2:  y = y + 1; break;
    default: y = 0;
}
```
`switch` evaluates `x` once and jumps to the `case` whose value matches, or to `default` if none
does, or past the whole statement if there's no `default`. Then it simply keeps running. It does
**not** stop at the next `case`: control **falls through** until a `break`. Above, with `x == 1`,
`y` becomes 10, then 11, then `break` leaves the switch. (Python 3.10's `match` looks similar but
never falls through.)

Grammar:
```
<statement> ::= ... | "switch" "(" <exp> ")" <statement>
              | "case" <exp> ":" <statement> | "default" ":" <statement>
```
A `case` is really just a label with a value. That's why it can appear *anywhere* inside the switch
body, even nested inside an `if` or a block (a famous trick called "Duff's device" relies on this).

Rules to enforce in semantic analysis:
- Each case value must be an integer **constant**. Accepting a plain constant node is enough for
  our C; reject anything else (`case a:`).
- No duplicate case values in one switch, and at most one `default`.
- No `case` or `default` outside a switch.

### `break` and `continue` inside a `switch`
`break` now exits the innermost enclosing loop **or switch**, whichever is nearer. `continue` still
refers to the innermost **loop**, skipping any switches in between:
```c
while (1) { switch (x) { case 1: continue; case 2: break; } x = x + 1; }
/* continue → next iteration of the while; break → leaves only the switch */
```
So the loop-labelling pass from 10.5 now carries **two** pieces of context: the current *break
target* and the current *continue target*. A loop sets both; a switch sets only the break target.
`continue` with no continue target is an error, even inside a switch.

The pass also has to find every `case` and `default` that belongs to each switch, however deeply
nested, and record them on the switch node (each with a unique label), so TACKY generation knows
where to jump. A switch inside a switch collects its own cases; the outer one doesn't see them.

### Lowering a switch
For a switch labelled `sw.4` with cases 1 and 5 and a default:
```
<exp → v>
tmp.5 = v == 1
JumpIfNotZero(tmp.5, case_1_sw.4)
tmp.6 = v == 5
JumpIfNotZero(tmp.6, case_5_sw.4)
Jump(default_sw.4)              # Jump(break_sw.4) if there's no default
<body, where each case/default emits its Label, then its statement>
Label(break_sw.4)
```
A switch with no cases and no default jumps straight to `break_sw.4`: its body never runs.

### Jump tables: what real compilers do
That compare chain costs one comparison per case. When case values are dense (say 0 to 20),
optimising compilers build a **jump table**: an array of code addresses indexed by the value. They
check the value is in range, load the address from the table, and jump to it (`jmp *%rax`) in a
constant number of steps. You don't need one, but compare `clang -O2 -S` output on Godbolt for a
dense switch and a sparse one (cases 1, 1000, 50000) to see the compiler choose.

## Build
1. **goto: parsing.** Two-token lookahead; `Goto` and `Labeled` statement nodes.
2. **goto: label resolution.** A pass (in `--validate`) that renames labels, and rejects duplicate
   labels and undefined targets. Must reject: `goto missing;`, two `foo:` in one function, `lbl: }`,
   `lbl: int x;`. Must accept: forward and backward `goto`, `goto` into or out of a nested block, a
   label with the same name as a variable, `done: ;`.
3. **goto: TACKY** lowering. Run `./test_compiler ./target/debug/rcc --chapter 6 --goto`.
   (Later chapters' tests also exercise `goto` when you pass the flag.)
4. **switch: parsing.** `Switch`, `Case` and `Default` nodes with label fields; `switch`, `case` and
   `default` keywords.
5. **switch: labelling.** Separate break and continue targets; collect each switch's cases; reject
   `case` outside a switch, duplicate cases, two `default`s, non-constant cases, and `continue` in a
   switch that isn't inside a loop.

## Common pitfalls
- Scoping labels by block like variables, so a `goto` to a label in another block fails.
- Using the user's label name directly as an assembly label, clashing with generated labels (or, in Unit 11, with another function's).
- `continue` inside a switch targeting the switch.
- Only scanning the top level of a switch body for cases, missing nested ones.
- Forgetting the jump to the break label when there's no `default`, so control falls into the first case.
