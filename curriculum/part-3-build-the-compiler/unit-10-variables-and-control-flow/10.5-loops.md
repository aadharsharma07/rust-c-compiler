# Lesson 10.5 — Loops
**Part:** 3 — Build the Compiler · **Unit:** 10 — Variables, Scope and Control Flow · **Type:** Builds loops + loop labelling · **Est. time:** 5–7 h · **Tests:** ch. 8
**Prerequisites:** lesson 10.4

## Overview
Chapter 8 adds C's three loops (`while`, `do … while` and `for`) and the `break` and `continue`
statements. Lowering the loops is a direct use of 9.6's jumps. The interesting new problem is that
a `break` has to know *which* loop it leaves, so you'll write a second semantic pass, **loop
labelling**, that attaches every `break` and `continue` to its loop. You'll also give the `for`
header its own scope.

## The lesson

### C's loops, compared with Python
```c
while (n > 0) n = n - 1;                 /* test first, maybe run zero times */

do n = n - 1; while (n > 0);             /* run once, then test: at least one run */

for (int i = 0; i < 3; i = i + 1)        /* init; condition; post */
    s = s + i;
```
`while` is Python's `while`. `do … while` has no Python equivalent: its body always runs at least
once, because the test is at the bottom (note the `;` after the closing parenthesis). C's `for` is
not Python's `for x in …`; it's shorthand for a `while` loop with three parts in the header:
- **init** runs once before the loop (a declaration or an expression, or nothing);
- **condition** is tested before each iteration (missing means "always true", so `for (;;)` loops forever);
- **post** runs after each iteration (usually the step; its value is thrown away).

`break` leaves the innermost enclosing loop; `continue` skips the rest of the current iteration
and goes to the "next iteration" point. Both behave as in Python.

### Grammar
```
<statement> ::= ... | "break" ";" | "continue" ";"
              | "while" "(" <exp> ")" <statement>
              | "do" <statement> "while" "(" <exp> ")" ";"
              | "for" "(" <for-init> [ <exp> ] ";" [ <exp> ] ")" <statement>
<for-init>  ::= <declaration> | [ <exp> ] ";"
```
Look at `<for-init>`: a declaration already ends with its own `;`, so the `for` rule doesn't add one
after the init. The other two header parts are optional expressions. There's no comma operator in
our C, so `for (int i = 0, j = 0; …)` is a parse error.

AST: `While(condition, body, label)`, `DoWhile(body, condition, label)`,
`For(init, condition?, post?, body, label)`, `Break(label)`, `Continue(label)`. The `for` init is its
own two-way type: a declaration, or an optional expression. Every node has a **label** field that
the parser leaves empty; the labelling pass fills it in.

### Why `break` needs a pass
When the parser builds `Break`, it knows nothing about the surrounding loops. You *could* thread a
"current loop" through every parse function, but that mixes semantic work back into the parser
(exactly what 10.2 avoided). Instead, after variable resolution, a small pass walks the tree with
one piece of context: the label of the **innermost enclosing loop**, or none at the top.

- Entering any loop: make a fresh unique label (say `loop.7`), store it on the loop node, and use it
  as the current label while walking the body. (Walking the body of a *nested* loop replaces it with
  that loop's label, and the outer one comes back afterwards, simply because it's a parameter of the
  recursion.)
- `break` / `continue`: copy the current label onto the node. If there is none, report an error:
  **`break` outside a loop**.
- Everything else: recurse. An `if` inside a loop passes the label through unchanged.

Trace on `while (a) { while (b) break; x = 1; }`: the outer loop gets `loop.0` and walks its body
with it; the inner loop gets `loop.1`, so the `break` in its body records `loop.1`. The `break` exits
only the inner loop.

### Lowering to TACKY
Each loop derives its three jump targets from its one label `L`: `start_L`, `continue_L` and
`break_L`. Since `L` is unique, all three are too. `break` becomes `Jump(break_L)`, and `continue`
becomes `Jump(continue_L)`, using the label the pass stored on them.

`while (c) body`:
```
Label(continue_L)
<c → v>
JumpIfZero(v, break_L)
<body>
Jump(continue_L)
Label(break_L)
```
`do body while (c);`:
```
Label(start_L)
<body>
Label(continue_L)
<c → v>
JumpIfNotZero(v, start_L)      # test at the bottom: jump BACK while true
Label(break_L)
```
`for (init; c; post) body`:
```
<init>
Label(start_L)
<c → v>                        # both lines omitted if there's no condition
JumpIfZero(v, break_L)
<body>
Label(continue_L)
<post>                         # value discarded
Jump(start_L)
Label(break_L)
```
Notice where `continue` lands: in a `for`, it still runs `post` (otherwise `i = i + 1` would be
skipped and the loop could run forever); in a `do`, it still tests the condition.

### Worked example
```c
int main(void) { int s = 0; for (int i = 0; i < 3; i = i + 1) s = s + i; return s; }
```
TACKY (after resolution; your numbers may differ):
```
s.0 = 0
i.1 = 0                          # init
Label(start_loop.2)
tmp.3 = i.1 < 3
JumpIfZero(tmp.3, break_loop.2)
tmp.4 = s.0 + i.1                # body
s.0 = tmp.4
Label(continue_loop.2)
tmp.5 = i.1 + 1                  # post
i.1 = tmp.5
Jump(start_loop.2)
Label(break_loop.2)
return s.0                       # 0 + 1 + 2 = 3
```

### The `for` header's scope
`for (int i = 0; …) body` opens a new scope around the whole loop, holding `i`. If the body is a
block, that block opens *another* scope inside it. So `for (int i = 0; i < 3; i = i + 1) { int i = 9; }`
is legal shadowing, and `i` is not visible after the loop ends. In resolution: copy the map (or push
a scope) for the header, resolve init, condition, post and body inside it, then discard it.

## Build
1. **Lexer.** Keywords `while`, `do`, `for`, `break`, `continue`.
2. **AST.** The five statements, the `for`-init type, and a label field on each (empty after parsing).
3. **Parser.** The grammar above. Watch the `;` handling in the `for` header.
4. **Resolution.** A new scope for the `for` header; recurse into every loop part.
5. **Loop-labelling pass.** Runs after resolution, inside `--validate`. Error on `break` or `continue`
   outside a loop.
6. **TACKY.** The three lowerings plus `break` and `continue`.
7. **Must reject:** `break;` or `continue;` outside a loop; `do x = 1 while (y);` (missing `;` before
   `while`); `while () x = 1;`; `for (int i = 0, j = 0; …)`; `while (1) int a;`; using a header variable
   after the loop; `do { int a = 1; } while (a);` (the body's `a` is out of scope in the condition).
8. **Must accept:** `for (;;) { … break; }`, empty bodies like `while (x) ;`, nested loops with
   `break`/`continue` at each level, `continue` inside an `if` inside a loop.
9. **Run the suite.** `./test_compiler ./target/debug/rcc --chapter 8`. (The chapter's `--switch`
   extra credit is lesson 10.6.)

## Check your understanding

2. Where does `continue` jump in a `for` loop, and why not straight to the condition?
3. Why does `do … while` use `JumpIfNotZero` at the bottom, while `while` uses `JumpIfZero` at the top?
4. What does `for (;;) ;` lower to?
5. In which scope does `i` live in `for (int i = 0; i < n; i = i + 1) { … }`, and when does it stop being visible?
6. Why is it safe to derive all three jump targets from one loop label?

## Common pitfalls
- `continue` in a `for` jumping to the condition and skipping `post`: an infinite loop.
- Emitting a condition test for a `for` with no condition.
- No separate scope for the `for` header, so `i` leaks out of the loop or collides with a later `int i;`.
- Labelling `break` with the outermost loop because the current label isn't replaced for nested loops.
- Dropping `post` entirely because its value is unused; its side effect (the assignment) must happen.
