# Lesson 10.2 — Semantic Analysis
**Part:** 3 — Build the Compiler · **Unit:** 10 — Variables, Scope and Control Flow · **Type:** Builds variable-resolution pass · **Est. time:** 5–7 h · **Tests:** ch. 5
**Prerequisites:** lesson 10.1; 5.4 (ASTs and semantic analysis)

## Overview
Some wrong programs are perfectly grammatical: `return x;` when `x` was never declared, `int a; int a;`,
or `2 = 3`. Catching them needs a new kind of compiler stage, **semantic analysis**, which walks the
AST and checks meaning instead of shape. You'll build its first pass, **variable resolution**, which
also renames every variable to a globally unique name, and add a `--validate` stage flag. Every later
check in the course (loop labelling, type checking) joins this stage.

## The lesson

### Why a grammar can't catch these errors
Recall 5.3 and 5.4: a grammar describes the *shape* of a program. Each rule applies the same way
wherever it appears; it can't remember what came earlier. "Every variable must be declared before
it's used" depends on what came *before*, which is **context**. The grammars we use (context-free
grammars) can't express it, so the parser accepts `return x;` without complaint.

Python is the same: `print(x)` with no `x` parses fine, and only fails when it runs, with a
`NameError`. A C compiler must catch it at compile time, so it walks the tree after parsing.

You *could* check names inside the parser, threading a symbol table through every parse function.
A separate pass is cleaner: the parser stays about shape, errors come out of a distinct stage
(`--parse` vs. `--validate` tests), and new checks become new passes without touching the parser.

### What variable resolution does
The pass walks the AST in source order, keeping a map (a **symbol table**, 5.4) from the name the
user wrote to a **unique name** the compiler invents. For each node:

- **Declaration** `int x = init;`
  1. If `x` is already in the map: **duplicate declaration** error.
  2. Otherwise make a unique name (say `x.0`) and insert `x → x.0`.
  3. *Then* resolve the initializer, and output the declaration with the new name.
- **`Var(x)`**: look `x` up. Missing: **undeclared variable** error. Found: replace it with the unique name.
- **`Assignment(lhs, rhs)`**: if `lhs` is not a `Var`, it's an **invalid lvalue** error. Otherwise
  resolve both sides.
- **Everything else**: recurse into the children, rebuilding the node.

The result is a new AST where every variable has a unique name, or an error.

### The order in step 3 matters
Inserting the name *before* resolving the initializer means `int a = a + 1;` is accepted. That's
what C specifies: a variable's scope starts right after its declarator, so the `a` in the
initializer refers to the new `a`, which isn't initialized yet. Reading it is undefined behaviour at
run time (5.4), but not a compile error. If you resolved the initializer first, you'd reject a legal
program (or, once 10.4 adds nested scopes, silently pick up an outer `a`).

### Why rename at all?
Checking names would be enough to catch errors. Renaming buys something bigger: after this pass,
**every variable has a name that is unique in the whole program**. In 10.4, `x` in an inner block
and `x` in an outer block become `x.1` and `x.0`, two different TACKY variables with two different
stack slots, and no later stage ever has to know what scope is. In Unit 11 the same goes for local
variables in different functions.

As with temporaries (9.2), put a `.` in generated names: it can't appear in a C identifier, so
`x.0` can never collide with a user's variable. Use **one counter** shared by resolution and TACKY
generation. To see why, suppose each had its own counter starting at 0, and the user names a
variable `tmp`. Resolution renames it `tmp.0`; TACKY generation then makes its first temporary,
also `tmp.0`. Two different values now share one stack slot. One shared counter makes every
number unique, so that can't happen. A small context struct with a `&mut self` method that
hands out fresh numbers works well, passed from pass to pass by the driver.

### Worked example
```c
int main(void) { int a = 1; int b = a + 2; a = b; return a; }
```
```
step                       map after              output
int a = 1;                 {a → a.0}              Declaration(a.0, Constant 1)
int b = a + 2;             {a → a.0, b → b.1}     Declaration(b.1, Binary(Add, Var a.0, Constant 2))
a = b;                     (unchanged)            Expression(Assignment(Var a.0, Var b.1))
return a;                  (unchanged)            Return(Var a.0)
```
And three programs it rejects:
```c
int main(void) { return x; }               /* undeclared variable x */
int main(void) { int a; int a; return 0; } /* duplicate declaration of a */
int main(void) { int a = 2; a + 1 = 3; }   /* invalid lvalue: a + 1 is not a variable */
```
Note `(a) = 4` is fine: parentheses don't appear in the AST (9.1), so it's just `Var a`.

### Errors as values
Each error should be a value, not a crash. A semantic-error enum with one variant per kind
(undeclared, duplicate, invalid lvalue), each carrying the offending name or a description, fits
3.3 exactly. Every resolving function returns a `Result`, and `?` passes errors up through the
recursion. The driver prints the error (implement `Display`, 4.1) to stderr and exits non-zero.
Never `unwrap` a failed lookup: the test suite expects a clean non-zero exit, not a panic.

### Consume or borrow the tree?
Two reasonable designs. A pass that takes the AST **by value** can move unchanged pieces straight into
the new tree, with no copying. A pass that takes `&mut` can rename in place. The first tends to be
easier to reason about in Rust (2.2, 2.3); either is fine.

### The `--validate` stage
`rcc --validate prog.c` runs lex → parse → semantic analysis, then exits: 0 on success, non-zero
on an error, writing no files. The test suite's `--stage validate` uses it. `--tacky`, `--codegen`,
`-S` and a full compile must all run this stage too, since TACKY generation now relies on unique names.

## Build
1. **Semantic-analysis module** with a resolution function from a program to a result of either a
   resolved program or a semantic error.
2. **Name generator.** Move the fresh-name counter somewhere both resolution and TACKY generation
   can use it.
3. **Error type** with the three variants and a `Display` message for each.
4. **Driver.** Add `--validate`; make every later stage run resolution first.
5. **Must reject** (all of chapter 5's "invalid semantics" tests): `a = 1; int a;` (use before
   declaration), duplicates, `2 = 3`, `-a = 3`, `(a) + 1 = 2`. If you did `++`/`--`/compound
   assignment, their operands must be lvalues too.
6. **Must accept:** `int a = a + 1;`, `a = a = 4;` (after declaring `a`), `(a) = 4`.
7. **Unit tests:** one input and expected error per error kind; one renamed AST for the worked example.
8. **Run the suite.** `./test_compiler ./target/debug/rcc --chapter 5`, plus `--stage validate`.

## Check your understanding
1. Why is "undeclared variable" not a parse error? Could a context-free grammar ever express it?
2. In `int a = a + 1;`, which `a` does the initializer refer to? What changes if you resolve the initializer first?
3. What does renaming buy you that checking alone doesn't? Which later lessons rely on it?
4. Why must resolution and TACKY generation share one name counter?
5. What does `--validate` do that `--parse` doesn't, and what does it *not* do?

## Common pitfalls
- Resolving the initializer before inserting the name, rejecting the legal `int a = a + 1;`.
- Separate counters in resolution and TACKY generation, producing clashing names.
- Forgetting the lvalue check, or doing it after the left side has been transformed.
- Panicking on a missing name instead of returning an error; the tests check for a clean non-zero exit.
- Making `--validate` print output or write files; it should only succeed or fail.
