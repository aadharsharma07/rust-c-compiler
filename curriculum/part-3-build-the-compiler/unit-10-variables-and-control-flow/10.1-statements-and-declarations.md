# Lesson 10.1 — Statements and Declarations
**Part:** 3 — Build the Compiler · **Unit:** 10 — Variables, Scope and Control Flow · **Type:** Builds local vars + assignment · **Est. time:** 4–6 h · **Tests:** ch. 5
**Prerequisites:** lessons 9.1–9.6 (chapters 1–4 pass)

## Overview
Until now a function body has been exactly one `return`. This lesson lets it be a sequence of
**declarations** (`int a = 2;`) and **statements** (`a = a * 3;`, `return a;`), and adds variables
and the assignment operator. The surprise is how little the back end cares: a C variable is just
a TACKY variable, which becomes a pseudoregister, which gets a stack slot. The work is in the
parser, and in understanding C's three kinds of syntax. Checking that variables are used
correctly is the next lesson.

## The lesson

### Three kinds of syntax
C separates three things that Python blurs together:

- An **expression** produces a value: `2 + 3`, `a`, `a = 5`.
- A **statement** does something: `return a;`, `a = 5;`.
- A **declaration** introduces a name: `int a;` or `int a = 5;`.

In Python, `a = 5` is a statement that both creates `a` (if needed) and assigns it. C splits that
in two: `int a;` declares a variable called `a` of type `int`, and `a = 5` is an assignment, which
can only target a variable that was already declared. `int a = 5;` does both in one line, but it's
still a declaration whose `= 5` part is an **initializer**, not an assignment.

### The new grammar
A function body is now a list of **block items**, each a statement or a declaration:
```
<function>    ::= "int" <identifier> "(" "void" ")" "{" { <block-item> } "}"
<block-item>  ::= <statement> | <declaration>
<declaration> ::= "int" <identifier> [ "=" <exp> ] ";"
<statement>   ::= "return" <exp> ";" | <exp> ";" | ";"
<exp>         ::= <factor> | <exp> <binop> <exp>          (binop now includes "=")
<factor>      ::= <int> | <identifier> | <unop> <factor> | "(" <exp> ")"
```
Notation reminder (5.3): `{ … }` means "zero or more", `[ … ]` means "optional".

Two new statements appear. An **expression statement** `<exp> ";"` evaluates an expression for its
side effects and throws the value away: `a = a + 1;` is the typical one, though `2 + 2;` is also
legal (and useless). The **null statement** `;` does nothing at all.

Telling a declaration from a statement needs one token of lookahead: block items starting with the
keyword `int` are declarations; anything else is a statement. Note that in C17 a declaration is
*not* a kind of statement. That matters in 10.3, where `if (x) int y = 1;` must be a parse error.

### Assignment is an expression
In Python, `a = b = 5` is special syntax. In C it falls out of one rule: `=` is a binary operator,
and `a = 5` is an expression whose **value is the value stored**. So `a = b = 5` means
`a = (b = 5)`: store 5 in `b`, and the result 5 is stored in `a`. That grouping is
**right-associative**, unlike every operator so far. Assignment also has the **lowest precedence**:
`a = 1 + 2` must mean `a = (1 + 2)`.

Your precedence climber (9.4) handles both with two small changes. Give `=` precedence 1 (below
`||` at 5). And when the operator is `=`, parse the right operand with minimum precedence **`p`**,
not `p + 1`. In 9.4 you saw that `p + 1` forbids the right operand from containing another
operator of the same level, forcing left grouping; using `p` allows it, so the right side swallows
the rest of the chain:
```
a = b = 5      parse_exp(0): left = a; see '=' (1 >= 0); right = parse_exp(1)
                 │ left = b; see '=' (1 >= 1, allowed); right = parse_exp(1) → 5
                 │ return Assignment(b, 5)
               result: Assignment(a, Assignment(b, 5))
```
With `p + 1` you'd get `(a = b) = 5`, which tries to store into the *value* of `a = b`: nonsense.

### Lvalues
Only some expressions can sit on the left of `=`. An **lvalue** ("left value") is an expression
that names a storage location. For now, the only lvalue is a variable; later units add `*p` and
`a[i]`. `2 = 3` and `a + 1 = 3` are not lvalues.

Here's a design point: your parser will happily build `Assignment(Constant 2, Constant 3)`,
because grammatically it's just `<exp> "=" <exp>`. That's *fine*. Whether the left side is an
lvalue is a **semantic** question, checked in 10.2. Don't hack it into the parser: it would work
today and fight you when pointers arrive.

### AST changes
```
function_definition = Function(identifier name, block_item* body)
block_item  = S(statement) | D(declaration)
declaration = Declaration(identifier name, exp? init)
statement   = Return(exp) | Expression(exp) | Null
exp         = Constant(int) | Var(identifier) | Unary(unary_operator, exp)
            | Binary(binary_operator, exp, exp) | Assignment(exp, exp)
```
`exp?` means optional: an `Option` (3.3). Assignment gets its own variant rather than being a
`binary_operator`, because it lowers completely differently.

### Lowering to TACKY: variables are free
A variable `a` translates to TACKY `Var("a")`, the same `val` your temporaries use. Instruction
selection already turns every `Var` into a `Pseudo`, and pseudo replacement already gives every
distinct name a stack slot. So no back-end changes at all.

The new rules:
- **`Var(a)`** → emit nothing; the result is `Var(a)`.
- **`Assignment(Var a, rhs)`** → translate `rhs` to `v`; emit `Copy(v, Var a)`; the result is `Var a`
  (the assignment's value is what was stored).
- **`Declaration(a, Some(init))`** → exactly like assigning `init` to `a`. **Without** an initializer
  it emits *nothing*: the stack slot appears when `a` is first used.
- **`Expression(e)`** → translate `e` and ignore the result. **`Null`** → nothing.

### `main` without a `return`
C says that if `main` reaches its closing `}` without returning, it returns 0. (For other functions,
using the missing return value is undefined behaviour.) The simplest fix covers every case: always
append `Return(Constant 0)` to the end of every function's TACKY. When it's unreachable, it costs
one instruction.

### Worked example
```c
int main(void) { int a = 2; int b; b = a * 3; return b; }
```
(C syntax note: `int main(void)` defines a function `main` that takes no arguments and returns an `int`.)
```
TACKY                 source
a = 2                 int a = 2;        Copy(2, a)
                      int b;            (nothing)
tmp.0 = a * 3         b = a * 3;        Binary(Multiply, a, 3, tmp.0)
b = tmp.0                               Copy(tmp.0, b)
return b              return b;
return 0              (appended; unreachable, harmless)
```
Pseudo replacement gives `a`, `tmp.0` and `b` the slots `-4`, `-8` and `-12(%rbp)` in order of
first appearance. `int b;` emitted nothing. The `Copy` from `tmp.0` to `b` becomes a memory-to-memory `movl`, which
your fix-up pass from 9.3 already splits. Exit status: 6.

## Build
1. **Lexer.** Add the `=` token (`==` must still lex as one token).
2. **AST.** Block items, declarations with an optional initializer, `Expression` and `Null`
   statements, `Var` and `Assignment` expressions. Function bodies become a list of block items.
3. **Parser.** Dispatch block items on the `int` keyword; identifiers as factors; `=` in the
   precedence table at 1, right-associative.
4. **TACKY.** The lowering rules above, plus the trailing `Return(0)`. No back-end changes should be
   needed: if you find yourself editing them, stop and check why.
5. **Must reject (parse errors):** `int = 3;`, `int a = ;`, `int a 3;`, `return int;`, a missing
   `;`, `a = = 3;`, `int 3a;`.
6. **Must parse:** `int a = a = 3;`, `a = 1 + (b = 2);`, `;;;` inside a body, a body with no `return`.
   (Some are semantically questionable; parsing them is still correct.)
7. **Optional extra credit:** compound assignment (`+=`, `-=`, …) and `++`/`--` (suite flags
   `--compound` and `--increment`; check `--help`). Postfix `a++` needs a temporary holding the *old* value.
8. **Run the suite.** `./test_compiler ./target/debug/rcc --chapter 5 --stage parse`. Valid chapter-5
   programs should also run correctly; the "invalid semantics" tests will fail until 10.2.

## Common pitfalls
- Reusing the `p + 1` rule for `=`, making `a = b = 5` parse as `(a = b) = 5`.
- Rejecting non-lvalues in the parser instead of in semantic analysis.
- Emitting a `Copy` for a declaration with no initializer, or translating the initializer twice.
- Forgetting to lower expression statements: `a = 3;` must still emit its `Copy`.
- Parsing a declaration as a kind of statement, which makes `if (x) int y;` wrongly accepted later.
