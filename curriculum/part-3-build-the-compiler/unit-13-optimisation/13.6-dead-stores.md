# Lesson 13.6 — Dead stores
**Part:** 3 — Build the Compiler · **Unit:** 13 — Optimisation · **Type:** Builds dead-store elimination · **Est. time:** 5–7 h · **Tests:** ch. 19
**Prerequisites:** lessons 13.1–13.5

## Overview
An instruction whose only effect is writing a variable that nothing will ever read is wasted work: a *dead store*. To find them you need *liveness*, a backward, may dataflow analysis. This lesson teaches liveness by hand, step by step, then has you delete dead stores and finish the Unit 13 pipeline so `--optimize` runs all four passes to a fixpoint. Liveness returns in Unit 14 as the heart of register allocation.

## The lesson

### Liveness
A variable `v` is **live** at a point if some path from that point *reads* `v` before *writing* it. In other words, its current value might still be needed. If an instruction writes `v` and `v` is not live immediately after it, the write is a **dead store**. If the instruction has no other effect, you can delete it.

In Python terms: in `a = f(); a = 2; print(a)`, the value from `f()` is never used. You still can't delete `f()` (it might print something), but if the first line were `a = 1 + 1`, it could simply go.

### The analysis, in the four ingredients
- **Direction:** backward ("what happens *after* this point?"). **Facts:** sets of variables.
- **Meet:** ∪. Live on *some* path is enough to keep a value: deleting it would break that path.
- **Boundary at Exit:** every **static-storage** variable (globals and `static` locals, 11.4) is live, because the caller or a later call may read it after we return. Locals are dead once the function returns.
- **Initial value for blocks:** ∅ (the identity of ∪; recall 13.4).
- **Transfer, per instruction**, from live-after L to live-before:
  - General rule: `live_before = (L − {written variable}) ∪ {variables read}`. Remove the write **first**, then add the reads. So for `x = x + 1`, `x` is live before: the instruction needs the old `x`.
  - `Return(v)`, `JumpIfZero(v, _)`, `JumpIfNotZero(v, _)`: read `v`.
  - `FunCall(f, args, dst)`: kills `dst`, reads every variable among the arguments, and makes **every aliased variable** live (statics and address-taken locals, as defined in 13.5), since the callee may read them.
  - `Store(src, ptr)` (12.5): reads `src` and `ptr`; kills nothing, since you don't know which object it writes.
  - `Load(ptr, dst)`: kills `dst`, reads `ptr`, and makes every aliased variable live, since it might read any of them.
  - `GetAddress(x, dst)`: kills `dst`. It doesn't read `x`'s *value*, so `x` needn't become live.
  - `CopyToOffset(src, dst, offset)` (12.9): reads `src`; writes only *part* of `dst`, so it does not kill `dst` (the other parts may still be needed). `CopyFromOffset(src, offset, dst)`: reads `src`, kills `dst`.
  - `Jump`, `Label`: no change. Constants are never "read variables".

### Worked example 1: a straight line
Compute live sets from the bottom up (`a` and `b` are parameters):

```
                        live after       live before
1: x = a + 1            {x, b}           {a, b}
2: y = x * 2            {b}              {x, b}       <- y not in live-after: dead store
3: x = b                {x}              {b}
4: return x             {}               {x}
```

Step by step: after 4 (at Exit) nothing is live. 4 reads `x`: before = {x}. 3 writes `x`, reads `b`: ({x} − {x}) ∪ {b} = {b}. 2 writes `y`, reads `x`: ({b} − {y}) ∪ {x} = {x, b}. 1 writes `x`, reads `a`: ({x, b} − {x}) ∪ {a} = {a, b}.

Delete instruction 2. Now instruction 1's `x` is dead too: nothing reads it before instruction 3 overwrites it. This round's liveness didn't see that, because instruction 2 was still there when it ran. The *next* round catches it. Don't add special code for chains like this: the fixpoint loop from 13.1 handles them.

### Worked example 2: a loop, iterated to a fixpoint
```
B0: i = 0                     preds: Entry    succs: B1
    s = 0
B1: Label(loop)               preds: B0, B2   succs: B2, B3
    tmp.0 = i < 10
    JumpIfZero(tmp.0, end)
B2: s = s + i                 preds: B1       succs: B1
    t = s * 2
    i = i + 1
    Jump(loop)
B3: Label(end)                preds: B1       succs: Exit
    return s
```

Backward, so each step computes `out[B]` as the union of the successors' `in`, then walks the block upwards. All `in` start as ∅; Exit's boundary is ∅ (no statics here). Worklist in reverse order: B3 B2 B1 B0.

| Step | Pop | out = ∪ of successors' in | Walk upwards | in | Changed? | Worklist after |
|---|---|---|---|---|---|---|
| 1 | B3 | Exit = ∅ | `return s` reads s | {s} | yes | B2 B1 B0 |
| 2 | B2 | in[B1] = ∅ | Jump: ∅; `i = i + 1`: {i}; `t = s * 2`: {i, s}; `s = s + i`: {i, s} | {i, s} | yes | B1 B0 |
| 3 | B1 | in[B2] ∪ in[B3] = {i, s} ∪ {s} = {i, s} | JumpIfZero: {i, s, tmp.0}; `tmp.0 = i < 10`: {i, s}; Label: {i, s} | {i, s} | yes | B0 B2 |
| 4 | B0 | in[B1] = {i, s} | `s = 0`: {i}; `i = 0`: ∅ | ∅ | no | B2 |
| 5 | B2 | in[B1] = {i, s} | Jump: {i, s}; `i = i + 1`: {i, s}; `t = s * 2`: {i, s}; `s = s + i`: {i, s} | {i, s} | no | (empty) |

At the fixpoint, the live-after sets in B2 are: after `s = s + i`: {i, s}; after `t = s * 2`: {i, s}; after `i = i + 1`: {i, s}. So `t = s * 2` is dead (`t` isn't live after it) and goes. `i = i + 1` stays.

Look at step 2: there, the live-after set of `i = i + 1` was ∅, which would have made it look dead. Only after B1 was processed did the back edge carry `i` round. Liveness is about *paths*, and the back edge is a path: `i` is read by `tmp.0 = i < 10` on the next trip, even though nothing after the loop uses `i`. Never delete using facts from before the fixpoint.

### What may and may not be deleted
Only instructions whose *only* effect is writing their destination are candidates: `Copy`, `Unary`, `Binary`, the type conversions, `GetAddress`, `Load`, `AddPtr`, `CopyFromOffset`, and `CopyToOffset` (dead if the whole destination variable isn't live after it).

Never delete:
- `FunCall`, even when its result is unused: the callee may print, write memory or change globals.
- `Store`: it writes memory that something else may read.
- Anything without a destination: jumps, labels, `Return`.

Why statics are live at Exit, with a C example (in C, a variable declared outside any function is a global):

```c
int counter = 0;
int bump(void) { counter = counter + 1; return 0; }
```

Nothing in `bump` reads `counter` after the write, but the caller can. The Exit boundary keeps it live, so the write stays.

### Aliasing, again
A local whose address is taken can be read through a pointer by a `Load` or by a callee. In C, `*p` reads through the pointer `p`:

```c
int a = 5; int *p = &a; return *p;
```

The TACKY is roughly `a = 5; p = GetAddress(a); tmp = Load(p); return tmp`. Nothing reads `a` by name, so without the "Load makes every aliased variable live" rule, `a = 5` would look dead, and the program would return garbage.

## Build
**Behaviour to implement:**
- **Liveness analysis** as an instance of your 13.4 framework: backward, ∪, Exit boundary = static variables, initial ∅, transfer as above. Reuse the static and aliased variable sets from 13.5.
- **Dead-store pass:** for each candidate instruction, delete it if its destination is not in the live-after set. Returns the new CFG.
- **Flag:** active with `--eliminate-dead-stores` or `--optimize`. Each round: fold → build CFG → unreachable code → copy propagation → dead stores → flatten; repeat until unchanged.
- **Correctness:** never delete calls or stores; treat every aliased variable as possibly read by calls and loads; keep statics live at Exit.
- **Edge cases:** variables live round a back edge (example 2); a function whose whole body becomes `return <constant>`; a variable only read through a pointer; an unused parameter; a call whose result is unused.

**Suggested order:**
1. Two small helpers, "which variables does this instruction read" and "which does it write", with unit tests. Keep them separate: Unit 14 needs the same idea for assembly.
2. The transfer function, tested on example 1 instruction by instruction.
3. Plug it into the framework; unit-test example 2 against the table.
4. The deletion pass, then wire in the flag.
5. Run chapter 19 with `--eliminate-dead-stores`, then with `--optimize`, then every earlier chapter with `--optimize`.

2. Why does the Exit boundary include static variables but not locals?
3. A `FunCall`'s result is never used. Why can't you delete the call?
4. In `x = x + 1`, why must you remove `x` before adding it back?

## Common pitfalls
- Adding the reads before removing the written variable, which wrongly drops `x` in `x = x + 1`.
- Deleting `FunCall`s whose result is unused.
- Forgetting statics at Exit, so a final write to a global disappears.
- Ignoring aliasing: a write to an address-taken local looks dead if only a `Load` or a callee reads it.
- Expecting one round to remove chains of dead stores, and patching that with special-case code instead of trusting the fixpoint loop.
