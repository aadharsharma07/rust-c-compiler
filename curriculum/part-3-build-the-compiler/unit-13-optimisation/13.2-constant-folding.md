# Lesson 13.2 — Constant folding
**Part:** 3 — Build the Compiler · **Unit:** 13 — Optimisation · **Type:** Builds constant folding · **Est. time:** 4–6 h · **Tests:** ch. 19
**Prerequisites:** lesson 13.1

## Overview
Constant folding computes, at compile time, any TACKY operation whose inputs are all constants, and turns a conditional jump on a constant into an unconditional jump or nothing. It is the simplest pass, so this lesson also adds the scaffolding every later pass plugs into: the new flags and the "repeat until nothing changes" loop.

## The lesson

### Folding is local
Constant folding looks at one instruction at a time. It needs no CFG and no analysis. Recall from 9.2 that TACKY operands (`Val`s) are either a `Constant` or a `Var`. If every *source* operand of a `Unary` or `Binary` is a `Constant`, compute the answer now and replace the instruction with a `Copy` of the result into the same destination:

| Before | After |
|---|---|
| `Binary(Add, 2, 3, tmp.0)` | `Copy(5, tmp.0)` |
| `Unary(Negate, 7, tmp.1)` | `Copy(-7, tmp.1)` |
| `Unary(Complement, 0, tmp.2)` | `Copy(-1, tmp.2)` |
| `Binary(LessThan, 4, 9, tmp.3)` | `Copy(1, tmp.3)` |
| `Unary(Not, 0, tmp.4)` | `Copy(1, tmp.4)` |
| `JumpIfZero(0, else.4)` | `Jump(else.4)` |
| `JumpIfZero(5, else.4)` | *(deleted)* |
| `JumpIfNotZero(0, end.5)` | *(deleted)* |
| `JumpIfNotZero(3, end.5)` | `Jump(end.5)` |

Two details. Comparisons and `!` always produce the `int` 0 or 1 (recall 9.6). And folding does *not* delete `tmp.0` or rewrite later uses of it: it only creates a `Copy`. Copy propagation (13.5) pushes the constant into the uses, and dead-store elimination (13.6) deletes the then-unused `Copy`. Each pass stays small because it trusts the others.

Why is deleting `JumpIfZero(5, L)` correct? The condition is 5, which is never zero, so the jump is never taken: execution always falls through to the next instruction, which is exactly what happens if the jump isn't there. The label `L` stays; 13.3 tidies it away if nothing else jumps to it.

### Worked example
Take `return (3 + 4) * 2 > 10 ? 1 : 2;`. Recall from 10.3 that `?:` (the conditional operator: "if the condition is non-zero, the value is the first branch, else the second") lowers to a conditional jump. Your TACKY looks something like this; the right column shows round 1 of folding:

```
tmp.0 = 3 + 4                  ->  tmp.0 = 7
tmp.1 = tmp.0 * 2                  (unchanged: tmp.0 is a Var)
tmp.2 = tmp.1 > 10                 (unchanged)
JumpIfZero(tmp.2, cond_else.1)     (unchanged)
result.3 = 1
Jump(cond_end.2)
Label(cond_else.1)
result.3 = 2
Label(cond_end.2)
return result.3
```

Only the first instruction folds this round. Once copy propagation exists, it rewrites `tmp.1 = 7 * 2`, the next round folds that to `tmp.1 = 14`, then `tmp.2 = 14 > 10` becomes `tmp.2 = 1`, then `JumpIfZero(1, cond_else.1)` is deleted, and unreachable-code elimination removes the `else` branch. With folding alone, you only get round 1. That is fine: the tests for `--fold-constants` are written with that in mind.

### Match the machine, not mathematics
The folded value must equal what the generated machine code would have computed at run time. Otherwise the optimised program behaves differently.

- **`int` is 32-bit two's complement** (Part 2 lesson 6.1). `2147483647 + 1` must fold to `-2147483648`. Signed overflow is UB in C, so any answer is technically allowed, but `rcc` must not *panic*. In debug builds Rust's `+` on `i32` panics on overflow, so use the wrapping methods:
  ```rust
  assert_eq!(i32::MAX.wrapping_add(1), i32::MIN);
  ```
- **Division truncates toward zero.** `-7 / 2` is `-3` and `-7 % 2` is `-1`, exactly like Rust's `/` and `%` on integers (and unlike Python's `//` and `%`, which round toward negative infinity: in Python `-7 // 2` is `-4`).
- **Division or remainder by zero: do not fold.** Leave the instruction alone. The program might never execute it (it could sit in a branch that is never taken), and if your compiler crashed or invented a value, a perfectly good program would break.
- **`INT_MIN / -1`** (and `% -1`) makes `idiv` trap on x86-64, and Rust's `/` panics on it too. The simplest correct choice is: don't fold it. Rust's `checked_div` and `checked_rem` return `None` for both this case and division by zero, which is exactly the "don't fold" set:
  ```rust
  assert_eq!(5_i32.checked_div(0), None);
  ```

### The types from Unit 12
Since Unit 12, constants carry a type, and you must fold *at the operand's type*:
- `long` is 64-bit; `unsigned int` wraps modulo 2³²; `unsigned long` modulo 2⁶⁴; `char` types truncate to 8 bits.
- Unsigned division and comparison differ from signed: `4294967295u > 0u` is true, but the same bits as an `int` (-1) are less than 0.
- Conversion instructions (`SignExtend`, `Truncate`, `ZeroExtend`, and the int↔double conversions from 12.4) can fold when their source is a constant. Produce exactly the bits the instruction would produce. Converting a `double` that's out of range for the integer type is UB; leaving such a conversion unfolded is the safe choice.

Same bits, different answers, depending on type:

| TACKY (operand type) | Folds to | Why |
|---|---|---|
| `Binary(Add, 2147483647, 1, t)` (`int`) | `Copy(-2147483648, t)` | wraps at 32 bits |
| `Binary(Add, 2147483647L, 1L, t)` (`long`) | `Copy(2147483648L, t)` | 64 bits: no wrap |
| `Binary(Divide, 4294967295u, 2u, t)` (`unsigned`) | `Copy(2147483647u, t)` | unsigned division |
| `Binary(Divide, -1, 2, t)` (`int`, same bits) | `Copy(0, t)` | signed, truncates toward zero |
| `Truncate(4294967298L, t)` (`long` → `int`) | `Copy(2, t)` | keeps the low 32 bits |

- `double` (12.4): NaN compares unequal to everything, including itself, and `-0.0 == 0.0` is true. Double division by zero does not trap: it gives ±infinity or NaN, which Rust's `f64` also produces, so you *may* fold it. When printing a folded `double` constant into assembly, make sure every bit survives (recall how 12.4 emits doubles).

### The pipeline skeleton
For each function definition (not declarations), the optimiser repeats a round until the body stops changing:

```
loop:
    before = copy of body
    if folding is on: body = fold(body)
    (13.3, 13.5, 13.6 add more passes here)
    if body is empty or body == before: stop
```

"Changed" means "not equal to the body at the start of the round", compared instruction by instruction. Comparing only the length is wrong: folding usually keeps the length the same (`Binary` becomes `Copy`). To compare whole TACKY lists you need equality on your IR types; in Rust that means deriving `PartialEq`. Note that `f64` implements `PartialEq` but not `Eq` (because NaN ≠ NaN), so derive only `PartialEq` on types containing doubles.

## Build
**Behaviour to implement:**
- **Flags.** `rcc` accepts `--fold-constants`, `--eliminate-unreachable-code`, `--propagate-copies`, `--eliminate-dead-stores` and `--optimize` (turns on all four). They may appear in any order alongside existing flags (`--lex`, `--tacky`, `-S`, …). Passes you haven't built yet are no-ops, but their flags must be accepted, not rejected.
- **Optimiser entry point.** Takes one function's TACKY instruction list plus the set of enabled passes; returns the optimised list. It runs on every function definition after TACKY generation and before assembly generation. Static variable definitions are not touched.
- **Fixpoint loop.** As above: repeat until a round leaves the body identical, or the body is empty.
- **Folding pass.** Input a list, output a new list:
  - `Unary`/`Binary` with all-constant sources → `Copy(result, dst)`, computed at the operand type. Division and remainder by zero, and the `MIN / -1` cases, are left unchanged.
  - `JumpIfZero(c, L)` → `Jump(L)` if `c` is zero, deleted otherwise. `JumpIfNotZero(c, L)` → `Jump(L)` if `c` is non-zero, deleted otherwise.
  - Type conversions with a constant source fold (except out-of-range double → integer).
  - Everything else passes through unchanged.
- **Correctness.** For every program with defined behaviour, output and exit code are identical with and without the flag.

**Suggested order:**
1. Parse the five flags into a small struct of booleans in your driver and pass it down. Run the test suite with no flags to confirm nothing changed.
2. Write the empty fixpoint loop and wire it between TACKY generation and assembly generation.
3. Fold `int` `Binary` and `Unary`, with unit tests on hand-written TACKY: overflow, every operator, division by zero, `INT_MIN / -1`.
4. Fold the two conditional jumps, with tests.
5. Extend to `long`, `unsigned`, `char` and `double`, then the conversions. Test the unsigned comparison and wrapping cases explicitly.
6. Run chapter 19 with `--fold-constants`. If a test fails, compare `rcc --tacky` output with and without the flag on that program.

## Check your understanding
1. Why does folding produce `Copy(5, tmp.0)` rather than deleting the instruction and rewriting later uses of `tmp.0`?
2. What should `JumpIfZero(3, L)` become, and why is that correct?
3. Rust's `i32` addition panics on overflow in debug builds. How do you avoid that, and what value must `2147483647 + 1` produce?
4. Why is it wrong to fold `x = 1 / 0` into anything, even though the program's behaviour is undefined if it runs?
5. What do `4294967295u + 1u` and `-1 < 0u` fold to? (In the second, the C rules from 12.3 convert `-1` to `unsigned` first.)
6. How does your loop decide that "nothing changed"?

## Common pitfalls
- Panicking in the compiler on overflow or division by zero instead of leaving the instruction alone.
- Folding with the wrong semantics: using `i64` for an `int` operation and forgetting to truncate, or signed comparison for `unsigned` operands.
- Checking only lengths to detect change; folding rarely changes the length.
- Parsing the flags but only running the optimiser when `--optimize` is given, so `--fold-constants` alone does nothing.
- Folding a `double` correctly but losing bits when emitting the constant (for example printing it with too few digits).
