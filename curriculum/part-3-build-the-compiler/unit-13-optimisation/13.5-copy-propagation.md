# Lesson 13.5 — Copy propagation
**Part:** 3 — Build the Compiler · **Unit:** 13 — Optimisation · **Type:** Builds copy propagation · **Est. time:** 6–8 h · **Tests:** ch. 19
**Prerequisites:** lessons 13.1–13.4

## Overview
After `y = x`, a later read of `y` can use `x` instead, as long as neither has changed on any path in between. Copy propagation finds those reads with a forward, must dataflow analysis called *reaching copies*, then rewrites them. It is the pass that carries constants from where folding creates them to where folding can use them, so after this lesson the passes really start to feed each other.

## The lesson

### When does a copy "reach" an instruction?
A **copy** is a TACKY `Copy(src, dst)`, written `dst = src`. The source is a constant or a variable; the destination is a variable. The copy **reaches** an instruction I if, on **every** path from Entry to I, the copy runs and afterwards neither `dst` nor `src` is written. If `y = x` reaches an instruction that reads `y`, that read can use `x` instead (and if the copy is `y = 3`, the read can use `3`).

Why *every* path? Suppose one path sets `y = x` and another sets `y = 4`. At the join, `y` might be either, so replacing `y` with `x` would be wrong on the second path. This is a must analysis, so the meet is intersection (13.4).

### The analysis, in the four ingredients
- **Direction:** forward. **Facts:** sets of copies, each a (source, destination) pair.
- **Meet:** ∩. **Boundary:** nothing reaches the start of the function: Entry = ∅.
- **Initial value for every block:** the universe, meaning every `Copy` that appears anywhere in the function. (Recall from 13.4 why ∩ analyses must start full.)
- **Transfer, per instruction**, given the incoming set R:
  - `Copy(src, dst)`: if `dst = src` is already in R, or the reverse copy `src = dst` is, nothing changes: the instruction is redundant. Otherwise remove every copy in R that mentions `dst` as *either* source or destination, then add `dst = src`.
  - Any other instruction that writes a variable `v`: remove every copy that mentions `v`.
  - `FunCall`: additionally remove every copy that mentions an **aliased** variable (below).
  - `Store` (through a pointer, 12.5): remove every copy that mentions an aliased variable.
  - `Jump`, `JumpIfZero`, `JumpIfNotZero`, `Label`, `Return`: no change.

Why does writing `x` kill `y = x` and not only copies *to* `x`? After `y = x; x = 7;`, `y` still holds the *old* `x`. Replacing a later `y` with `x` would read 7. Both directions must go.

### Worked example 1: a join
Facts are shown *before* each instruction (`c` is a parameter):

```
                          reaching before
x = 3                     {}
y = x                     {x=3}
JumpIfZero(c, L)          {x=3, y=x}
y = 4                     {x=3, y=x}
Label(L)                  meet of {x=3, y=x} (jump taken) and {x=3, y=4} = {x=3}
tmp.0 = y + x             {x=3}
return tmp.0              {x=3}
```

At `y = 4`, the old `y = x` is removed (it mentions `y`) and `y = 4` added, giving {x=3, y=4} at the end of that block. The rewrite uses each instruction's "before" fact:

```
x = 3
y = 3                     <- x replaced by 3
JumpIfZero(c, L)
y = 4
Label(L)
tmp.0 = y + 3             <- x replaced; y not: the two paths disagree
return tmp.0
```

Notice the analysis tracked `y = x`, while the rewritten code says `y = 3`. That's fine: `x = 3` reached that point too. Next round, the analysis sees `y = 3` directly. `x = 3` is now unread; 13.6 deletes it.

### Worked example 2: a loop, iterated to a fixpoint
This one shows why stopping early would be *wrong*, not just weak.

```
B0: x = 3                    preds: Entry    succs: B1
    y = x
B1: Label(loop)              preds: B0, B2   succs: B2, B3
    tmp.0 = y < c
    JumpIfZero(tmp.0, end)
B2: x = 5                    preds: B1       succs: B1
    c = c - 1
    Jump(loop)
B3: Label(end)               preds: B1       succs: Exit
    return y
```

Universe U = {x=3, y=x, x=5}. Every `out` starts as U. Worklist: B0 B1 B2 B3.

| Step | Pop | in | out | Changed? | Worklist after |
|---|---|---|---|---|---|
| 1 | B0 | Entry = ∅ | {x=3, y=x} | yes | B1 B2 B3 |
| 2 | B1 | out[B0] ∩ out[B2] = {x=3, y=x} ∩ U = {x=3, y=x} | {x=3, y=x} | yes | B2 B3 |
| 3 | B2 | {x=3, y=x} | `x = 5` kills both, adds x=5: {x=5} | yes | B3 B1 |
| 4 | B3 | {x=3, y=x} | {x=3, y=x} | yes (Exit: push nothing) | B1 |
| 5 | B1 | {x=3, y=x} ∩ {x=5} = ∅ | ∅ | yes | B2 B3 |
| 6 | B2 | ∅ | {x=5} | no | B3 |
| 7 | B3 | ∅ | ∅ | yes | (empty) |

If you'd stopped after step 4, the fact before `tmp.0 = y < c` would be {x=3, y=x}, and you'd rewrite it to `tmp.0 = x < c`. On the second trip round the loop `x` is 5, so that is a real bug. At the fixpoint, nothing reaches B1 or B3, and the only rewrite is in B0: `y = x` becomes `y = 3`.

Now round 2 of the pipeline. The universe is {x=3, y=3, x=5}. This time `x = 5` does *not* kill `y = 3` (it doesn't mention `x`), so B1's `in` settles at {x=3, y=3} ∩ {y=3, x=5} = {y=3}. The rewrites give `tmp.0 = 3 < c` and `return 3`. After dead-store elimination (13.6) removes the three unread copies, the function is:

```
Label(loop)
tmp.0 = 3 < c
JumpIfZero(tmp.0, end)
c = c - 1
Jump(loop)
Label(end)
return 3
```

Two rounds and two passes cooperating: this is the fixpoint loop from 13.1 doing its job.

### Rewriting
Using the fact *before* each instruction:
- Replace each **read** operand `v` with `s` if a copy `v = s` is in the set. Never replace a destination.
- **Delete** a `Copy(src, dst)` if `dst = src` or `src = dst` already reaches it: `dst` already holds that value. A self-copy `x = x` can also go.
- Don't replace the operand of `GetAddress`: `&x` needs the variable itself, not its value.

### Aliasing: when other code can change a variable
A variable is **aliased** if something other than a direct TACKY write to it can change it. In a function, that's:
- every variable with **static storage duration** (11.4): globals and `static` locals. Any function you call might read or write them.
- every local whose address is taken by a `GetAddress` anywhere in the function (12.5). A pointer to it may be passed to a callee, or written through with `Store`.

So `FunCall` and `Store` must kill every copy that mentions an aliased variable. In C, `*p = 2` writes through the pointer `p`:

```c
int a = 1; int *p = &a; *p = 2; return a;
```

If the `Store` for `*p = 2` didn't kill `a = 1`, you'd rewrite `return a` to `return 1`, but the program returns 2.

### The other Unit 12 instructions
Each writes its destination, so it kills copies mentioning it: `Load` (writes `dst` from memory), `GetAddress`, `AddPtr`, `CopyFromOffset`, and the type conversions (`SignExtend`, `Truncate`, `ZeroExtend`, int↔double). `CopyToOffset` (12.9) writes *part* of a struct or array variable: kill every copy mentioning that variable.

**Types.** Two variables of different types with the same size (`int` and `unsigned`) can be connected by a plain `Copy` (recall 12.3). Substituting one for the other would change which instructions codegen picks for later uses: signed vs. unsigned division, comparison or conversion. So only add a copy to the set when its source and destination have the **same type**. A `Copy` between different types still kills like any write; it just doesn't add a fact.

## Build
**Behaviour to implement:**
- **Aliased-variable set** for a function: every static-storage variable (look them up in your symbol table) plus every variable that is the source of a `GetAddress`. Compute it once per round.
- **Reaching-copies analysis** as an instance of your 13.4 framework, configured as above. Represent a copy as a small comparable, hashable (source operand, destination variable) pair.
- **Rewrite pass:** for every block, use the per-instruction "before" facts to replace read operands and delete redundant copies. Returns the new CFG.
- **Flag:** active with `--propagate-copies` or `--optimize`. Each round is now: fold → build CFG → unreachable code → copy propagation → (13.6) → flatten.
- **Correctness:** never substitute where a copy might not hold on some path; never change what a `FunCall`, `Store` or `GetAddress` can observe; only propagate same-type copies.
- **Edge cases:** a copy inside a loop whose source is redefined later in the loop (example 2); self-copies; copies of function parameters (they are ordinary variables, written on entry); a function with no copies at all (the universe is empty).

**Suggested order:**
1. The aliased-variable set, with a unit test.
2. The transfer function on its own, tested instruction by instruction (copy, redundant copy, reverse copy, write, call with a static, store).
3. Plug it into the framework. Unit-test both worked examples, comparing per-instruction facts with the tables above.
4. The rewrite pass, then wire in the flag.
5. Run chapter 19 with `--propagate-copies`, then with all flags so far. When something fails, dump the CFG with per-instruction facts using your 13.3 debug printer.

## Common pitfalls
- Killing only copies *to* a redefined variable, not copies *from* it.
- Forgetting that calls clobber statics, or that stores clobber address-taken locals.
- Rewriting with the fact *after* an instruction (so `x = x + 1` reads the new `x`).
- Initialising blocks to ∅, which silently disables the pass inside loops.
- Replacing a destination operand, or the operand of `GetAddress`.
- Propagating a copy between `int` and `unsigned`.
