# Lesson 13.1 — What optimisers do
**Part:** 3 — Build the Compiler · **Unit:** 13 — Optimisation · **Type:** Learning · **Est. time:** 2–3 h · **Tests:** none
**Prerequisites:** lessons 8.1–12.9 (test chapters 1–18 pass); Part 2 lesson 6.6

## Overview
An optimiser rewrites a program into a *different* program that behaves the same but is smaller or faster. This lesson explains what "behaves the same" means, shows the four passes you will build in this unit working together on one TACKY function, and explains why they run in a loop. No code yet: you finish with notes and a plan.

## The lesson

### Where we are on the map
Recall the back-end map from Part 2 lesson 6.6: front end → IR → *optimisation* → code generation → register allocation → emission. Since 9.2 your compiler has gone straight from TACKY to assembly. This unit fills in the optimisation box. The optimiser is a function from one TACKY function body to another TACKY function body:

```
 C source → lex → parse → validate → TACKY ──► [ optimiser ] ──► TACKY → assembly → emit
                                              (new in Unit 13)
```

Because input and output are both TACKY, the rest of `rcc` doesn't change. With no optimisation flags the optimiser is skipped, so `rcc` must produce exactly what it produced before.

### "Same behaviour": what the compiler may change
In Python, if you write `x = 2; y = x * 3; print(y + 1)`, you would be surprised if anything other than `7` were printed. But you would not care whether the interpreter actually created a variable called `x`. That intuition is the rule for C compilers too.

A C program's **observable behaviour** is, roughly: its exit code, what it does through library calls (printing, writing files), and accesses to `volatile` objects (a C keyword for memory that hardware may change; our subset doesn't have it). Everything else is the compiler's business: which temporaries exist, which instructions run, whether a variable lives on the stack or nowhere at all.

An optimisation is **sound** if every program whose behaviour is defined behaves identically before and after it. C has **undefined behaviour** (UB): situations like signed integer overflow or dividing by zero where the C standard places no requirement on the result. UB gives a compiler freedom, but your compiler itself must never crash on a program containing it. That matters in 13.2.

### Seeing it on Godbolt
Paste this C into Godbolt (compiler: x86-64 clang). In C, `int f(void)` declares a function taking no arguments and returning an `int`:

```c
int f(void) { int x = 2; int y = x * 3; return y + 1; }
```

With `-O0` (no optimisation) you get roughly this (exact output varies by version):

```
f:
    pushq   %rbp
    movq    %rsp, %rbp
    movl    $2, -4(%rbp)           # x = 2, on the stack
    imull   $3, -4(%rbp), %eax     # eax = x * 3
    movl    %eax, -8(%rbp)         # y = eax, on the stack
    movl    -8(%rbp), %eax         # reload y
    addl    $1, %eax               # + 1
    popq    %rbp
    retq
```

With `-O1`:

```
f:
    movl    $7, %eax
    retq
```

Four separate ideas got from the first to the second:
1. **Constant folding:** computing `2 * 3` and `6 + 1` at compile time.
2. **Copy propagation:** replacing a use of `x` with `2`, because `x` was just set to `2`.
3. **Dead-store elimination:** deleting writes to `x` and `y` that nothing reads any more.
4. **Register allocation:** keeping surviving values in registers, not stack slots. That is Unit 14.

### The four passes in this unit
All four run on TACKY:

| Pass | What it removes or rewrites | What it needs |
|---|---|---|
| Constant folding (13.2) | `Unary`/`Binary` on constants; conditional jumps on constants | nothing: one instruction at a time |
| Unreachable-code elimination (13.3) | code no path reaches; useless jumps and labels | a control-flow graph (CFG) |
| Copy propagation (13.5) | after `y = x`, later reads of `y` become `x` | CFG + forward dataflow (13.4) |
| Dead-store elimination (13.6) | writes to variables never read afterwards | CFG + backward dataflow (13.4) |

Folding is *local*: it looks at one instruction and needs no context. The others are *global* (within one function): whether `y` still equals `x` at some instruction depends on every path that leads there, including round loops. That is why 13.3 and 13.4 build infrastructure first.

### Passes feed each other: a worked run
Here is `f` as TACKY. Recall 9.2: TACKY is three-address code, at most one operation per instruction, with `Copy(src, dst)` written `dst = src` below. (Your real names will be renamed, like `x.0`; plain names keep this readable.)

```
x = 2
y = x * 3
tmp.0 = y + 1
return tmp.0
```

Run the passes in the order fold → propagate → dead stores, and repeat:

```
Round 1
  fold:        nothing (y = x * 3 has a variable operand)
  propagate:   y = 2 * 3            (x = 2 reaches it, so x becomes 2)
               tmp.0 = y + 1        (unchanged: y = 2 * 3 is not a Copy)
  dead stores: delete x = 2         (nothing reads x any more)
  now:         y = 2 * 3 ; tmp.0 = y + 1 ; return tmp.0
Round 2
  fold:        y = 6
  propagate:   tmp.0 = 6 + 1
  dead stores: delete y = 6
  now:         tmp.0 = 6 + 1 ; return tmp.0
Round 3
  fold:        tmp.0 = 7
  propagate:   return 7
  dead stores: delete tmp.0 = 7
  now:         return 7
Round 4
  nothing changes → stop
```

No single pass gets there alone. What matters is not the exact order inside a round, but **repeating rounds until the function stops changing**. A state that stays the same when you apply the process again is a **fixpoint**. The loop is guaranteed to stop because each pass only ever deletes instructions or replaces an operand with a "simpler" one (a variable with a constant, a computation with a `Copy`). There are finitely many such steps available.

### Phase ordering, briefly
Real compilers such as clang and GCC run dozens of passes, and the order changes the result (the *phase-ordering problem*). This course keeps it simple: one fixed order per round, repeated to a fixpoint. That order is: fold → build CFG → unreachable code → copy propagation → dead stores → flatten back to a list.

### How the flags will work
Each pass gets a flag on `rcc`: `--fold-constants`, `--eliminate-unreachable-code`, `--propagate-copies`, `--eliminate-dead-stores`, plus `--optimize` for all four. The test suite's chapter 19 checks two things: that optimised programs still behave correctly, and that the assembly no longer contains the code that should have been optimised away. So the passes have to really work, not just be harmless.

## Check your understanding

2. If constant folding sees `x = 10 / 0`, what should it do, and why can't it simply compute an answer?

5. How do you know the "repeat until nothing changes" loop terminates?

## Common pitfalls
- Thinking an optimisation may change behaviour "a little". It may not. One wrong rewrite fails tests far from the cause.
- Treating `-O1` output as the target. Clang also inlines, picks clever instructions and much more; you only want the four ideas above.
- Planning the optimiser as one giant pass. Small independent passes are easier to test and debug.
- Forgetting that the no-flags path must produce exactly what `rcc` produced before.
