# Lesson 13.3 — Control-flow graphs
**Part:** 3 — Build the Compiler · **Unit:** 13 — Optimisation · **Type:** Builds CFG + unreachable-code elimination · **Est. time:** 6–8 h · **Tests:** ch. 19
**Prerequisites:** lessons 13.1–13.2

## Overview
A flat TACKY list hides the shape of a program: which instructions can run after which. A control-flow graph (CFG) makes that shape explicit. You'll build one, use it to delete code that can never run, and flatten it back into TACKY. Every remaining pass in this unit, and the register allocator in Unit 14, works on this graph.

## The lesson

### Basic blocks
A **basic block** is a maximal straight-line run of instructions with one way in (the top) and one way out (the bottom). If its first instruction runs, all of them run, in order. "Maximal" means you can't extend it without breaking that rule.

Where do blocks start and end? Think about where control can arrive or leave:
- A `Label` always **starts** a new block, because some jump might land there.
- A `Jump`, `JumpIfZero`, `JumpIfNotZero` or `Return` always **ends** the current block, because control may leave.
- A `FunCall` does **not** end a block. Control goes into the callee but always comes back to the next instruction, just like a Python function call returns to the line after it.

So partitioning is one walk down the list: start a new block before every `Label` and after every jump or `Return`.

### Edges, Entry and Exit
The CFG's nodes are the blocks plus two pseudo-nodes: **Entry** (where the function starts) and **Exit** (where it returns to its caller). An edge A → B means "control can go straight from the end of A to the start of B". Entry → the first block. Then look at each block's last instruction:
- `Return` → Exit.
- `Jump(L)` → the block starting with `Label(L)`.
- `JumpIfZero(_, L)` or `JumpIfNotZero(_, L)` → the block of `L` **and** the next block in order (the fall-through, when the jump isn't taken).
- Anything else → the next block in order, or Exit if it's the last block.

Each block keeps a set of **successors** (where it can go) and a set of **predecessors** (where it can come from). You'll update both whenever you delete something.

### Worked example: building a CFG
In C, `if (a) ... else ...` runs the first branch if `a` is non-zero. Take:

```c
int f(int a) { if (a) return 1; else return 2; return 3; }
```

Its TACKY (from 10.3), including the `Return(0)` your generator appends to the end of every function:

```
JumpIfZero(a, else.0)
Return(1)
Jump(end.1)
Label(else.0)
Return(2)
Label(end.1)
Return(3)
Return(0)
```

Partitioned into blocks:

```
B0: JumpIfZero(a, else.0)
B1: Return(1)
B2: Jump(end.1)              <- after a Return, so it starts a new block
B3: Label(else.0)
    Return(2)
B4: Label(end.1)
    Return(3)
B5: Return(0)                <- after a Return, so a new block
```

Edges: Entry → B0; B0 → B1 (fall-through) and B3 (taken); B1 → Exit; B2 → B4; B3 → Exit; B4 → Exit; B5 → Exit. Drawn:

```
              Entry
                |
                v
     +-----------------------+
     | B0 JumpIfZero(a,else) |
     +-----------------------+
        | fall-through    | taken
        v                 v
   +-----------+    +--------------+
   | B1 Ret(1) |    | B3 Lbl else  |
   +-----------+    |    Ret(2)    |
        |           +--------------+
        v                 |
       Exit <-------------+

   B2 Jump(end) --> B4 Lbl end; Ret(3) --> Exit
   B5 Ret(0) --> Exit
   (nothing from Entry reaches B2, B4 or B5)
```

The picture shows immediately what the flat list hid: B2, B4 and B5 can never run.

### Unreachable-code elimination
This pass has four steps, done in this order.

1. **Unreachable blocks.** Traverse from Entry along successor edges (depth-first or breadth-first, with a "visited" set, like walking a tree but without revisiting). Delete every block you never visited, and remove it from its successors' predecessor sets. Above, B2, B4 and B5 go.
2. **Useless jumps.** Walk the *remaining* blocks in order. If a block ends with a jump (conditional or not) and *every* successor is simply the next remaining block, the jump does nothing: delete it. The classic case is `Jump(L)` immediately followed by `Label(L)`.
3. **Useless labels.** If a block starts with a `Label` and its *only* predecessor is the previous remaining block (or Entry, for the first block), it's only ever reached by fall-through: delete the label.
4. **Empty blocks.** Steps 2 and 3 can leave a block with no instructions. Remove it, and connect each of its predecessors to its single successor.

For the example: after step 1 the blocks are B0, B1, B3. B0's jump has two different successors, so it stays. B3's label has predecessor B0, but the previous remaining block is B1, so it stays. Result:

```
JumpIfZero(a, else.0)
Return(1)
Label(else.0)
Return(2)
```

### Worked example: folding makes code unreachable
```c
int g(int a) { if (0) a = 5; return a; }
```
After constant folding (13.2) the TACKY is:

```
Jump(end.0)              <- was JumpIfZero(0, end.0)
a = 5
Label(end.0)
Return(a)
Return(0)
```

Blocks and edges, then each step:

```
B0: Jump(end.0)                Entry -> B0 -> B2 -> Exit
B1: a = 5                      B1 -> B2          (no predecessors)
B2: Label(end.0); Return(a)    B3 -> Exit        (no predecessors)
B3: Return(0)

step 1  delete B1, B3          B2.preds = {B0}
step 2  B0 ends in Jump, its only successor B2 is next  -> delete the Jump; B0 is now empty
step 3  B2 starts with a Label, only pred B0 is previous -> delete the Label
step 4  B0 empty -> remove it, connect Entry -> B2
result  Return(a)
```

Order matters: in step 1 `B1` was between B0 and B2, so if you'd checked useless jumps first, `Jump(end.0)` would have looked necessary. That's why step 2 uses the order of blocks that *still exist*.

### Representing a graph in Rust
In Python you might give each block a list of other block objects. In Rust, blocks that hold references to each other fight the borrow checker, and `Rc<RefCell<…>>` cycles (4.4) are painful and leak. The usual Rust answer is an **arena**: store blocks in a `Vec` (or an ordered map keyed by block ID) and refer to blocks by **index**. Predecessors and successors are then sets of small IDs, which are `Copy` and never dangle. An enum for node IDs with variants for Entry, a numbered block, and Exit lets the pseudo-nodes exist without fake blocks. Deleting a block means removing its entry and its ID from neighbours' sets, not freeing memory anyone points at.

Make the CFG generic over the instruction type, so Unit 14 can build one over assembly instructions. Also leave room in each block for a fact per instruction: 13.4 needs it.

### Flattening back
To go from CFG to TACKY, concatenate the remaining blocks' instructions **in their original order**. Order matters because fall-through edges mean "the next block in the list"; shuffling blocks would change where conditional jumps fall through to.

## Build
**Behaviour to implement:**
- **CFG type**, generic over instructions: blocks with their instructions, predecessor set and successor set; successor set for Entry and predecessor set for Exit; space for per-instruction annotations later.
- **TACKY → CFG**: partition as above. Build a map from label name to block ID in a first pass, then add edges in a second.
- **CFG → TACKY**: concatenate surviving blocks in original order.
- **Unreachable-code pass** (on with `--eliminate-unreachable-code` or `--optimize`): the four steps, keeping both edge sets consistent after every deletion.
- **Pipeline**: each round is now fold (if on) → build CFG → unreachable-code elimination (if on) → (13.5, 13.6 later) → flatten.
- **Edge cases**: a body that is only `Return`; a jump to the immediately following label; a label nothing jumps to; a loop (a block that is its own successor, or a cycle); a conditional jump whose target is the next block.

**Suggested order:**
1. Partitioning, with unit tests: count blocks for small lists, including back-to-back labels and `Return` followed by more code.
2. Edges for each kind of last instruction, with tests. Write a debug printer that shows each block and its edges (as text, or Graphviz `dot`) and use it constantly.
3. Flattening. Test that building then flattening with no pass in between returns the original list exactly; run the whole suite with `--eliminate-unreachable-code` wired to "build and flatten only".
4. Each of the four steps, one at a time, each with a test (the two worked examples above make good tests).
5. Run chapter 19 with `--eliminate-unreachable-code`, then together with `--fold-constants`.

## Check your understanding
1. Why does a `Label` start a block, while a `FunCall` doesn't end one?
2. What are the successors of a block ending in `JumpIfNotZero(x, L)`? Ending in a `Copy`?
3. Why must useless-jump removal run after unreachable-block removal? Use the `g` example.
4. A label is targeted only by a jump in a block you just deleted. Is the label still useful?
5. What would go wrong with predecessors stored as `Rc<RefCell<Block>>`? What do indices give up in exchange?
6. Why must flattening keep the original block order?

## Common pitfalls
- Forgetting the fall-through edge of conditional jumps.
- Deleting a block but leaving its ID in another block's predecessor set, so a label later looks "still targeted".
- Deleting a label that a surviving jump still targets.
- Checking "next block" against the original numbering instead of the blocks that still exist.
- Forgetting that `Return` ends a block (harmful), or ending blocks at `FunCall` (harmless but wasteful).
