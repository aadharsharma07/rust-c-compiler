# Lesson 13.4 — Dataflow analysis
**Part:** 3 — Build the Compiler · **Unit:** 13 — Optimisation · **Type:** Builds dataflow framework · **Est. time:** 6–10 h · **Tests:** ch. 19
**Prerequisites:** lessons 13.1–13.3

## Overview
Copy propagation and dead-store elimination both need facts about *all paths* through a function, and loops make those facts depend on themselves. Dataflow analysis is the standard way out: start with a guess and iterate until nothing changes. You'll learn the four ingredients of an analysis, run the worklist algorithm by hand to a fixpoint, and build one reusable framework that 13.5, 13.6 and Unit 14 all plug into.

## The lesson

### The problem: circular facts
Optimisations need facts like "on *every* path to this instruction, `y` holds a copy of `x`" (13.5) or "on *some* path from here, `t` is read again" (13.6). The fact at a point depends on the facts at its neighbours in the CFG (13.3). In a straight line that's easy: compute top to bottom. But a loop's header block depends on the end of the loop body, which depends on the header. You can't compute either first.

The trick is the same one you'd use in Python to find, say, the set of everything reachable in a graph: start with an initial guess, recompute each node from its neighbours, and repeat until a full pass changes nothing. That stable state is a **fixpoint** (13.1).

### The four ingredients
Every dataflow analysis is described by four choices.

1. **Direction.** *Forward* analyses ask "what has happened before this point?": facts flow from Entry along edges. *Backward* analyses ask "what will happen after this point?": facts flow from Exit against the edges.
2. **Domain.** What a fact is. In this unit, always a *set*: a set of copies (13.5) or a set of variables (13.6). The **universe** is the set of all possible elements, for example every variable in the function.
3. **Meet.** How facts from several edges combine where paths join. **Intersection (∩)** for *must* analyses: an element survives only if it's true on *all* incoming paths. **Union (∪)** for *may* analyses: it survives if it's true on *some* path.
4. **Transfer function.** How one instruction changes the fact. Typically: remove the elements the instruction invalidates (its **kill** set), then add the ones it creates (its **gen** set): `out = gen ∪ (in − kill)`.

### Block equations
For a **forward** analysis, for each block B:
- `in[B]` = meet of `out[P]` over every predecessor P. If P is Entry, use the **boundary** fact (what's true at the start of the function).
- `out[B]` = apply each instruction's transfer function, first to last, starting from `in[B]`.

For a **backward** analysis, mirror everything:
- `out[B]` = meet of `in[S]` over every successor S, using the boundary fact for Exit.
- `in[B]` = apply the transfer functions from the *last* instruction to the *first*, starting from `out[B]`.

Entry and Exit are boundary conditions, not blocks: you never run a transfer on them.

### The worklist algorithm
1. **Initialise** every block's output fact (forward: `out[B]`; backward: `in[B]`) to the meet's **identity**: the value that doesn't change anything when you meet with it. For ∩ that's the full universe (`X ∩ everything = X`); for ∪ it's the empty set (`X ∪ ∅ = X`). Intuition: a block you haven't processed yet "doesn't get a vote" at a join.
2. Put every block on a **worklist** (a queue of blocks still to process). Any order gives the right answer; processing in roughly program order (forward) or reverse order (backward) is faster.
3. Pop a block. Recompute its incoming fact with the meet, run the transfer, store the new outgoing fact, and record the fact at every instruction along the way.
4. If the outgoing fact **changed**, push the blocks that read it: successors for forward, predecessors for backward. Skip any already on the list.
5. When the worklist is empty, you're at a fixpoint.

**Why it stops.** Transfer functions here are **monotone**: give them a bigger input and they never give a smaller output. Starting from the meet's identity, each block's fact can only move one way (shrink for ∩, grow for ∪), and a set over a finite universe can only shrink or grow a finite number of times. So each block changes a bounded number of times, and so the worklist eventually empties.

### Worked example: a forward, must analysis, step by step
A toy analysis: **"definitely assigned"**, the set of variables that have been written on *every* path to this point. Forward; meet = ∩; boundary at Entry = ∅; transfer for an instruction that writes `v`: `out = in ∪ {v}`. Universe = {x, y} (`c` is a parameter; ignore it).

```
B0: x = 1                  preds: Entry      succs: B1
B1: Label(loop)            preds: B0, B2     succs: B2, B3
    JumpIfZero(c, end)
B2: y = 2                  preds: B1         succs: B1      <- back edge
    Jump(loop)
B3: Label(end)             preds: B1         succs: Exit
    return x
```

```
        Entry
          |
          v
      +-------+
      |B0 x=1 |
      +-------+
          |
          v
      +-------+  taken  +-------+
 +--->|B1 loop|-------->|B3 end |---> Exit
 |    +-------+         +-------+
 |        | fall-through
 |        v
 |    +-------+
 +----|B2 y=2 |
      +-------+
```

Initialise all `out` to the universe {x, y}. Worklist: B0, B1, B2, B3.

| Step | Pop | in = meet of predecessors' out | out | Changed? | Worklist after |
|---|---|---|---|---|---|
| 1 | B0 | Entry boundary = ∅ | {x} | yes ({x,y} → {x}) | B1 B2 B3 |
| 2 | B1 | out[B0] ∩ out[B2] = {x} ∩ {x,y} = {x} | {x} | yes | B2 B3 |
| 3 | B2 | out[B1] = {x} | {x,y} | no | B3 |
| 4 | B3 | out[B1] = {x} | {x} | yes (successor is Exit: push nothing) | (empty) |

Fixpoint. At `return x`, `x` is definitely assigned; `y` isn't, because one path skips the loop body. That's right.

### What a bad initial value does
Now initialise every `out` to ∅ instead:

| Step | Pop | in | out | Changed? | Worklist after |
|---|---|---|---|---|---|
| 1 | B0 | ∅ | {x} | yes | B1 B2 B3 |
| 2 | B1 | {x} ∩ ∅ = ∅ | ∅ | no | B2 B3 |
| 3 | B2 | ∅ | {y} | yes | B3 B1 |
| 4 | B3 | ∅ | ∅ | no | B1 |
| 5 | B1 | {x} ∩ {y} = ∅ | ∅ | no | (empty) |

It settles on "`x` is *not* definitely assigned at `return x`". That's safe (claiming less is never wrong) but needlessly weak: the bad starting value went round the loop and fed itself. For copy propagation, this mistake silently disables the pass inside every loop.

### Facts per instruction, not just per block
The passes rewrite individual instructions, so they need the fact *at each instruction*, not just at block boundaries. In the example, inside B2 the fact before `y = 2` is {x} and before `Jump(loop)` is {x, y}. Record these during step 3 of the algorithm: for forward analyses, the fact *before* each instruction; for backward analyses, the fact *after* each instruction (because that's what you compute as you walk upwards). The final recorded values are the ones from the last time each block was processed.

### Designing it in Rust
One algorithm, many analyses: 13.5 is forward with ∩, 13.6 is backward with ∪, Unit 14 is backward over *assembly*. So the framework should take the varying parts as parameters: direction, boundary fact, initial fact, meet, and per-instruction transfer. Two Rust tools fit. A **trait** (4.1) describing an analysis, possibly with an **associated type** for the fact, which looks like this in an unrelated toy:

```rust
trait Shape { type Unit; fn area(&self) -> Self::Unit; }
```

Or **closures** (4.3) passed in, like Python passing `key=lambda ...` to `sorted`. Sketch both on paper before choosing. For the worklist, `std::collections::VecDeque` is a queue; pair it with a set recording what's already queued.

## Build
**Behaviour to implement:** a generic dataflow framework over your 13.3 CFG.
- **Inputs:** a CFG; a direction; the boundary fact (for Entry when forward, Exit when backward); the initial fact for blocks; a meet over two facts; a transfer function for one instruction.
- **Outputs:** for each block, the facts at its start and end; for each instruction, the fact just before it (forward) or just after it (backward), keyed by block ID and instruction index.
- **Algorithm:** the worklist above. A block is never queued twice at once. Entry and Exit are never transferred.
- **Facts:** sets with cheap union, intersection and equality. A `BTreeSet` is fine.
- **Generic over the instruction type**, so Unit 14 can reuse it on assembly.
- **No new flag.** Chapter 19 must keep passing for the flags you already support.

**Suggested order:**
1. Write the "definitely assigned" analysis and the example above as a unit test, checking every block's in/out and the per-instruction facts against the first table.
2. Implement the forward direction until that test passes. Add tests for a diamond (an `if`/`else` that joins) and a straight line.
3. Add the backward direction. Test it with a toy "is this variable read later on some path?" analysis (backward, ∪, boundary ∅; an instruction that reads `v` adds it) on the same loop. Fill in the table by hand first.
4. Test a block with no predecessors. (Unreachable-code elimination normally removes these; with ∩, meeting over zero predecessors gives the initial "everything", which is fine for code that never runs.)
5. Re-run chapter 19 with the existing flags.

## Check your understanding
1. Why is "definitely assigned" a must analysis, and why does that mean meet = intersection?
2. What should block facts start as for a ∩ analysis, and what goes wrong if you start them at ∅?
3. When a block's output changes, which blocks are revisited in a forward analysis? In a backward one?
4. Why do the passes need facts per instruction, not only per block?
5. What property of the transfer function guarantees the worklist empties?
6. How does your design let 13.5 and 13.6 use different directions, meets and transfers without copying the algorithm?

## Common pitfalls
- Initialising a ∩ analysis to ∅: facts get stuck too small, especially in loops.
- Running the transfer on Entry or Exit as if they were blocks.
- Revisiting the wrong neighbours for the direction (successors vs. predecessors).
- Recording only per-block facts, then recomputing per-instruction facts ad hoc in each pass, often in the wrong order for backward analyses.
- Hard-coding TACKY instructions into the framework, so Unit 14 can't reuse it.
