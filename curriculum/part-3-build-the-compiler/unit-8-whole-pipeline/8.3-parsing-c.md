# Lesson 8.3 — Parsing C
**Part:** 3 — Build the Compiler · **Unit:** 8 — The Whole Pipeline for `return 2;` · **Type:** Builds AST + parser · **Est. time:** 5–8 h · **Tests:** ch. 1 (`--stage parse`)
**Prerequisites:** lessons 5.3, 5.4, 7.2, 8.2

## Overview
You design `rcc`'s abstract syntax tree (AST) and write a recursive-descent parser that builds it from the tokens of
lesson 8.2, rejecting every malformed program with a clear error. The grammar is tiny, so the interesting part is
design: an AST shaped to *grow* (it will gain dozens of node kinds over the course), precise error messages, and a
parser structure you will extend in every unit from here on. At the end, `--parse` works.

## The lesson

### The chapter-1 grammar
Quoted strings are terminals (tokens); names in angle brackets are non-terminals (lesson 5.3):

```
<program>    ::= <function>
<function>   ::= "int" <identifier> "(" "void" ")" "{" <statement> "}"
<statement>  ::= "return" <exp> ";"
<exp>        ::= <int>
<identifier> ::= an Identifier token
<int>        ::= a Constant token
```

This little grammar pins a lot down: a program is exactly one function; it returns `int`, takes `void`, and its body is
exactly one `return` statement whose expression is a constant. Every rule is a fixed **sequence**; there are no
alternatives (no `|`) yet. Alternatives arrive in Unit 9, when an expression can be a constant *or* a negation *or*…

### Concrete syntax vs. abstract syntax
Recall from lesson 5.4: the *concrete* syntax is every token as written; the *abstract* syntax keeps only what later
stages need. The parentheses, braces, `int`, `void` and `;` guided the parser to the right structure, but carry no
further meaning: every chapter-1 function returns `int` and takes no parameters, so storing that would tell later
stages nothing. Here is the AST in a compact notation (similar to ASDL, the notation Python uses to describe its own
`ast` module):

```
program             = Program(function_definition)
function_definition = Function(identifier name, statement body)
statement           = Return(exp)
exp                 = Constant(int)
```

Read `Function(identifier name, statement body)` as "a function definition has a field `name` that is an identifier
and a field `body` that is a statement". Compare Python: `ast.dump(ast.parse("return 2"))` shows a `Return` node with a
`value=Constant(value=2)` child, and no trace of the keyword itself. Same idea.

The AST is **not** a mirror of the grammar, and it will diverge more over time. For example, in Unit 9, `(2)` and `2`
will parse to the identical tree: parentheses never become nodes.

### Turning the notation into Rust types
Each line of the notation becomes a type. The rule of thumb:

- a node with **exactly one form** and named fields → a **struct** (program, function definition);
- a node that **will have several forms** → an **enum**, even if it has only one variant today (statement,
  expression).

Why make `Statement` an enum with a single `Return` variant? Because Unit 10 adds `if`, loops, declarations and more,
and Unit 9 adds new expression kinds. If they are enums from day one, adding a form means adding a variant, and
`rustc` then points at every `match` that must handle it. If you start with a struct, you will rewrite every use site.

Derive `Debug`, `Clone` and `PartialEq` on every AST type. `PartialEq` lets tests compare whole trees with
`assert_eq!`; `Debug` gives you a free dump with `{:#?}` (pretty-printed, indented), which you will use constantly.

For the function name, the same owned-vs-borrowed choice from lesson 8.2 appears again: a `String` is simplest; a
borrowed `&str` means the AST, too, carries a lifetime and cannot outlive the source text. Most people choose `String`
in the AST even when tokens borrow: the AST is passed through many later stages, and lifetimes on every pass get
tiresome.

### Recursive descent for sequences
As in lesson 7.2, the parser is a struct holding the tokens and a cursor, with one method per non-terminal returning
`Result<Node, ParseError>`, and a few helpers:

- **peek** at the current token (an `Option`, since there may be none);
- **advance** past it;
- **expect** a specific token kind: advance if it matches, otherwise return an error naming what was expected and what
  was found (or "end of input").

With those, parsing a **sequence** rule is reading the rule left to right: parse_function expects `int`, then parses
an identifier (a token of kind Identifier, whose name it keeps), then expects `(`, `void`, `)` and `{`, calls
parse_statement, expects `}`, and builds the function node. parse_statement expects `return`, calls parse_exp,
expects `;`. parse_exp takes a Constant token or fails. The code reads almost exactly like the grammar, which is the
whole charm of recursive descent.

`expect` compares token *kinds*. For dataless tokens like `OpenParen` that is plain equality. For tokens that carry
data (Identifier, Constant) you can't use `expect` with a fixed value, since you don't know the name in advance; match
on the variant instead and extract its data. (`std::mem::discriminant` is another way to compare variants while
ignoring their data.)

### Worked example
Tokens `Int Identifier("main") OpenParen Void CloseParen OpenBrace Return Constant(2) Semicolon CloseBrace` parse to:

```
Program(
    Function(
        name = "main",
        body = Return(
            Constant(2))))
```

Step by step: parse_program calls parse_function. It expects `Int` ✓ (cursor 1), takes `Identifier("main")` (cursor
2), expects `(` `void` `)` `{` ✓ (cursor 6), calls parse_statement, which expects `Return` ✓, calls parse_exp, which
takes `Constant(2)`, then expects `;` ✓ (cursor 9). Back in parse_function, expect `}` ✓ (cursor 10). parse_program
then checks that the cursor is at the end: it is, so the parse succeeds.

### End of input, and why it matters
After parse_program, **no tokens may remain**. `int main(void) { return 2; } foo` begins with a perfectly valid
program, and a parser that stops there would accept it. Chapter 1 has a test for exactly this "extra junk" case.

### What the parser must reject
Every one of these lexes fine (lesson 8.2) but must fail to parse:

| Input (inside or around `int main(void) { … }`) | What the parser sees |
|---|---|
| `return 2` (no `;`) | expected `;`, found `}` |
| `return;` | expected a constant, found `;` |
| `RETURN 2;` or `returm 2;` | expected `return`, found identifier |
| `retur n 2;` | expected `return`, found identifier `retur` |
| `return int;` | expected a constant, found keyword `int` |
| `int main(void) { return 2;` | expected `}`, found end of input |
| `int main(void { return 2; }` | expected `)`, found `{` |
| `main(void) { return 2; }` | expected `int`, found identifier |
| `int 3(void) { return 2; }` | expected an identifier, found a constant |
| `… return 2; } foo` | extra tokens after the program |

Return an `Err` the moment something is wrong; don't invent a placeholder node and carry on. Index the token list with
`get`, never `tokens[i]`, so running off the end becomes "unexpected end of input" instead of a panic.

### Errors worth reading
Design `ParseError` so its message says **what was expected and what was found**, and where (if your tokens carry
positions). For `int main(void) { return 2 }` that might be `error: expected ';' but found '}' at line 1,
column 27`. To print tokens nicely in such messages, give
your token type a `Display` impl that prints the lexeme (`;` rather than `Semicolon`).

## Build
1. **AST module.** Create an `ast` module: structs for program and function definition, enums for statement and
   expression. Derive `Debug, Clone, PartialEq`. Store the function name as you decided.
2. **Error type.** `ParseError` covering "expected X, found Y", "unexpected end of input" and "extra tokens after the
   program", with a `Display` impl.
3. **Parser module.** A public entry point: tokens in, `Result<Program, ParseError>` out. Inside: a parser struct,
   peek/advance/expect helpers, and one method per non-terminal, written in the order exp → statement → function →
   program, with tests at each step.
4. **End check.** After parsing the program, fail if any token remains.
5. **Driver.** `--parse` now lexes and parses, then stops: exit 0 for valid input, non-zero (with the error on stderr)
   for invalid input. Later stages remain stubbed.
6. **AST dump.** Make it easy to see the tree: print `{:#?}` behind a debug flag of your own (for example
   `--print-ast`), or at least in a test. You will rely on it in every later unit.
7. **Unit tests:** the worked example (compare the whole AST); the same program with different whitespace; and at least
   six invalid token sequences from the table above, each asserting the specific error variant.
8. **Run the test suite:** `./test_compiler ./target/debug/rcc --chapter 1 --stage parse`.

## Common pitfalls
- No end-of-input check: the "extra junk" test catches you.
- Returning placeholder nodes on error instead of `Err`.
- Mirroring concrete syntax in the AST (nodes for `int`, `void` or the braces).
- Indexing past the end of the token list and panicking.
- Holding a reference to a token while calling a `&mut self` method; return a clone (tokens are cheap) or extract the
  data you need first.
- Using structs where the node will grow new forms, and rewriting them in Unit 9 or 10.
