# Lesson 8.2 — Lexing C
**Part:** 3 — Build the Compiler · **Unit:** 8 — The Whole Pipeline for `return 2;` · **Type:** Builds C lexer · **Est. time:** 4–6 h · **Tests:** ch. 1 (`--stage lex`)
**Prerequisites:** lessons 4.5, 5.2, 7.1, 8.1

## Overview
You write `rcc`'s lexer: preprocessed C source in, a list of tokens (or a lexical error) out. The machinery is the
one you built for the calculator in lesson 7.1, but C brings three new ideas: **identifiers**, **keywords** that look
like identifiers, and a **word-boundary** rule that makes `1foo` an error. You also decide whether tokens own their
text or borrow it, which is your first real design use of lifetimes. At the end, `--lex` works and the first slice of
chapter 1 passes.

## The lesson

### What the lexer receives
The driver gives the lexer the contents of the `.i` file: C after preprocessing. The preprocessor has already removed
comments and, thanks to `-P`, there are no `#` line markers. What is left is plain text: words, numbers, punctuation
and whitespace. Here is the whole of chapter 1's language, written three equally valid ways:

```c
int main(void) { return 2; }
```
```c
int main(void){return 2;}
```
```c
int
main ( void )
{
    return 2 ;
}
```

A quick C reading for this program: `int` says what type of value the function returns (an integer); `main` is the
function's name; `(void)` says it takes no parameters; the braces `{ }` hold the function's body; `return 2;` ends the
function and hands back the value 2; every statement ends with `;`. For `main`, that returned value becomes the
program's exit status, which you will check with `echo $?`.

### The tokens of chapter 1

| Kind | Rule (informal) | Regular expression (lesson 5.2) | Examples |
|---|---|---|---|
| Identifier | a letter or `_`, then letters, digits or `_` | `[a-zA-Z_]\w*\b` | `main`, `_x1`, `returnValue` |
| Constant | one or more digits, at a word boundary | `[0-9]+\b` | `2`, `100`, `007` |
| Keyword | an identifier whose text is reserved | `int\b`, `void\b`, `return\b` | `int`, `void`, `return` |
| Punctuation | single characters | `\(` `\)` `\{` `\}` `;` | `(` `)` `{` `}` `;` |

`\w` means "letter, digit or underscore" and `\b` means "a word boundary": the position between a word character and
a non-word character (or the end of input). Whitespace (space, tab, newline, carriage return) separates tokens and is
discarded. Any other character, such as `@`, `$`, `` ` `` or `\`, is a lexical error.

### Keywords: match the word first, then look it up
How should the lexer decide between the keyword `return` and an identifier like `returnValue` or `result`? The
fragile way is to check "does the input start with `return`?" That lexes `returnValue` as `return` + `Value`. The
robust way follows longest match: lex the **entire** identifier first (letters, digits, underscores until something
else), and only then ask "is this exact text a keyword?" If yes, emit the keyword token; if no, emit an identifier.
`int1` is therefore the identifier `int1`, and `RETURN` is an identifier too, because C keywords are case-sensitive.

### The word-boundary rule
In the calculator, `1a` lexed as `Number(1)` and then failed at `a` because `a` was an unknown character. In C, `a` is
a perfectly good start of an identifier, so a naive lexer would turn `1foo` into `Constant(1) Identifier(foo)`. C says
no: a constant must end at a word boundary, so `1foo` is a single malformed token and a lexical error. (In real C it is
an invalid "preprocessing number".) Chapter 1's invalid-lex tests check exactly this. In a hand-written lexer, the rule
becomes: after the digit run ends, peek once more; if the next character is a letter, digit or `_`, report an error.

Contrast `foo1`: it starts with a letter, so the identifier rule consumes all of it. Order of dispatch is decided by
the *first* character, so the two never compete.

### Worked examples
`int main(void) { return 2; }` becomes ten tokens:

```
Int  Identifier("main")  OpenParen  Void  CloseParen  OpenBrace
Return  Constant(2)  Semicolon  CloseBrace
```

| Input | Result | Why |
|---|---|---|
| `int main(void) { return 0@; }` | error at `@` | not part of any token |
| `return 1foo;` | error at `1foo` | constant not followed by a word boundary |
| `int main(void) { RETURN 2; }` | lexes fine: `RETURN` is an identifier | the **parser** will reject it (lesson 8.3) |
| `int main(void) { retur n 2; }` | lexes fine: two identifiers | also a parse error, not a lex error |
| *(empty file)* | empty list | the parser will reject it |

A useful rule of thumb: the lexer rejects text that is not made of valid tokens; the parser rejects valid tokens in a
nonsensical order.

### Two ways to build the lexer
- **Hand-written** (like lesson 7.1): walk the characters with a peekable iterator (or a byte index), dispatch on the
  first character, and consume the longest valid token. No dependencies, fast, and it teaches you more Rust.
- **Regex-driven**: keep a list of (token kind, regular expression) pairs; at the current position, try each one
  anchored to the start (`^`), take the longest match, and on a tie prefer keywords over identifiers. This needs the
  `regex` crate and is closer to the formal description in lesson 5.2.

Either passes the tests. The hand-written one is recommended because you already know its shape; you only add the
identifier branch, the keyword lookup and the boundary check.

### Owned or borrowed text?
An identifier token must carry its name. Two designs:

- **Owned**: the token holds a `String`, a copy of the name. Simple, and the tokens live independently of the source.
- **Borrowed**: the token holds a `&str` slice pointing *into* the source text. No copying, but the tokens must not
  outlive the source. Rust expresses this with a lifetime parameter (lesson 4.5):

```
 source: "int main(void) { return 2; }"      (a String owned by the driver)
              ▲▲▲▲
 tokens: [Int, Identifier(&source[4..8]), OpenParen, …]   each slice borrows from source
```

A token type declared like `Token<'a>` with a variant holding `&'a str` reads "an identifier token cannot outlive the
text it points into". The lifetime does not make anything live longer; it lets `rustc` check that the driver keeps the
source around while tokens exist. Both designs are fine for this course. Borrowed is a good, contained first contact
with lifetimes in a real program; owned is less friction later, when the AST stores names. Choose one and be able to
justify it.

For constants, you can convert the digits to a number now, or keep the text and convert in the parser. Converting now
means the lexer must decide what to do with a constant too big for its integer type; keeping the text pushes that
decision later, where type information will exist (Unit 12). Either is acceptable for chapter 1.

### Positions
Chapter 1 does not require positions, but `error: unexpected character '@' at line 3, column 9` will save you hours
compared with `error: bad token`. The cheapest approach is to store the byte offset (as in the calculator) and compute
the line and column only when printing an error, by counting newlines before that offset.

## Build
1. **Token type.** In a `lexer` module (or a separate `token` module), define an enum with one variant per kind:
   identifiers and constants carry data; the three keywords and five punctuation marks are dataless. Derive `Debug`,
   `Clone`, `PartialEq`. Decide owned vs. borrowed, and where positions live (a wrapper struct, as in lesson 7.1, works
   well).
2. **Error type.** An enum carrying the offending character or text and its position, with a `Display` impl.
3. **Lexer entry point.** One public function: source text in, `Result` of a token list or a lexical error out.
   Implement in this order, testing as you go: whitespace; the five punctuation marks; identifiers; keyword lookup;
   constants; the word-boundary check; everything else is an error.
4. **Driver.** Replace the lex part of the stub: the compile step now lexes. With `--lex`, stop after lexing and exit
   0. On a lexical error, print it to stderr and exit non-zero. Later stages stay stubbed.
5. **Unit tests** (`#[cfg(test)]`): the worked example; the same program with no spaces and with tabs and newlines;
   `1foo` and `123abc` (errors); `foo1`, `int1`, `returnValue`, `_x` (identifiers); `RETURN` (identifier); `@`, `$`,
   `` ` ``, `\` (errors); an empty file.
6. **Run the test suite:** `./test_compiler ./target/debug/rcc --chapter 1 --stage lex`. Every valid program must lex
   and every invalid-lex program must fail. (Invalid-parse programs are expected to *pass* lexing at this stage.)

## Check your understanding
1. Give the token stream for `int main(void){return 42;}`.
2. Why is `1foo` an error while `foo1` is an identifier? Where in your code is that difference decided?
3. What goes wrong if you check for keywords by prefix before lexing the whole identifier? Give an input that breaks.
4. If your tokens borrow from the source, who owns the source, and what would `rustc` say if the driver dropped it
   while the tokens were still in use?
5. Sort these chapter-1 failures into lexer errors and parser errors: `0@`, `RETURN 2;`, `return 2` (no `;`), `1foo`,
   `int main(void) { return 2; } foo`.

## Common pitfalls
- Matching keywords by prefix, so `returnValue` becomes `return` + `Value`.
- Lexing `1foo` as two tokens: the most common chapter-1 lex failure.
- Forgetting `\t` and `\r` as whitespace (the tests include tab-indented files, and handling `\r` costs nothing).
- Slicing a `&str` by character count instead of byte offset.
- A loop branch that neither consumes input nor returns, hanging on the first unknown character.
- Rejecting `RETURN` or `retur n` in the lexer: they are made of valid tokens, so the parser must reject them.
