# Lesson 8.4 — Assembly generation
**Part:** 3 — Build the Compiler · **Unit:** 8 — The Whole Pipeline for `return 2;` · **Type:** Builds assembly AST + codegen · **Est. time:** 2–3 h · **Tests:** ch. 1 (`--stage codegen`)
**Prerequisites:** lessons 6.3, 6.4, 8.3

## Overview
You build the first back-end stage: a typed representation of x86-64 assembly (an **assembly AST**) and a pass that
converts the C AST into it. Nothing is printed yet; that is lesson 8.5. Splitting "decide which instructions" from
"spell them as text" looks like overkill for two instructions, but it is the decision that makes Units 9–14 possible,
because every later back-end pass rewrites this structure. At the end, `--codegen` works.

## The lesson

### What the program must do at machine level
Recall lessons 6.3 and 6.4. Under the System V calling convention, a function returns an integer by leaving it in the
`%rax` register; for a 32-bit `int`, the lower half, `%eax`. Then `ret` pops the return address off the stack and jumps
back to the caller. For `main`, the caller is the C runtime's start-up code, which passes `main`'s return value to
`exit`, so it becomes the process's exit status. So `return 2;` needs exactly two instructions:

```
movl  $2, %eax     # copy the immediate value 2 into %eax  (AT&T: source, destination; l = 32-bit "long" word)
ret                # return to the caller
```

### Why not print text straight from the C AST?
For `return 2;` you could walk the C AST and print those two lines directly. It would work today and hurt from Unit 9
on, because the back end needs to **inspect and rewrite** instructions after choosing them:

- Unit 9 generates instructions that use *pseudoregisters* (unlimited temporary names), then a later pass replaces
  each one with a stack slot, and another pass fixes instructions that x86-64 doesn't allow (such as a `mov` with
  memory on both sides).
- Unit 14 adds a graph-colouring register allocator that maps pseudoregisters to real registers, using stack slots
  only when it runs out.

Those are transformations of data. On a typed structure they are a `match` per instruction. On strings, they would
mean parsing your own output back, which is miserable and fragile. A typed structure also lets `rustc` stop you from
building nonsense, such as a `Mov` with one operand.

### Levels of representation
Each stage of `rcc` turns one representation into another, each closer to the machine:

```
C source ──lex──► tokens ──parse──► C AST ──codegen──► assembly AST ──emit──► assembly text
                                         (Unit 9 inserts TACKY here: C AST → TACKY → assembly AST)
```

The assembly AST is a near one-to-one model of the instructions you will emit, but it is still structured data.

### The chapter-1 assembly AST
In the same notation as lesson 8.3 (`instruction*` means "a list of zero or more instructions"):

```
program             = Program(function_definition)
function_definition = Function(identifier name, instruction* instructions)
instruction         = Mov(operand src, operand dst) | Ret
operand             = Imm(int) | Register
```

- `Imm(int)` is an **immediate**: a constant written directly in the instruction (printed `$2`).
- `Register` carries no data yet, because the only register you need is `%eax`. In Unit 9 it becomes a choice of
  specific registers; keep it an enum variant so that change is local.
- `Mov` and `Ret` are an enum because the instruction set will grow to dozens of forms.

As with the C AST, program and function definition become structs; instruction and operand become enums. Derive
`Debug`, `Clone` and `PartialEq` so tests can compare instruction lists.

**Naming collisions.** Both ASTs have a `Program` and a `Function`. Don't invent awkward names like `AsmProgram`;
put each AST in its own module and refer to them as `ast::Program` and `asm::Program`. That is what modules are for.

### The lowering rules
**Lowering** means translating to a lower-level representation. Chapter 1 needs one rule per C AST node:

| C AST node | Assembly AST |
|---|---|
| `Program(f)` | `Program(lower(f))` |
| `Function(name, body)` | `Function(name, lower(body))` |
| `Return(exp)` | `[Mov(lower(exp), Register), Ret]` |
| `Constant(n)` | `Imm(n)` |

The pass is a set of recursive functions, one per C AST type, each with a `match` over that type's variants. Notice
that one statement became **two** instructions: lowering is one-to-many. So lowering a statement produces a *list* of
instructions (or appends to a list passed in), not a single instruction. Lowering an expression, by contrast, produces
an *operand*: the place where the value can be found.

### Worked example
`Program(Function("main", Return(Constant(2))))` lowers to:

```
Program(
    Function(
        name = "main",
        instructions = [
            Mov(Imm(2), Register),
            Ret,
        ]))
```

Lesson 8.5 prints this as `movl $2, %eax` and `ret`.

### Design decisions to make
- **Can this pass fail?** Not in chapter 1: the parser already rejected every malformed program, and every valid AST
  lowers. So the entry point can return an assembly program directly rather than a `Result`. Later passes that *can*
  fail (semantic analysis, Unit 10) come before codegen for exactly this reason.
- **Borrow or consume the C AST?** Taking `&ast::Program` leaves the C AST available (for debugging dumps, say) but means
  cloning the function name. Taking it by value lets you move the name across without cloning, but the C AST is gone
  afterwards. Either is fine; know which you chose and why.
- **No wildcard arms.** Write a `match` arm for every variant, never `_ =>`. When Unit 9 adds expression kinds, `rustc`
  will then list every place that needs a new arm. A wildcard silently swallows the new variant.
- **Platform details don't belong here.** The macOS `_main` prefix and the spelling `%eax` are *text* concerns. The
  assembly AST stores the name `main` and an abstract `Register`; only the emitter knows how to spell them.

## Build
1. **Assembly AST.** Create an `asm` (or `assembly`) module with structs for program and function definition and enums
   for instruction and operand, exactly as above. Derive `Debug, Clone, PartialEq`. Resist adding more registers or
   instructions than chapter 1 needs.
2. **Codegen module.** A public entry point: C AST program in, assembly program out. Inside, one lowering function per
   C AST type, each matching exhaustively.
3. **Driver.** `--codegen` now runs lex → parse → codegen and stops, writing no files and exiting 0. A full compile
   still uses the stub emitter until lesson 8.5.
4. **Debug output.** Extend your debug flag (or add one) to dump the assembly AST with `{:#?}`.
5. **Unit tests:** lowering the worked example's C AST gives exactly the instruction list above; a different constant
   (say 7) gives `Imm(7)`.
6. **Run the test suite:** `./test_compiler ./target/debug/rcc --chapter 1 --stage codegen`.

## Common pitfalls
- Wildcard `_ =>` arms in matches over AST nodes: you lose `rustc`'s help when Unit 9 adds variants.
- Putting `_main` or the text `%eax` into the assembly AST instead of leaving spelling to the emitter.
- Awkward type names instead of modules to separate the two ASTs.
- Returning one instruction from statement lowering, then struggling when a statement needs two.
- Over-designing: all sixteen registers and every addressing mode before you need them.
