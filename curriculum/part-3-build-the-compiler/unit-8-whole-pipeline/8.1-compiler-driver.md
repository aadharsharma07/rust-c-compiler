# Lesson 8.1 — The compiler driver
**Part:** 3 — Build the Compiler · **Unit:** 8 — The Whole Pipeline for `return 2;` · **Type:** Builds `rcc` CLI + stage flags · **Est. time:** 3–5 h · **Tests:** none yet (manual smoke test; ch. 1 stages start passing in 8.2)
**Prerequisites:** lessons 6.5, 7.3

## Overview
You start `rcc`, the compiler you will grow for the rest of the course, with its outermost layer: the **driver**. The
driver reads the command line, runs the preprocessor, calls your compiler, then runs the assembler and linker, and
turns every failure into a non-zero exit status. For now the "compiler" in the middle is a stub that returns
hard-coded assembly, so you can prove the plumbing works before lessons 8.2–8.5 replace it piece by piece.

## The lesson

### What a driver is
Recall the toolchain from lesson 6.5. When you type `gcc prog.c`, the `gcc` program does not compile anything itself.
It is a **driver**: it runs the preprocessor, the real compiler, the assembler and the linker in turn, passing files
between them. `rcc` works the same way, except that only the middle step is yours:

```
 prog.c ──gcc -E -P──► prog.i ──rcc's compiler──► prog.s ──gcc──► prog
 (C source)            (preprocessed C)            (assembly)       (executable)
  yours to read         deleted after use           deleted unless -S
```

- `gcc -E` runs only the **preprocessor**: it expands `#include` and `#define` and strips comments. `-P` stops it from
  writing *line markers* such as `# 1 "prog.c"` into the output. Without `-P` your lexer would meet `#` lines it has
  no rule for.
- `gcc prog.s -o prog` runs the **assembler** (assembly text → machine-code object file) and the **linker** (object
  file + C runtime start-up code → executable) in one go.

On macOS, `gcc` is really `clang` under another name; that's fine, both accept these flags.

### The interface the test suite expects
The test suite (lesson 6.5) runs your binary as `rcc [one stage flag] path/to/prog.c`. The flags let it test a
compiler that is only partly written, one stage at a time:

| Invocation | Runs up to and including | Files left behind |
|---|---|---|
| `rcc --lex prog.c` | lexer | none |
| `rcc --parse prog.c` | lexer, parser | none |
| `rcc --codegen prog.c` | …, assembly generation (no emission) | none |
| `rcc -S prog.c` | …, emission | `prog.s` |
| `rcc prog.c` | everything, then assemble and link | `prog` (next to `prog.c`) |

Unit 9 adds `--tacky` (stop after generating the IR) and Unit 10 adds `--validate` (stop after semantic analysis).
Design so that a new stage costs one new enum variant, not a rewrite.

**Exit codes are the contract.** For partial stages, the test suite only checks the exit status: `0` for a valid
program, non-zero for one that should be rejected (an invalid token, a syntax error). Your error message on stderr is
for *you*; the test suite ignores it. A `panic!` also exits non-zero, but it means "bug in rcc", so return errors
instead.

### Modelling "where to stop"
In Python you might pass a string like `"lex"` around and compare it everywhere. In Rust, make it an enum with one
variant per stopping point, declared in pipeline order: lex, parse, codegen, emit-only (`-S`), full. If you derive
`PartialOrd` and `Ord` on it, Rust orders the variants by declaration order, so the driver can ask questions like "is
the requested stage at least parse?" with a plain comparison. Adding `--tacky` later then means inserting one variant
in the right place.

Argument parsing is small enough to do by hand with `std::env::args()`: skip the program name, then sort each
argument into "a flag I know", "a flag I don't know" (error), or "the input path" (exactly one allowed). Crates like
`clap` exist, but writing it yourself is half an hour and teaches you more.

### Running other programs from Rust
Python has `subprocess.run(["gcc", "-E", ...])`. Rust has `std::process::Command`, a **builder**: you create one with
the program name, add arguments, then run it. Each builder method returns the builder, so calls chain:

```rust
let status = Command::new("echo").arg("hello").status()?;
if !status.success() { /* the program ran, but reported failure */ }
```

There are **two** ways this can fail, and you must handle both:

1. `status()` returns `Err` if the program could not be started at all (for example, `gcc` is not installed).
2. It returns `Ok(status)` if the program ran, and `status.success()` is false if it exited non-zero (for example,
   the input file doesn't exist, or the assembler rejected your `.s`).

Forgetting the second check is the classic driver bug: `gcc` fails, your driver carries on, and the error surfaces
three steps later as something confusing.

### Paths, not strings
The driver derives file names: `dir/prog.c` → `dir/prog.i`, `dir/prog.s`, `dir/prog`. Doing this with string
operations breaks on names like `my.dir/prog.c` or `prog.test.c`. Use `std::path::Path` and `PathBuf` (the owned
version, like `&str` vs. `String` in lesson 2.4): `with_extension("i")` replaces only the final extension, and
`with_extension("")` removes it. Intermediate files go next to the source file, which is also where the test suite
looks for the executable.

### Cleaning up, even on failure
The `.i` file is an intermediate: delete it once the compiler has read it, **whether compilation succeeded or not**.
The `.s` file is deleted after linking unless the user asked for `-S`. Stages before `-S` write no files at all. If
you only clean up on the happy path, a run over the test suite's hundreds of invalid programs leaves hundreds of junk
files. A simple pattern: read the `.i` into a `String`, delete the file immediately, *then* compile the string.

### Platform details
Your output must be x86-64 code (lesson 6.3). Three setups from lesson 6.5:

- **Linux x86-64 (or an x86-64 Linux Docker container):** `gcc prog.s -o prog` just works.
- **Intel Mac:** the same, with the macOS spellings handled by the emitter (lesson 8.5).
- **Apple Silicon Mac:** add `-arch x86_64` to the assemble-and-link command so you get an x86-64 executable, which
  macOS runs through Rosetta (or explicitly with `arch -x86_64 ./prog`).

`cfg!(target_os = "macos")` asks "is `rcc` being compiled for macOS?". Inside Docker, `rcc` is built for Linux, so it
does the Linux thing automatically, which is exactly what you want.

### One place for errors
Follow the shape from the Rust Book's CLI chapter: `main` calls a `run` function that returns `Result<(), SomeError>`,
and `main` is the only place that prints the error to stderr and exits with status 1 (via `std::process::exit` or by
returning `std::process::ExitCode`). Everything inside uses `?`. Calling `process::exit` deep inside helper functions
skips cleanup and makes the code impossible to test.

### The stub
Until lesson 8.5, the "compile" step returns fixed assembly for `return 2`. On Linux:

```
	.globl main
main:
	movl	$2, %eax
	ret
	.section .note.GNU-stack,"",@progbits
```

On macOS, drop the last line and write `_main` in place of `main` (lesson 8.5 explains both). For the stages before
`-S`, the stub does nothing and succeeds. This lets you test the whole driver today.

## Build
Create the crate with `cargo new rcc`. The driver can live in `main.rs` or a `driver.rs` module; leave room for
`lexer`, `parser`, `codegen` and `emit` modules.

1. **Stage enum.** One variant per stopping point, in pipeline order, deriving comparison traits.
2. **Argument parsing.** Accept exactly one input path and at most one of `--lex`, `--parse`, `--codegen`, `-S`.
   Unknown flags, no path, two paths or two stage flags → a usage message on stderr and exit status 1.
3. **Error type.** One enum (or a boxed error) covering bad arguments, I/O failures, and "external command failed"
   (which command, and its status). Implement `Display` for it.
4. **Preprocess.** Run `gcc -E -P <input> -o <input>.i`; check both failure modes. Read the `.i` into a `String`, then
   delete it.
5. **Compile (stub).** A function taking the source text and the stage, returning either the assembly text (for `-S`
   and full compiles) or nothing, or an error. Return the stub assembly for your platform.
6. **Assemble and link.** For `-S`, write `<input>.s` and stop. Otherwise write the `.s`, run
   `gcc [-arch x86_64] <input>.s -o <input without extension>`, check it, then delete the `.s`.
7. **`main`.** Call `run`; on error print it to stderr and exit 1.
8. **Smoke test by hand.** Write `return_2.c` containing `int main(void) { return 2; }`. Then
   `cargo build && ./target/debug/rcc return_2.c && ./return_2; echo $?` prints `2`, and only `return_2` was created.
   Check `-S` leaves `return_2.s` and no executable; `--lex`/`--parse`/`--codegen` leave nothing; `rcc --lex missing.c`
   exits non-zero with a message.
9. **Tests.** Unit-test argument parsing (it is a pure function from a list of strings to a result) and the path
   derivations, including a directory with a dot in its name.

## Check your understanding
1. What does `-P` do in `gcc -E -P`, and what would your lexer face without it?
2. How does the test suite decide that `rcc --parse bad.c` "failed correctly"?
3. `Command::status()` returns `Result<ExitStatus, io::Error>`. Describe one situation that gives `Err` and one that
   gives `Ok` with a failed status.
4. Where exactly would `--tacky` go in your design, and what else would have to change?
5. Trace every file your driver creates and deletes for `rcc -S prog.c`, and for a failing `rcc prog.c`.

## Common pitfalls
- Ignoring the `ExitStatus`: `Ok` from `status()` only means the program *ran*.
- Leaving `.i` or `.s` files behind when compilation fails.
- Building paths by string concatenation, which breaks on dotted directory names.
- Writing output files for `--lex`, `--parse` or `--codegen`.
- Printing errors to stdout instead of stderr, or calling `process::exit` from deep inside the driver.
- On Apple Silicon, forgetting `-arch x86_64` and producing an arm64 binary from x86-64 assembly (the assembler
  rejects it).

## Done when
- [ ] `rcc prog.c` produces a runnable `prog` (from the stub) that exits with `2`, leaving no `.i` or `.s` behind.
- [ ] `rcc -S prog.c` leaves `prog.s` and no executable; `--lex`, `--parse`, `--codegen` exit 0 and write nothing.
- [ ] Bad arguments and a missing input file exit non-zero with a message on stderr.
- [ ] `cargo test` passes and `cargo clippy` is clean; `main` only calls `run` and reports errors.
- [ ] You can explain, without notes, what each toolchain step does and which flag stops where.
