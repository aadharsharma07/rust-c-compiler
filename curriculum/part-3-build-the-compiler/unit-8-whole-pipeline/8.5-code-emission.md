# Lesson 8.5 — Code emission
**Part:** 3 — Build the Compiler · **Unit:** 8 — The Whole Pipeline for `return 2;` · **Type:** Builds emitter → first executable · **Est. time:** 2–4 h · **Tests:** ch. 1
**Prerequisites:** lessons 6.3, 6.5, 8.1, 8.4

## Overview
You write the last stage of the pipeline: an emitter that prints the assembly AST as AT&T-syntax text that `gcc` (or
`clang`) can assemble. Then you replace the driver's stub, connect all five stages, and compile your first real C
program into a working executable. This lesson ends with the whole of chapter 1 passing: a complete, if tiny,
compiler.

## The lesson

### Emission is mechanical
All the decisions were made in lesson 8.4. The emitter only spells them out, and every node of the assembly AST has
exactly one textual form:

| Assembly AST node | Text |
|---|---|
| `Program(f)` | the function; then, on Linux only, `.section .note.GNU-stack,"",@progbits` |
| `Function(name, instrs)` | `.globl <symbol>`, then `<symbol>:`, then each instruction on its own line |
| `Mov(src, dst)` | `movl <src>, <dst>` |
| `Ret` | `ret` |
| `Imm(n)` | `$n` |
| `Register` | `%eax` |

where `<symbol>` is `_main` on macOS and `main` on Linux. Recall from lesson 6.3 the pieces of an assembly file:

- a **directive** starts with `.` and instructs the assembler rather than the CPU. `.globl main` says "make the symbol
  `main` visible to the linker", which is needed because the C runtime's start-up code, in another object file, calls
  it (lesson 6.5);
- a **label** like `main:` names the address of the next instruction;
- an **instruction** like `movl $2, %eax` becomes machine code.

Layout convention: labels start in column 0; directives and instructions are indented by a tab; a tab between the
mnemonic and its operands keeps columns tidy. End every line, including the last, with a newline: some assemblers
warn about a missing final newline.

### Worked example
`Program(Function("main", [Mov(Imm(2), Register), Ret]))` emits, on macOS:

```
	.globl _main
_main:
	movl	$2, %eax
	ret
```

and on Linux:

```
	.globl main
main:
	movl	$2, %eax
	ret
	.section .note.GNU-stack,"",@progbits
```

### The `$` matters
In AT&T syntax, `$2` is the *value* 2. A bare `2` as an operand means *the memory at address 2*. On Linux,
`movl 2, %eax` assembles without complaint and then, at run time, tries to read address 2, which is not mapped, and
the program crashes with a segmentation fault. (On macOS the assembler refuses it outright, with an error about 32-bit
absolute addressing.) If your executable crashes, or that error appears, check your `$` first.

### Why the platforms differ
- **The `_` prefix.** On macOS, the object file format (Mach-O) prefixes every C-level symbol with an underscore: the
  C function `main` is the assembly symbol `_main`, and that is what the start-up code calls. Linux's format (ELF)
  uses names unchanged. Get this wrong and the *linker* fails with an "undefined symbol" error for `_main` (macOS) or
  `main` (Linux).
- **The `.note.GNU-stack` section.** On Linux, this empty section tells the linker that the code does not need an
  executable stack. Without it, GNU `ld` warns, and some systems mark the stack executable, a security weakness.
  macOS's assembler doesn't know this directive, so emit it on Linux only.

Make the decision in exactly one place, in the emitter. Either check at `rcc`'s compile time with
`cfg!(target_os = "macos")` or at run time with `std::env::consts::OS`. Inside a Linux Docker container both say
Linux, which is correct.

Only C symbols get the prefix. In Unit 9 you will emit internal labels for jumps (like `.L_end0`); those are not C
symbols and must not be prefixed. Keep "symbol name" and "label name" as separate ideas from the start.

### Building text in Rust
Python would use an f-string per line, or `"\n".join(lines)`. In Rust, two traits are both called `Write`:

- `std::fmt::Write` is for **text destinations**, like a `String`. With it in scope, `write!` and `writeln!` append
  formatted text to a `String`.
- `std::io::Write` is for **byte streams**, like files, stdout and sockets.

The macro is the same; which trait is in scope decides what it does. The method only exists when the trait is
imported, which is a common source of confusing "no method named `write_fmt`" errors:

```rust
use std::fmt::Write;
let mut s = String::new();
writeln!(s, "{}", 42).unwrap(); // appending to a String cannot actually fail
```

Writing to a `String` cannot fail, but `writeln!` returns a `Result` because the trait also serves destinations that
can. A neat design is to implement `Display` for operands and instructions, so the function emitter can write `{}` for
each instruction. Build the whole file in one `String`, then let the driver write it to disk in one go. If you import
both `Write` traits in one module, their names clash; import one with `as _` (which brings its methods into scope
without its name).

### The whole pipeline
With the emitter in place, a full compile looks like this, with the type that flows between each pair of stages:

```
prog.c ─gcc -E -P─► prog.i ─read+delete─► String
  ─lexer─► Vec<Token> ─parser─► ast::Program ─codegen─► asm::Program ─emit─► String
  ─write─► prog.s ─gcc [-arch x86_64]─► prog          (prog.s deleted unless -S)
```

Run it and check the exit status by hand:

```
$ ./target/debug/rcc return_2.c
$ ./return_2
$ echo $?
2
```

`$?` is the shell variable holding the last command's exit status. Exit statuses are a single byte, so only 0–255
survive: a program returning 256 reports 0. The test suite's chapter-1 programs stay in range.

### When something goes wrong
- **The assembler rejects your file:** run `rcc -S prog.c` and read `prog.s`. Compare it with what `clang -S -O0` (add
  `-arch x86_64` on Apple Silicon) or Godbolt produces for the same C. Real compilers emit extra directives you can
  ignore; the instructions are what matter.
- **The linker complains about `main`/`_main`:** your prefix logic is wrong for the platform you're on.
- **The program crashes (or the macOS assembler mentions absolute addressing):** look for a missing `$`.
- **Wrong exit status:** dump the assembly AST and check the immediate value.

## Build
1. **Emit module.** A public entry point: assembly program in, `String` out.
2. **Spelling.** `Display` impls (or private helper functions) for operands and instructions, producing exactly the
   text in the table.
3. **Platform handling.** The symbol prefix and the GNU-stack section, both decided in one place in this module.
4. **Driver.** Delete the stub. A full compile now runs lex → parse → codegen → emit, writes `prog.s`, assembles and
   links with `gcc` (plus `-arch x86_64` on Apple Silicon), and deletes `prog.s`. `-S` writes `prog.s` and stops.
5. **Unit test.** Emitting the worked example's assembly AST gives exactly the expected text for your platform (a raw
   string literal, `r"..."`, keeps the tabs and newlines readable). If you want to test both platforms, make the
   platform a parameter of an internal function and test each value.
6. **Run the whole chapter:** `./test_compiler ./target/debug/rcc --chapter 1`. Valid programs must compile and return
   the right status; invalid ones must fail in the lexer or parser.
7. **Tidy up.** Every stage in its own module (`driver`, `lexer`, `parser`, `ast`, `codegen`, `asm`, `emit`, or your
   names), each with its own tests.

## Common pitfalls
- A missing `$` on immediates: on Linux the program assembles, then segfaults.
- Getting the prefix wrong for your platform, or hard-coding it and then building inside Docker.
- Emitting `.section .note.GNU-stack` on macOS, where the assembler rejects it.
- Importing `std::fmt::Write` and `std::io::Write` into one module without aliasing one.
- Forgetting the final newline, or leaving `prog.s` behind after a successful full compile.
