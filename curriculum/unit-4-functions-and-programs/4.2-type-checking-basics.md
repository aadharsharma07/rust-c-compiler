# Lesson 4.2 — Type Checking Basics
**Unit:** 4 — Functions and Whole Programs · **Type:** Builds type-checker pass · **Est. time:** 5–7 h · **Tests:** ch. 9 (`--stage validate`)
**Prerequisites:** lesson 4.1

## Learning goals
- Explain what a **type checker** does, and why it is separate from identifier resolution.
- Build a **symbol table**: a single, program-wide map from (unique) names to what the compiler knows about them.
- Detect arity errors, conflicting declarations, double definitions, and functions/variables used as the wrong kind of thing.
- Design a symbol table that later stages (codegen, Unit 5's types) can keep using.
- Use `HashMap` entry inspection and enums-with-data to represent "kinds of type".

## Key ideas
**Why another pass?** Resolution answers "which declaration does this name refer to?" using *scoped* maps that are
discarded as blocks end. Type checking answers "is this *use* consistent with what was declared?" and needs
information that outlives scopes. After resolution, every local has a unique name and every function keeps its
own name, so a **flat** table keyed by name is enough.

**Types, for now.** Only two kinds of thing exist: `int` (variables and parameters) and "function taking *n*
`int` parameters and returning `int`". Unit 5 will turn this into a real recursive `Type` enum, so design for
growth: an enum with an `Int` case and a function case that records a parameter count today and parameter types later.

**Symbol-table entries** hold the type plus attributes. For a function: *defined yet?* (Lesson 4.5 adds linkage and
initial values.)

**Rules.**
- **Function declaration** `f`: if `f` is already in the table, its type must be identical (same parameter count),
  else *incompatible declarations*. If it was already defined and this declaration has a body: *defined twice*.
  Record `defined = old_defined || has_body`. If there is a body, add each parameter as `int`, then check the body.
- **Local variable declaration**: add as `int`; check the initializer.
- **Function call** `f(args)`: if `f`'s type is `int`: *variable used as a function*. If the argument count differs from
  the parameter count: *wrong number of arguments*. Check every argument.
- **Var(x)** whose type is a function: *function used as a variable* (e.g. `return f;`, `f + 1`, `f = 3`).

**Why a flat table catches cross-scope conflicts.** In
```c
int f(int a);
int main(void) { int f(void); return f(); }
```
both declarations of `f` have linkage and therefore name the *same* function, so the second one is checked against
the first even though they are in different scopes: *incompatible declarations*. A scoped map would miss this.

**Worked example.**
```c
int sq(int x);
int main(void) { int sq_val = sq(3); return sq_val; }
int sq(int x) { return x * x; }
```
Table after checking (names after resolution):
```
sq       → FunType(params: 1), defined: true
x.0      → Int          (parameter of the prototype; harmless to record)
sq_val.1 → Int
x.2      → Int
```
Errors this pass catches:
```c
int f(int a, int b); int main(void) { return f(1); }        /* wrong number of arguments */
int f(void); int f(int a);                                   /* incompatible declarations */
int f(void) { return 1; } int f(void) { return 2; }          /* defined twice */
int main(void) { int x = 3; return x(); }                    /* variable used as function */
```

## Questions the tutor should ask you
1. Why can't the resolution pass's scoped maps detect `int f(int a);` conflicting with a block-scope `int f(void);`?
2. Why is a flat table safe for local variables? What property of the previous pass makes that true?
3. What does `defined = old_defined || has_body` protect against, and what goes wrong if you simply overwrite the entry?
4. Should the table be thrown away after type checking? Who might need it later?
5. How would you represent "function of (int, int) returning int" so that it extends to `long` and pointers in Unit 5?

## What you build
- A **type-checker pass** that runs after resolution (and loop labelling) and is part of `--validate`.
- A **symbol table** type: name → entry (type + attributes), kept alive and handed to later stages (TACKY gen and codegen will query it in 4.4–4.5).
- A **type** representation: `int` or function-with-parameter-count, designed to grow.
- **Errors** (non-zero exit, clear message): incompatible function declarations, function defined more than once,
  variable called as a function, function used as a variable, wrong number of arguments.
- **Must reject:** all chapter-9 `invalid_types` programs, including conflicts across scopes and a call where a local variable
  shadows the function name (`int f(void); int main(void) { int f = 1; return f(); }`).
- **Must accept:** repeated identical prototypes; prototype after definition; calls inside arguments; a local variable shadowing a
  function name when it is *not* called; recursion.

## Rust focus
- Enums with data for types and for symbol attributes; deriving `PartialEq` to compare types ([Book ch. 6.1](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html), [`PartialEq`](https://doc.rust-lang.org/std/cmp/trait.PartialEq.html)).
- `HashMap::get` returning `Option<&Entry>` and the borrow you hold while inspecting it; copying out the small parts you need before inserting
  ([HashMap](https://doc.rust-lang.org/std/collections/struct.HashMap.html)).
- `Iterator::zip` / `len()` comparisons for argument checks ([Iterator](https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.zip)).
- Returning the table *and* the checked program from a pass: tuples or a small struct; ownership of the table moving to later stages.
- A borrow-checker classic: you can't hold `let e = table.get(name)` and then call `table.insert(...)` while `e` is alive. Ask why.

## Common pitfalls
- Overwriting an entry for a prototype after a definition, losing the "defined" flag.
- Forgetting to check arguments (the call's arguments may themselves contain bad calls).
- Comparing only the *number* of declarations, not their types.
- Putting type checking inside resolution and then struggling with scope-limited maps.
- Discarding the symbol table at the end of `--validate`; 4.4 and 4.5 need it.
