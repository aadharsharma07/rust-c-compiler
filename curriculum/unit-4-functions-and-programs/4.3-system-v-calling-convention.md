# Lesson 4.3 — The System V Calling Convention
**Unit:** 4 — Functions and Whole Programs · **Type:** Learning only · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 2.3, 4.2

## Learning goals
- Know where integer arguments and return values go under the System V AMD64 ABI (Linux and macOS on x86-64).
- Draw the stack at the instant of `call`, on entry to the callee, and after the callee's prologue.
- Explain the 16-byte alignment rule and compute the padding a call needs.
- Distinguish caller-saved from callee-saved registers and see why your current codegen gets away with ignoring them.
- Read compiler output on Godbolt to verify all of the above. (Rust focus: reading the docs carefully before designing types.)

## Key ideas
**Why a convention?** Your `rcc`-compiled code must call `putchar` from libc and be called by `gcc`-compiled test
drivers. Both sides must agree on where arguments live, who cleans up, and which registers survive a call. That
agreement is the **ABI**. On x86-64 Linux and macOS it is System V AMD64 (Windows uses a different one).

**Integer/pointer arguments.** The first six go in registers, in order:

| Arg | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 64-bit | `%rdi` | `%rsi` | `%rdx` | `%rcx` | `%r8` | `%r9` |
| 32-bit (`int`) | `%edi` | `%esi` | `%edx` | `%ecx` | `%r8d` | `%r9d` |

Arguments 7 and up go on the stack, pushed **right to left**, so the 7th argument is at the lowest address,
`0(%rsp)`, when `call` executes. Each stack argument occupies 8 bytes even for an `int`. The **caller** removes them after the call.
An `int` return value comes back in `%eax`. (When calling a *variadic* function such as `printf`, `%al` must hold
an upper bound on the number of vector registers used; `movl $0, %eax` suffices for int-only calls.)

**The stack at a call** (addresses grow upward in this picture; the stack grows down):
```
   caller's frame ...
   arg 8                 <- 24(%rbp) in callee
   arg 7                 <- 16(%rbp) in callee    (= 0(%rsp) just before `call`)
   return address        <-  8(%rbp)               (pushed by `call`)
   caller's saved %rbp   <-  0(%rbp)               (pushed by callee prologue)
   callee locals         <- -4(%rbp), -8(%rbp), ...
```

**Alignment.** `%rsp` must be a multiple of 16 *immediately before* `call`. Then on entry `%rsp ≡ 8 (mod 16)`
(the return address), and after `pushq %rbp` it is aligned again. If every function rounds its local-stack size
up to a multiple of 16, `%rsp` is aligned after the prologue; before pushing *k* stack arguments, subtract 8 more
when *k* is odd. Misalignment often "works" until libc uses an aligned SSE instruction and crashes.

**Who saves what.**
- *Caller-saved* (may be clobbered by any call): `%rax %rcx %rdx %rsi %rdi %r8–%r11`.
- *Callee-saved* (a function must restore them before returning): `%rbx %rbp %rsp %r12–%r15`.
Your compiler currently keeps every value in a stack slot and uses registers only *within* one instruction sequence,
so nothing is live in a register across a `call`. That's why you can ignore saving for now; Unit 7 can't.

**Worked example.** `int r = f(1, 2, 3, 4, 5, 6, 7);` inside a function with 16 bytes of locals (macOS names):
```
    subq  $8, %rsp           # 1 stack arg (odd) -> pad to keep 16-byte alignment
    pushq $7                 # arg 7
    movl  $6, %r9d
    movl  $5, %r8d
    movl  $4, %ecx
    movl  $3, %edx
    movl  $2, %esi
    movl  $1, %edi
    call  _f
    addq  $16, %rsp          # 8 bytes of arg + 8 bytes of padding
    movl  %eax, -4(%rbp)     # r
```
Inside `f`, after its prologue, parameter 1 is in `%edi` and parameter 7 at `16(%rbp)`.

**The red zone.** System V lets leaf functions use 128 bytes below `%rsp` without adjusting it. You won't
rely on it, but it explains some `gcc -O2` output you'll see on Godbolt.

## Questions the tutor should ask you
1. Why are stack arguments pushed right to left? Where would argument 7 be otherwise?
2. On entry to a function, why is `%rsp` *not* 16-byte aligned, and what restores alignment?
3. A call has 9 arguments and the frame is a multiple of 16. How many bytes are pushed, is padding needed, and what does `addq` remove?
4. Why does it not matter (yet) that `putchar` may clobber `%rcx`?
5. After the prologue, at what `%rbp` offset is the 8th parameter? The 10th?
6. Why might misaligned code pass most tests and then crash only when calling libc?

## What you build
Nothing in `rcc`. Instead, produce evidence you understand the ABI:
- On Godbolt (x86-64 gcc or clang, `-O0`), compile a function with 8 `int` parameters and a caller passing 8 constants.
  Annotate each instruction: register args, stack args, alignment, clean-up, where the callee reads params 7 and 8.
- Draw (on paper or in your journal) the stack frames of `main → f(1..8)` at the `call` instruction and after `f`'s prologue,
  with absolute offsets from both `%rsp` and `%rbp`.
- Write down, in prose, the assembly-AST changes you expect 4.4 to need: new registers, push, call, stack allocation/deallocation,
  how a parameter's pseudoregister gets its initial value.
- Compute alignment padding for 0, 1, 6, 7, 8 and 11 arguments.

## Common pitfalls
- Pushing stack arguments left to right.
- Forgetting the padding when the number of stack arguments is odd, or forgetting to remove it afterwards.
- Assuming the 7th parameter is at `8(%rbp)`; that's the return address.
- Mixing up `%ecx` (4th argument) and `%edx` (3rd).
- Believing callee-saved means "the callee can't touch it": it can, but must restore it.
