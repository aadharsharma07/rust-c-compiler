# Lesson 4.1 — Functions in the Front End
**Unit:** 4 — Functions and Whole Programs · **Type:** Builds function decls/calls in parser + resolver · **Est. time:** 4–6 h · **Tests:** ch. 9 (`--stage parse`)
**Prerequisites:** lessons 3.1–3.5 (chapters 5–8 pass)

## Learning goals
- Distinguish a function **declaration** (prototype) from a **definition**, and why C needs prototypes at all.
- Parse parameter lists, function calls and a program made of many top-level functions.
- Extend identifier resolution with **linkage**: names that refer to the same entity across scopes must *not* be renamed.
- Restructure the AST so `Declaration` is either a variable or a function declaration.
- Practise reshaping a large enum hierarchy and following compiler errors through every pass.

## Key ideas
**Grammar.**
```
<program>          ::= { <function-declaration> }
<declaration>      ::= <variable-declaration> | <function-declaration>
<function-declaration> ::= "int" <identifier> "(" <param-list> ")" ( <block> | ";" )
<param-list>       ::= "void" | "int" <identifier> { "," "int" <identifier> }
<factor>           ::= ... | <identifier> "(" [ <argument-list> ] ")"
<argument-list>    ::= <exp> { "," <exp> }
```
`int f(void);` declares; `int f(void) { … }` defines. A declaration promises the function exists somewhere
(this file or another one) so calls can be checked and compiled. C17 has no implicit declarations: calling an
undeclared function is an error. Note `int f();` (empty parens) means "unspecified parameters" in C17; this course,
like the tests, only uses `(void)` or a named list.

**Distinguishing a variable from a function declaration** takes lookahead: after `int <identifier>`, a `(` means function.
In a call, an identifier followed by `(` is a call; each argument is a full expression (assignment allowed;
there's no comma operator, so `,` always separates arguments).

**Block-scope function declarations** are legal (`int main(void) { int f(int a); return f(1); }`); block-scope
function *definitions* are not.

**Linkage in resolution.** Every function name has (external) linkage: all declarations of `f` anywhere in the
program refer to the same function, so the resolver must leave its name as `f`. Variables declared in blocks have
*no linkage* and keep getting unique names. Each map entry therefore gains a "has linkage" flag. Conflict rule in
the same scope: redeclaring a name is an error unless *both* the old and new declarations have linkage.

**Parameters** are resolved like local variables declared in a new scope that is shared with the function body's outer
block. So `int f(int a) { int a = 1; }` is a duplicate-declaration error, but `int f(int a) { { int a = 1; } }` is fine.
Parameter names in a pure declaration are resolved too (for duplicate checking) but have no further use.

**Worked example.**
```c
int add(int a, int b);
int main(void) { return add(1, 2); }
int add(int a, int b) { return a + b; }
```
Resolved AST (sketch):
```
Program([
  FunDecl("add", params ["a.0", "b.1"], body None),
  FunDecl("main", params [], body Some([ S(Return(FunctionCall("add", [Constant 1, Constant 2]))) ])),
  FunDecl("add", params ["a.2", "b.3"], body Some([ S(Return(Binary(Add, Var a.2, Var b.3))) ])) ])
```
TACKY (chapter 9 form): a program is a list of function definitions only; the prototype emits nothing.
```
Function main():   FunCall("add", [1, 2], tmp.4); Return(tmp.4); Return(0)
Function add(a.2, b.3):   Binary(Add, a.2, b.3, tmp.5); Return(tmp.5); Return(0)
```

## Questions the tutor should ask you
1. Why must the resolver *not* rename `add`, but must rename `a` and `b`?
2. Why is `int f(void); int f(void);` legal at file scope, but `int x; int x;` inside a block is not?
3. `int foo(void) { int foo = 3; return foo; }`: legal? Which `foo` does `return` read?
4. How does your parser tell apart `int x;`, `int x = 1;`, `int f(void);` and `int f(void) { … }`?
5. Why are parameters in the same scope as the function body's outermost block, and not an enclosing one?

## What you build
- **Lexer:** the `,` token.
- **AST:** a program as a list of function declarations; a function declaration (name, parameter names, optional body);
  `Declaration` becomes variable-or-function; expression `FunctionCall(name, args)`.
- **Parser:** the grammar above; block items may be function declarations.
- **Resolution:** a "has linkage" flag per entry; function names kept as-is; parameters renamed in the body scope;
  `--validate` should succeed on all valid chapter-9 programs.
- **TACKY:** functions carry a parameter list; `FunCall(name, args, dst)` instruction; prototypes produce nothing.
  (Codegen for calls comes in 4.4; until then, `--tacky` is the furthest stage you can run.)
- **Must reject (parse):** `int f(int a, );`, `int f(void) int x;`, `f(1, 2` (unclosed call), `int f(void, int a)`, `int f(int a int b);`.
  (Unnamed parameters such as `int f(int);` are legal C but outside this course's grammar; decide and document what you do.)
- **Must reject (resolution):** calling an undeclared function, `f() = 1` (a call is not an lvalue), duplicate parameter names, a parameter redeclared in the body's
  outer block, a nested function *definition*, a local variable and a function declared with the same name in the same block.
- **Edge cases:** recursion, calls before the definition (with a prototype), calls nested in arguments `f(g(1), 2)`, local function
  declarations shadowing a variable from an outer block.

## Rust focus
- Restructuring enums: `Declaration::{Var(VarDecl), Fun(FunDecl)}` with standalone structs ([Book ch. 5](https://doc.rust-lang.org/book/ch05-01-defining-structs.html)).
- `Option<Block>` for "body or prototype"; `Vec<String>` params; `Vec<Exp>` arguments.
- Peeking two tokens ahead: `Peekable` only gives one; consider an index-based token cursor or slice patterns
  ([slice patterns](https://doc.rust-lang.org/reference/patterns.html#slice-patterns)).
- Parsing comma-separated lists with a loop; avoid recursion for lists.
- Adding a field to a struct used as a map value and updating every construction site (the compiler will find them for you).

## Common pitfalls
- Renaming function names, which then don't match across declarations, across files, or with libc's `putchar`.
- Putting parameters in a scope *outside* the body, so `int f(int a) { int a; }` is wrongly accepted.
- Accepting nested function definitions because "it parsed".
- Resolving arguments in the wrong scope, or forgetting to resolve them at all.
- Losing `Return(0)` at the end of non-`main` functions (harmless and simplest to keep for every function).
