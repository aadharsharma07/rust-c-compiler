# Lesson 3.2 — Semantic Analysis
**Unit:** 3 — Variables, Scope and Control Flow · **Type:** Builds variable-resolution pass · **Est. time:** 5–7 h · **Tests:** ch. 5
**Prerequisites:** lesson 3.1

## Learning goals
- Explain why some errors (undeclared names, duplicates, bad lvalues) can't be caught by a context-free grammar.
- Design a compiler pass as a pure tree-to-tree transformation: AST in, renamed AST (or an error) out.
- Generate globally unique names so later stages never have to think about scope.
- Use `HashMap` for name lookup and a counter for fresh names; return structured errors with `Result`.
- Add a `--validate` stage to the driver that stops after semantic analysis.

## Key ideas
**Why a separate pass?** A grammar describes *shape*. "Every variable must be declared before use" depends
on *what came before*, i.e. context. You could thread a symbol table through the parser, but separating the
two keeps each simple, gives clean error stages (`--parse` vs. `--validate`) and lets you add more passes
(loop labelling in 3.5, type checking in 4.2) without touching the parser.

**Variable resolution** walks the AST in source order with a map from *user-written name* → *unique name*:
- **Declaration** `int x = init;`: if `x` is already in the map → *duplicate declaration* error. Otherwise
  create a unique name, insert it, **then** resolve the initializer (so `int a = a + 1;` is legal C: it reads
  the indeterminate `a`, which is undefined behaviour at run time, but not a compile error).
- **Var(x)**: look up `x`; missing → *undeclared variable* error; else replace with the unique name.
- **Assignment(lhs, rhs)**: if `lhs` is not a `Var` → *invalid lvalue* error. Resolve both sides.
- Everything else: recurse.

**Unique names.** Use a character that can't appear in a C identifier, e.g. `x.0`, `x.1`, so a renamed variable
can never collide with a user's name or with TACKY temporaries (`tmp.3`). One global counter shared by
resolution and TACKY generation guarantees uniqueness across the whole program. After this pass, every later
stage can treat names as plain unique keys, so shadowing (3.4) costs the back end nothing.

**Worked example.**
```c
int main(void) { int a = 1; int b = a + 2; a = b; return a; }
```
Resolution map grows `{a → a.0}` then `{a → a.0, b → b.1}`. Output AST (sketch):
```
D(Declaration("a.0", Some(Constant 1)))
D(Declaration("b.1", Some(Binary(Add, Var a.0, Constant 2))))
S(Expression(Assignment(Var a.0, Var b.1)))
S(Return(Var a.0))
```
Errors this pass catches:
```c
int main(void) { return x; }               /* undeclared variable x */
int main(void) { int a; int a; return 0; } /* duplicate declaration of a */
int main(void) { int a = 2; a + 1 = 3; }   /* invalid lvalue */
```

**Driver stage.** `rcc --validate file.c` runs lex → parse → resolve and exits 0 on success, non-zero on
error, without generating TACKY. The test suite uses `--stage validate` to call it.

## Questions the tutor should ask you
1. Why is "undeclared variable" not a parse error? Could a context-free grammar ever express it?
2. In `int a = a + 1;`, is the `a` inside the initializer in scope? What would your pass do if you resolved the initializer *before* inserting `a`?
3. Why rename at all? What would go wrong in later lessons (shadowing, multiple functions) if you kept the source names?
4. Why use a character like `.` in generated names? What could collide if you used `a0`?
5. Should the pass mutate the AST in place or build a new one? What are the ownership trade-offs of each?

## What you build
- A **semantic-analysis module** with a resolution function from a program to `Result<Program, SemanticError>`.
- A **name map** (user name → unique name) and a **unique-name generator** shared with TACKY generation.
- A **`--validate` flag** in the driver; also make `--tacky`, `--codegen`, `-S` and the default run this stage.
- An **error type** with variants for undeclared variable, duplicate declaration and invalid lvalue, each carrying the name
  (or a description of the bad expression). The driver prints it to stderr and exits non-zero.
- TACKY generation now relies on resolved names; it no longer needs to care what the user called things.
- **Must reject:** every `invalid_semantics` test in chapter 5: use before declaration (`a = 1; int a;`), duplicates, invalid lvalues
  such as `(a) + 1 = 2`, `-a = 3`, `2 = 3`.
- **Must accept:** `int a = a + 1;`, `a = a = 4;` (after declaring `a`), and a parenthesised lvalue `(a) = 4`
  (parentheses don't appear in your AST, so this is just `Var a`).
- If you did `++`/`--`/compound assignment, their operands must also be lvalues.

## Rust focus
- `HashMap<String, String>`: `get`, `insert`, `contains_key`, and the `entry` API
  ([Book ch. 8.3](https://doc.rust-lang.org/book/ch08-03-hash-maps.html), [std HashMap](https://doc.rust-lang.org/std/collections/struct.HashMap.html)).
- Error enums + `?` propagation through recursive functions ([Book ch. 9.2](https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html));
  implement `Display` for nice messages ([std::fmt](https://doc.rust-lang.org/std/fmt/trait.Display.html)).
- Consuming vs. borrowing the tree: a pass taking `Program` by value can move children into the new tree; one taking `&mut` can edit in place.
- Passing shared mutable state (a counter) through passes: a small context struct with `&mut self` methods.
- `format!` to build names: `format!("{name}.{n}")` illustrates inline format args in isolation.

## Common pitfalls
- Resolving the initializer before inserting the name, which rejects the legal `int a = a + 1;`.
- Two separate counters (one in resolution, one in TACKY) producing clashing names.
- Checking the lvalue *after* resolving the left side into something else, or forgetting to check at all.
- Panicking (`unwrap`) on a missing name instead of returning a semantic error; the tests check the exit code.
- Making `--validate` print or emit files; it should only succeed or fail.
