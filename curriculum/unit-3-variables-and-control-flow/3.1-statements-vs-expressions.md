# Lesson 3.1 — Statements vs. Expressions
**Unit:** 3 — Variables, Scope and Control Flow · **Type:** Builds local vars + assignment · **Est. time:** 4–6 h · **Tests:** ch. 5 (`--stage parse`; valid programs end-to-end)
**Prerequisites:** lessons 2.1–2.6 (chapters 1–4 pass)

## Learning goals
- Distinguish *expressions* (produce a value), *statements* (do something) and *declarations* (introduce a name).
- Understand **lvalues**: why `a = 3` is meaningful and `2 = 3` is not, and why assignment is itself an expression.
- Parse a right-associative, lowest-precedence binary operator with your existing precedence climber.
- Refactor large Rust enums (`Statement`, `Expression`, a new `BlockItem`) without losing exhaustiveness checking.
- Lower variables to TACKY with no new back-end machinery: a C variable *is* a pseudoregister.

## Key ideas
**Three syntactic categories.** Until now a function body was one `return` statement. Now it is a
sequence of *block items*, each either a declaration or a statement:

```
<function>    ::= "int" <identifier> "(" "void" ")" "{" { <block-item> } "}"
<block-item>  ::= <statement> | <declaration>
<declaration> ::= "int" <identifier> [ "=" <exp> ] ";"
<statement>   ::= "return" <exp> ";" | <exp> ";" | ";"
<exp>         ::= <factor> | <exp> <binop> <exp>        (binop now includes "=")
<factor>      ::= <int> | <identifier> | <unop> <factor> | "(" <exp> ")"
```

A declaration is *not* a statement in C17: `if (x) int y = 1;` is a syntax error (you'll meet this in 3.3).
An expression statement (`a = a + 1;`) evaluates an expression for its side effects and discards
the value. The null statement `;` does nothing.

**Assignment is an expression.** `a = b = 5` parses as `a = (b = 5)` and its value is the value stored.
In the precedence table assignment gets the lowest precedence (below `||`) and is
**right-associative**: when the climber sees `=`, the right operand is parsed with the *same*
minimum precedence instead of one higher.

**Lvalues.** An lvalue designates a storage location. For now only a variable is an lvalue. The parser
will happily build `Assignment(Constant(2), Constant(3))`, since grammatically it is `<exp> = <exp>`.
Rejecting it is a *semantic* check (lesson 3.2). Decide now where it will live; don't hack it into the parser.

**`main` without `return`.** C says reaching the closing `}` of `main` returns 0. The simple, general fix:
always append `Return(Constant(0))` to every function's TACKY. If it is unreachable, it costs one instruction.

**Worked example.**
```c
int main(void) { int a = 2; int b; b = a * 3; return b; }
```
AST (sketch): `Function("main", [D(Declaration("a", Some(Constant 2))), D(Declaration("b", None)),
S(Expression(Assignment(Var b, Binary(Multiply, Var a, Constant 3)))), S(Return(Var b))])`

TACKY:
```
Copy(Constant 2, Var a)
Binary(Multiply, Var a, Constant 3, Var tmp.0)
Copy(Var tmp.0, Var b)
Return(Var b)
Return(Constant 0)
```
A declaration without an initializer emits **nothing**. After pseudo-replacement `a`, `b`, `tmp.0` become
`-4(%rbp)`, `-8(%rbp)`, `-12(%rbp)`, and the fix-up pass you already have handles the memory-to-memory `movl`.

## Questions the tutor should ask you
1. Why does `a = b = 5` need right associativity? What tree do you get if `=` were left-associative, and why is it nonsense?
2. Your climber parses `2 = 3` without complaint. Is that a bug in the parser? Where should it be rejected, and why?
3. What TACKY does `int x;` produce? What does `x = 4;` produce, and what is the *result* operand of that expression?
4. Why can a variable name go straight into a TACKY `Var` without any new back-end code?
5. How will the parser decide whether a block item is a declaration or a statement, using one token of lookahead?

## What you build
- **Lexer:** the `=` token (make sure `==` still lexes as one token).
- **AST:** a block-item type (declaration or statement); a declaration with a name and optional initializer;
  `Expression` and `Null` statements; `Var(name)` and `Assignment(lhs, rhs)` expressions. Function bodies become a list of block items.
- **Parser:** block-item dispatch on the `int` keyword; `=` in the precedence table (lowest, right-associative);
  identifiers as factors. `--parse` must succeed on every valid chapter-5 program and fail on `invalid_parse`.
- **TACKY:** declarations with initializers lower to "evaluate init, `Copy` into the variable"; assignment lowers
  to "evaluate rhs, `Copy` into lhs, result is lhs"; expression statements discard their result; append `Return(0)`.
- **Codegen:** no new instructions. Confirm stack allocation counts the new pseudoregisters.
- **Must reject (parse errors):** `int = 3;`, `int a = ;`, `int a 3;`, `return int;`, missing `;`, `a = = 3`.
- **Edge cases:** `int a = a = 3;` parses; `a = 1 + (b = 2)`; `;;;` in a body; a body with no `return`.
- Optional extra credit (`--compound`, `--increment`): `+=`, `-=`, …, prefix/postfix `++`/`--`. Postfix needs a
  temporary holding the *old* value.

## Rust focus
- Refactoring enums: add variants, then let `match` exhaustiveness errors walk you to every place that must change.
  Avoid `_ =>` catch-alls in passes for exactly this reason. ([Book ch. 6.2](https://doc.rust-lang.org/book/ch06-02-match.html))
- `Option<Exp>` for optional initializers; `Option::map` / `if let` ([std::option](https://doc.rust-lang.org/std/option/enum.Option.html)).
- `Box<Exp>` for the two children of `Assignment` ([Book ch. 15.1](https://doc.rust-lang.org/book/ch15-01-box.html)).
- Matching on a borrowed token without consuming it (`match self.peek()` returning `Option<&Token>`).

## Common pitfalls
- Giving `=` left associativity by reusing the "min_prec + 1" rule for every operator.
- Rejecting `2 = 3` in the parser: it works today but blocks later lvalues (`*p = 3`, `a[i] = 3`).
- Emitting a `Copy` for a declaration without an initializer, or evaluating the initializer twice.
- Forgetting that an expression statement still needs to be lowered (`a = 3;` must emit its `Copy`).
- Parsing a declaration as a statement, which then makes `if (x) int y;` accepted later.
