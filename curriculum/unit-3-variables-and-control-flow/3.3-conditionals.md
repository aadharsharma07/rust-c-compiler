# Lesson 3.3 — Conditionals
**Unit:** 3 — Variables, Scope and Control Flow · **Type:** Builds `if`/`else`, `?:` · **Est. time:** 3–5 h · **Tests:** ch. 6
**Prerequisites:** lesson 3.2

## Learning goals
- Understand the dangling-`else` ambiguity and how recursive descent resolves it for free.
- Parse the ternary `?:` as a special "binary" operator with a full expression in the middle.
- Lower structured branches into flat TACKY with labels and conditional jumps.
- Generate unique labels and reuse them consistently between TACKY and assembly.
- Practise extending an enum with a variant holding `Option<Box<…>>`.

## Key ideas
**Grammar additions.**
```
<statement> ::= ... | "if" "(" <exp> ")" <statement> [ "else" <statement> ]
<exp>       ::= ... | <exp> "?" <exp> ":" <exp>
```
The bodies are `<statement>`, not `<block-item>`: `if (a) int b = 1;` is a parse error. (Braced blocks
arrive in 3.4, so chapter 6 only has single-statement bodies.)

**Dangling else.** In `if (a) if (b) x = 1; else x = 2;` the grammar is ambiguous: which `if` owns the `else`?
C says the *nearest* one. A recursive-descent parser does this naturally: after parsing the inner `if`'s
then-branch it sees `else` and takes it greedily. Nothing to implement, but you should be able to explain why.

**The conditional operator.** `?:` has precedence just above assignment and is right-associative:
`a ? b : c ? d : e` means `a ? b : (c ? d : e)`. Treat `?` as a binary operator in the climber, but when you
see it, parse the *middle* as a complete expression (min precedence 0) up to `:`, then the right operand at
the `?:` precedence. That means `a ? b = 1 : 2` is legal and `a = 1 ? 2 : 3` assigns 2 to `a`.
`1 ? 2 : 3 = 4` parses as `1 ? 2 : (3 = 4)`, and resolution rejects it (invalid lvalue).

**Lowering to TACKY.** No new instructions are needed; you already have `Jump`, `JumpIfZero`,
`JumpIfNotZero` and `Label` from short-circuit operators.

`if (c) S1 else S2`:
```
<instructions for c → v>
JumpIfZero(v, else.3)
<instructions for S1>
Jump(end.4)
Label(else.3)
<instructions for S2>
Label(end.4)
```
Without `else`, jump straight to the end label. `c ? e1 : e2` has the same shape but each branch ends with
`Copy(vᵢ, result)`, and the expression's value is the fresh temporary `result`.

**Worked example.**
```c
int main(void) { int a = 5; return a > 3 ? 10 : 20; }
```
TACKY (names after resolution):
```
Copy(5, a.0)
Binary(GreaterThan, a.0, 3, tmp.1)
JumpIfZero(tmp.1, cond_else.2)
Copy(10, tmp.4)
Jump(cond_end.3)
Label(cond_else.2)
Copy(20, tmp.4)
Label(cond_end.3)
Return(tmp.4)
```
x86-64 (macOS; Linux uses `.L` local labels):
```
    cmpl $3, -4(%rbp)          # a.0 vs 3
    movl $0, -8(%rbp)
    setg -8(%rbp)
    cmpl $0, -8(%rbp)
    je   Lcond_else.2
    movl $10, -12(%rbp)
    jmp  Lcond_end.3
Lcond_else.2:
    movl $20, -12(%rbp)
Lcond_end.3:
    movl -12(%rbp), %eax
```

## Questions the tutor should ask you
1. Draw both possible trees for `if (a) if (b) x; else y;`. Which does your parser build, and which line of your code decides it?
2. Why is the middle operand of `?:` parsed with minimum precedence 0, but the right operand is not?
3. Why do both branches of a conditional `Copy` into the *same* temporary? What breaks if each uses its own?
4. What happens to your labels if a program has two `if` statements? Two functions (Unit 4)?
5. Is `if (a) ; else ;` legal? What TACKY does it produce?

## What you build
- **Lexer:** keywords `if`, `else`; tokens `?` and `:`.
- **AST:** `If { condition, then, else: optional statement }`; expression `Conditional { condition, then, else }`.
- **Parser:** the `if` statement; `?` in the precedence table (just above `=`, right-associative) with the middle-operand rule.
- **Resolution:** recurse into the new nodes (no new rules).
- **TACKY:** lowering as above, with unique labels from your shared generator (labels and variables may share a counter).
- **Must reject:** `if a return 1;`, `if (a) int b = 2;`, `else return 0;` with no `if`, `a ? b`, `a : b`,
  `1 ? 2 : 3 = 4` (semantic), undeclared variables inside branches.
- **Edge cases:** nested ternaries, `else if` chains (just nested `If`), assignments inside branches,
  an `if` whose branches both `return`.
- Optional extra credit `--goto` belongs to this chapter; it is covered in lesson 3.6.

## Rust focus
- `Option<Box<Statement>>` for the optional else ([std::option](https://doc.rust-lang.org/std/option/enum.Option.html));
  `if let Some(s) = …` to lower it.
- Struct-like enum variants (`If { condition, then_branch, else_branch }`) for readability ([Book ch. 6.1](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)).
- Writing a small helper method that returns a fresh label `String`, borrowing the generator as `&mut self`.
- Pattern matching on token kinds with guards inside your precedence loop.

## Common pitfalls
- Parsing the middle operand of `?:` at the ternary's own precedence, so `a ? b = 1 : 2` fails to parse.
- Reusing the same label names for every `if` (assembler error "symbol already defined").
- Emitting the `Jump(end)` when there is no else branch but forgetting to emit the `end` label.
- Evaluating both branches of `?:` unconditionally (watch side effects: `a ? (b = 1) : (b = 2)`).
- Allowing a declaration as an `if` body.
