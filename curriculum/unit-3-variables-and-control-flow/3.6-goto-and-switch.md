> after Unit 4 if you like (then also handle labels being per-function).

## Learning goals
- Understand that labels have **function scope** and live in a separate namespace from variables.
- Write a label-resolution pass that checks every `goto` target exists and every label is unique.
- Lower `switch` to a chain of comparisons and jumps; understand when a real compiler uses a jump table.
- Extend the loop-labelling pass so `break` can target a `switch` while `continue` skips past it.
- Collect information in one walk and validate it in a second, using `HashMap`/`HashSet`.

## Key ideas
**goto.**
```
<statement> ::= ... | "goto" <identifier> ";" | <identifier> ":" <statement>
```
A labelled statement needs two tokens of lookahead (identifier, then `:`) to distinguish it from an expression
statement. Labels are visible throughout the whole function, even before their definition, so
`goto end; … end: return 0;` is fine. Label names don't clash with variables: `int a; a: a = 1;` is legal.
Because a label must be followed by a *statement*, `end: }` and `lbl: int x;` are errors in C17.

Label resolution: walk the function once collecting labels (error on duplicates), and check every `goto`
against that set (error on unknown targets); this can be one walk with a check at the end. Rename labels
uniquely (e.g. prefix with the function name later) so they can't clash with compiler-generated labels.
Lowering is trivial: `Goto(l)` → `Jump(l)`; `Labeled(l, s)` → `Label(l)` then `s`.

**switch.**
```
<statement> ::= ... | "switch" "(" <exp> ")" <statement>
              | "case" <exp> ":" <statement> | "default" ":" <statement>
```
`case`/`default` may appear anywhere inside the switch body (even nested in other statements), and control
**falls through** from one case into the next unless there is a `break`. Rules: case values must be integer
constants (a literal constant is enough for this course), no duplicate values, at most one `default`, and no
`case`/`default` outside a switch. `break` inside a switch exits the switch; `continue` refers to the
enclosing *loop*. So the labelling pass must track the current break target and current continue target
separately, and collect each switch's cases.

**Lowering a switch** with cases 1 and 5 and a default (label `sw.4`):
```
<exp → v>
Binary(Equal, v, 1, tmp.5); JumpIfNotZero(tmp.5, case_sw.4_1)
Binary(Equal, v, 5, tmp.6); JumpIfNotZero(tmp.6, case_sw.4_5)
Jump(default_sw.4)                (Jump(break_sw.4) if there is no default)
<body, where case 1 emits Label(case_sw.4_1), etc.>
Label(break_sw.4)
```
**Jump tables.** For dense case values, optimising compilers instead bounds-check `v` and index a table of
addresses: e.g. `leaq Ltable(%rip), %rdx` then a load and `jmp *%rax`. It's O(1) instead of O(n) compares. You
don't need it, but compare `gcc -O2 -S` output for a dense and a sparse switch on Godbolt.

**Example: fall-through.**
```c
switch (x) { case 1: y = 10; case 2: y = y + 1; break; default: y = 0; }
```
With `x == 1`, `y` ends as 11.

## Questions the tutor should ask you
1. Why can't label checking happen in the same single pass as variable resolution without forward references?
2. Why do labels and variables not conflict? What does that say about how many maps you need?
3. In `while (1) { switch (x) { case 1: continue; } }`, where does `continue` go? And `break`?
4. How does the labelling pass find a `case` that is nested inside an `if` within the switch body?
5. When does a jump table beat a compare chain, and what does it cost?

## What you build
- **goto:** AST nodes for `goto` and labelled statements; a label-resolution pass (duplicate label, undefined target);
  TACKY lowering. Run `--chapter 6 --goto` (tests may also exercise later chapters' features with `--goto`).
- **switch:** AST nodes for `switch`, `case` and `default`, each with a label field; extend loop labelling so `break` targets the
  innermost loop *or* switch and `continue` targets the innermost loop; collect case values per switch; TACKY lowering.
- **Must reject:** `goto missing;`, two `foo:` labels in one function, `lbl: }`, `case 1:` outside a switch, two `default`s,
  duplicate `case 3:`, non-constant case (`case a:`), `continue` in a switch not inside a loop.
- **Edge cases:** a switch with no `case` or `default` (control jumps straight past the body, which is never executed), a declaration inside a switch body
  whose initializer is skipped, `goto` into a nested block, a label on a null statement (`done: ;`).

## Rust focus
- `HashSet<String>` for defined labels and `Vec` for pending gotos ([std HashSet](https://doc.rust-lang.org/std/collections/struct.HashSet.html)).
- `HashSet::insert` returning `bool` as a duplicate check, in isolation: `if !seen.insert(name.clone()) { /* duplicate */ }`.
- Threading two independent `Option` contexts (break target, continue target) through recursion.
- Collecting data during a walk into a `Vec` owned by the switch node (`std::mem::take` can help: [docs](https://doc.rust-lang.org/std/mem/fn.take.html)).

## Common pitfalls
- Treating labels as block-scoped like variables.
- Using the user's label name directly as an assembly label, which can clash with your generated ones.
- `continue` inside a switch targeting the switch.
- Losing case labels nested inside other statements because you only scan the switch body's top level.
- Forgetting the jump to the break label when there is no `default`.
