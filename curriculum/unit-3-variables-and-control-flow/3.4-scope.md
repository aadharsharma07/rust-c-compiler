# Lesson 3.4 — Scope
**Unit:** 3 — Variables, Scope and Control Flow · **Type:** Builds compound statements · **Est. time:** 4–6 h · **Tests:** ch. 7
**Prerequisites:** lesson 3.3

## Learning goals
- Define block scope, shadowing and the lifetime of a local variable.
- Model a scope chain: what is visible here, and what was declared in *this* block?
- Compare two Rust designs for scoped maps: copy-the-map-on-entry vs. a stack of maps.
- Decide when cloning is the clearest answer and when borrowing is worth the complexity.
- See how renaming in resolution makes nested scopes disappear by the time you reach TACKY.

## Key ideas
**Compound statements.** A block `{ … }` is a statement containing a list of block items. The function body
is now just a block:
```
<block>     ::= "{" { <block-item> } "}"
<statement> ::= ... | <block>
<function>  ::= "int" <identifier> "(" "void" ")" <block>
```

**Scope rules.** A name is visible from the end of its declarator to the end of the enclosing block. An inner
block may **shadow** an outer name by declaring the same identifier; the outer variable is hidden but still
alive. Two declarations of the same name in the *same* block are an error.

```c
int main(void) {
    int x = 1;
    {
        int x = 2;      /* legal: shadows outer x */
        x = x + 10;     /* inner x becomes 12 */
    }
    return x;           /* outer x: returns 1 */
}
```

**Resolution with scopes.** Each map entry now records *two* things: the unique name and whether it was
declared in the current block. Rules:
- Entering a block: build the inner map from the outer one with every entry's "current block" flag cleared.
- Declaration: error only if the name exists **and** was declared in the current block; otherwise insert
  (possibly replacing an outer entry) with the flag set.
- Leaving a block: the outer map is restored unchanged, because you never mutated it.

On the example above: outer map `{x → (x.0, current)}`; in the inner block it becomes
`{x → (x.0, outer)}`, then the declaration replaces it with `{x → (x.1, current)}`. After the block, `return x`
resolves to `x.0`. Resolved AST:
```
D(Declaration("x.0", Some(1)))
S(Compound([ D(Declaration("x.1", Some(2))), S(Expression(Assignment(Var x.1, Binary(Add, Var x.1, 10)))) ]))
S(Return(Var x.0))
```
TACKY simply flattens the block. There is no "enter/leave scope" instruction, and `x.0` and `x.1` just get
different stack slots. Scope is a purely compile-time concept here.

**Two implementation shapes.**
1. *Copy on entry*: clone the map, clear the flags, pass the clone down. Simple, obviously correct, O(n) per block.
2. *Scope stack*: a `Vec` of maps; push on entry, pop on exit; lookup searches from the innermost map outward.
   No clone, but you must pop on every exit path (including early `?` returns).

Either passes the tests. Choose one and be able to defend it.

## Questions the tutor should ask you
1. In `int x = 1; { int y = x; int x = 2; }`, which `x` does `y`'s initializer read? Why?
2. Why do we need the "declared in current block" flag at all? What does `{ int a; } int a;` do with and without it?
3. With copy-on-entry, why don't you need to do anything on block exit?
4. With a scope stack, what happens if resolution of an inner statement fails with `?` before you pop?
5. Why does TACKY need no notion of scope? What invariant from 3.2 makes that true?
6. A clone of a `HashMap<String, Entry>` clones every `String`. When does that cost actually matter for a compiler?

## What you build
- **AST:** a `Block` (list of block items); a `Compound(Block)` statement; function bodies become a `Block`.
- **Parser:** `{` starts a compound statement anywhere a statement is allowed (e.g. `if (a) { int b = 1; }`).
- **Resolution:** scoped maps as described; each entry knows if it belongs to the current block.
- **TACKY:** lower a compound statement by lowering its items in order. No other changes.
- **Must reject:** duplicate declarations in the same block (including at the function body's top level), use of a
  variable after its block ended (`{ int a = 1; } return a;`), unbalanced braces, `int a; { a = b; }` with `b` undeclared.
- **Must accept:** shadowing at any depth, empty blocks `{}`, blocks as `if`/`else` bodies, a name redeclared in a
  sibling block, reading an outer variable in an inner initializer before the inner declaration.
- **Edge cases:** `int x = 1; { int x = x + 1; }`: the inner initializer reads the *inner* `x` (uninitialised; legal to compile).

## Rust focus
- `Clone` and its cost; deriving it on a small entry struct ([std::clone](https://doc.rust-lang.org/std/clone/trait.Clone.html)).
- Iterating mutably to clear flags: `for v in map.values_mut()` ([HashMap::values_mut](https://doc.rust-lang.org/std/collections/struct.HashMap.html#method.values_mut)).
- Scope stack alternative: `Vec<HashMap<…>>`, `iter().rev()` for innermost-first lookup ([Iterator::rev](https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.rev)).
- Borrowing rules when passing `&map` down vs. owning a clone: why a `&mut` to the outer map would be the *wrong* type for copy-on-entry
  ([Book ch. 4.2](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)).
- Recursive enums through a struct (`Statement::Compound(Block)` where `Block` contains statements).

## Common pitfalls
- Mutating the outer map when entering a block, so shadowed names stay overwritten after the block ends.
- Forgetting to clear the "current block" flag on copy, which rejects all shadowing.
- Treating the function body as special and not giving it the same duplicate check as other blocks.
- Using the *source* name as the map value in an inner block and then emitting duplicate pseudo names.
- With a scope stack: forgetting to pop on the error path, or searching outermost-first.
