# Lesson 5.8 — Memory
**Unit:** 5 — A Real Type System · **Type:** Builds `void`, `sizeof`, `malloc` · **Est. time:** 5–8 h · **Tests:** ch. 17
**Prerequisites:** lessons 5.1–5.7

## Learning goals
- Explain *complete* vs. *incomplete* types, and why `void` is an incomplete type that can never be completed.
- Support `void` functions, `void` expressions and casts to `void`.
- Use `void *` as a generic pointer, with its special implicit-conversion rules.
- Implement `sizeof` for types and expressions, and explain why its operand is never evaluated.
- Allocate and free heap memory by calling `malloc`, `calloc` and `free` from libc.

## Key ideas
**Incomplete types.** A type is *complete* when the compiler knows its size. `void` has no size, so you cannot declare a
`void` variable, make an array of `void`, dereference a `void *`, or do arithmetic on one. (GCC allows `void *` arithmetic
as an extension; standard C does not, and neither should you.) In lesson 5.9, `struct s;` adds incomplete types that
*can* later be completed.

**`void` in three roles.**
- *Return type:* `void f(void)` returns nothing. `return;` is required to have no expression in a `void` function, and
  `return expr;` is an error there, even if `expr` has type `void`. Conversely, `return;` in a non-`void` function is an error.
- *Expression type:* a call to a `void` function, or `(void) e`, has type `void`. Such an expression may appear only as an
  expression statement, as the operand of a cast to `void`, as both branches of `?:`, or as the first or third clause of a
  `for` header. Using it anywhere a value is needed (`int x = f();`, `if (f())`, `f() + 1`, `!f()`) is an error.
- *Parameter list:* `(void)` means "no parameters". A parameter of type `void` otherwise is an error.

**`void *`.** A pointer to `void` converts implicitly *to and from* any other object pointer type, in assignments,
arguments, returns and initialisers, so `int *p = malloc(…);` needs no cast. For `==`, `!=` and `?:`, if one side is
`void *` and the other is another object pointer, the common type is `void *`.

**`sizeof`.** `sizeof (type-name)` and `sizeof expr` both produce an `unsigned long` (the type of `size_t` on
x86-64 Linux and macOS) constant computed at compile time. The operand of `sizeof` is type-checked but **not evaluated**,
and an array operand does **not** decay:

```c
int a[10]; int x = 1;
sizeof a;         /* 40, not 8 */
sizeof (x = 5);   /* 4, and x is still 1 */
sizeof x + 1;     /* (sizeof x) + 1 == 5 : sizeof is a unary operator */
```

Parsing ambiguity: after `sizeof (`, look at the next token. A type specifier means a type name; anything else means a
parenthesised expression. `sizeof` on `void`, on a function, or on an incomplete type is an error.

**Worked example.**

```c
void *malloc(unsigned long size);
void free(void *ptr);

int main(void) {
    int *a = malloc(4 * sizeof(int));
    a[3] = 42;
    int r = a[3];
    free(a);
    return r;
}
```

TACKY for the first line (the checker has converted `4` to `unsigned long` and the result from `void *` to `int *`):

```
tmp.0 = SignExtend(4)          # int → unsigned long: signed source, so sign-extend
tmp.1 = tmp.0 * 4UL            # sizeof(int) is just a constant
tmp.2 = malloc(tmp.1)
a = tmp.2                       # void * → int * is a plain copy
```

The call is ordinary System V: `%rdi` holds the size and `%rax` holds the returned pointer. On Linux it is `call malloc@PLT`,
on macOS `call _malloc`. A call to a `void` function has no destination, so make the TACKY call's destination optional
and do not read `%rax` afterwards.

## Questions the tutor should ask you
1. Why is `void` called an incomplete type, and which operations does that rule out?
2. Why does `int *p = malloc(8);` compile without a cast, while `int *p = (long *) q;` does not?
3. What is printed if a program does `sizeof (puts("hi"))`? Why?
4. Why is the result of `sizeof` unsigned, and what does that mean for `sizeof(int) - 5 < 0`?
5. How does your parser tell `sizeof (int) * 2` from `sizeof (x) * 2`, and do they parse the same way?
6. Which pass decides that `return;` in an `int` function is an error?

## What you build
- **Lexer/parser:** the `void` and `sizeof` keywords; `void` as a type specifier (alone only); `sizeof` as a unary operator
  with two forms; `return` with an optional expression; `(void)` parameter lists still mean "no parameters".
- **Types:** `Void`. Add predicates you will reuse: is this type *complete*, *scalar*, *arithmetic*, a pointer to a complete type?
- **Type checker:** all the `void` rules above; `void *` conversions and common pointer type; reject dereferencing or
  subscripting `void *`, pointer arithmetic on `void *`, `sizeof` on incomplete or function types, arrays of incomplete
  element type, and variables of type `void`. Controlling expressions of `if`, loops, `?:`, `!`, `&&`, `||` must be scalar.
  `sizeof` does not decay its operand and does not change the AST of what it inspects.
- **TACKY:** `sizeof` lowers to an `unsigned long` constant; `return;` lowers to a `Return` without a value; the call
  instruction's destination is optional; a cast to `void` evaluates its operand and discards the result.
- **Codegen:** a `void` function's epilogue does not touch `%rax`; a call without a destination skips the result copy.
- **Edge cases:** a `void` function that falls off the end; `?:` with two `void` branches as a statement; comparing a
  `void *` against an `int *`; `calloc` returning zeroed memory; storing `double`s into `malloc`ed memory through a `double *`.

## Rust focus
- **Predicates as methods.** `is_complete`, `is_scalar` and friends are natural methods on your `Type` in an `impl` block.
  Write them once, use them everywhere, and unit-test them.
- **`Option` for "maybe a value".** An optional return expression and an optional call destination are both
  `Option`s. Practise [`Option::map`](https://doc.rust-lang.org/std/option/enum.Option.html#method.map) and `if let`
  instead of `unwrap`:

```rust
if let Some(dst) = maybe_dst { println!("copy result into {dst}"); }
```

- **Recursion over types.** `sizeof` of `int[3][4]` multiplies through nested arrays; write it as a recursive method.

## Common pitfalls
- Evaluating the operand of `sizeof`, so `sizeof (x = 5)` changes `x` or `sizeof f()` calls `f`.
- Decaying an array operand of `sizeof`, so `sizeof a` gives 8.
- Accepting `void *` arithmetic because it "works" with a scale of 1.
- Typing `sizeof` as `int`. It is `unsigned long`, which affects the usual arithmetic conversions around it.
- Forgetting that a `void` call used as an expression statement still needs to be emitted.
