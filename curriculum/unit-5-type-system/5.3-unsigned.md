# Lesson 5.3 — unsigned
**Unit:** 5 — A Real Type System · **Type:** Builds `unsigned` · **Est. time:** 8–12 h · **Tests:** ch. 12
**Prerequisites:** lessons 5.1–5.2

## Learning goals
- Explain which operations on two's-complement bits depend on signedness and which do not.
- Extend the usual arithmetic conversions with signedness, and describe the integer promotions.
- Emit unsigned comparisons (`seta`, `setae`, `setb`, `setbe`) and unsigned division (`div`).
- Implement zero extension, and know why a 32-bit `mov` already zero-extends into a 64-bit register.

## Key ideas
**Same bits, different meaning.** The 32-bit pattern `0xFFFFFFFF` is `-1` as an `int` and `4294967295` as an
`unsigned int`. Addition, subtraction, multiplication (low half) and truncation produce the *same bits* in
both readings, so `addl`, `subl`, `imull` and `movl` work unchanged. Four things differ:
**comparison, division/remainder, widening, and conversion to floating point** (lesson 5.4). Unsigned
arithmetic wraps modulo 2ⁿ by definition. Signed overflow is undefined behaviour, so the compiler may
produce whatever the hardware does.

**Comparisons use different flags.** After `cmp`, signed conditions read SF and OF (`l`, `le`, `g`, `ge`),
while unsigned conditions read CF and ZF (`b` "below", `be`, `a` "above", `ae`). With AT&T operand order,
`cmpl %ebx, %eax` computes `eax - ebx`, so `setb %al` means "eax < ebx, unsigned".

```c
unsigned int lt(unsigned int a, unsigned int b) { return a < b; }
```

```asm
    movl    -4(%rbp), %r10d       # a  (mem→mem fix-up for cmp)
    cmpl    -8(%rbp), %r10d       # a - b
    movl    $0, -12(%rbp)
    setb    -12(%rbp)             # 1 if a < b (unsigned)
```

**Division.** `idiv` is signed. `div` is unsigned and expects the dividend's high half in `%edx`/`%rdx` to be
*zero*, not sign-extended:

```asm
    movl    -4(%rbp), %eax
    movl    $0, %edx              # zero the high half; no cdq
    divl    -8(%rbp)              # quotient → %eax, remainder → %edx
```

**Zero extension.** Widening an unsigned value fills the upper bits with zeros. On x86-64, *any* write to
a 32-bit register zeroes the upper 32 bits of the full register, so `movl src, %r11d` followed by
`movq %r11, dst` is a complete zero extension. Model it as a TACKY `ZeroExtend` and an assembly
`MovZeroExtend` that the fix-up pass lowers to those two moves when the destination is in memory.

**Which conversion instruction?** It depends on the *source* type: a signed source is sign-extended and an
unsigned source is zero-extended, whatever the target. Same-size conversions (`int` ↔ `unsigned int`) are
plain copies, and narrowing is always a `Truncate`.

**Common type with signedness.** If the types are equal, use that type. If they have the same size, the unsigned
one wins. Otherwise the larger one wins. So:
- `-1 < 0u`: `-1` becomes `unsigned int` 4294967295, and the result is `0`.
- `-1L < 0u`: `0u` becomes `long`, and the result is `1`.
- `-1 < 0ul`: `-1` becomes `unsigned long`, and the result is `0`.

**Integer promotions.** Before arithmetic, C converts types narrower than `int` to `int`. You have no such
types yet, but in lesson 5.7 `char` arrives, and every arithmetic operator and unary operator on a `char`
first promotes it. Find the single place in your checker where operands are converted, because that is where promotion will go.

**Constant typing.** `u`/`U` makes a constant unsigned; `ul`, `lu`, `UL`, etc. make it `unsigned long`.
A `u` constant that does not fit in 32 bits becomes `unsigned long`. An unsuffixed decimal constant is
`int` or else `long`, and never becomes unsigned in your compiler.

## What you build
- **Lexer:** `unsigned` and `signed` keywords; constants with `u`, `U`, `l`, `L` suffixes in either order
  (`10ul`, `10LU`). Reject `10uu`, `10lul` and similar.
- **Parser:** specifier lists with signedness: `unsigned`, `unsigned int`, `long unsigned`, `signed long int`.
  Reject `signed unsigned`, and repeated `signed` or `unsigned`.
- **Types:** add `UInt` and `ULong`. Static initial values add unsigned int and unsigned long forms.
  Constants carry four kinds of value.
- **Type checker:** the new common-type rule; constant typing; compile-time conversion of static
  initialisers between all four integer types (wrap, truncate or extend as C does).
- **TACKY:** `ZeroExtend`; casts choose `SignExtend`, `ZeroExtend`, `Truncate` or `Copy` from source and target types.
- **Assembly:** a `Div` instruction; unsigned condition codes `A`, `AE`, `B`, `BE`; `MovZeroExtend`.
  The codegen picks condition codes from the *operand* type of a comparison. TACKY `Binary` `/` and `%`
  pick `Div` vs `Idiv` the same way.
- **Fix-ups:** `div` cannot take an immediate operand (same as `idiv`); `MovZeroExtend` is lowered as above.
- **Edge cases:** `4294967295u + 1u == 0`; `(unsigned long) -1`; division of large unsigned values whose top bit
  is set; `unsigned` parameters passed on the stack; `static unsigned long x = 18446744073709551615ul;`.

## Rust focus
- **Wrapping arithmetic.** When folding static initialisers, use explicit
  [`wrapping_*`](https://doc.rust-lang.org/std/primitive.u64.html#method.wrapping_add) methods or `as`
  casts. Plain `+` panics on overflow in debug builds.
- **`as` between signed and unsigned keeps the bits.** `-1_i32 as u32` is `4294967295`, and `-1_i32 as u64` sign-extends first.
  Write tiny `#[test]`s to confirm each conversion you rely on.
- **`matches!` for predicates.** Yes/no questions about an enum value ("is this type signed?") read well
  with [`matches!`](https://doc.rust-lang.org/std/macro.matches.html), shown here on a plain `char`:

```rust
let is_ident_start = matches!(c, 'a'..='z' | 'A'..='Z' | '_');
```

## Common pitfalls
- Choosing sign vs. zero extension from the *target* type instead of the *source* type.
- Choosing condition codes from the comparison's *result* type (always `int`) instead of its *operand* type.
  Equality is sign-agnostic; `<`, `<=`, `>` and `>=` are not.
- Emitting `cdq` before `div`, so the result looks correct for small values and is wrong for large ones.
- Storing an unsigned constant in an `i64` and then range-checking it as signed. `18446744073709551615ul`
  does not fit in an `i64` but is valid.
- Looking for a 32→64-bit `movz` instruction. There is none (`movzbl`/`movzwl` exist only for 8/16-bit
  sources); a plain `movl` into a register *is* the zero extension.
