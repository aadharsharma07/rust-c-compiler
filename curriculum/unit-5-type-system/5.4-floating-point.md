# Lesson 5.4 — Floating point
**Unit:** 5 — A Real Type System · **Type:** Builds `double` · **Est. time:** 12–18 h · **Tests:** ch. 13
**Prerequisites:** lessons 5.1–5.3, 4.3 (System V calling convention)

## Learning goals
- Describe the IEEE 754 binary64 format (sign, 11-bit exponent, 52-bit fraction) and why most decimals are inexact.
- Generate SSE scalar code: `movsd`, `addsd`/`subsd`/`mulsd`/`divsd`, `xorpd`, `comisd`, using `%xmm0–%xmm15`.
- Convert between integers and doubles with `cvtsi2sd` and `cvttsd2si`, including the unsigned cases.
- Place double constants in read-only data and address them RIP-relatively, on both Linux and macOS.
- Pass and return doubles by the System V rules, and compare doubles correctly when NaN is involved.

## Key ideas
**IEEE 754 doubles.** A double is 64 bits: 1 sign bit, an 11-bit biased exponent and a 52-bit fraction. `2.0` is
`0x4000000000000000`; `-0.0` is `0x8000000000000000`, which is a different bit pattern from `0.0` even though they compare equal.
Constants are rounded to the nearest representable value *at compile time*, so `0.1` is stored as
`0x3FB999999999999A`.

**A second register file.** Doubles live in the 128-bit `%xmm` registers (scalar ops use the low 64 bits).
There is no SSE instruction with an immediate operand, so every double constant becomes a labelled 8-byte
value in read-only data:

```asm
# Linux                              # macOS
    .section .rodata                     .literal8
    .balign 8                            .balign 8
.Lconst.0:                           Lconst.0:
    .quad 4611686018427387904            .quad 4611686018427387904   # 2.0
```

Local labels start with `.L` on Linux and `L` on macOS (no `_` prefix). Use them as `Lconst.0(%rip)`.
Emitting the raw bits with `.quad` avoids any decimal round-trip error. The negation mask for `xorpd` must be
16-byte aligned (`.literal16` on macOS, `.balign 16` on Linux), because `xorpd` with a memory operand reads 16 bytes.

**Worked example.**

```c
double half(double x) { return x / 2.0; }
```

```
half(x):
    tmp.0 = x / 2.0
    Return(tmp.0)
```

```asm
    movsd   %xmm0, -8(%rbp)          # x arrives in xmm0
    movsd   -8(%rbp), %xmm14
    movsd   %xmm14, -16(%rbp)        # tmp.0 = x   (mem→mem fix-up)
    movsd   -16(%rbp), %xmm15
    divsd   Lconst.0(%rip), %xmm15   # SSE arithmetic needs a register destination
    movsd   %xmm15, -16(%rbp)
    movsd   -16(%rbp), %xmm0         # return value in xmm0
```

Reserve `%xmm14`/`%xmm15` as fix-up scratch registers, in the same way you use `%r10`/`%r11`.

**Conversions.** `cvtsi2sdl`/`cvtsi2sdq` convert a signed 32/64-bit integer to a double; the source cannot be an
immediate and the destination must be an `xmm` register. `cvttsd2sil`/`cvttsd2siq` convert a double to an integer,
*truncating* toward zero, and their destination must be a general-purpose register. Unsigned types need extra work:
- `unsigned int` → double: zero-extend to 64 bits, then `cvtsi2sdq`.
- double → `unsigned int`: `cvttsd2siq` into a 64-bit register, keep the low 32 bits.
- `unsigned long` → double: if the value is non-negative as a signed number, use `cvtsi2sdq`. Otherwise halve it with
  `shrq $1`, OR the lost low bit back in (so rounding stays correct), convert, then `addsd` the result to itself.
- double → `unsigned long`: if the value is below 2⁶³, use `cvttsd2siq` directly. Otherwise subtract 2⁶³ (as a double),
  convert, then add 2⁶³ back as an integer (a 64-bit immediate, so it needs a register).

**The calling convention for doubles.** The first eight double arguments go in `%xmm0–%xmm7`, counted
*separately* from integer arguments in `%rdi…%r9`. Any argument left over goes on the stack, pushed
right to left, in its original order among the other stack arguments. A double is returned in `%xmm0`. All `xmm`
registers are caller-saved.

```c
double f(int a, double b, long c, double d);  /* a→%edi  b→%xmm0  c→%rsi  d→%xmm1 */
```

**Comparisons and NaN.** `comisd %xmm1, %xmm0` compares `xmm0` with `xmm1` and sets ZF, PF and CF like an
unsigned compare: greater = all clear, less = CF, equal = ZF. *Unordered* (either is NaN) sets ZF=PF=CF=1.
Read naively, `setb` would say NaN < x is true and `sete` would say NaN == NaN is true. NaN-safe lowering:
- `a > b` → `seta`; `a >= b` → `setae` (both are false when unordered, as required).
- `a < b` → compute `b > a` (swap operands, then `seta`); likewise `<=` becomes swapped `setae`.
- `a == b` → `sete` AND `setnp`; `a != b` → `setne` OR `setp`.
- Truthiness (`if (d)`, `!d`, `&&`): compare against `0.0` (zero a register with `xorpd %xmm0, %xmm0`) and
  treat unordered as *true*, since NaN is non-zero.

## What you build
- **Lexer:** floating constants: `1.0`, `1.`, `.5`, `1e10`, `1E-3`, `2.5e+2`. Reject `1.0.0`, `1e`, `1.e+`, `2._`
  and a constant followed directly by a letter or `.`.
- **Parser/types:** the `double` keyword (not combinable with `long`, `signed` or `unsigned`); a `Double` type;
  double constants and static initial values.
- **Type checker:** if either operand is `double`, the common type is `double`. Reject `%`, `~` and (if you did the extra
  credit) bitwise and shift operators on doubles. Convert static initialisers between doubles and integers at compile time
  (truncating toward zero).
- **TACKY:** `DoubleToInt`, `DoubleToUInt`, `IntToDouble`, `UIntToDouble`.
- **Assembly:** `Double` assembly type; `Cvtsi2sd`, `Cvttsd2si`; SSE binary ops including `xorpd`;
  `Cmp` on doubles emits `comisd`; parity condition codes; `xmm` registers; a table of static constants
  keyed by (value bits, alignment) so equal constants share one label.
- **Calls:** classify each argument and parameter as integer or SSE; copy parameters from `xmm` registers and the stack;
  read the return value from `%xmm0` based on the return type.
- **Fix-ups:** SSE arithmetic and `comisd` need a register destination (use `%xmm15`); `cvttsd2si` needs a register
  destination (`%r11`); `cvtsi2sd` needs a non-immediate source and a register destination; `movsd` cannot go from memory to memory.

## Rust focus
- **`f64` bit handling.** [`f64::to_bits`](https://doc.rust-lang.org/std/primitive.f64.html#method.to_bits) gives
  you a `u64` that is exact, hashable and distinguishes `-0.0` from `0.0`, unlike `f64` itself, which is neither
  `Eq` nor `Hash`:

```rust
assert_ne!(0.0_f64.to_bits(), (-0.0_f64).to_bits());
```

- **Parsing.** `str::parse::<f64>` rounds correctly to nearest, which is what C requires for decimal literals.
- **`as` casts from float** saturate in Rust (`f64::NAN as i32 == 0`), while x86 returns `0x80000000`. Out-of-range
  conversion is undefined behaviour in C, so do not rely on either.
- **Deriving `Eq` on an enum that contains an `f64`** will fail. Decide where you store bits rather than floats.

## Common pitfalls
- Using `.align 8` on macOS (that means 256 bytes) or forgetting the alignment directive entirely.
- Numbering integer and SSE argument registers with one shared counter.
- `comisd` operand order: AT&T `comisd %xmm1, %xmm0` compares `%xmm0` *to* `%xmm1`.
- Emitting doubles in decimal with `{}`, so `0.1` round-trips through text. `.quad` with the bits is exact.
- Truthiness tests that use `je` after `comisd` without checking parity, so `if (nan)` is skipped.
- Giving `double` stack slots 4-byte alignment.
