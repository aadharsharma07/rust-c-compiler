# Lesson 5.1 — Types in a compiler
**Unit:** 5 — A Real Type System · **Type:** Builds `Type` enum + typed AST · **Est. time:** 4–6 h · **Tests:** ch. 11 (front end only: `--stage validate`)
**Prerequisites:** lessons 4.1–4.5 (a compiler passing chapters 1–10)

## Learning goals
- Explain what a *type* means to a compiler: a size, an alignment, and a set of legal operations.
- Describe a typed AST: every expression node knows its type after type checking.
- Apply the *usual arithmetic conversions* to find the common type of a binary expression.
- Distinguish explicit conversions (a cast written by the programmer) from implicit ones (inserted by the compiler).
- Prepare the front end for `long` so that lesson 5.2 can concentrate on the back end.

## Key ideas
**Until now every value was an `int`.** Your type checker only checked *function* types (arity,
conflicting declarations). From this lesson on, every expression has a type, and that type decides
which instructions the back end emits. `a + b` on two `int`s is `addl`; on two `long`s it is `addq`.

**A type is data the compiler carries around.** You need a type representation with at least `Int`,
`Long` and a function type (a list of parameter types plus a return type). Later lessons add
`UInt`, `ULong`, `Double`, `Pointer(T)`, `Array(T, n)`, three `char` types, `Void` and `Structure(tag)`,
so design for growth.

**Annotating the AST.** After type checking, each expression node carries its type. There are two
common designs: (a) an optional type field on every expression, filled in by the checker; (b) a
separate "typed" expression tree the checker produces. Both work. Option (a) is less code; option (b)
lets the compiler prove that later passes never see an untyped node. Choose one and explain your choice in your journal.

**Implicit conversions become explicit casts.** The type checker inserts a `Cast` node wherever C
converts a value without being asked. After this pass, later stages never need to work out a conversion; they
only lower `Cast` nodes. Example:

```c
long f(int a, long b) {
    return a + b;
}
```

After type checking (types in brackets):

```
Return(
  Binary(Add,
    Cast(Long, Var a [Int]) [Long],
    Var b [Long]
  ) [Long]
)
```

**The usual arithmetic conversions (for now).** If both operands have the same type, that is the common
type. Otherwise, with only `int` and `long`, the common type is `long`. The result of `+ - * / %` has the
common type. The result of a comparison or `&& || !` is always `int`, though the *operands*
of a comparison are still converted to their common type before comparing.

**Conversion "as if by assignment."** Assignments, initialisers, function arguments and `return`
convert the value to the *target's* type, even when that narrows `long` to `int`.

**Casts and type specifiers.** `(long) x` needs the parser to recognise a type name after `(`. A type
specifier is now a *list* of keywords in any order: `long`, `long int`, `int long` all mean `long`.
Constants get types too: `100` is `int`, `100L`/`100l` is `long`, and an unsuffixed constant too big
for `int` (such as `2147483648`) is `long`.

**Static initialisers are converted at compile time.** In `static int x = 4294967297L;` the
compiler must compute the converted value itself (wrap modulo 2³², giving `1`) because no code runs to
convert it.

## Questions the tutor should ask you
1. Why is the type of `a < b` always `int`, even when `a` and `b` are `long`?
2. Where else, apart from binary operators, does C convert a value implicitly? List at least four places.
3. What do you gain if the checker makes conversions explicit as `Cast` nodes, instead of TACKY generation inferring them?
4. A parameter is declared `int` in the prototype and `long` in the definition. Which pass reports this, and why?
5. How would you tell `(long) x` (a cast) from `(x)` (a parenthesised expression) with one token of lookahead?
6. Why must `static long x = 2147483648;` be computed by the compiler, while `long x = 2147483648;` inside a function need not be?

## What you build
- **Lexer:** the `long` keyword; long constants with an `l`/`L` suffix. Reject malformed suffixes such as
  `1LL`, `1lL` or `1L2`. Make sure a constant is still not allowed to run into an identifier character.
- **Parser:** type-specifier lists in declarations, parameters and casts. Reject an empty specifier list,
  duplicates like `int int` or `long int long`, and storage-class problems as before. Add a `Cast(target type, expr)` expression
  at the same precedence as unary operators. A constant node now stores either an int or a long value.
  Decide the constant's type in the parser or the checker: `int` if it fits in 32 bits and has no suffix, otherwise `long`.
  A constant that does not fit in 64 bits is an error.
- **Data types:** a `Type` with `Int`, `Long`, and a function type holding parameter types and a return type. A
  constant value type holding an `i32` or an `i64`. Symbol-table entries now store a full type, and static variables
  store a typed initial value (int or long).
- **Type checker:** annotate every expression; insert `Cast` for every implicit conversion; check that
  redeclarations of variables and functions use *identical* types; convert static initialisers at compile
  time; convert `return` values to the function's return type, and arguments to parameter types.
- **Leave alone for now:** TACKY and codegen. It is fine if `long` programs do not run yet. Chapters 1–10
  must still pass end to end.

## Rust focus
- **Growing an enum with data.** `Type` will gain variants in nearly every lesson. Derive `Debug, Clone,
  PartialEq, Eq` from the start (`Hash` too if you key maps by type).
  See [Rust Book ch. 6](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html).
- **Exhaustive `match` as a refactoring safety net.** Avoid `_ =>` catch-alls on `Type`. When you add `UInt`
  in 5.3, the compiler will then list every place that must handle it.
- **Fallible numeric conversions.** `i32::try_from(value)` tells you whether a constant fits, and
  `value as i32` does the C-style wrap. Know which one you mean each time. See
  [`TryFrom`](https://doc.rust-lang.org/std/convert/trait.TryFrom.html) and
  [`as` casts](https://doc.rust-lang.org/reference/expressions/operator-expr.html#type-cast-expressions):

```rust
let fits = i32::try_from(4_294_967_297_i64).is_ok(); // false
let wrapped = 4_294_967_297_i64 as i32;              // 1
```

## Common pitfalls
- Forgetting that the *operands* of `<` are converted to the common type, while its *result* is `int`.
- Giving an unsuffixed `2147483648` type `int` (it is `long`) or parsing `-2147483648` as one constant
  (it is unary minus applied to a `long` constant).
- Comparing function types by parameter count only. `int f(int)` and `int f(long)` conflict.
- Inserting a cast only when types differ in some places and always in others. Pick one rule (for example,
  "cast only when the types differ") and apply it everywhere.
- Annotating `Assignment` with the right-hand side's type instead of the left-hand side's.
