# Lesson 0.6 — Parsing
**Unit:** 0 — Rust Foundations · **Type:** Builds calculator parser + evaluator · **Est. time:** 5–8 h · **Tests:** none (your own `cargo test`)
**Prerequisites:** lessons 0.1–0.5 (a working calculator lexer)

## Learning goals
- Read and write a grammar in BNF/EBNF, and distinguish terminals (tokens) from non-terminals (rules).
- Implement recursive descent: one function per grammar rule, consuming tokens left to right.
- Encode precedence with grammar *levels* and left associativity with *loops*, and explain why left recursion breaks recursive descent.
- Build a `Box`-based AST and evaluate it recursively with checked arithmetic and `Result` errors.

## Key ideas
**Grammars.** A grammar is a set of rules saying which token sequences are valid and how they
group. The calculator's grammar in EBNF (`{ … }` = zero or more, `|` = or):
```
<expr>    ::= <term>   { ("+" | "-") <term> }
<term>    ::= <unary>  { ("*" | "/") <unary> }
<unary>   ::= "-" <unary> | <primary>
<primary> ::= <int> | "(" <expr> ")"
```
**Precedence via levels.** Lower rules bind tighter. Because `<term>` sits *below* `<expr>`, a
`*` is grouped before the surrounding `+` ever sees it. Parentheses jump back to the top
(`<expr>`), which is how they override precedence.

**Recursive descent.** Each rule becomes a function that looks at the current token, decides what
to do, consumes what it recognises, and returns an AST node (or an error). Rules call each other
exactly as the grammar references them, so the call stack *is* the parse tree.

**Associativity via loops.** The tempting rule `<expr> ::= <expr> "-" <term>` is *left-recursive*:
a function for `<expr>` would call itself first, without consuming anything, forever. The `{ … }`
form instead parses one `<term>`, then loops: while the next token is `+`/`-`, consume it, parse
another `<term>`, and make a new node whose **left** child is everything so far. That builds a
left-leaning tree, i.e. left associativity.

**Worked example.** `1 - 2 - 3`: the loop builds `Sub(Num 1, Num 2)`, then wraps it:
`Sub(Sub(Num 1, Num 2), Num 3)` → `-4` (not `2`, which right association would give).

`2 * (3 + 4) - -1`:
```
Tokens: 2 * ( 3 + 4 ) - - 1
AST:    Sub( Mul( Num 2, Add(Num 3, Num 4) ), Neg(Num 1) )
Value:  14 - (-1) = 15
```
Trace: `expr` → `term` → `unary` → `primary` reads `2`; `term` sees `*`, calls `unary` → `primary`,
which sees `(` and recurses into `expr` for `3 + 4`, then expects `)`. Back in `expr`, `-` is seen;
the right `term` → `unary` sees `-` and recurses into `unary` for `1`.

**Errors.** A parser must reject: an unexpected token (`1 + * 2`), premature end (`(1 + 2`),
and leftover tokens (`1 2` — `expr` succeeds on `1`, but input isn't finished).

**Evaluation.** A recursive post-order walk. Use C-like integer semantics: division truncates
toward zero (`-7 / 2 = -3`). Division by zero and overflow (`9223372036854775807 + 1`, and the
sneaky `i64::MIN / -1`) are runtime *errors*, not panics.

## Questions the tutor should ask you
1. Which rule would you change to add `%` with the same precedence as `*`? Why only that one?
2. Write the left-recursive rule for subtraction. What happens when you translate it naively into a function?
3. How does the parser know `1 2` is an error, if `expr` happily parses `1`?
4. Draw the AST for `-2 * 3`. Does unary minus bind tighter than `*` in this grammar?
5. Should "division by zero" be reported by the parser or the evaluator? Why?
6. Is `- -1` valid? What about `--1`? (C has a `--` token. Your lexer doesn't. Lesson 2.1 revisits this.)

## What you build
A **parser and evaluator** for the calculator, continuing the `calc` crate.
- **AST to design (as a recursive enum):** integer literal; unary negation (one boxed child);
  binary operation (an operator and two boxed children). Choose whether operators are a separate
  small enum (recommended) or one variant per operator. Derive `Debug` and `PartialEq`.
- **Parser:** input is the token vector from 0.5; output is `Result<Expr, ParseError>`. Track the
  current position in the token list. One function per grammar rule.
- **Parse errors to design:** unexpected token (what was found, at which offset, and ideally what
  was expected); unexpected end of input; trailing input after a complete expression.
- **Evaluator:** `&Expr` → `Result<i64, EvalError>`, with errors for division by zero and overflow.
- **Pipeline:** `main` reads one line → lex → parse → evaluate → print the value, or print the
  first error from any stage. Lexer errors, parse errors and eval errors must all reach the user.
- **Tests (≥12):** precedence (`1+2*3` → 7), parentheses (`(1+2)*3` → 9), left associativity
  (`1-2-3` → -4, `8/4/2` → 1), unary (`-3`, `- -1`, `-2*3`), nesting (`((((5))))`),
  truncation (`-7/2` → -3), each parse error, divide by zero, overflow. Test the parser by comparing
  ASTs, and the evaluator separately on hand-built ASTs.

## Common pitfalls
- Writing left-recursive functions → stack overflow. Use the loop form.
- Building right-leaning trees in the loop, so `1-2-3` evaluates to `2`.
- Forgetting to check for leftover tokens at the end, so `1 2` silently returns `1`.
- Indexing `tokens[pos]` past the end and panicking instead of returning "unexpected end of input".
- Evaluating during parsing; keep the AST as the interface so later passes can reuse it.
- Using `/` and `+` on `i64` directly: overflow panics in debug and wraps in release.
