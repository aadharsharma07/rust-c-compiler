# Lesson 0.4 — Trees in Rust
**Unit:** 0 — Rust Foundations · **Type:** Learning only · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 0.1–0.3

## Learning goals
- Explain what an abstract syntax tree (AST) is and why a compiler uses a tree rather than a token list.
- Understand why a recursive `enum` needs indirection, and use `Box<T>` to provide it.
- Write recursive functions over trees by `match`ing on variants (evaluate, count, print, measure depth).
- Distinguish abstract syntax (structure) from concrete syntax (parentheses, spacing).

## Key ideas
**Why a tree?** Tokens are flat; meaning is nested. In `1 + 2 * 3` the multiplication is a
*sub-part* of the addition. A tree makes that grouping explicit, so later passes never
re-think precedence:

```
Tokens: Number(1) Plus Number(2) Star Number(3)

AST:        Add
           /   \
     Num(1)     Mul
               /   \
          Num(2)   Num(3)
```
`(1 + 2) * 3` gives a different tree (`Mul` at the root, `Add` on the left), and the parentheses
themselves do **not** appear in the AST: they only shaped it. That's what *abstract* means.

**Recursive types need indirection.** A type that contains itself directly would have infinite
size. Rust must know every type's size at compile time, so the recursive field is stored behind a
pointer: `Box<T>` puts the child on the heap and has a fixed pointer size. The compiler's error
(E0072, "recursive type has infinite size") even suggests this.

**Isolated illustration** (the classic cons list, not your calculator):
```rust
enum List { Cons(i32, Box<List>), Nil }
let l = List::Cons(1, Box::new(List::Cons(2, Box::new(List::Nil))));
```

**Ownership of trees.** Each `Box` owns its child, so the root owns the whole tree and dropping it
frees everything. A tree built this way has no sharing and no cycles, which fits ASTs perfectly.
Functions that only *inspect* a tree take `&Node`; functions that *rebuild* it take ownership.

**Recursion over a tree** mirrors the type: one `match` arm per variant; leaf arms return
directly; branch arms recurse into children (through the `Box`, which derefs automatically in
most expressions and can be matched via `&**child` or by binding a reference).

**Worked example: evaluation order.** Evaluating the AST above: `Add` evaluates its left child
(`1`), then its right child; `Mul` evaluates `2` and `3` → `6`; `Add` combines → `7`. This is a
post-order traversal: children first, then the node.

## Questions the tutor should ask you
1. Draw the trees for `1 - 2 - 3` and `1 - (2 - 3)`. Which one does ordinary arithmetic mean?
2. Why does the compiler reject a recursive enum without `Box`? What size would it need?
3. Where do parentheses go in an AST? Why is it fine to drop them?
4. A function computes a tree's depth. Should it take the tree by value or by reference? Why?
5. What would be inconvenient about evaluating directly from the token list instead of from a tree?

## What you build
Learning only. Practise on toy trees **unrelated to arithmetic**, so the calculator AST in 0.6
is still yours to design:
1. **Binary search tree of `i32`.** Define it with `Option<Box<...>>` children. Write `insert`,
   `contains`, `len`, `depth` and an in-order traversal returning a `Vec<i32>`. Test with an empty
   tree, one node, and a degenerate (sorted-insert) tree.
2. **Boolean expression tree.** Variants: literal true/false, `Not`, `And`, `Or`. Write
   `eval`, `count_nodes`, and a `to_string`-style function that prints fully parenthesised form,
   e.g. `(true AND (NOT false))`. Build trees by hand in tests.
3. Trigger E0072 on purpose by removing a `Box`, and explain the message.
4. **On paper:** draw the AST for `2 * (3 + 4) - -1` using the token list you designed in 0.3. Mark
   which nodes are leaves. Discuss with the tutor how a unary minus differs from a binary minus in the tree.
5. Rustlings: `19_smart_pointers` (the `box1` exercise), and revisit `08_enums` if shaky.

## Common pitfalls
- Boxing everything (including leaf data) when only the recursive field needs it.
- Moving a child out of a tree you only borrowed ("cannot move out of `*x`"); match on references instead.
- Writing a deeply recursive function without a base case for the leaf variants.
- Confusing `Option<Box<T>>` (maybe a child) with `Box<Option<T>>`.
- Storing parentheses as a node kind: that's concrete syntax leaking into the AST.
