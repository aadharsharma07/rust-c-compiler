# Lesson 0.7 — Organising Code
**Unit:** 0 — Rust Foundations · **Type:** Builds calculator REPL in modules · **Est. time:** 3–4 h · **Tests:** none (your own `cargo test`)
**Prerequisites:** lessons 0.1–0.6 (a working lexer, parser and evaluator)

## Learning goals
- Split a crate into modules that mirror compiler phases, and decide what each module makes `pub`.
- Define and implement a trait you didn't write (`std::fmt::Display`) for your own AST and error types.
- Build a read–eval–print loop that survives errors and exits cleanly on end-of-file.
- Explain why a pipeline of modules with narrow interfaces makes a compiler easier to extend and test.

## Key ideas
**Modules mirror phases.** Each phase gets a module with a small public surface: the lexer exposes
"text → tokens", the parser "tokens → AST", the evaluator "AST → value". Helpers (peeking,
precedence-level functions) stay private. Your C compiler will have the same layout, with more
phases: lexer, parser, semantic passes, TACKY generation, codegen, emission.

**How Rust finds modules.** `mod lexer;` in `main.rs` (or `lib.rs`) tells the compiler to load
`src/lexer.rs` (or `src/lexer/mod.rs`). Items are private to their module by default; `pub` makes
them visible to the parent. Paths: `crate::ast::Expr` from anywhere, `super::` for the parent.
`use` brings a path into scope. A common shape is `lib.rs` declaring the modules and `main.rs`
being a thin binary that uses the library, so integration tests in `tests/` can call it too.

**Traits.** A trait is a set of methods a type promises to provide. Implementing
`std::fmt::Display` for a type means `{}` in `println!`/`format!` works for it, and you get
`.to_string()` for free. `Debug` (`{:?}`) is for developers and can be derived; `Display` is for
users and must be written by hand.

**Isolated illustration** (toy type, not your AST):
```rust
struct Celsius(f64);
impl fmt::Display for Celsius { fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result { write!(f, "{}°C", self.0) } }
```

**Worked example: pretty-printing an AST.** A fully parenthesised printer makes the tree's shape
visible. For input `2 * (3 + 4) - -1`, the AST `Sub(Mul(2, Add(3, 4)), Neg(1))` displays as:
```
((2 * (3 + 4)) - (-1))
```
Re-parsing that text gives the **same** AST: a "round-trip" property worth testing. (A printer
that omits redundant parentheses is harder: it must know precedence. Try it as a stretch goal.)

**REPL session the spec expects:**
```
> 1 + 2 * 3
7
> :ast (1+2)*3
((1 + 2) * 3)
> 2 $ 3
error: unexpected character '$' at column 3
> 4 / 0
error: division by zero
> (Ctrl-D)
```

## Questions the tutor should ask you
1. Which items in your lexer must be `pub`, and which should stay private? Why keep the surface small?
2. Why does `Display` need to be hand-written while `Debug` can be derived?
3. What should the REPL do on an empty line? On end-of-file? On an error?
4. Where should the "column 3" (1-based, for humans) conversion from a 0-based offset happen?
5. If you later add a `%` operator, which modules change? Which shouldn't?

## What you build
Refactor `calc` into modules and wrap it in a **REPL**.
- **Layout (suggested):** `token`/`lexer`, `ast`, `parser`, `eval` and an `error` module (or errors
  per module), declared from `lib.rs`; `main.rs` contains only the REPL. Each module exposes one entry
  function plus the types callers need.
- **`Display` impls:** for the AST (fully parenthesised, spaces around binary operators, `(-x)` for
  negation), for each error type (human-readable, 1-based column), and for tokens (their lexeme).
- **REPL behaviour:** print a `> ` prompt and flush stdout; read a line; skip blank lines; `:ast <expr>`
  prints the parsed AST via `Display` instead of evaluating; `:quit` or EOF exits with status 0;
  any error prints `error: …` and the loop continues. Errors go to stderr, results to stdout.
- **Non-interactive use:** piping works: `echo "6*7" | cargo run -q` prints `42` (and a prompt is
  acceptable). Optional: `--ast` flag on the command line.
- **Tests:** existing unit tests move into their modules under `#[cfg(test)]`; add `Display` tests
  for the AST and errors, and a round-trip test (parse → display → parse gives the same AST) over at
  least five expressions. Optional: one integration test in `tests/` that uses only `pub` items.

## Common pitfalls
- Making everything `pub` "to get it compiling"; it hides the real interface.
- Forgetting to flush stdout, so the `> ` prompt appears after the input.
- Treating `read_line` returning `Ok(0)` as an empty line and looping forever at EOF.
- Not clearing the `String` buffer between `read_line` calls (it appends).
- Recursion in `Display` that calls `{:?}` on children instead of `{}`, mixing formats.
- Circular `use` tangles: keep dependencies flowing one way (lexer ← parser ← eval ← main).

## Done when
- [ ] The crate is split into phase modules with minimal `pub` items; `main.rs` holds only the REPL.
- [ ] `cargo test` passes (all previous tests plus `Display` and round-trip tests); `cargo clippy` is clean; `cargo fmt --check` passes.
- [ ] The REPL session above behaves as shown, including EOF and errors.
- [ ] You can explain how `mod`, `pub` and `use` work, and what implementing a trait means, without notes.
- [ ] You can sketch which modules your C compiler will have and what each one's public function takes and returns.
