# Lesson 0.5 — Lexing
**Unit:** 0 — Rust Foundations · **Type:** Builds calculator lexer · **Est. time:** 3–5 h · **Tests:** none (your own `cargo test`)
**Prerequisites:** lessons 0.1–0.4

## Learning goals
- Define *token*, *lexeme* and *token kind*, and explain what a lexer discards (whitespace) and keeps (positions).
- Apply the *longest-match* (maximal munch) rule and use one character of lookahead to decide where a token ends.
- Iterate over input with `chars()` / `char_indices()` and `peekable()`, using `peek` vs. `next` correctly.
- Report lexical errors as values (`Result`) carrying a position, never by panicking.

## Key ideas
**Vocabulary.** A *lexeme* is a run of source characters (`"42"`); a *token* is the classified
result (`Number(42)`); the *kind* is the classification alone (`Number`). The lexer turns a
character stream into a token stream, throwing away whitespace and (in C) comments.

**Longest match.** At each position, take the longest prefix that forms a valid token. `123`
is one number, not `1`,`2`,`3`. In C this decides that `>=` is one token rather than `>` then `=`,
and why `a---b` lexes as `a -- - b`. For the calculator only numbers span several characters.

**Lookahead.** To know a number has ended you must look at the *next* character without
consuming it: is it another digit? `Peekable` adds `peek()` (look) alongside `next()` (consume).
One character of lookahead is enough for everything in this calculator.

**Worked example.** Input `"12*(3 - 40)"`, written as `kind@byte-offset`:
```
Number(12)@0  Star@2  LParen@3  Number(3)@4  Minus@6  Number(40)@8  RParen@10
```
`" 7 "` → `[Number(7)]`; `""` → `[]`; `"2 $ 3"` → error: unexpected character `$` at offset 2.

**Minus is never part of a number literal.** `"3-5"` must be `Number(3) Minus Number(5)`; if the
lexer glued `-5` together, the parser would see two numbers in a row. Negation is the parser's job.
C does the same: `-1` is a unary minus applied to `1`.

**Lexer state machine.** A hand-written lexer is a loop: peek a character; dispatch on it
(whitespace → skip; digit → consume all following digits; single-char operator → emit; anything
else → error). Each branch either consumes at least one character or returns, so the loop terminates.

## Questions the tutor should ask you
1. What's the difference between a lexeme and a token? Which one does the parser want?
2. How do you know where `123` ends without consuming the character after it?
3. Why shouldn't the lexer turn `-5` into a single negative number?
4. What should happen for `99999999999999999999` (too big for `i64`)? Whose job is it to report it?
5. Why return `Result<Vec<Token>, _>` rather than printing an error and exiting?
6. Should positions be byte offsets or character counts? Does it matter for ASCII input?

## What you build
A **calculator lexer** in a new crate `cargo new calc` (one file is fine this lesson; 0.7 splits it).
- **Input:** a `&str` (one line of user input).
- **Output:** `Ok` with a vector of tokens, or `Err` with a lexical error.
- **Token kinds to design (as an enum):** integer literal (carrying its value as `i64`), `+`, `-`,
  `*`, `/`, `(`, `)`. Optional: `%`. Each token also records the byte offset where it starts
  (a struct wrapping the kind and position is a good design; you choose).
- **Error type to design:** unexpected character (which char, which offset); integer literal out of
  range (which offset). Derive `Debug` and `PartialEq` so tests can compare.
- **Rules:** skip ASCII whitespace; maximal munch for digit runs; leading zeros are fine (`007` → 7);
  `1a` → `Number(1)` then an error at `a` (the first error wins and lexing stops).
- **Temporary main:** read one line from stdin and print the `Debug` form of the result.
- **Tests (write at least 8):** empty input; whitespace only; single number; multi-digit number;
  every operator; `"3-5"`; no spaces vs. lots of spaces give the same kinds; bad character position;
  overflow; parentheses nesting `"((1))"`.

This is the same job your C lexer does in lesson 1.3, with more token kinds.

Isolated illustration of peeking (unrelated to tokens):
```rust
let mut it = "aab".chars().peekable();
while it.next_if_eq(&'a').is_some() {} // consumes both 'a's, stops before 'b'
```

## Common pitfalls
- Calling `next()` to "check" a character and losing it; use `peek()` until you've decided.
- An infinite loop: a branch that neither consumes a character nor returns.
- Building numbers with unchecked arithmetic and silently wrapping (or panicking in debug builds) on overflow.
- Including the trailing `\n` from `read_line` as an "unexpected character"; it is whitespace.
- Recording character counts in one place and byte offsets in another.
- Lexing negative literals.
