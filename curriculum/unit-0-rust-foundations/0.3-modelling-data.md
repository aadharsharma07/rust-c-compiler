# Lesson 0.3 — Modelling Data
**Unit:** 0 — Rust Foundations · **Type:** Learning only · **Est. time:** 4–6 h · **Tests:** none
**Prerequisites:** lessons 0.1–0.2

## Learning goals
- Model "one of several shapes" with an `enum` whose variants carry data, and "several fields together" with a `struct`.
- Use exhaustive `match` (with bindings, guards and `_`) and explain why exhaustiveness helps compiler writers.
- Represent absence with `Option<T>` and failure with `Result<T, E>`; propagate errors with `?`.
- Design a small custom error type and describe how a token type for a lexer could be modelled.

## Key ideas
**Sum and product types.** A `struct` is a *product*: a value has all its fields. An `enum` is a
*sum*: a value is exactly one variant, and each variant can carry different data. Compilers are
full of sums: a token is a number *or* a plus *or* a left paren; an expression is a constant *or*
a binary operation.

**`match` is exhaustive.** The compiler rejects a `match` that forgets a variant. When you later
add a new operator variant, every `match` that doesn't handle it becomes a compile error, which
is a free to-do list. Avoid `_ =>` catch-alls where you want that protection.

**Option and Result.** `Option<T>` is `Some(T)` or `None` ("maybe a value"). `Result<T, E>` is
`Ok(T)` or `Err(E)` ("a value or a reason it failed"). Neither is magic; both are ordinary enums.
The `?` operator on a `Result` returns early with the `Err` (converting it via `From` if needed)
and otherwise unwraps the `Ok`.

**Worked example: modelling a calculator token (in words).** The input `(7 - 2)` contains five
tokens: left paren, number 7, minus, number 2, right paren. A good model is one enum with a
variant per kind of token; only the number variant carries data (its value). You might also
want each token's *position* (byte offset) for error messages; that suggests a struct wrapping
the kind plus a position. Writing this down as data:

```
[LParen@0, Number(7)@1, Minus@3, Number(2)@5, RParen@6]
```

**Errors as data.** Rather than `String` errors everywhere, an error enum (e.g. "unexpected
character `c` at position p", "unexpected end of input") lets callers `match` on what went wrong
and lets tests assert the exact error.

**Isolated illustration** (unrelated toy type):
```rust
enum Shape { Circle { r: f64 }, Square(f64) }
let area = match s { Shape::Circle { r } => 3.14 * r * r, Shape::Square(w) => w * w };
```

## Questions the tutor should ask you
1. Why is "a token is one of these kinds" better modelled as an `enum` than a struct with a `kind: String` field?
2. What does the compiler do if you add a variant and forget a `match` arm? Is that good or annoying?
3. When should a function return `Option` versus `Result`?
4. What exactly does `?` do on `Err(e)`, and in what kind of function may you use it?
5. Where in the calculator would a panic (`unwrap`) be acceptable, and where would it be a bug?

## What you build
Learning only. In a scratch crate:
1. **Shapes.** Define a `Shape` enum (circle, rectangle, triangle with three sides) with `area` and
   `perimeter` methods in an `impl` block. Test each variant.
2. **Redo `split_numbers` with `Result`.** `"3 14 15"` → `Ok([3, 14, 15])`; `"3 x 4"` →
   `Err(...)` that says which word failed and where. Use `str::parse::<i64>()` and `?`.
3. **Custom error enum.** Define an error type with at least two variants (bad number, empty input)
   and make your function return it. Write tests that `match` on the specific variant, or derive
   `PartialEq` and use `assert_eq!`.
4. **`key=value` parser.** Parse `"width=80"` into a struct with a name and a `u32` value; reject
   missing `=`, empty name and non-numeric value with distinct errors.
5. **On paper:** list every token kind your calculator will need for `+ - * / ( )` and integers,
   and which kinds carry data. Show it to the tutor (no code yet).
6. Rustlings: `07_structs`, `08_enums`, `12_options`, `13_error_handling`.

## Common pitfalls
- Using `.unwrap()` in library code instead of returning `Result`; reserve it for tests and true invariants.
- Stringly-typed data (`kind: String`, `op: char`) where an enum would let the compiler check you.
- A `_ =>` arm that silently swallows new variants later.
- Forgetting `#[derive(Debug, PartialEq)]`, then being unable to `assert_eq!` or print values.
- Using `?` in `main` or a function that returns `()`; it needs a `Result`/`Option` return type.
