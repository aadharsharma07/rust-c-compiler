# Lesson 6.6 — Dead stores
**Unit:** 6 — Optimisation · **Type:** Builds dead-store elimination · **Est. time:** 5–7 h · **Tests:** ch. 19
**Prerequisites:** lessons 6.1–6.5

## Learning goals
- Define *liveness* as a backward, may (union) dataflow analysis and compute live sets per instruction by hand.
- Delete instructions whose result is never read, without deleting anything with side effects.
- Handle static variables, aliased variables, function calls and memory operations conservatively.
- Finish the Unit 6 pipeline so `--optimize` runs all four passes to a fixpoint.

## Key ideas
**Liveness.** A variable `v` is *live* at a point if some path from that point reads `v` before writing it. If the destination of an instruction is not live immediately after it, the write is a **dead store**, and (if the instruction has no other effect) it can go.

**Analysis shape.**
- Direction: backward. Facts: sets of variables. Meet: union (live on *some* path is enough).
- Boundary at `Exit`: every **static-storage** variable is live, because the caller or a later call may read it after we return. Local variables are dead after return.
- Initial value for blocks: ∅.

**Transfer function, per instruction**, from live-after `L` to live-before:
- General rule: `live_before = (L − {written variable}) ∪ {variables read}`. Remove the write *first*, then add the reads, so `x = x + 1` keeps `x` live before.
- `Return(v)`, `JumpIfZero(v, _)`, `JumpIfNotZero(v, _)`: read `v`.
- `FunCall(f, args, dst)`: kills `dst`, reads every variable argument, and makes **every aliased variable** live (statics and address-taken locals), since the callee may read them.
- `Store(src, ptr)` (Unit 5): reads `src` and `ptr`; kills nothing, because you don't know which object it writes.
- `Load(ptr, dst)`: kills `dst`, reads `ptr`, and makes every aliased variable live (it may read any of them).
- `GetAddress(x, dst)`: kills `dst`; it does not read `x`'s *value*, so `x` need not become live.
- `Jump`, `Label`: no change.

**Worked example.** Live sets *after* each instruction, computed bottom-up:

```
                          live after
1: x = a + 1              {x, b}
2: y = x * 2              {b}        <- y not live: dead store
3: x = b                  {x}
4: return x               {}
```

Working backwards: before 4 is {x}. Instruction 3 writes `x` and reads `b`: before 3 is {b}. Instruction 2 writes `y` (not in {b}) and reads `x`: before 2 is {x, b}. Instruction 1 writes `x`, reads `a`: before 1 is {a, b}.

Delete instruction 2. But now instruction 1's `x` is dead too: nothing reads it before instruction 3 overwrites it. One round of liveness doesn't see that, because instruction 2 was still there when liveness ran. The *next* round of the pipeline catches it: this is the fixpoint loop from 6.1 paying off.

**What is never deleted.** `FunCall` (the callee may print, or write memory), `Store` (writes memory), and anything without a destination (jumps, labels, returns). Only instructions whose *only* effect is writing their destination variable are candidates: `Copy`, `Unary`, `Binary`, `GetAddress`, `Load`, and conversions.

**A loop.**

```
B0: i = 0
B1: Label(loop)
    tmp.0 = i < 10
    JumpIfZero(tmp.0, end)
B2: i = i + 1
    Jump(loop)
B3: Label(end)
    return 0
```

`i` is live at the end of B2 because B1 (a successor) reads it, so `i = i + 1` is *not* dead even though nothing after the loop uses `i`. Liveness is about paths, and the back edge is a path.

## Questions the tutor should ask you
1. Why is liveness a *may* analysis while reaching copies was a *must* one?
2. Why does the `Exit` boundary include static variables but not locals?
3. A `FunCall`'s result is never used. Why can't you delete the call?
4. In `x = x + 1`, why must you remove `x` before adding it back?
5. With pointers: `int a = 5; int *p = &a; return *p;`. Which rule keeps `a = 5` alive?
6. Your worked example needed two rounds to remove instruction 1. Could a smarter analysis do it in one? Is it worth it?

## What you build
- **Liveness analysis** as an instance of the 6.4 framework: backward, union, `Exit` boundary = static variables, initial ∅, transfer as above. Needs the static and aliased variable sets from 6.5 (reuse that code; statics come from your symbol table).
- **Dead-store pass:** for each instruction that writes a variable and has no other side effect, delete it if its destination is not in the live-after set. Returns the new CFG.
- **CLI:** active when `--eliminate-dead-stores` or `--optimize` is given. Pipeline order per round: fold → build CFG → unreachable code → copy propagation → dead stores → flatten; repeat until unchanged.
- **Correctness conditions:** never delete calls or stores; treat every aliased variable as possibly read by calls and loads; never delete writes to static variables that might be observed after return.
- **Edge cases:** variables live around a loop back edge; a function whose whole body becomes `return <constant>`; writes to a variable that is only read through a pointer; a parameter that is never used.

## Rust focus
- Your framework now serves a forward and a backward analysis; check that neither needed special-casing in the framework itself. If one did, fix the abstraction ([Rust Book ch. 10, generics and traits](https://doc.rust-lang.org/book/ch10-00-generics.html)).
- Set operations: [`BTreeSet::remove`](https://doc.rust-lang.org/std/collections/struct.BTreeSet.html#method.remove), [`difference`](https://doc.rust-lang.org/std/collections/struct.BTreeSet.html#method.difference), and [`extend`](https://doc.rust-lang.org/std/iter/trait.Extend.html) (sets implement `Extend`, so you can add any iterator of items).

  ```rust
  let only_in_a: BTreeSet<u32> = a.difference(&b).copied().collect();
  ```
- Deleting from a block's instruction `Vec` while keeping per-instruction facts aligned: decide first which indices to keep, then rebuild (or use `Vec::retain` with an index counter), rather than removing during iteration.
- Liveness will come back in Unit 7 over *assembly* instructions; keep the "which variables does this instruction read/write" logic in small, testable functions.

## Common pitfalls
- Adding reads before removing the written variable, which wrongly kills `x` in `x = x + 1`.
- Deleting `FunCall`s whose result is unused.
- Forgetting statics at `Exit`, so a final write to a global disappears.
- Ignoring aliasing: a write to an address-taken local looks dead if only `Load`/`FunCall` read it.
- Expecting one round to remove chains of dead stores, and "fixing" that with ad-hoc code instead of relying on the fixpoint loop.
