# Lesson 6.4 — Dataflow analysis
**Unit:** 6 — Optimisation · **Type:** Builds dataflow framework · **Est. time:** 6–10 h · **Tests:** ch. 19
**Prerequisites:** lessons 6.1–6.3

## Learning goals
- Describe a dataflow analysis in terms of a direction, a lattice of facts, a meet operator and a transfer function.
- Run the iterative worklist algorithm to a fixpoint, and explain why it terminates.
- Choose the right initial value (top vs. bottom) for "must" and "may" analyses.
- Build one reusable framework that 6.5 (forward), 6.6 (backward) and Unit 7 (backward, on assembly) all plug into.

## Key ideas
**The question.** Optimisations need facts like "on *every* path to here, `y` holds a copy of `x`" or "on *some* path from here, `t` is read again". Facts at a point depend on facts at its neighbours, and loops make that circular. Dataflow analysis solves the circularity by iterating until nothing changes.

**The four ingredients.**
1. **Direction.** *Forward*: facts flow from `Entry` along edges (what happened before?). *Backward*: from `Exit` against edges (what happens after?).
2. **Domain / lattice.** The set of possible facts at a point, usually *sets* (of copies, of variables), ordered by inclusion. It has a *top* and a *bottom* (e.g. "all copies" and "no copies").
3. **Meet.** How facts from several incoming edges combine at a join point. Intersection (∩) for *must* analyses: true on all paths. Union (∪) for *may* analyses: true on some path.
4. **Transfer function.** How one instruction (or one whole block) changes the fact: typically `out = gen ∪ (in − kill)`.

**Block equations.** For a forward analysis:
- `in[B] = meet of out[P] for each predecessor P` (with `Entry`'s fact as the boundary condition)
- `out[B] = transfer(B, in[B])`, applying each instruction's transfer in order and recording the fact *at each instruction* along the way (you will need per-instruction facts to rewrite code).

Backward is the mirror image: `out[B]` = meet over successors, `in[B]` = transfer applied from the last instruction to the first.

**The worklist algorithm.**
1. Initialise every block's fact. For an intersection-meet analysis, start at *top* (the full set), so the meet doesn't wrongly shrink facts before predecessors have been computed. For a union-meet analysis, start at the empty set.
2. Put every block on a worklist (in reverse postorder for forward, postorder for backward, if you want it fast; any order is correct).
3. Pop a block. Recompute its incoming fact with the meet, run the transfer, store the result.
4. If the block's outgoing fact changed, push its successors (forward) or predecessors (backward) that aren't already on the list.
5. Stop when the worklist is empty: you have reached a **fixpoint**.

**Why it terminates.** Transfer functions are *monotone* (a bigger input never gives a smaller output), and each block's fact can only move in one direction through a finite lattice (a finite set of copies or variables). So each block changes a bounded number of times.

**Worked example (forward, meet = ∩).** Track "which variables are definitely assigned". A loop:

```
B0: x = 1                  preds: Entry
B1: Label(loop)            preds: B0, B2
    JumpIfZero(c, end)
B2: y = 2                  preds: B1
    Jump(loop)
B3: Label(end)             preds: B1
    return x
```

Universe = {x, y}. Initialise out[B1], out[B2], out[B3] = {x, y} (top). Entry's fact = {}.
- B0: in = {} → out = {x}.
- B1: in = out[B0] ∩ out[B2] = {x} ∩ {x,y} = {x} → out = {x}. Changed: push B2, B3.
- B2: in = {x} → out = {x, y}. Unchanged from its initial top, so nothing new to push.
- B3: in = {x} → out = {x}.
- Worklist empty. At `return x`, `x` is definitely assigned; `y` is not (one path skips the loop).

If you had initialised out[B2] to {} instead, B1 would compute {x} ∩ {} = {}, B2 would then produce {y}, B1 would compute {x} ∩ {y} = {}, and the analysis would settle on "x is not definitely assigned at `return x`". That answer is safe but needlessly weak: the loop feeds the bad initial value back into itself and it never recovers. For copy propagation this means missed optimisations.

## Questions the tutor should ask you
1. Why is "definitely assigned" a *must* analysis, and why does that mean meet = intersection?
2. What does a block's fact get initialised to, and what goes wrong if you initialise an intersection analysis to the empty set?
3. When a block's output changes, which blocks need revisiting in a forward analysis? In a backward one?
4. Why do you need facts *per instruction* and not only per block?
5. What property of the transfer function guarantees termination?
6. How will your framework let 6.5 and 6.6 plug in different directions, meets and transfers without copying the algorithm?

## What you build
A generic dataflow framework over your `Cfg` from 6.3:
- **Inputs:** a CFG; a direction (forward or backward); the initial/top fact; the boundary fact for `Entry` (forward) or `Exit` (backward); a meet operation over two facts; a per-instruction transfer function.
- **Outputs:** for each block, the fact at its start and its end, and for each instruction, the fact immediately before it (forward) or immediately after it (backward). Store these as annotations keyed by (block ID, instruction index), either inside the blocks or in a separate map.
- **Algorithm:** the worklist algorithm above. A block is never on the worklist twice at once. `Entry` and `Exit` are boundary conditions, not blocks that get transferred.
- **Facts:** sets with cheap union/intersection and equality. A `BTreeSet` of names is fine to start; a bitset indexed by a numbering of copies/variables is an optional speed-up later.
- **Test it** on a toy analysis (e.g. "definitely assigned" above) with unit tests, *before* 6.5 relies on it. Include a loop, a diamond (`if`/`else` merge), and a block with no predecessors.
- No new CLI flag. Chapter 19 tests should keep passing for the flags you already support.

## Rust focus
- Traits to describe an analysis: a trait with an associated type for the fact and methods for meet and transfer ([Rust Book ch. 10.2, traits](https://doc.rust-lang.org/book/ch10-02-traits.html); [associated types, ch. 20](https://doc.rust-lang.org/book/ch20-02-advanced-traits.html)). Alternatively, pass closures (`impl Fn(&Fact, &Instr) -> Fact`, [ch. 13](https://doc.rust-lang.org/book/ch13-01-closures.html)). Try sketching both before choosing.

  ```rust
  trait Lattice: Clone + PartialEq { fn meet(&self, other: &Self) -> Self; }
  ```
  (An illustration of trait bounds only; your design may differ.)
- Worklist: [`VecDeque`](https://doc.rust-lang.org/std/collections/struct.VecDeque.html) plus a `HashSet`/`BTreeSet` "on the list" flag to avoid duplicates.
- Set algebra: [`BTreeSet::intersection`](https://doc.rust-lang.org/std/collections/struct.BTreeSet.html#method.intersection) and `union` return iterators; `.cloned().collect()` gives a new set. `&a & &b` also works for `BTreeSet`/`HashSet` of `Clone` items.
- Generic over the instruction type, so Unit 7 can run it on assembly.

## Common pitfalls
- Initialising an intersection analysis to the empty set: facts get stuck too small.
- Treating `Entry`/`Exit` as ordinary blocks and running the transfer on them.
- Revisiting the wrong neighbours (successors vs. predecessors) for the direction.
- Recording only per-block facts, then trying to recompute per-instruction facts ad hoc in each pass (and getting the order wrong for backward analyses).
- Hard-coding `Tacky::Instruction` into the framework, so it can't be reused in Unit 7.
