# Lesson 6.2 — Constant folding
**Unit:** 6 — Optimisation · **Type:** Builds constant folding · **Est. time:** 4–6 h · **Tests:** ch. 19
**Prerequisites:** lesson 6.1

## Learning goals
- Evaluate TACKY `Unary` and `Binary` instructions with constant operands at compile time, with exactly the semantics the generated machine code would have had.
- Fold conditional jumps whose condition is a constant into an unconditional `Jump` or nothing.
- Add the optimisation pipeline skeleton: CLI flags, a per-function loop that repeats until nothing changes.
- Know which expressions must *not* be folded.

## Key ideas
**Folding is local.** Constant folding looks at one instruction at a time; no CFG, no analysis. If every source operand is a `Constant`, compute the result and replace the instruction:

| Before | After |
|---|---|
| `Binary(Add, 2, 3, tmp.0)` | `Copy(5, tmp.0)` |
| `Unary(Negate, 7, tmp.1)` | `Copy(-7, tmp.1)` |
| `Binary(LessThan, 4, 9, tmp.2)` | `Copy(1, tmp.2)` |
| `Unary(Not, 0, tmp.3)` | `Copy(1, tmp.3)` |
| `JumpIfZero(0, else.4)` | `Jump(else.4)` |
| `JumpIfZero(5, else.4)` | *(deleted)* |
| `JumpIfNotZero(0, end.5)` | *(deleted)* |

Folding only creates `Copy` instructions; it does not remove `tmp.0`. Copy propagation (6.5) and dead-store elimination (6.6) clean those up later. Comparisons and `!` always produce an `int` 0 or 1.

**Worked example.** `return (3 + 4) * 2 > 10 ? 1 : 2;` might lower to:

```
tmp.0 = 3 + 4             ->  tmp.0 = 7
tmp.1 = tmp.0 * 2             (unchanged: tmp.0 is a variable, not a constant)
tmp.2 = tmp.1 > 10            (unchanged)
JumpIfZero(tmp.2, e2.1)       (unchanged)
...
```

Only the first instruction folds this round. After copy propagation rewrites `tmp.1 = 7 * 2`, the next round folds it, and so on. This is why the pipeline loops.

**Matching the machine, not maths.** The folded value must equal what the CPU would have computed:
- `int` arithmetic is 32-bit two's complement. `2147483647 + 1` must fold to `-2147483648` (signed overflow is undefined in C, but `rcc` must not panic). Use wrapping arithmetic.
- Division and remainder truncate toward zero (`-7 / 2` is `-3`, `-7 % 2` is `-1`); this matches Rust's `/` and `%` on integers.
- **Division or remainder by zero:** do not fold. Leave the instruction alone; the program may never execute it.
- `INT_MIN / -1` (and `% -1`) traps on x86 with `idiv`. Rust's plain `/` panics here too. Simplest correct choice: don't fold it.
- If you did Unit 5: fold at the operand's *type* (`long` is 64-bit, `unsigned` wraps modulo 2³², unsigned comparison and division differ from signed, `char` truncates). Conversion instructions (`SignExtend`, `Truncate`, `ZeroExtend`, int↔double) can fold too. For `double`, remember NaN compares unequal to everything, and `-0.0 == 0.0`. Don't fold `double` division by zero unless you are sure your result matches IEEE (it gives ±infinity or NaN, not a trap).

**The pipeline skeleton.** For each function: loop { if enabled, fold constants; later lessons add more passes here; if the instruction list equals the one at the start of the round, stop }. Also stop if the body becomes empty.

## Questions the tutor should ask you
1. Why does folding produce `Copy(5, tmp.0)` instead of deleting the instruction and rewriting later uses of `tmp.0`?
2. What should `JumpIfZero(3, L)` become, and why is deleting it correct?
3. Rust's `i32` addition panics on overflow in debug builds. How do you avoid that, and what value must you produce?
4. Why is it wrong to fold `x = 1 / 0` into anything, even though the C standard says the program is undefined?
5. If you have `unsigned`: what does `4294967295u + 1u` fold to, and what does `-1 < 0u` fold to?
6. How will your pipeline decide that "nothing changed"?

## What you build
- **CLI:** `rcc` accepts `--fold-constants`, `--eliminate-unreachable-code`, `--propagate-copies`, `--eliminate-dead-stores` and `--optimize` (which enables all four). Flags may appear in any order alongside existing ones (`--lex`, `--tacky`, `-S`, …). Unimplemented passes may be no-ops for now, but the flags must be accepted.
- **Optimiser entry point:** takes one TACKY function body (a `Vec` of instructions) plus the enabled-pass settings, returns the optimised body. It runs only on function definitions, after TACKY generation and before assembly generation.
- **Fixpoint loop:** repeats the enabled passes until a round produces an identical body, or the body is empty.
- **Constant-folding pass:** input a list of instructions, output a new list. Rules:
  - `Unary`/`Binary` with all-constant sources → `Copy(result, dst)`, except division/remainder by zero and `MIN / -1` cases, which are left unchanged.
  - `JumpIfZero(c, L)` → `Jump(L)` if `c` is zero, removed otherwise; `JumpIfNotZero(c, L)` → `Jump(L)` if `c` is non-zero, removed otherwise.
  - Conversions with a constant source fold if you implemented Unit 5.
  - Everything else is copied through unchanged.
- **Correctness condition:** for every program with defined behaviour, output and exit code are identical with and without the flag.

## Rust focus
- Wrapping and checked arithmetic on primitives: [`i32::wrapping_add`](https://doc.rust-lang.org/std/primitive.i32.html#method.wrapping_add), [`checked_div`](https://doc.rust-lang.org/std/primitive.i32.html#method.checked_div) (returns `None` for both `/0` and `MIN / -1`, which is exactly the "don't fold" set).

  ```rust
  assert_eq!(i32::MAX.wrapping_add(1), i32::MIN);
  assert_eq!(5_i32.checked_div(0), None);
  ```
- Matching on two values at once with tuple patterns: `match (op, a, b)` ([Rust Book ch. 19, patterns](https://doc.rust-lang.org/book/ch19-00-patterns.html)).
- Building the new list with `iter().filter_map(...)` or a plain loop pushing into a fresh `Vec`: both are fine; pick the one you can read.
- Unit-test the folder directly with hand-written TACKY: `#[test]` functions in a `mod tests` ([Rust Book ch. 11](https://doc.rust-lang.org/book/ch11-01-writing-tests.html)).

## Common pitfalls
- Panicking in the compiler on overflow or division by zero instead of leaving the instruction alone.
- Folding with Rust semantics that differ from the target: e.g. using `i64` for an `int` operation and forgetting to truncate, or signed comparison for `unsigned`.
- Forgetting that a deleted `JumpIfZero` must not leave behind the jump's label as a problem; the label stays, it's just now only reached by fall-through (6.3 tidies that up).
- Comparing instruction lists for "changed" before writing `PartialEq`, or comparing lengths only (folding often keeps the length the same).
- Flags parsed but silently ignored because the optimiser runs only when `--optimize` is given.
