# Lesson 6.3 — Control-flow graphs
**Unit:** 6 — Optimisation · **Type:** Builds CFG + unreachable-code elimination · **Est. time:** 6–8 h · **Tests:** ch. 19
**Prerequisites:** lessons 6.1–6.2

## Learning goals
- Partition a TACKY function into basic blocks and connect them into a control-flow graph (CFG).
- Represent a graph in Rust with indices into a `Vec` instead of shared pointers.
- Remove unreachable blocks, useless jumps, useless labels and empty blocks.
- Convert a CFG back into a flat TACKY instruction list.

## Key ideas
**Basic block:** a maximal straight-line run of instructions with one way in (the top) and one way out (the bottom). If the first instruction runs, all of them run, in order.
- A `Label` always *starts* a new block (something might jump to it).
- A `Jump`, `JumpIfZero`, `JumpIfNotZero` or `Return` always *ends* the current block.
- `FunCall` does **not** end a block: control comes back to the next instruction.

**Edges.** Add two pseudo-nodes, `Entry` and `Exit`. `Entry` → the first block. For each block, look at its last instruction:
- `Return` → `Exit`.
- `Jump(L)` → the block starting with `Label(L)`.
- `JumpIfZero`/`JumpIfNotZero(_, L)` → the block of `L` *and* the next block in order (fall-through).
- anything else → the next block in order (or `Exit` if it is the last block).

**Worked example.**

```c
int f(int a) { if (a) return 1; else return 2; return 3; }
```

```
B0: JumpIfZero(a, else.0)
B1: Return(1)
B2: Jump(end.1)              <- follows a Return, so it starts a new block
B3: Label(else.0)
    Return(2)
B4: Label(end.1)
    Return(3)
```

Edges:

```
Entry -> B0      B0 -> B1, B3      B1 -> Exit      B2 -> B4
B3 -> Exit       B4 -> Exit
```

B2 has no predecessors, and B4's only predecessor is B2.

**Unreachable-code elimination** has four steps, in this order:
1. **Unreachable blocks:** traverse from `Entry` (DFS or BFS over successors). Delete every block not visited, and remove its edges from its successors' predecessor sets. Above, B2 and B4 go.
2. **Useless jumps:** walk the *remaining* blocks in order. If a block ends with a jump (conditional or not) and every successor of that block is simply the next remaining block in order, delete the jump. The classic case is `Jump(L)` immediately followed by `Label(L)`.
3. **Useless labels:** if a block starts with a `Label` and its only predecessor is the previous block in order (or `Entry` for the first block), the label is reached only by fall-through: delete it.
4. **Empty blocks:** blocks left with no instructions are removed, and each of their predecessors is connected to their successor.

Result for the example: `JumpIfZero(a, else.0); Return(1); Label(else.0); Return(2)`.

Together with constant folding this handles `if (0) { ... }`: folding turns the branch into `Jump`, which makes the body unreachable.

**Arena graphs.** In Rust, a graph where nodes point at each other fights the borrow checker if you use references. Store blocks in a `Vec`, refer to them by index (`usize` or a small newtype), and keep each block's predecessors and successors as *sets of indices*. Use an enum for node IDs (`Entry`, `Block(i)`, `Exit`) so the pseudo-nodes don't need fake blocks. Removing a node then means "mark it dead / drop it from the map", not freeing memory others point to.

## Questions the tutor should ask you
1. Why does a `Label` start a block but a `FunCall` not end one?
2. Before running anything, what are the successors of a block ending in `JumpIfNotZero(x, L)`?
3. Why must step 2 (useless jumps) run *after* step 1 (unreachable blocks)? Give an example where the order matters.
4. A label is targeted by a jump in a block you just deleted. Is it still useful?
5. What would go wrong if you stored predecessors as `Vec<Rc<RefCell<Block>>>`? What do indices give up?
6. How will you convert the CFG back into a flat instruction list?

## What you build
- **CFG type**, generic enough to reuse in 6.4–6.6 and over assembly in Unit 7: blocks stored in a `Vec` (or ordered map keyed by block ID), each block holding its instructions, a set of predecessor node IDs and a set of successor node IDs; plus `Entry`/`Exit` successor/predecessor sets. Each block also needs room for per-instruction annotations later (6.4); leave a slot or plan for it.
- **`TACKY instructions → CFG`:** partitions as above; resolves label targets via a `HashMap` from label name to block ID built in a first pass.
- **`CFG → TACKY instructions`:** concatenates the remaining blocks in their original order. Order matters: fall-through edges depend on it.
- **Unreachable-code pass** (on when `--eliminate-unreachable-code` or `--optimize` is given): the four steps above, keeping predecessor/successor sets consistent after every deletion.
- **Pipeline:** each round now does: fold (if enabled) → build CFG → unreachable-code elimination (if enabled) → [6.5, 6.6 later] → flatten.
- **Edge cases:** empty function body; a function whose body is only `Return`; a jump to the immediately following label; a label with no jumps to it at all; loops (a block that is its own successor); a block that falls off the end of a function (C `main` has an implicit `return 0`, which your TACKY generator should already add).

## Rust focus
- Index-based graphs instead of `Rc<RefCell<…>>`: see [Rust Book ch. 15.6, reference cycles](https://doc.rust-lang.org/book/ch15-06-reference-cycles.html) for why cycles of `Rc` are painful.
- Sets of indices: [`BTreeSet`](https://doc.rust-lang.org/std/collections/struct.BTreeSet.html) gives deterministic iteration order (useful for reproducible output and debugging); `HashSet` is fine but iteration order varies.
- A newtype for block IDs prevents mixing them up with instruction indices: `struct BlockId(usize);` with `#[derive(Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord, Debug)]`.
- Mutating a graph while iterating it: collect the IDs to change first, then mutate ([`Vec::retain`](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.retain) is handy for deletions).
- Make the CFG generic over the instruction type (`Cfg<I>`) now, so Unit 7 can build one over assembly instructions.

## Common pitfalls
- Forgetting the fall-through edge of conditional jumps.
- Deleting a block but leaving it in some other block's predecessor set; later steps then think a label is still targeted.
- Removing a label that is still the target of a surviving jump.
- Checking "next block" against the original numbering instead of the order of blocks that still exist.
- Treating `FunCall` as a block terminator (harmless but wasteful) or forgetting `Return` is one (harmful).
