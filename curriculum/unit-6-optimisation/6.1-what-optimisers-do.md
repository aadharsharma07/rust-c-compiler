# Lesson 6.1 — What optimisers do
**Unit:** 6 — Optimisation · **Type:** Learning only · **Est. time:** 2–3 h · **Tests:** none
**Prerequisites:** lessons 1.1–4.5 (a working compiler through test chapter 10); Unit 5 optional

## Learning goals
- Explain what "optimisation" means for a compiler: producing a *different* program with the *same observable behaviour* that is smaller or faster.
- Read `clang -O0` and `clang -O1` output side by side on Godbolt and name the transformations you see.
- Describe the four passes in this unit and the order they run in.
- Explain why passes enable each other, and why the pipeline repeats until nothing changes.

## Key ideas
**Observable behaviour.** A C program's observable behaviour is roughly: what it returns, what it writes (via library calls), and accesses to `volatile` objects. Anything else (which temporaries exist, which instructions run, whether a variable lives on the stack) is the compiler's business. An optimisation is *sound* if every program with defined behaviour behaves the same before and after. Undefined behaviour (signed overflow, division by zero) gives the compiler freedom, but your compiler must still never *crash* on it.

**`-O0` vs. `-O1`.** Paste this into Godbolt (x86-64 clang) and compare both flags:

```c
int f(void) { int x = 2; int y = x * 3; return y + 1; }
```

At `-O0` clang stores `x` and `y` to stack slots, reloads them, multiplies, adds: roughly 8–10 instructions. At `-O1` the whole function is `mov eax, 7` then `ret`. Several separate ideas produced that result:
1. **Constant folding:** `2 * 3` is computed at compile time.
2. **Copy propagation:** uses of `x` are replaced by `2`, so the multiply sees two constants.
3. **Dead-store elimination:** the assignments to `x` and `y` are no longer read, so they are deleted.
4. **Register allocation** (Unit 7): whatever survives lives in registers, not stack slots.

**Your four passes, all on TACKY:**

| Pass | What it removes or rewrites | Needs |
|---|---|---|
| Constant folding | `Binary`/`Unary` on constants, conditional jumps on constants | nothing (one instruction at a time) |
| Unreachable-code elimination | blocks no path reaches, useless jumps and labels, empty blocks | a CFG |
| Copy propagation | uses of `y` after `y = x` are replaced by `x` | CFG + forward dataflow |
| Dead-store elimination | writes to variables that are never read afterwards | CFG + backward dataflow |

**Passes feed each other.** The same function in TACKY:

```
x = 2
y = x * 3
tmp.0 = y + 1
return tmp.0
```

Copy propagation turns line 2 into `y = 2 * 3`. Folding turns it into `y = 6`. A second round of copy propagation turns line 3 into `tmp.0 = 6 + 1`, then folding gives `tmp.0 = 7`, then propagation gives `return 7`. Dead-store elimination then removes the first three lines. No single pass gets there alone, and the order of one round doesn't matter much: what matters is **repeating the round until the function stops changing** (a *fixpoint*). Each pass only ever removes instructions or replaces operands with "simpler" ones, so the loop terminates.

**Where the optimiser sits.** It is a function `TACKY function → TACKY function`, run between TACKY generation and assembly generation, controlled by CLI flags. With no flags, `rcc` must behave exactly as before.

**Phase-ordering, briefly.** Real compilers run dozens of passes and the order changes the result. This course keeps it simple: one fixed order, iterate to a fixpoint.

## Questions the tutor should ask you
1. At `-O1` clang deleted the variable `x` entirely. Why is that allowed? What would make it *not* allowed?
2. If constant folding sees `x = 10 / 0`, what should it do, and why can't it just compute the answer?
3. Why does copy propagation need to know about *paths* through the function while constant folding does not?
4. Give an example where dead-store elimination only finds a dead store *after* copy propagation has run.
5. How do you know the "repeat until nothing changes" loop will terminate?
6. Which of the four passes would you expect to need the most test cases, and why?

## What you build
Nothing in code. Instead, produce notes (in `JOURNAL.md` or a scratch file):
- Three small C functions of your own (one with an `if` on a constant, one with a chain of copies, one with a variable assigned and never read). For each, record the `clang -O0` and `-O1` assembly from Godbolt and label which of the four ideas above explains each difference.
- The TACKY your own `rcc --tacky` (or your debug printer) produces for each, and a hand-optimised version you expect your finished Unit 6 to produce.
- A one-paragraph plan for where the optimiser will live in your crate (which module, what its entry function takes and returns, how CLI flags reach it).

## Rust focus
- Think ahead about representing "which passes are enabled": a small `struct` of `bool`s you build from `std::env::args`, passed by reference into the optimiser ([Rust Book ch. 5](https://doc.rust-lang.org/book/ch05-00-structs.html)).
- Detecting "nothing changed" needs equality on TACKY: deriving `PartialEq` on your IR enums ([std::cmp::PartialEq](https://doc.rust-lang.org/std/cmp/trait.PartialEq.html)). Check whether every type inside your IR can derive it (watch `f64` if you have `double`: it implements `PartialEq` but not `Eq`).

## Common pitfalls
- Assuming optimisation may change behaviour "a little". It may not; one wrong rewrite fails tests far from the cause.
- Treating `-O1` assembly as the target. Clang does far more (inlining, instruction selection tricks); you are only after the four ideas above.
- Planning the optimiser as one giant pass. Small independent passes are easier to test and debug.
- Forgetting the no-flags path must be byte-for-byte what you emitted before.
