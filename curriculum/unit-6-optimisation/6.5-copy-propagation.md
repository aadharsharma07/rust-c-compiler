# Lesson 6.5 — Copy propagation
**Unit:** 6 — Optimisation · **Type:** Builds copy propagation · **Est. time:** 6–8 h · **Tests:** ch. 19
**Prerequisites:** lessons 6.1–6.4

## Learning goals
- Define *reaching copies* as a forward, must (intersection) dataflow analysis and write its transfer function in words.
- Use the analysis to replace variable uses with the source of a copy, and to delete redundant copies.
- Identify aliased variables (address-taken and static) and explain why function calls and stores through pointers kill copies.
- Plug the analysis into the framework from 6.4 without changing the framework.

## Key ideas
**A copy** is a TACKY `Copy(src, dst)`, written `dst = src`. It *reaches* a point P if, on **every** path from `Entry` to P, the copy executes and afterwards neither `dst` nor `src` is changed. If `y = x` reaches an instruction that reads `y`, the read can use `x` (or the constant) instead.

**Analysis shape.**
- Direction: forward. Facts: sets of copies. Meet: intersection (must hold on all paths).
- Boundary: nothing reaches the start of the function (`Entry` fact = ∅).
- Initial value for every block: top = *every* `Copy` that appears in the function.

**Transfer function, per instruction**, given the incoming set `R`:
- `Copy(src, dst)`: if `dst = src` is already in `R`, or the reverse copy `src = dst` is, the instruction changes nothing (it is redundant; see rewriting). Otherwise remove every copy in `R` that mentions `dst` as source or destination, then add `dst = src`.
- Any other instruction that writes a variable `v` (`Unary`, `Binary`, `FunCall` result, and, if you have them, `Load`, `GetAddress`, conversions): remove every copy that mentions `v`.
- `FunCall` additionally removes every copy that mentions an **aliased** variable, because the callee may read or write it.
- `Store` (through a pointer) removes every copy mentioning an aliased variable: you don't know which object it writes.
- `Jump`, `JumpIfZero`, `JumpIfNotZero`, `Label`, `Return`: no change.

**Aliased variables** in a function are those with static storage duration (globals, `static` locals) and, once you have pointers, any local whose address is taken by a `GetAddress` anywhere in the function. Without pointers, only statics matter, and only calls kill them.

**Rewriting.** Using the fact *before* each instruction:
- Replace each *read* operand `v` with `s` if a copy `v = s` is in the set.
- Delete a `Copy(src, dst)` whose `dst = src` or `src = dst` copy already reaches it.
- Don't replace the operand of `GetAddress`: it needs the variable itself, not its value.

**Worked example.**

```
x = 3                    reaching before: {}
y = x                    {x=3}
JumpIfZero(c, L)         {x=3, y=x}
y = 4                    {x=3, y=x}
Label(L)                 meet of {x=3, y=x} and {x=3, y=4} = {x=3}
tmp.0 = y + x            {x=3}
return tmp.0             {x=3}
```

After rewriting:

```
x = 3
y = 3                    <- x replaced
JumpIfZero(c, L)
y = 4
Label(L)
tmp.0 = y + 3            <- x replaced; y not, the paths disagree
return tmp.0
```

`x = 3` is now dead; 6.6 removes it. Note the copy `y = x` became `y = 3` in the rewrite but the *analysis* tracked `y = x`; that is fine because `x = 3` reaches both.

**Types (Unit 5).** If source and destination have different types of the same size (`int` and `unsigned`), substituting one for the other changes which instruction codegen picks for later uses (signed vs. unsigned division, comparison, conversion). Only propagate a copy whose source and destination have the same type.

## Questions the tutor should ask you
1. Why is reaching copies a *must* analysis? What wrong rewrite would a *may* version allow?
2. Why does assigning to `x` kill the copy `y = x`, not just copies *to* `x`?
3. `g` is a global and `y = g` reaches a call `f()`. Why must the call kill that copy?
4. With pointers: `int a = 1; int *p = &a; *p = 2; return a;` What goes wrong if `Store` doesn't kill `a = 1`?
5. Why is `Copy(x, y)` removable when `x = y` already reaches it?
6. Why must `GetAddress(x, p)` keep `x` even when `x = 5` reaches it?

## What you build
- **Aliased-variable set** for a function: all static-storage variables referenced, plus every variable used as the source of `GetAddress`. Computed once per round.
- **Reaching-copies analysis** as an instance of your 6.4 framework: forward, intersection, boundary ∅, initial = all copies in the function, transfer as above. Represent a copy as a (source operand, destination variable) pair, comparable and hashable.
- **Rewrite pass:** walks every block, uses the per-instruction "before" fact to replace read operands and delete redundant copies. Returns the new CFG.
- **CLI:** active when `--propagate-copies` or `--optimize` is given. Pipeline order per round: fold → build CFG → unreachable code → copy propagation → (6.6) → flatten.
- **Correctness conditions:** never substitute through a path where the copy might not hold; never change what a `FunCall`, `Store` or `GetAddress` can observe; propagated constants keep their type.
- **Edge cases:** a copy inside a loop whose source is redefined later in the loop; self-copies `x = x`; copies of function parameters (they are ordinary variables, assigned on entry); a function with no copies at all (the universe is empty).

## Rust focus
- Representing a copy as a small `#[derive(Clone, PartialEq, Eq, Hash, PartialOrd, Ord)]` struct so it can live in a `BTreeSet` or `HashSet`.
- Removing many elements by predicate: [`BTreeSet::retain`](https://doc.rust-lang.org/std/collections/struct.BTreeSet.html#method.retain) / [`HashSet::retain`](https://doc.rust-lang.org/std/collections/struct.HashSet.html#method.retain).

  ```rust
  let mut evens: BTreeSet<i32> = (1..10).collect();
  evens.retain(|n| n % 2 == 0);
  ```
- Implementing your 6.4 trait (or passing closures) for a second analysis is the real test of that design; if it's awkward, refactor the framework now, before 6.6.
- Borrowing the aliased set inside the transfer closure: a closure capturing `&aliased` ([Rust Book ch. 13](https://doc.rust-lang.org/book/ch13-01-closures.html)).

## Common pitfalls
- Only killing copies *to* a redefined variable, not copies *from* it.
- Forgetting that calls clobber statics, or that stores clobber address-taken locals.
- Rewriting using the fact *after* the instruction (e.g. replacing `x` in `x = x + 1` with the value of the new `x`).
- Initialising non-entry blocks to ∅, which silently disables the pass inside loops.
- Replacing the destination of an instruction, or the operand of `GetAddress`.
