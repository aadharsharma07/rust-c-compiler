# Lesson 2.4 — Precedence Climbing
**Unit:** 2 — Expressions and an IR · **Type:** Builds binary-expression parser · **Est. time:** 4–6 h · **Tests:** ch. 3 (`--stage parse`)
**Prerequisites:** lessons 0.6, 2.1

## Learning goals
- Define precedence and associativity, and show how each changes the shape of the AST.
- Explain why the naive rule `<exp> ::= <exp> <binop> <exp>` can't be parsed directly by recursive descent (ambiguity and left recursion).
- Implement precedence climbing: one loop driven by a precedence table instead of one function per level.
- Separate "factors" (constants, unary expressions, parenthesised expressions) from binary expressions.
- Use a method on an enum (or a `match` returning `Option<u8>`) to map tokens to precedences.

## Key ideas
**Precedence** decides which operator binds tighter: `1 + 2 * 3` is `1 + (2 * 3)`.
**Associativity** decides grouping among equal precedence: all binary operators in this unit
are left-associative, so `10 - 4 - 3` is `(10 - 4) - 3 = 3`, not `10 - (4 - 3) = 9`.

**Grammar.** The textbook-style ambiguous grammar is
```
<exp>    ::= <factor> | <exp> <binop> <exp>
<factor> ::= <int> | <unop> <factor> | "(" <exp> ")"
<binop>  ::= "-" | "+" | "*" | "/" | "%"
```
It doesn't say which tree `1 - 2 - 3` gets, and a recursive-descent function for `<exp>` would
call itself first and never consume a token (left recursion). Unit 0 solved this with one grammar
level per precedence (`expr`/`term`/`factor`); that works, but every new precedence level means a
new function. Unary operators now apply to a `<factor>`, so `-2 + 3` is `(-2) + 3`.

**Precedence climbing.** Give each binary operator a number:

| Operators | Precedence |
|---|---|
| `*` `/` `%` | 50 |
| `+` `-` | 45 |

(Gaps leave room: lesson 2.6 adds relational and logical operators below these, and the optional
bitwise operators slot in between.) The expression parser takes a *minimum precedence*. It parses
a factor as the left operand, then loops: while the next token is a binary operator whose
precedence is **at least** the minimum, consume it, parse the right operand with a minimum of
**that operator's precedence + 1**, and combine left and right into a new left. The "+ 1" is what
makes operators left-associative: the right operand may not contain another operator of the same
level, so it stops and the loop picks it up instead.

**Trace: `1 - 2 * 3 - 4`, starting at minimum 0.**
1. Left = `1`. Next is `-` (45 ≥ 0): parse right with minimum 46.
2. Inside: left = `2`; next is `*` (50 ≥ 46): parse right with minimum 51 → `3`; left = `2*3`.
   Next is `-` (45 < 46): stop, return `2*3`.
3. Outer left = `1 - (2*3)`. Next is `-` (45 ≥ 0): right with minimum 46 → `4`.
4. Result: `Binary(Subtract, Binary(Subtract, 1, Binary(Multiply, 2, 3)), 4)`.

**AST additions:**
```
exp             = Constant(int) | Unary(unary_operator, exp) | Binary(binary_operator, exp, exp)
binary_operator = Add | Subtract | Multiply | Divide | Remainder
```
Note `-` is now ambiguous at the token level: the *parser* decides — in factor position it is
negation, after an operand it is subtraction. The lexer just emits `Hyphen`.

## What you build
- **Lexer:** add `+`, `*`, `/`, `%`. (Optional bitwise extension: `&`, `|`, `^`, `<<`, `>>`;
  enable those tests with `--bitwise`.)
- **AST:** a binary variant with an operator and two boxed operands; a binary-operator enum.
- **Parser:** rename the old expression function to "parse factor" (constants, unary operators
  applied to a factor, parenthesised expressions); write "parse expression with minimum
  precedence" as described; a helper mapping a token to its precedence (or "not a binary
  operator"). `Return` parses an expression at minimum 0.
- **Errors:** missing operands, two operators in a row (other than a unary operator starting a
  factor), unbalanced parentheses, a trailing operator.
- **TACKY/codegen:** don't need to handle `Binary` yet; return a "not yet supported" error. Lesson 2.5 does them.
- **Unit tests:** ASTs for `1 + 2 * 3`, `10 - 4 - 3`, `(1 + 2) * 3`, `-2 * 3`, `2 * -3`, `6 / 3 % 2`.

`let p = tok.precedence()?;` inside a function returning `Option` exits early with `None` — handy, but in a parse loop you usually want `while let Some(p) = …` instead.

## Common pitfalls
- Using `p` instead of `p + 1` for the right operand: everything becomes right-associative and `10 - 4 - 3` evaluates to 9.
- Applying unary operators to a whole `<exp>` instead of a `<factor>`, so `-2 + 3` parses as `-(2 + 3)`.
- Consuming the operator token before checking its precedence, then losing it when the loop exits.
- Turning `-` into separate lexer tokens for unary and binary minus.
