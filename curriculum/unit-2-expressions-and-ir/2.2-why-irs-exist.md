# Lesson 2.2 — Why IRs Exist
**Unit:** 2 — Expressions and an IR · **Type:** Builds TACKY IR + AST→TACKY · **Est. time:** 5–7 h · **Tests:** ch. 2 (`--stage tacky`)
**Prerequisites:** lesson 2.1

## Learning goals
- Explain what an intermediate representation is and why compilers put one between the AST and assembly.
- Define three-address code: every instruction has at most one operator, and operands are constants or named temporaries.
- Flatten a nested expression tree into a sequence of instructions in evaluation order.
- Generate fresh, collision-free temporary names using state threaded through `&mut self`.
- Add the `--tacky` stage flag to the driver.

## Key ideas
**The gap problem.** An AST is a tree; assembly is a flat list of instructions where each does
one small thing. Bridging both at once (tree shape *and* machine details) in one pass gets messy
fast. An IR splits the work: AST → IR handles *structure* (flattening, evaluation order,
later control flow); IR → assembly handles *machine details* (registers, instruction forms).
Optimisations in Unit 6 also run on the IR, independent of both C syntax and x86-64.

**Three-address code (TAC).** Each instruction has the shape `dst = src1 op src2` (or `dst = op src`).
Intermediate results get names: *temporaries*. The course's TAC is called **TACKY**:
```
program        = Program(function_definition)
function_definition = Function(identifier name, instruction* body)
instruction    = Return(val) | Unary(unary_operator, val src, val dst)
val            = Constant(int) | Var(identifier)
unary_operator = Complement | Negate
```
A `val` is always simple: never a nested expression. That is the whole point.

**Flattening.** To translate an expression, first translate its operands (emitting their
instructions), receive back a `val` naming each result, then emit one instruction for this node
into a fresh temporary and return that temporary. Constants need no instructions: they translate
directly to `Constant(n)`. A `Return(exp)` statement translates `exp`, then emits `Return(val)`.

**Worked example.** `return ~(-2);` with AST `Return(Unary(Complement, Unary(Negate, Constant(2))))`:
```
Unary(Negate,     Constant(2),  Var("tmp.0"))     # tmp.0 = -2
Unary(Complement, Var("tmp.0"), Var("tmp.1"))     # tmp.1 = ~tmp.0
Return(Var("tmp.1"))
```
The innermost operation comes first: the tree's post-order becomes the instruction order.
`return 5;` becomes just `Return(Constant(5))`, no temporaries at all.

**Fresh names.** Temporaries need globally unique names. A counter that increments on each
request works; including a character that can't appear in a C identifier (the `.` in `tmp.0`)
guarantees no clash with user variables in Unit 3. The counter is *state*: it must be shared and
mutated across the whole translation, which in Rust means a struct you pass as `&mut`.

**Stage flag.** `rcc --tacky prog.c` runs lex → parse → TACKY generation and stops (exit 0, no
files). The test suite's `--stage tacky` uses it. It sits between `--parse` and `--codegen`.

## Questions the tutor should ask you
- Why not generate assembly directly from the AST, now that expressions nest?
- In `~(-2)`, which instruction must come first, and how does recursion naturally produce that order?
- What does your translation function for an expression return, and where do the instructions it generates go?
- Why is `tmp.0` a safe name and `tmp0` a risky one?
- Where does the temporary counter live? What happens if two functions (Unit 4) each start from 0?

## What you build
- A `tacky` module with types for program, function, instruction, val and unary operator as above.
  Decide whether TACKY's unary-operator enum is a separate type from the AST's (recommended:
  separate types, so each stage can evolve independently) or shared.
- A `tacky_gen` (or similar) module: C AST `Program` in, TACKY `Program` out. Internally a
  generator struct holding the temporary counter, with methods to translate a statement and an
  expression; expression translation appends to an instruction list and returns a `val`.
- **Driver:** add the `--tacky` stage between parse and codegen. A full compile now runs
  AST → TACKY; codegen will consume TACKY from lesson 2.3, so for now full compiles of chapter 2
  programs may still fail. Keep chapter 1 working (e.g. leave the old AST→asm path in place until 2.3).
- **Debug printing:** a readable TACKY dump (one instruction per line, like the worked example)
  you can print with a debug flag.
- **Unit tests:** TACKY for `2`, `-2`, `~(-2)`, `-(-(-2))`; check temporary names are unique.

Two mutable borrows can't overlap, but sequential ones can: calling `self.fresh_temp()` and then
`out.push(...)` on separate lines is fine; nesting one inside the other's argument sometimes isn't.

## Common pitfalls
- Emitting the outer instruction before the inner ones (wrong evaluation order).
- Creating a temporary for constants: wasteful, and it makes later fix-ups harder to reason about.
- Keeping the counter in a `static mut` or global: unsafe and unnecessary; thread it through a struct.
- Reusing the AST's enum for TACKY's `val` "to save time" and then needing to unpick it.
- Forgetting the `--tacky` flag in argument parsing so the test suite sees "unknown flag".
