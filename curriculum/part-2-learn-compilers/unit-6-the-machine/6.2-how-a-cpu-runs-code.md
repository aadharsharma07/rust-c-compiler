# Lesson 6.2 — How a CPU Runs Code
**Part:** 2 — Learn Compilers · **Unit:** 6 — The Machine · **Type:** Learning · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lesson 6.1

## Overview
Before reading real x86-64 assembly, you need a working model of the machine that runs it. This
lesson builds that model with a deliberately tiny **toy CPU**: memory, a handful of registers, an
instruction pointer and condition flags, driven by the **fetch–decode–execute** cycle. You'll
trace a loop through it instruction by instruction, and see that it is the three-address code from
lesson 5.5 in disguise. Every idea here carries over directly to x86-64 in lesson 6.3.

## The lesson

### The two big pieces: memory and the CPU
**Memory** (RAM) is one enormous array of bytes. Each byte has a numeric **address**, its index
in that array. "The value at address 1000" just means "element 1000 of the array". Both your
program's *data* and its *instructions* live in memory, as bytes.

```
address:   0     1     2     3    ...   1000  1001  1002  1003  ...
byte:     55    48    89    e5    ...    2a    00    00    00   ...
          \___ instructions ___/         \__ the int 42 (little-endian, 6.1) __/
```

The **CPU** (processor) does the work. It can't compute on memory directly at full speed; instead
it has a small number of **registers**: storage slots built into the CPU itself, each holding one
fixed-width value (64 bits on x86-64). Registers are extremely fast (accessed in under a
nanosecond, many per cycle) but there are very few of them (16 general-purpose ones on x86-64).
Memory is huge but, relative to registers, slow; caches in between hide some of the cost. This
trade-off is why compilers work hard to keep values in registers (Unit 14).

A Python bridge: think of registers as a handful of local variables the CPU can touch instantly,
and memory as a giant `bytearray` it must explicitly read from and write to.

### Special registers
Besides general-purpose registers, every CPU has a few with fixed jobs:
- The **instruction pointer** (IP, also called the *program counter*, PC) holds the address of the
  next instruction to run. On x86-64 it's called `rip`.
- The **flags register** holds single-bit **condition flags** describing the result of the last
  arithmetic or comparison instruction. The important ones:
  - **ZF** (zero flag): the result was 0;
  - **SF** (sign flag): the result's top bit was 1, i.e. negative if read as signed;
  - **CF** (carry flag): an unsigned overflow (a carry out of the top bit) happened;
  - **OF** (overflow flag): a signed overflow happened (like 127 + 1 in 8 bits, from 6.1).
- The **stack pointer** holds the address of the top of the *stack*, a region of memory used for
  function calls and local variables. It gets its own lesson (6.4).

### The fetch–decode–execute cycle
A CPU does one thing, forever:

```
loop:
    1. FETCH:   read the instruction bytes at address IP from memory
    2. DECODE:  work out which operation it is and which registers/values it uses
    3. EXECUTE: do it (compute, read/write memory, update flags)
    4. ADVANCE: set IP to the next instruction, unless the instruction was a jump,
                in which case IP = the jump target
```

That's all "running a program" is. There's no understanding of functions or loops or variables at
this level: a loop is just a jump to an earlier address, and an `if` is a jump that's taken only
when a flag says so. (Real CPUs overlap many instructions at once with *pipelining* and run them
out of order, but they carefully preserve the *illusion* of this simple loop, so it's the right
model for a compiler writer.)

Notice that CPython's VM (5.1) is the same loop written in C, where the "instructions" are
bytecode and "IP" is an index into the bytecode array. A CPU is that loop built from transistors.

### A toy CPU
Our toy machine has four general-purpose registers `R0`–`R3`, an instruction pointer `IP`, and
two flags, `Z` (zero) and `N` (negative). Instructions are numbered 0, 1, 2, ... (one per address,
to keep things simple). Its whole instruction set:

| Instruction | Effect |
|---|---|
| `LOADI r, n` | r = n (load an immediate constant) |
| `ADD r, s` | r = r + s; set flags from the result |
| `SUB r, s` | r = r − s; set flags from the result |
| `CMP r, s` | compute r − s, set flags, **throw the result away** |
| `JMP a` | IP = a |
| `JLE a` | if Z or N (last result ≤ 0), IP = a; otherwise fall through |
| `HALT` | stop |

`CMP` is the key trick: comparisons are done by subtracting and looking at the flags. If
`R1 − R2` is zero then `R1 == R2`; if it's negative then `R1 < R2`.

### A program: summing 4 + 3 + 2 + 1
Recall the `while` loop from 5.4/5.5 (`total = total + n; n = n - 1;` while `n > 0`). Here it is
for the toy CPU, with `R0` = total and `R1` = n:

```
0: LOADI R0, 0      ; total = 0
1: LOADI R1, 4      ; n = 4
2: LOADI R2, 0      ; constant 0
3: LOADI R3, 1      ; constant 1
4: CMP   R1, R2     ; loop: compare n with 0
5: JLE   9          ; if n <= 0, exit the loop
6: ADD   R0, R1     ; total = total + n
7: SUB   R1, R3     ; n = n - 1
8: JMP   4          ; back to the test
9: HALT             ; result is in R0
```

Compare it with the TAC from lesson 5.5: `loop.0:` became address 4, `jump_if_zero tmp.0, break.0`
became `CMP` + `JLE 9`, and `jump loop.0` became `JMP 4`. Code generation (6.6) is largely this
kind of translation.

### Tracing it, cycle by cycle
Each row shows the state *after* executing the instruction at `IP`:

```
 IP  instruction      R0  R1  R2  R3   Z  N   next IP
  0  LOADI R0, 0       0   -   -   -   -  -    1
  1  LOADI R1, 4       0   4   -   -   -  -    2
  2  LOADI R2, 0       0   4   0   -   -  -    3
  3  LOADI R3, 1       0   4   0   1   -  -    4
  4  CMP R1, R2        0   4   0   1   0  0    5      4 - 0 = 4: not zero, not negative
  5  JLE 9             0   4   0   1   0  0    6      not taken
  6  ADD R0, R1        4   4   0   1   0  0    7
  7  SUB R1, R3        4   3   0   1   0  0    8
  8  JMP 4             4   3   0   1   0  0    4      always taken
  4  CMP R1, R2        4   3   0   1   0  0    5
  ... (two more iterations: R0 becomes 7, then 9; R1 becomes 2, then 1) ...
  6  ADD R0, R1       10   1   0   1   0  0    7
  7  SUB R1, R3       10   0   0   1   1  0    8      result 0: Z set
  8  JMP 4            10   0   0   1   1  0    4
  4  CMP R1, R2       10   0   0   1   1  0    5      0 - 0 = 0: Z set
  5  JLE 9            10   0   0   1   1  0    9      taken!
  9  HALT             10   0   0   1   1  0    -
```

Note that `JMP` doesn't change the flags, and `JLE` only *reads* them. The decision to leave the
loop was made by `CMP` one instruction earlier; this "set flags, then branch on them" pairing is
exactly how x86-64 works (`cmpl` then `jle`, lesson 6.3).

### Instructions are numbers
To store the program in memory, each instruction is **encoded** as bytes. Our toy CPU might use
one byte for the operation and one per operand: `ADD R0, R1` → `02 00 01`. Real x86-64 encodings
are variable-length and intricate: when you disassemble a compiled function (lesson 6.5) you'll
see lines like

```
55             pushq %rbp
48 89 e5       movq  %rsp, %rbp
c3             retq
```

Decoding these bytes is the CPU's job; producing them is the **assembler's** job. Your compiler
only writes the human-readable text on the right, which is a big relief.

### How a running program's memory is laid out
When the operating system starts a program, it arranges its memory into regions:

```
high addresses   +--------------------+
                 |       stack        |   grows DOWN: function calls, locals (6.4)
                 |         |          |
                 |         v          |
                 |                    |
                 |         ^          |
                 |         |          |
                 |        heap        |   grows up: malloc (Unit 12); Python objects live here
                 +--------------------+
                 |   data / bss       |   global and static variables (lesson 11.4)
                 +--------------------+
low addresses    |   text (code)      |   your machine instructions; IP points in here
                 +--------------------+
```

You met the stack and heap in lesson 2.1 from Rust's point of view; this is the same picture from
the machine's side.

4. **Flags in binary.** For 8-bit arithmetic, give the values of ZF, SF, CF and OF after:

## Common pitfalls
- Thinking the CPU "knows" about loops or `if`s. It only knows jumps and flags.
- Expecting `JMP` to change flags. Only arithmetic and comparison instructions set them, and
  only conditional jumps read them.
- Forgetting that `CMP` discards its result; it exists *only* to set flags.
- Mixing up the instruction *addresses* with the values in registers when tracing.
