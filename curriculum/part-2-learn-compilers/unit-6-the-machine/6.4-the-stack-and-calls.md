# Lesson 6.4 — The Stack and Function Calls
**Part:** 2 — Learn Compilers · **Unit:** 6 — The Machine · **Type:** Learning · **Est. time:** 4–6 h · **Tests:** none
**Prerequisites:** lessons 2.1, 6.1–6.3

## Overview
Functions are the trickiest thing a CPU does *not* natively understand. This lesson shows how the
**stack** makes them work: how `push`, `pop`, `call` and `ret` move the stack pointer, how each
call gets a **stack frame** for its locals, and how `rbp` and `rsp` are used to find things in it.
You'll step through a real call, instruction by instruction, with a picture of memory at each
step. Then you'll learn the **System V calling convention**, the rulebook that lets code compiled
by `rcc` call, and be called by, code compiled by `clang` and the C library.

## The lesson

### Why a stack?
In Python, every call creates a *frame object* holding that call's local variables; when you get
a traceback, you're looking at the chain of frames, newest last. Calls nest strictly: if `f` calls
`g`, then `g` finishes before `f` does. Storage that's created and destroyed in strict
last-in-first-out order is exactly what a **stack** gives you. At machine level, the stack is just
a region of memory (6.2) plus one register, `rsp`, the **stack pointer**, which holds the address
of the current top.

Two conventions to fix in your head:
- **The stack grows downward**, towards lower addresses. "Pushing" *decreases* `rsp`.
- `rsp` points *at* the last thing pushed (the top item), not past it.

All the diagrams below draw **high addresses at the top**, so the stack grows down the page.

### push and pop
`pushq %rax` does two things: `rsp = rsp − 8`, then store the 8 bytes of `rax` at address `rsp`.
`popq %rbx` reverses it: load 8 bytes from address `rsp` into `rbx`, then `rsp = rsp + 8`.

```
 before pushq $7        after pushq $7          after popq %rbx  (rbx = 7)
 0x1000 | ...    |      0x1000 | ...    |       0x1000 | ...    |  <- rsp
        +--------+  <- rsp     +--------+              +--------+
 0x0ff8 |        |      0x0ff8 |   7    | <- rsp 0x0ff8 |   7    |  (stale, ignored)
```

Popping doesn't erase anything; the old value is simply "above the top" and will be overwritten
later. That's also why reading an uninitialised local in C can give you leftover garbage.

### call and ret
How does a function know where to return to? `call f` does:
1. push the address of the instruction *after* the `call` (the **return address**);
2. jump to `f`.

`ret` does: pop the return address off the stack into `rip`, so execution continues right after
the original `call`. This only works if, by the time `ret` runs, `rsp` points at that return
address again: every function must leave the stack exactly as it found it.

### Stack frames, rbp and the prologue/epilogue
Each call needs space for its local variables. It **reserves** it by subtracting from `rsp`. To
make locals easy to find, functions traditionally also use `rbp`, the **base pointer** (frame
pointer), as a fixed reference point for the current frame. The standard code at the start and
end of every function:

```
    pushq   %rbp            # prologue: save the caller's rbp
    movq    %rsp, %rbp      #   our frame's base = current top
    subq    $16, %rsp       #   reserve 16 bytes for locals
    ...                     # body: locals are at -4(%rbp), -8(%rbp), ...
    movq    %rbp, %rsp      # epilogue: free the locals
    popq    %rbp            #   restore the caller's rbp
    ret                     #   pop the return address and go back
```

(The two epilogue moves are sometimes written as one `leave` instruction.) The result is a
**stack frame** with a fixed shape:

```
 higher addresses
        |  caller's frame ...                  |
        |  stack args 7, 8, ... (if any)       |  16(%rbp), 24(%rbp), ...
        |  return address                      |   8(%rbp)
 rbp -> |  caller's saved rbp                  |   0(%rbp)
        |  local 1                             |  -4(%rbp)
        |  local 2                             |  -8(%rbp)
 rsp -> |  ...                                 |
 lower addresses
```

Because `rbp` doesn't move during the function body, a local always has the same offset, even if
`rsp` moves (for pushes before a call). This is exactly how `rcc` will place every variable and
temporary at first: one slot per value, at a fixed negative offset from `rbp` (lesson 9.3).

### Stepping through a real call
Here's a C program with a function that takes **parameters** (inputs, like Python's) and the
`clang -O0 -arch x86_64` output for it (directives removed):

```c
int add(int a, int b) {
    return a + b;
}

int main(void) {
    int x = 5;
    return add(x, 3);
}
```

```
_add:                                 _main:
    pushq   %rbp                          pushq   %rbp
    movq    %rsp, %rbp                    movq    %rsp, %rbp
    movl    %edi, -4(%rbp)   # a          subq    $16, %rsp
    movl    %esi, -8(%rbp)   # b          movl    $0, -4(%rbp)
    movl    -4(%rbp), %eax                movl    $5, -8(%rbp)     # x = 5
    addl    -8(%rbp), %eax   # a + b      movl    -8(%rbp), %edi   # arg 1 = x
    popq    %rbp                          movl    $3, %esi         # arg 2 = 3
    retq                                  callq   _add
                                          addq    $16, %rsp
                                          popq    %rbp
                                          retq
```

Suppose the C startup code calls `main` with `rsp = 0x1000`. Let `R1` be the return address into
the startup code and `R2` the address of `addq $16, %rsp` in `main`. Step by step:

```
(1) entering main (call pushed R1)    (2) after main's prologue + subq $16
    0x0ff8 | R1          | <- rsp         0x0ff8 | R1          |
                                          0x0ff0 | old rbp     | <- rbp = 0x0ff0
                                          0x0fec | 0 (clang)   |  -4(%rbp)
                                          0x0fe8 | x = 5       |  -8(%rbp)
                                          0x0fe0 | (unused)    | <- rsp = 0x0fe0

(3) callq _add: pushes R2, jumps      (4) after add's prologue
    edi = 5, esi = 3                      0x0ff0 | old rbp     |
    0x0fe0 | (unused)    |                0x0fe8 | x = 5       |
    0x0fd8 | R2          | <- rsp         0x0fd8 | R2          |
                                          0x0fd0 | 0x0ff0      | <- rsp = rbp = 0x0fd0
                                          0x0fcc | a = 5       |  -4(%rbp)
                                          0x0fc8 | b = 3       |  -8(%rbp)

(5) eax = 5 + 3 = 8; popq %rbp        (6) retq pops R2, back in main
    rbp = 0x0ff0 (main's again)           rsp = 0x0fe0; addq $16 -> rsp = 0x0ff0
    rsp = 0x0fd8, pointing at R2          popq %rbp -> rbp restored, rsp = 0x0ff8
                                          retq pops R1 -> back in startup code, eax = 8
```

Things to notice:
- Each call got its own frame, and `rbp` always pointed at the current one.
- `add`'s locals are *below* `rsp`, because `add` never subtracted from `rsp`. That's allowed for
  a **leaf function** (one that calls nothing): System V guarantees a 128-byte **red zone** below
  `rsp` that signal handlers won't clobber. `rcc` won't rely on it, but you'll see it in `-O0`
  output.
- Every push had a matching pop, so each `ret` found its return address.
- The program exits with status 8, delivered in `eax`.

### The System V calling convention
`add` read its arguments from `edi` and `esi` and returned in `eax`. Who decided that? The
**calling convention** (part of the platform's **ABI**, application binary interface). Linux and
macOS on x86-64 both use the **System V AMD64** convention. Every compiler follows it, which is why
your `rcc` output will be able to call `putchar` from the C library, and why the test suite's
`clang`-compiled code can call your functions. The rules you need:

**Integer and pointer arguments.** The first six go in registers, in this order:

| Argument | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 64-bit | `rdi` | `rsi` | `rdx` | `rcx` | `r8` | `r9` |
| 32-bit (`int`) | `edi` | `esi` | `edx` | `ecx` | `r8d` | `r9d` |

(Mnemonic: "**D**iane's **S**ilk **D**ress **C**osts **8** **9** dollars".) Arguments 7 and up go
**on the stack**, 8 bytes each, with argument 7 at the lowest address (just above the return
address once the call happens), so the callee finds them at `16(%rbp)`, `24(%rbp)`, ... The
**caller** removes them afterwards. Here's `main` calling `sum8(1, 2, ..., 8)` (clang `-O0`):

```
    subq    $32, %rsp        # space for 2 stack args, keeping alignment
    movl    $1, %edi         # args 1-6 in registers
    ...
    movl    $6, %r9d
    movl    $7, (%rsp)       # arg 7 at the lowest address
    movl    $8, 8(%rsp)      # arg 8 just above it
    callq   _sum8            # inside sum8: arg 7 = 16(%rbp), arg 8 = 24(%rbp)
    addq    $32, %rsp        # caller cleans up
```

(Clang stores stack arguments with `mov`; pushing them in reverse order with `pushq` is equally
valid and is what `rcc` will do in lesson 11.3.)

**Return value.** In `rax` (`eax` for an `int`).

**Stack alignment.** `rsp` must be a **multiple of 16 immediately before every `call`**. Then, on
entry to the callee, `rsp` is 8 more than a multiple of 16 (the return address was pushed), and
after `pushq %rbp` it's aligned again. In the trace above, `rsp` was `0x0fe0` at the `call`: a
multiple of 16. Misalignment often "works" until a library function uses an instruction that
requires alignment, and then crashes mysteriously.

**Who saves which registers.** A call may need registers the caller was using. The convention
splits the work:
- **Caller-saved** ("volatile"): `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`–`r11`. Any call may
  overwrite them. If the caller needs a value in one of these after the call, the *caller* must
  save it first.
- **Callee-saved** ("non-volatile"): `rbx`, `rbp`, `r12`–`r15` (and `rsp`). A function that
  wants to use one must save the old value and restore it before returning. The prologue's
  `pushq %rbp` / epilogue's `popq %rbp` is exactly this, for `rbp`.

Until Unit 14, `rcc` keeps every value in a stack slot, never in a register across a call, so it
only has to respect `rbp` and `rsp`. Register allocation is where these rules start to bite.

(One extra rule for later: when calling a *variadic* function like `printf`, `al` must hold the
number of vector registers used; `movl $0, %eax` before the call is enough for integer-only calls.)

### Recursion is free
Because every call gets a fresh frame, a recursive function needs nothing special: each active
call of `fact(n)` has its own `n` at `-4(%rbp)` in its own frame, stacked on top of the previous
one. Too deep a recursion runs off the end of the stack region: in C that's a crash
(segmentation fault); Python protects you with `RecursionError` long before that happens.

## Common pitfalls
- Drawing the stack growing upward, then getting offsets' signs backwards. Locals are at
  *negative* offsets from `rbp`; stack arguments at *positive* ones.
- Forgetting the return address when computing offsets: stack argument 7 is at `16(%rbp)`, not
  `8(%rbp)`.
- Assuming argument registers survive a call: `edi` is caller-saved, and the callee may reuse it.
- Getting the argument order wrong (`rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`).
- Testing alignment only with your own functions, which don't care; it's library calls that crash.
