# Lesson 6.6 — The Back End at a Glance
**Part:** 2 — Learn Compilers · **Unit:** 6 — The Machine · **Type:** Learning · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 5.5, 6.3–6.5

## Overview
Unit 5 covered the front end (source → AST → IR) and Unit 6 so far covered the machine. This
lesson connects them: how a compiler's **back end** turns three-address code into correct x86-64
assembly, and then how it makes that assembly *good*. You'll hand-compile a small program through
the same steps `rcc` will use (instruction selection, assigning memory, fixing illegal
instructions, adding the prologue), then survey optimisation, **control-flow graphs** and
**register allocation**. The lesson ends with a map of Part 3, Units 8–14, so you know where every
piece fits before you start building.

## The lesson

### The plan: small passes
Rather than one giant "IR to assembly" function, `rcc`'s back end is a chain of small passes, each
easy to test. Starting from the IR (called **TACKY** in Part 3, the three-address code of 5.5):

```
 TACKY ──(1) instruction selection──> assembly with pseudoregisters
       ──(2) replace pseudoregisters──> assembly with stack slots
       ──(3) fix-up illegal instructions──> valid assembly + prologue
       ──(4) emission──> text in a .s file
```

The intermediate "assembly" stages are *data structures* (a Rust enum per instruction and
operand, much like the AST), not text. Only the last pass prints text.

### A worked example, by hand
Take `return 1 + 2 * 3;`, whose TAC (5.5) is:

```
tmp.0 = 2 * 3
tmp.1 = 1 + tmp.0
return tmp.1
```

**(1) Instruction selection** picks x86-64 instructions for each TAC instruction. x86-64
arithmetic is *two-address* (`addl src, dst` means `dst = dst + src`), so `a = b + c` becomes
"copy `b` into `a`, then add `c` to `a`". Temporaries are left as **pseudoregisters**: imaginary
registers, one per variable, with unlimited supply.

```
    movl    $2, %tmp.0          # tmp.0 = 2
    imull   $3, %tmp.0          # tmp.0 = tmp.0 * 3
    movl    $1, %tmp.1          # tmp.1 = 1
    addl    %tmp.0, %tmp.1      # tmp.1 = tmp.1 + tmp.0
    movl    %tmp.1, %eax        # return value goes in eax (6.4)
    ret
```

**(2) Replace pseudoregisters.** The real machine has no `%tmp.0`, so give each pseudoregister its
own 4-byte stack slot below `rbp` (6.4): `tmp.0` → `-4(%rbp)`, `tmp.1` → `-8(%rbp)`.

```
    movl    $2, -4(%rbp)
    imull   $3, -4(%rbp)            # ILLEGAL: imul's destination must be a register
    movl    $1, -8(%rbp)
    addl    -4(%rbp), -8(%rbp)      # ILLEGAL: two memory operands
    movl    -8(%rbp), %eax
    ret
```

**(3) Fix-up.** Rewrite each illegal instruction using a spare **scratch register** (this course
uses `r10d` and `r11d`, which nothing else uses yet), and add the prologue and stack reservation:

```
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $16, %rsp               # 8 bytes needed, rounded up to 16 for alignment (6.4)
    movl    $2, -4(%rbp)
    movl    -4(%rbp), %r11d         # imul via a register
    imull   $3, %r11d
    movl    %r11d, -4(%rbp)
    movl    $1, -8(%rbp)
    movl    -4(%rbp), %r10d         # memory-to-memory via a register
    addl    %r10d, -8(%rbp)
    movl    -8(%rbp), %eax
    movq    %rbp, %rsp              # epilogue before every ret
    popq    %rbp
    ret
```

**(4) Emission** prints this with the platform details: `.globl _main`, the `_main:` label on
macOS, or the GNU-stack note on Linux. Build and run it, and the exit status is 7.

It's long-winded compared with the `movl $7, %eax` a good compiler would produce, but it is
*correct*, and every step is simple. That's the right trade-off for a first compiler. You'll build
step 1 for `return` in lesson 8.4, emission in 8.5, and steps 2–3 in lesson 9.3.

### Control flow in the back end
TAC's jumps map almost one-to-one onto 6.3's instructions: `jump L` → `jmp L`;
`jump_if_zero v, L` → `cmpl $0, v` then `je L`; labels stay labels. A comparison that produces a
*value*, such as `tmp.0 = a < b`, becomes `cmpl`, then a `setl` into an 8-bit register to get 1 or
0 (lesson 9.6). Functions add the System V work from 6.4: moving arguments into `edi`, `esi`, ...,
pushing extras, keeping `rsp` aligned, and reading parameters back out in the callee (11.3).

### Optimisation: making it good
An **optimiser** rewrites the program so it runs faster or is smaller, *without changing what it
does*. `rcc`'s optimisations (Unit 13) work on TACKY, between the front and back ends:

- **Constant folding:** compute operations on constants at compile time. `tmp.0 = 2 * 3` →
  `tmp.0 = 6`.
- **Copy propagation:** after `x = y`, replace later uses of `x` with `y` where that's safe, so
  `tmp.1 = 1 + tmp.0` with `tmp.0 = 6` becomes `tmp.1 = 1 + 6`, which folds to 7.
- **Unreachable-code elimination:** delete code no path can reach (after an unconditional jump,
  or in `if (0) { ... }`).
- **Dead-store elimination:** delete assignments whose value is never read afterwards.

Each one alone is small; run repeatedly together, they feed each other. Our example collapses to
`return 7`. That is what you saw clang do at `-O2` in lesson 6.3.

### Control-flow graphs
To reason about *which values can reach which instructions*, optimisers organise code into a
**control-flow graph** (CFG). A **basic block** is a straight run of instructions with one entry
(at the top) and one exit (at the bottom): no jumps in or out of the middle. Edges show where
control can go next. The `while` loop's TAC from 5.5 as a CFG:

```
            [ ENTRY ]
                |
                v
     +----------------------+
     | total = 0            |      B0
     | n = 4                |
     +----------------------+
                |
                v
     +----------------------+ <-----------+
     | loop.0:              |      B1     |
     | tmp.0 = n > 0        |             |
     | jump_if_zero tmp.0   |             |
     +----------------------+             |
        |              |                  |
   true |              | false            |
        v              v                  |
 +--------------+  +-----------+          |
 | total = ...  |  | break.0:  |   B3     |
 | n = n - 1    |  | return    |          |
 | jump loop.0  |  | total     |          |
 +--------------+  +-----------+          |
   B2   |              |                  |
        +--------------)------------------+
                       v
                   [ EXIT ]
```

A **dataflow analysis** then propagates facts around this graph until they stop changing, for
instance "which copies are still valid at the start of each block" (for copy propagation) or
"which variables might still be read later" (**liveness**, for dead-store elimination). Lessons
13.3–13.6 build the CFG, a general dataflow framework, and the optimisations on top.

### Register allocation
Our hand-compiled code touches memory on almost every instruction. Registers are far faster (6.2),
so the last big back-end job is **register allocation**: decide which pseudoregisters live in real
registers instead of stack slots. The key idea: two values **interfere** if both are *live* (still
needed later) at the same time, so they can't share a register. Draw a node per pseudoregister and
an edge between each interfering pair: that's the **interference graph**. Assigning registers is
then **graph colouring**: give each node one of *k* colours (registers) so that no edge joins two
nodes of the same colour.

```
  a --- b        a: red     With 2 registers, a and c can share red,
  |     |        b: blue    b and d can share blue.
  d --- c        c: red
                 d: blue
```

If the graph needs more colours than there are registers, some values are **spilled** to the
stack, exactly as they are today. **Coalescing** then removes pointless `mov`s by giving both sides
of a `movl %x, %y` the same register when they don't interfere. Here the caller-/callee-saved
rules from 6.4 finally matter: a value living in `ecx` across a `call` may be destroyed. Unit 14
builds all of this.

## Build
1. **Hand-compile.** Take your TAC for `return 2 * (3 + 4);` from lesson 5.5 and run it through
   all four back-end steps on paper, exactly as in the worked example. Write the final version to
   a `.s` file, build it with `clang -arch x86_64`, run it under `arch -x86_64`, and check the
   exit status.
2. **Hand-compile with control flow.** Do the same for the TAC of
   `int a = 6; int b = 7; if (a < b) { return b; } return a;`. Use `cmpl` and a conditional jump.
   Run it and check you get 7. Then swap the values and check you get 7 again.
3. **Count fix-ups.** For each instruction, say whether it's legal once pseudoregisters become
   stack slots, and fix the illegal ones: `movl %x, %y` · `addl $5, %x` · `subl %x, %y` ·
   `imull %x, %y` · `cmpl %x, %y` · `cmpl %x, $5`.
4. **Draw CFGs.** Split into basic blocks and draw the CFG for your TAC of: the `if`/`else` from
   5.5, and the full `while`/`if` program from 5.4.
5. **Optimise by hand.** Apply constant folding and copy propagation repeatedly to:
   `a = 4; b = a * 2; c = b + a; if (0) { c = 99; } return c;`. Show each step and which
   optimisation it was.
6. **Colour a graph.** Values `a, b, c, d, e` with interference pairs a–b, a–c, b–c, c–d, d–e.
   What is the fewest registers that avoids spills? Give a colouring. If only 2 registers are
   available, which value would you spill, and why?
7. **Compare with clang.** Compile a small function at `-O0` and `-O2` (Godbolt or `clang -S`),
   and for each difference, name the optimisation you think did it (folding, removing stores,
   keeping values in registers, ...).
8. **Your map.** Write a one-page summary in your notes: for each Part 3 unit, which Part 2
   lessons it relies on. You'll refer back to it all through Part 3.

## Common pitfalls
- Thinking the unoptimised output is "wrong" because it's long. Correctness first; Units 13–14 make
  it fast.
- Forgetting that x86-64 arithmetic is two-address: `addl src, dst` overwrites `dst`, so you must
  copy the first operand into the destination before adding.
- Forgetting the epilogue before *every* `ret`, not just the last one.
- Putting a jump target in the middle of a basic block: a block ends at every jump and starts at
  every label.
