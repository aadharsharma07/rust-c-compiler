# Lesson 6.5 — The Toolchain
**Part:** 2 — Learn Compilers · **Unit:** 6 — The Machine · **Type:** Learning · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 6.3, 6.4

## Overview
When you type `clang prog.c -o prog`, four separate programs run in sequence: the
**preprocessor**, the **compiler** proper, the **assembler** and the **linker**. `rcc` will
replace only the second one, and rely on the others. In this lesson you run each stage by hand,
look inside **object files** and their **symbols**, see what the linker does and what its errors
mean, and finally set up the test suite you'll use for all of Part 3, checking it against `clang`.

## The lesson

### Four stages
```
 prog.c --[preprocess]--> prog.i --[compile]--> prog.s --[assemble]--> prog.o --[link]--> prog
         clang -E -P              clang -S             clang -c              clang
         (rcc's driver)           ** rcc **            (as)                  (ld)
```

`clang` is a **driver**: a program that runs the stages for you and passes files between them.
You can stop it after any stage with a flag, which is how you'll inspect each one. Your `rcc` will
also be a driver (lesson 8.1): it'll call the system's preprocessor, do the compiling itself, and
then call the system's assembler and linker. Throughout, remember `-arch x86_64` on Apple Silicon.

### Stage 1: the preprocessor
C has a separate text-substitution language layered on top, made of lines starting with `#`. The
**preprocessor** handles them before the compiler sees anything:
- `#include <stdio.h>` pastes in the entire contents of another file (a *header*, which mostly
  contains declarations of library functions);
- `#define LIMIT 10` defines a **macro**: every later `LIMIT` is textually replaced by `10`;
- it also strips comments.

```c
#define LIMIT 10
// a comment
int main(void) { return LIMIT * 2; }
```

`clang -E -P prog.c` (stop after preprocessing; `-P` drops the line-marker noise) prints:

```c
int main(void) { return 10 * 2; }
```

This is a gift to a compiler writer: `rcc` never sees `#`, macros or comments. Python has nothing
like it; `import` is a run-time operation that loads a module object, not text pasting.

### Stage 2: the compiler
This is the part you'll write: preprocessed C in, assembly text out. `clang -S prog.c` stops here
and writes `prog.s`. You've already read plenty of these files in 6.3 and 6.4.

### Stage 3: the assembler
The **assembler** translates assembly text into machine code, one instruction at a time (the
`55`, `48 89 e5`, `c3` bytes from 6.2). Its output is an **object file** (`.o`): machine code plus
bookkeeping. `clang -c prog.s` (or `clang -c prog.c`) stops here.

An object file isn't runnable yet, because it may refer to things it doesn't contain. Take:

```c
// main2.c
int square(int n);              // a declaration: "square exists somewhere"
int main(void) { return square(7); }
```

```c
// sq.c
int square(int n) { return n * n; }
```

The line `int square(int n);` is a **function declaration** (a *prototype*): it tells the
compiler `square`'s parameter and return types without giving a body, so the call can be compiled
and type-checked (5.4). The body lives in another file.

### Symbols
Each object file has a **symbol table** listing the names it *defines* and the names it *needs*.
`nm` prints it:

```
$ clang -arch x86_64 -c main2.c sq.c
$ nm main2.o
0000000000000000 T _main          T = defined here, in the text (code) section
                 U _square        U = undefined: used here, defined elsewhere
$ nm sq.o
0000000000000000 T _square
```

When `main2.o` was assembled, the address of `_square` was unknown, so the `call` instruction was
left with a placeholder and a **relocation** entry: a note saying "patch in the address of
`_square` here". `objdump -r main2.o` shows these.

Only symbols marked **global** are visible to other object files. That's what `.globl _main` in
6.3 did; without it, `main` would be private to its file and the startup code couldn't find it.
(C's `static` keyword makes a function file-private in the same way; lesson 11.4.)

### Stage 4: the linker
The **linker** combines object files (and libraries) into one executable. It:
1. lays out all the code and data in the final memory image;
2. **resolves** every undefined symbol to a definition in some other object file or library;
3. applies the relocations, patching in real addresses;
4. adds the C **startup code**, which sets things up, calls `main`, and passes its return value to
   the operating system as the exit status (5.1).

Try linking only `main2.o`:

```
$ clang -arch x86_64 main2.o -o prog
Undefined symbols for architecture x86_64:
  "_square", referenced from:
      _main in main2.o
ld: symbol(s) not found for architecture x86_64
```

That's a **link error**, not a compile error: each file compiled fine, but no file defined
`_square`. Link both and it works: `clang -arch x86_64 main2.o sq.o -o prog`, and
`arch -x86_64 ./prog; echo $?` prints 49. On Linux the message reads
`undefined reference to 'square'`. Learn to recognise link errors; you'll cause a few.

### Libraries
Functions like `putchar` (print one character) come from the **C standard library** (libc;
`libSystem` on macOS), which the driver links in automatically. Your compiled code calls it
exactly like `square`: a `call _putchar` with an undefined symbol, resolved at link time (on
macOS and most Linux systems, at load time from a shared library). Because both sides follow
System V (6.4), code from `rcc` and code from `clang` can call each other freely. The test suite
relies on this from chapter 9 on, linking your output with `clang`-compiled helpers.

### The test suite
Part 3 is checked by `writing-a-c-compiler-tests`, a collection of small C programs organised by
chapter, plus a Python script, `test_compiler`, that runs your compiler on each and checks the
result. For a *valid* program, it compiles it with your compiler, runs the executable and
compares its exit status and output with the expected ones. For an *invalid* program (in folders
like `invalid_lex`, `invalid_parse`), it checks that your compiler *rejects* it with a non-zero
exit code. The basic usage:

```
./test_compiler /path/to/compiler --chapter 1
./test_compiler /path/to/compiler --chapter 1 --stage lex      # only check lexing
```

With `--stage`, the script asks your compiler to stop early (lesson 8.1 adds the `--lex`,
`--parse`, `--codegen` flags this needs). Run `./test_compiler --help` to see every option; don't
rely on memory for flag names.

Before writing a line of `rcc`, it's worth proving the setup works by testing a compiler that is
already correct: `clang` itself. The script calls your compiler as `compiler path/to/prog.c` and
expects an executable `path/to/prog` to appear, so a tiny wrapper script adapts `clang` to that
interface (see Build step 6).

## Build
1. **Run each stage by hand.** With a small C file that uses `#define` and has comments, run
   `clang -E -P`, then `clang -S -arch x86_64 -fno-asynchronous-unwind-tables` on the result,
   then `clang -c -arch x86_64` on the `.s`, then `clang -arch x86_64` on the `.o`. Run the
   result with `arch -x86_64`. Write down the file produced at each stage and what's in it.
2. **Symbols.** Build `main2.c` and `sq.c` as object files. Run `nm` on each, then
   `objdump -r main2.o`. Explain each `T` and `U`, and what the relocation is for.
3. **Break the link.** Link `main2.o` alone and read the error. Then remove `.globl _main` from a
   hand-written `.s` file and try to link it; read that error too. Explain both in a sentence each.
4. **Disassemble.** Run `objdump -d --x86-asm-syntax=att sq.o` and match the bytes on the left to
   the instructions on the right. Which instruction is one byte long?
5. **Call the library.** Compile and run this, and use `nm` on its object file to find the
   undefined symbol:
   ```c
   int putchar(int c);
   int main(void) { putchar(72); putchar(105); putchar(10); return 0; }
   ```
6. **Set up the test suite.**
   - Clone it next to your project folder:
     `git clone https://github.com/nlsandler/writing-a-c-compiler-tests.git`
   - On Apple Silicon, open an x86-64 shell first: `arch -x86_64 zsh` (`uname -m` → `x86_64`).
     The script needs Python 3.8+; the system `/usr/bin/python3` works under Rosetta, but an
     arm64-only Python (some Homebrew installs) may not.
   - Run `./test_compiler --check-setup` and fix anything it reports.
   - Create a wrapper script `clang-as-rcc.sh` *outside* the test-suite folder:
     ```sh
     #!/bin/sh
     # Adapts clang to the test suite's interface: compile path/prog.c to path/prog
     src="$1"
     exec clang -arch x86_64 "$src" -o "${src%.c}"
     ```
     Make it executable (`chmod +x clang-as-rcc.sh`), then run
     `./test_compiler /full/path/to/clang-as-rcc.sh --chapter 1`. Valid programs should pass;
     invalid ones should be rejected by clang. Try `--chapter 2` and `--chapter 3` too. (This
     wrapper only handles the simple interface; later chapters pass extra options, so don't expect
     it to cover everything. Check `--help` if something looks odd.)
7. **Browse the tests.** Open `tests/chapter_1/`. Read three valid programs and three invalid
   ones, and for each invalid one, say whether a lexer or a parser should reject it (5.2–5.4).

## Check your understanding
1. Name the four stages, what each takes in and puts out, and which one `rcc` implements.
2. Why does `rcc` never have to handle `#define` or comments?
3. What do `T` and `U` mean in `nm` output, and what is a relocation?
4. Why is "undefined symbol" a linker error rather than a compiler error?
5. How does the test suite decide whether your compiler handled an invalid program correctly?

## Common pitfalls
- Confusing compile errors with link errors: if every file compiles but you see `ld:`, look for a
  missing definition, a missing `.globl`, or a missing `_` prefix on macOS.
- Forgetting `-arch x86_64` at *one* stage, producing a mix of arm64 and x86-64 files that refuse
  to link.
- Running `test_compiler` from a native arm64 shell on Apple Silicon; use `arch -x86_64 zsh`.
- Pointing `test_compiler` at the compiler with a relative path that breaks when the script changes
  directory; use a full path.
