# Lesson 5.2 — Lexing
**Part:** 2 — Learn Compilers · **Unit:** 5 — How Languages Are Processed · **Type:** Learning · **Est. time:** 3–5 h · **Tests:** none
**Prerequisites:** lesson 5.1

## Overview
The **lexer** (also called a *scanner* or *tokeniser*) is the first phase of a compiler. It
turns a flat string of characters into a list of meaningful chunks called **tokens**, throwing
away whitespace and comments. In this lesson you learn what tokens are, how regular expressions
describe them, how a lexer is really a *finite automaton*, and the "longest match" rule that
settles ambiguities. You will then watch CPython's own tokenizer at work on your code.

## The lesson

### Why lex at all?
Look at this C fragment as the computer first sees it: a sequence of characters.

```
r e t u r n ␣ 4 2 ;
```

The parser (5.3) wants to reason about *words*: "a return keyword, then a number, then a
semicolon". It does not want to worry about whether there were two spaces or a tab, or whether
`42` is one thing or two. So the lexer groups characters into tokens once, and the parser only
ever sees tokens. This is the same reason you split a sentence into words before working out its
grammar.

### Tokens, lexemes and kinds
A **token** has:
- a **kind** (or *type*): what category it belongs to, such as `Identifier`, `Constant`,
  `Semicolon`, `KeywordReturn`;
- a **lexeme**: the exact characters it was made from, such as `"main"` or `"42"`;
- usually a **position** (line and column), so error messages can point at the right place.

Some kinds have only one possible lexeme (`;` is always `;`), so the lexeme carries no extra
information. Others, like identifiers and constants, need the lexeme (or a value derived from it,
such as the integer 42) to be kept. In Rust you will model this with an `enum` whose variants
carry data, exactly as in lesson 3.2: `Identifier(String)`, `Constant(i64)`, `Semicolon`, ...

Here is a C function and its token stream:

```c
int main(void) {
    return 42; // the answer
}
```

```
 Keyword(int)  Identifier(main)  OpenParen  Keyword(void)  CloseParen  OpenBrace
 Keyword(return)  Constant(42)  Semicolon
 CloseBrace
```

Notice what is missing: spaces, newlines and the comment `// the answer`. In C, `//` starts a
comment that runs to the end of the line, and `/* ... */` is a comment that can span lines. The
lexer skips them all. (In Part 3, comments are removed even earlier, by the preprocessor; see 6.5.)

### Describing tokens with regular expressions
You have probably used Python's `re` module. A **regular expression** (regex) is a tiny language
for describing a set of strings. The handful of operators that matter for lexing:

| Regex | Meaning | Matches |
|---|---|---|
| `abc` | the characters in order | `abc` |
| `a\|b` | either | `a` or `b` |
| `[a-z]` | one character from a set | `q` |
| `x*` | zero or more `x` | ``, `x`, `xxx` |
| `x+` | one or more `x` | `x`, `xxx` |
| `x?` | optional | ``, `x` |
| `\b` | a word boundary (no character consumed) | between `2` and `;` in `2;` |

The C tokens you need first can each be written as a regex:

```
Identifier   [a-zA-Z_][a-zA-Z0-9_]*\b      a letter or _, then letters, digits or _
Constant     [0-9]+\b                       one or more digits, then a word boundary
int          int\b          void   void\b          return  return\b
(  \(        )  \)          {  {        }  }         ;  ;
```

Why the `\b` on `Constant`? Without it, `123abc` would lex as the constant `123` followed by the
identifier `abc`. With it, `123` is only a constant if it is *not* immediately followed by a
letter, digit or underscore, so `123abc` matches no token at all and the lexer reports an error.
Real C compilers reject `123abc` too.

### Two rules that settle ambiguity
At any point the lexer may find several regexes that match. Two rules decide which one wins:

1. **Longest match** (also called *maximal munch*): take the regex that matches the *most*
   characters. In `returned = 1`, the identifier regex matches `returned` (8 characters) while
   the keyword regex `return` would match only 6, so we get `Identifier(returned)`, not
   `Keyword(return)` followed by `Identifier(ed)`. Similarly, in C `x<=y` lexes as `x`, `<=`, `y`,
   never `x`, `<`, `=`, `y`.
2. **Priority on ties**: if two regexes match the *same* length, the one listed first wins.
   `return` matches both `Identifier` and `Keyword(return)` with length 6. Keywords take
   priority, so it's a keyword. (A common practical trick: lex it as an identifier, then check
   whether the lexeme is in the keyword list.)

### Under the hood: finite automata
How does a regex actually match? Every regex can be turned into a **finite automaton**: a little
machine with a fixed set of **states** and **transitions** labelled by characters. It reads the
input one character at a time, following transitions. If it stops in an **accepting state**, the
characters read so far form a token.

Here is a **deterministic finite automaton (DFA)** that recognises identifiers, constants, and the
operators `<` and `<=` (accepting states are drawn with double brackets):

```
                 letter or _               letter, digit or _
   (start) ----------------------> [[ident]] <-------+
      |                                  |           |
      |                                  +-----------+
      |  digit                    digit
      +-----------> [[number]] <-----+
      |                  |           |
      |                  +-----------+
      |   '<'                     '='
      +-----------> [[less]] ------------> [[less_equal]]
```

Run it on `x1<=9`:
```
 read 'x'  start -> ident        (accepting: could stop here with "x")
 read '1'  ident -> ident        (accepting: "x1")
 read '<'  no transition from ident on '<'  => emit Identifier("x1"), restart at '<'
 read '<'  start -> less         (accepting: "<")
 read '='  less  -> less_equal   (accepting: "<=")
 read '9'  no transition from less_equal   => emit LessEqual, restart at '9'
 read '9'  start -> number; end of input     => emit Constant(9)
```

This "keep going while you can, then emit the last accepting state" loop *is* the longest-match
rule. You never need to build a DFA table yourself; Rust's `regex` crate (or a hand-written loop
over characters) does it. But knowing the model explains why lexing is fast (one pass, a fixed
amount of work per character) and why regexes cannot match nested structures like balanced
parentheses: a finite automaton has no memory of how deep it is. Nesting is the parser's job.

### What a lexer rejects
The lexer's errors are about characters that form no token at all:
- a character that no regex starts with, such as `@` or `` ` `` in C;
- a malformed literal, such as `123abc`.

It does *not* catch `return return ;;`: every piece is a valid token. Whether tokens are in a
sensible *order* is the parser's job.

### Case study: CPython's tokenizer
Python exposes its tokenizer in the standard library. Given this `t.py`:

```python
x = 3 + 4 * y
if x >= 10:
    print("big")
```

`python3 -m tokenize -e t.py` prints (columns trimmed):

```
1,0-1,1:    NAME          'x'
1,2-1,3:    EQUAL         '='
1,4-1,5:    NUMBER        '3'
1,6-1,7:    PLUS          '+'
1,8-1,9:    NUMBER        '4'
1,10-1,11:  STAR          '*'
1,12-1,13:  NAME          'y'
1,13-1,14:  NEWLINE       '\n'
2,0-2,2:    NAME          'if'
2,3-2,4:    NAME          'x'
2,5-2,7:    GREATEREQUAL  '>='
2,8-2,10:   NUMBER        '10'
2,10-2,11:  COLON         ':'
2,11-2,12:  NEWLINE       '\n'
3,0-3,4:    INDENT        '    '
3,4-3,9:    NAME          'print'
  ...
4,0-4,0:    DEDENT        ''
4,0-4,0:    ENDMARKER     ''
```

Things to notice:
- Every token has a kind, a lexeme and a start/end position (`line,col`).
- `>=` is one token (longest match).
- The keyword `if` comes out as `NAME`: this tokenizer leaves the keyword check to the parser.
  Either design works.
- Python's indentation is *significant*, so the tokenizer turns it into `INDENT` and `DEDENT`
  tokens, which play the role of C's `{` and `}`. That is a job C's lexer never has to do,
  because C ignores whitespace entirely.
- `-e` asks for exact kinds (`PLUS`); without it you would see the generic `OP`.

## Common pitfalls
- Matching keywords *before* checking length, so `returned` lexes as `return` + `ed`.
- Forgetting the word boundary on constants, so `123abc` is accepted.
- Expecting the lexer to catch grammar mistakes. `return return;` is perfectly lexable.
- Assuming whitespace never matters. It *separates* tokens: `int x` is two tokens, `intx` is one.
