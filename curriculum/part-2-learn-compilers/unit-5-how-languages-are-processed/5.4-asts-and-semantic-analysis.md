# Lesson 5.4 — ASTs and Semantic Analysis
**Part:** 2 — Learn Compilers · **Unit:** 5 — How Languages Are Processed · **Type:** Learning · **Est. time:** 4–5 h · **Tests:** none
**Prerequisites:** lessons 5.1–5.3

## Overview
A parse tree records *every* detail of how a program was written. A compiler's later phases want
something leaner: the **abstract syntax tree** (AST), which keeps only the meaning. In this lesson
you learn how an AST differs from a parse tree, inspect real ASTs with Python's `ast` module, and
then meet **semantic analysis**: the checks a grammar cannot express, such as "this variable was
declared" and "this function got the right number of arguments". Along the way you'll learn C's
variables, `if` and `while`, and the scope and symbol-table ideas you'll implement in Units 10–11.

## The lesson

### From parse tree to AST
Recall the parse tree for `return 2;` from 5.3: it had leaves for `"return"`, `";"`, and chains
like `<exp> -> <term> -> <factor> -> <int>`. None of that matters after parsing. The `;` only told
the parser where the statement ended; the chain of nonterminals only encoded precedence, which the
tree's *shape* now records. An **AST** throws those away:

```
  Parse tree for  1 + 2 * 3              AST
         <exp>                          Add
       /   |   \                       /   \
  <term>  "+"  <term>            Const(1)   Mul
     |        /  |  \                      /   \
 <factor> <term> "*" <factor>        Const(2)  Const(3)
     |       |        |
     1   <factor>     3
             |
             2
```

The AST has one node per *meaningful construct*. Parentheses vanish too: `(1 + 2) * 3` is simply
a `Mul` whose left child is an `Add`. In practice your recursive-descent functions build AST nodes
directly (as in 5.3's pseudocode); the parse tree is never stored.

In Rust, AST nodes are enums and structs. A sketch in words: an *expression* is either a constant
(holding an integer), a variable (holding a name), a unary operation (an operator and one boxed
sub-expression) or a binary operation (an operator and two boxed sub-expressions). That is exactly
the recursive enum with `Box` you met in lesson 4.4.

### A little more C: variables, `if` and `while`
To have something worth analysing, here is a slightly bigger C program:

```c
int main(void) {
    int total = 0;
    int n = 4;
    while (n > 0) {
        total = total + n;
        n = n - 1;
    }
    if (total > 5) {
        return total;
    } else {
        return 0;
    }
}
```

New pieces of C:
- `int total = 0;` is a **declaration**: it creates a variable named `total` of type `int` and
  **initialises** it to 0. In Python, assigning a name creates it; in C you must declare a variable,
  with its type, before using it. `total = total + n;` later is plain **assignment** to an
  existing variable.
- `while (cond) { ... }` repeats the body while `cond` is true. The parentheses are required.
- `if (cond) { ... } else { ... }` works like Python's `if`/`else`. C has no `elif`; you write
  `else if (...)`.
- Conditions are integers: `0` means false, anything else means true. `n > 0` evaluates to 1 or 0.

The AST for the `while` loop, drawn as a tree:

```
                 While
               /       \
       cond: Binary(>)   body: Block
          /     \            /            \
    Var(n)   Const(0)   Assign             Assign
                       /      \           /       \
                Var(total)  Binary(+)  Var(n)   Binary(-)
                           /     \              /     \
                    Var(total) Var(n)       Var(n)  Const(1)
```

### Case study: Python's AST
The `ast` module gives you CPython's real AST. `ast.dump(ast.parse("x = 3 + 4 * y"), indent=2)`:

```
Module(
  body=[
    Assign(
      targets=[
        Name(id='x', ctx=Store())],
      value=BinOp(
        left=Constant(value=3),
        op=Add(),
        right=BinOp(
          left=Constant(value=4),
          op=Mult(),
          right=Name(id='y', ctx=Load()))))])
```

Compare it with the trees above: `BinOp(op=Add)` at the top, `Mult` nested on the right.
Precedence is in the shape; no parentheses or tokens survive. `ctx=Store()` vs. `ctx=Load()`
records whether a name is being *written* or *read*, which the bytecode compiler needs.
`python3 -m ast file.py` dumps a whole file the same way, and `ast.parse(src, mode="eval")`
parses a single expression.

### What the grammar can't check
This C program parses perfectly:

```c
int main(void) {
    int a = 1;
    int a = 2;
    return b;
}
```

Yet it is nonsense: `a` is declared twice and `b` is never declared. A grammar describes *shape*,
and these rules are about *meaning* across distant parts of the program. Catching them is
**semantic analysis**, a pass (or several) that walks the AST after parsing. Typical checks:

- every variable is declared before it is used, and not declared twice in the same scope;
- the left side of `=` is something assignable (`2 = x;` parses as an expression but is invalid);
- functions are called with the right number and types of arguments;
- the types of operands make sense (in Unit 12: you can't multiply two pointers).

Python does almost none of this before running; that's why `NameError` and `TypeError` are
run-time exceptions. C does it at compile time, and so will `rcc`.

### Scopes
A **scope** is a region of the program where a name has a particular meaning. In C, every
`{ ... }` block opens a new scope, and a declaration inside it is visible from that point to the
closing `}`. An inner scope may **shadow** an outer name:

```c
int main(void) {
    int x = 1;          // outer x
    {
        int x = 2;      // a different variable, shadowing the outer x
        x = x + 10;     // refers to the inner x (now 12)
    }
    return x;           // the outer x: returns 1
}
```

Python's scoping is different: an `if` or `while` body does *not* create a new scope; only
functions (and classes, comprehensions) do. This is a classic surprise when moving between the
two languages.

### Symbol tables
A **symbol table** maps each name to what the compiler knows about it: which declaration it
refers to, its type, and later, where it lives in memory. For nested scopes, the natural structure
is a **stack of dictionaries** (in Rust, a `Vec<HashMap<...>>`): push a new map on entering a
block, pop it on leaving, and look names up from the innermost map outward.

Walking the shadowing example:

```
statement              scope stack (innermost last)              action
int x = 1;             [ {x: x.0} ]                              declare x in top map
{                      [ {x: x.0}, {} ]                          push
int x = 2;             [ {x: x.0}, {x: x.1} ]                    declare: x not in TOP map, OK
x = x + 10;            lookup x -> found in top map -> x.1
}                      [ {x: x.0} ]                              pop
return x;              lookup x -> x.0
```

Here each declaration got a **unique name** (`x.0`, `x.1`). Once every use is rewritten to its
unique name, later phases can forget about scopes entirely: two variables can never be confused.
That renaming is exactly the variable-resolution pass you'll build in lesson 10.2. A duplicate
declaration is an error only if the name is already in the *top* map; finding it in an outer map
is legal shadowing.

### Type checking
A **type checker** computes the type of every expression and checks it against the rules. For
now C has only `int`, so the interesting part is functions:

```c
int add(int a, int b) {     // a function taking two ints, returning an int
    return a + b;
}

int main(void) {
    return add(1, 2, 3);    // error: add takes 2 arguments, got 3
}
```

The checker records in the symbol table that `add` is a function of type "(int, int) -> int",
then checks every call against it. Python would raise `TypeError: add() takes 2 positional
arguments but 3 were given`, but only when that line runs. You'll build this in lesson 11.2, and
grow it into a full type system in Unit 12.

### Python's own symbol tables
CPython also has a symbol-table pass; you can see it with the `symtable` module. For
`def f(a): b = a + x` it reports that `a` is a parameter, `b` is local and `x` is global. This is
how CPython decides, *at compile time*, whether a name is a fast local or a global lookup, which is
also why assigning to a name anywhere in a function makes it local everywhere in that function
(the cause of `UnboundLocalError`).

## Common pitfalls
- Checking for duplicate declarations against *all* scopes instead of only the innermost one,
  which wrongly rejects legal shadowing.
- Forgetting to pop the scope at the end of a block, so inner variables leak out.
- Treating `ctx=Load()`/`Store()` in Python's AST as noise: reading vs. writing a name is a
  semantic distinction every compiler needs.
- Assuming C's `if` body shares Python's "no new scope" behaviour.
