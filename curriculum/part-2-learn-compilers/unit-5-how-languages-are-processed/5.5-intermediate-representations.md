# Lesson 5.5 — Intermediate Representations
**Part:** 2 — Learn Compilers · **Unit:** 5 — How Languages Are Processed · **Type:** Learning · **Est. time:** 3–5 h · **Tests:** none
**Prerequisites:** lessons 5.1–5.4

## Overview
An AST is a tree that mirrors the source language. Machine code is a flat list of tiny steps. An
**intermediate representation** (IR) sits in between: flat like machine code, but still
independent of any particular CPU. In this lesson you learn **three-address code**, the style of
IR you will build in Part 3 (called TACKY there), how expressions, `if` and `while` become IR, why
compilers bother with an IR at all, and how CPython's bytecode is itself an IR you can inspect
with the `dis` module.

## The lesson

### The gap an IR fills
Consider `return 1 + 2 * 3;`. Its AST is a nested tree: `Return(Add(1, Mul(2, 3)))`. A CPU, on
the other hand, does one small operation at a time on values held in a few fixed places. Going
straight from a deep tree to x86-64 assembly means solving two problems at once: *flattening* the
tree into an ordered sequence of steps, and dealing with the *quirks* of x86-64 (which operations
can touch memory, which registers are special, and so on). An IR lets you solve the first
problem in one phase and the second in another.

### Three-address code
In **three-address code** (TAC), every instruction does *one* operation and names at most three
"addresses": up to two sources and one destination. Intermediate results get fresh **temporary
variables** (temporaries), which you can think of as an unlimited supply of named boxes.

```
source:   return 1 + 2 * 3;

TAC:      tmp.0 = 2 * 3
          tmp.1 = 1 + tmp.0
          return tmp.1
```

To produce it, walk the AST **post-order** (children before parents): to emit code for
`Add(1, Mul(2, 3))`, first emit code for each operand, which gives you a value (a constant or a
temporary) for each, then emit one instruction combining them into a new temporary. The order of
the instructions now makes evaluation order explicit, which the tree only implied.

Unary operators work the same way. `return -(4 - 6);`:

```
tmp.0 = 4 - 6
tmp.1 = -tmp.0
return tmp.1
```

Variables from the source simply become IR variables (using the unique names from 5.4):

```c
int a = 5;           a.0 = 5
int b = a * 2 + 1;   tmp.0 = a.0 * 2
                     tmp.1 = tmp.0 + 1
                     b.1 = tmp.1
return b;            return b.1
```

### Control flow in a flat world
A flat list has no nested blocks, so `if` and `while` must be expressed with **labels** (named
positions in the list) and **jumps**. Three jump instructions are enough:

- `jump L`: continue at label `L` (like `goto`);
- `jump_if_zero v, L`: if `v` is 0 (false), go to `L`, otherwise fall through to the next line;
- `jump_if_not_zero v, L`: the opposite.

An `if`/`else`:

```c
if (x > 5) {             tmp.0 = x > 5
    y = 1;               jump_if_zero tmp.0, else.0
} else {                 y = 1
    y = 2;               jump end.0
}                      else.0:
                         y = 2
                       end.0:
```

A `while` loop (the program from 5.4):

```c
while (n > 0) {        loop.0:
    total = total + n;   tmp.0 = n > 0
    n = n - 1;           jump_if_zero tmp.0, break.0
}                        tmp.1 = total + n
                         total = tmp.1
                         tmp.2 = n - 1
                         n = tmp.2
                         jump loop.0
                       break.0:
```

Read it as the CPU would: compute the condition; if it is false, leave; otherwise run the body and
jump back to re-test. Every structured construct in C (`for`, `do`, `break`, `continue`, even
`&&` and `||`, which skip evaluating their right side) becomes labels and jumps this way. You'll
generate exactly these patterns in Units 9 and 10. Real CPUs have direct equivalents of these
jumps, as you'll see in lesson 6.3.

### Why IRs exist
- **Separation of concerns.** The front end worries about C; the back end worries about the
  machine. Each is simpler, and each can be tested on its own.
- **Many languages, many machines.** With an IR, *M* front ends and *N* back ends need *M + N*
  pieces instead of *M × N* compilers. That's how LLVM works: `clang` (C), `rustc` (Rust) and
  Swift all produce LLVM IR, and LLVM turns it into x86-64, ARM, RISC-V, and more.
- **Optimisation.** Flat code with explicit temporaries and jumps is much easier to analyse than a
  tree. For instance, `tmp.0 = 2 * 3` has constant operands, so an optimiser can replace it with
  `tmp.0 = 6` (constant folding, lesson 13.2). Unit 13 builds several optimisations on TACKY.

### Stack machines: CPython's bytecode
TAC is a **register-style** IR: instructions name where their inputs and outputs live. The other
big family is the **stack machine**: instructions take their operands from the top of a stack and
push the result back, so they rarely name anything. CPython's bytecode is a stack machine.

The same `total`/`n` loop in Python, disassembled with `dis.dis` on Python 3.14 (instruction names
and details change between Python versions, so yours may differ):

```python
def g(n):
    total = 0
    while n > 0:
        total = total + n
        n = n - 1
    return total
```

```
  9           LOAD_SMALL_INT           0
              STORE_FAST               1 (total)

 10   L1:     LOAD_FAST_BORROW         0 (n)
              LOAD_SMALL_INT           0
              COMPARE_OP             148 (bool(>))
              POP_JUMP_IF_FALSE       20 (to L2)
              NOT_TAKEN

 11           LOAD_FAST_BORROW_LOAD_FAST_BORROW 16 (total, n)
              BINARY_OP                0 (+)
              STORE_FAST               1 (total)

 12           LOAD_FAST_BORROW         0 (n)
              LOAD_SMALL_INT           1
              BINARY_OP               10 (-)
              STORE_FAST               0 (n)
              JUMP_BACKWARD           26 (to L1)

 13   L2:     LOAD_FAST_BORROW         1 (total)
              RETURN_VALUE
```

How to read it: the left column is the source line; `L1`/`L2` are labels; the number after the
name is the instruction's argument. Trace line 12 with the **value stack**:

```
LOAD_FAST n        stack: [n]
LOAD_SMALL_INT 1   stack: [n, 1]
BINARY_OP (-)      stack: [n-1]        pops two, pushes the result
STORE_FAST n       stack: []           pops into local variable n
```

Notice that the *control flow* has the same shape as the TAC above: a label at the loop top, a
conditional jump out (`POP_JUMP_IF_FALSE`, like `jump_if_zero`), and a jump back. Only the way
values are passed differs. (`NOT_TAKEN`, `LOAD_SMALL_INT` and the `_BORROW`
variations are version details; older Pythons show `LOAD_FAST`, `LOAD_CONST` and `JUMP_ABSOLUTE`.)

Stack bytecode is compact and trivially easy to generate from an AST, which suits an interpreter.
Register-style TAC maps more naturally onto real CPUs, which have registers, so native compilers
like `rcc` prefer it.

### Where TAC goes next
In the back end (6.6 and Unit 8 onward), each TAC instruction becomes a few assembly
instructions. As a preview, `tmp.1 = 1 + tmp.0` becomes roughly "copy 1 into a register, add
`tmp.0` to it, store the register into `tmp.1`'s memory slot". Temporaries live in memory on the
stack at first (lesson 9.3); register allocation (Unit 14) later moves them into real registers.

## Build
1. **Expressions to TAC.** Write TAC (fresh temporaries `tmp.0`, `tmp.1`, ...) for:
   `return 2 * (3 + 4);` · `return -5 + 10 / 2;` · `return 1 - 2 - 3;` (watch associativity) ·
   `return ((1 + 2) * (3 + 4)) - 5;`. Then "run" each by hand, recording each temporary's value.
2. **Variables.** Write TAC for `int a = 3; int b = a * a; a = b - a; return a + b;` and evaluate it.
3. **Control flow.** Write TAC with labels and jumps for:
   - `if (a < b) { r = b; } else { r = a; }`
   - an `if` with no `else`
   - the whole `while`/`if` program from lesson 5.4. Then trace it with `n = 4` and write down the
     returned value.
4. **Short-circuit.** In C, `a && b` doesn't evaluate `b` if `a` is 0, and the result is 1 or 0.
   Write TAC for `r = (x > 0) && (y > 0);` using `jump_if_zero`, then for `||`.
5. **Explore `dis`.** Disassemble (`import dis; dis.dis(f)`) your own small functions: one with
   arithmetic, one with an `if`/`else`, one with a `while` loop, and one that calls another
   function. For each, trace the value stack for at least one line, and match labels and jumps to
   the source. Note your Python version.
6. **Compare.** For one of your `dis` functions, write the equivalent TAC by hand. In two or three
   sentences, compare stack-style and three-address style: which is shorter, which names more
   things, which looks more like what a CPU needs?
7. **Find the cache.** Revisit the `__pycache__` file from lesson 5.1. Explain in one sentence what
   it contains, using the word "bytecode".

## Common pitfalls
- Reusing a temporary for two different values; always take a fresh one.
- Emitting the parent's instruction before the children's, so it reads temporaries that don't
  exist yet.
- Getting the jump sense backwards: `jump_if_zero cond, else` jumps when the condition is
  *false*.
- Treating `dis` output as stable: instruction names change between Python versions; the ideas
  (stack, labels, jumps) don't.
