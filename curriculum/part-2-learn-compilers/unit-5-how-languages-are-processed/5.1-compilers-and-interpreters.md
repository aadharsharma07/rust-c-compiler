## Overview
A compiler is just a program that reads a program and writes another one. In this lesson you
learn the big picture: the *phases* every language implementation passes through, the difference
between a compiler, an interpreter and a bytecode virtual machine, and exactly what CPython does
when you type `python script.py`. You will also read your first (tiny) C program. Every later
lesson zooms in on one box of the diagram you draw here.

## The lesson

### What "running a program" really means
Your CPU understands only one language: **machine code**, a sequence of numbers, each encoding a
simple instruction such as "add these two registers" or "jump to address 4096". It has no idea
what `for x in items:` means. So something must bridge the gap between the text you write and the
numbers the CPU runs. There are two broad strategies.

- **Translate ahead of time.** A **compiler** reads the whole source program and produces an
  equivalent program in another language, usually machine code (or assembly, a human-readable
  spelling of machine code). You then run the *output*. The compiler is not present at run time.
  This is what `rustc` did for you in Part 1, and what `rcc` will do for C.
- **Execute directly.** An **interpreter** reads the program and *performs* it, step by step,
  without producing a standalone translated program. The interpreter must be present every time
  the program runs.

A useful mental picture: a compiler is a translator who turns a French book into an English book
you can read later; an interpreter is a translator standing next to you reading the French book
aloud in English, sentence by sentence, every time you want to hear it.

### The middle way: bytecode virtual machines
Real systems mix the two. Python, Java and C# **compile** source code into **bytecode**: a
compact, simple instruction set for an imaginary computer. Then a **virtual machine (VM)**, which
is an interpreter for that bytecode, executes it. Bytecode is far easier to interpret quickly
than raw source text, because all the hard work (understanding the syntax, resolving names) has
already been done once.

```
  Native compiler (C, Rust):    source --compile--> machine code ---------> CPU runs it
  Tree-walking interpreter:     source --parse----> tree --> interpreter walks the tree
  Bytecode VM (CPython, Java):  source --compile--> bytecode --> VM loop runs it
```

So "Python is interpreted" is half true: CPython has a compiler inside it. It just doesn't
target your CPU.

### The phases of a compiler
Every compiler, from CPython's to `clang`, is a **pipeline**: a chain of phases, each turning one
data structure into the next. Here is the shape you will build in Part 3:

```
 "int main(void) { return 2; }"        characters (a string)
            |  1. Lexer (lesson 5.2)
            v
 [int] [main] [(] [void] [)] [{] [return] [2] [;] [}]     tokens
            |  2. Parser (lesson 5.3)
            v
 Program(Function("main", Return(Constant(2))))           abstract syntax tree (AST)
            |  3. Semantic analysis (lesson 5.4): names resolved, types checked
            v
 the same tree, now known to be meaningful
            |  4. IR generation (lesson 5.5)
            v
 return 2                                                 intermediate representation
            |  5. Code generation (Unit 6, lesson 6.6)
            v
 movl $2, %eax                                            assembly
 ret
```

The first three phases form the **front end**: they understand the *source language* and reject
bad programs. The last phases form the **back end**: they understand the *target machine*. The IR
sits in the middle. Splitting things this way means each phase is small enough to understand,
test and debug on its own. In Rust, each phase will be a function from one type to another, for
example "a `&str` in, a `Vec<Token>` out".

### Case study: what CPython does with your file
Suppose `hello.py` contains:

```python
x = 3 + 4 * y
```

When you run `python hello.py`, CPython goes through these steps (you will look at each one with
real tools in later lessons):

1. **Read** the file as text and decode it (UTF-8).
2. **Tokenise** it (5.2): `NAME 'x'`, `EQUAL '='`, `NUMBER '3'`, `PLUS '+'`, `NUMBER '4'`,
   `STAR '*'`, `NAME 'y'`, `NEWLINE`.
3. **Parse** the tokens into an **AST** (5.3, 5.4): an assignment whose value is
   `3 + (4 * y)`. Notice that the parser already knows that `*` binds tighter than `+`.
4. **Compile** the AST to **bytecode** (5.5), roughly: "push 3, push 4, push y, multiply, add,
   store into x". It may also cache this in a `__pycache__/*.pyc` file so step 2–4 can be
   skipped next time. (You may have seen those folders and wondered what they were.)
5. **Execute** the bytecode in the VM, a big loop in C (in `Python/ceval.c`) that reads one
   bytecode instruction at a time and does what it says.

Only at step 5 does anything happen to `y`. If `y` is undefined, you get a `NameError` at *run
time*, after compilation succeeded. A C compiler would reject the same mistake at *compile time*,
because C requires every variable to be declared before use, so the compiler can check. This is
the deepest difference between the two worlds: **static** checks happen before the program runs;
**dynamic** checks happen while it runs.

### Case study: what a C compiler does
For C, the pipeline ends in machine code for a real CPU, and there is no VM. Run-time support is
tiny: a little startup code that calls your `main` function. Because of that:

- C programs start instantly and run fast: no interpretation overhead.
- The compiler must know the type and size of everything up front (an `int` is 4 bytes), so that
  it can choose real CPU instructions and lay out memory.
- Mistakes that the compiler can't catch become *undefined behaviour* rather than a friendly
  exception. You will learn what that means in Part 3.

### Your first C program
You have never written C, so let's read the smallest useful program, the one `rcc` will compile
first in Unit 8:

```c
int main(void) {
    return 2;
}
```

Piece by piece:
- `int` is the **return type**: this function gives back an integer. In Python you'd write
  `def main() -> int:`, but in C the type comes *first* and is *mandatory*.
- `main` is the function's name. Every C program starts running at `main`.
- `(void)` means "takes no parameters". (Empty `()` means something subtly different in older C,
  so we always write `void`.)
- `{ ... }` is the function **body**. C uses braces where Python uses indentation, and the
  indentation is only for humans.
- `return 2;` returns the value 2. Every **statement** ends with a semicolon `;`.

What happens to the 2? The startup code passes `main`'s return value to the operating system as
the program's **exit status**. In a shell, `echo $?` prints the exit status of the last command,
so after running this program you would see `2`. That is how the test suite in Part 3 checks
most of your compiled programs: by their exit status.

### Compiler, interpreter: why do we care which?
Interpreters are easier to write and great for quick feedback. Compilers produce faster programs
and catch errors earlier. The phases up to the AST are identical in both; they diverge after.
That's why Unit 7 starts with a tiny calculator *interpreter* (walk the tree and compute) before
Unit 8 switches to emitting assembly: the front end you build for the calculator carries over.

## Common pitfalls
- Thinking "interpreted vs. compiled" is a property of a *language*. It's a property of an
  *implementation*: there are C interpreters and Python compilers (PyPy, Cython).
- Believing CPython has no compiler. It does; it targets bytecode, not your CPU.
- Treating the phases as optional decoration. Every phase exists to keep the next one simple;
  skipping one makes the others much harder.
- Reading C braces as optional, like Python indentation is mandatory. In C it's the reverse:
  braces and semicolons are syntax, indentation is ignored.
