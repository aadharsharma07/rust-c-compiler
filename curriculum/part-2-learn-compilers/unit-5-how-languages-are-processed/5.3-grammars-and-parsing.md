# Lesson 5.3 — Grammars and Parsing
**Part:** 2 — Learn Compilers · **Unit:** 5 — How Languages Are Processed · **Type:** Learning · **Est. time:** 5–7 h · **Tests:** none
**Prerequisites:** lessons 5.1, 5.2

## Overview
The lexer gives you a flat list of tokens. The **parser** discovers the *structure* hidden in
that list: which tokens form an expression, which expressions form a statement, which statements
form a function. To do that, you first need a precise description of the language's structure,
called a **grammar**. This lesson teaches grammar notation (BNF), derivations, parse trees,
ambiguity, precedence and associativity, and finally **recursive descent**, the parsing technique
you will hand-code in Rust in Units 7 and 8. You will trace it by hand until it feels mechanical.

## The lesson

### Syntax is structure
In English, "dog the bites man" uses valid words in an invalid order. Programming languages are
the same: `return ; 2` is made of valid C tokens, but they are in the wrong order. The rules for
*which orders are allowed* are the language's **syntax**, and a grammar writes them down.

### BNF: a notation for grammars
A **grammar** is a set of **production rules**. Each rule says how one **nonterminal** (a named
piece of structure, written `<like_this>`) can be built from a sequence of **terminals** (tokens,
written in quotes or by kind) and other nonterminals. This notation is called **BNF**
(Backus–Naur Form). Here is a grammar for a tiny subset of C, enough for `return 2;`:

```
<program>   ::= <function>
<function>  ::= "int" <identifier> "(" "void" ")" "{" <statement> "}"
<statement> ::= "return" <exp> ";"
<exp>       ::= <int>
```

Read `::=` as "is made of". `<identifier>` and `<int>` are token kinds from the lexer
(`Identifier`, `Constant`). A `|` separates alternatives, and many grammars also borrow regex
operators, giving **EBNF** (extended BNF): `{ x }` means "zero or more `x`" and `[ x ]` means
"optional `x`". For example, a function body with any number of statements:

```
<function>  ::= "int" <identifier> "(" "void" ")" "{" { <statement> } "}"
```

### Derivations
A grammar *generates* programs. Start from `<program>` and repeatedly replace a nonterminal with
the right-hand side of one of its rules. When only terminals remain, you have a valid program.
That sequence of steps is a **derivation**. Replacing the leftmost nonterminal each time:

```
<program>
=> <function>
=> "int" <identifier> "(" "void" ")" "{" <statement> "}"
=> "int" main "(" "void" ")" "{" <statement> "}"
=> "int" main "(" "void" ")" "{" "return" <exp> ";" "}"
=> "int" main "(" "void" ")" "{" "return" <int> ";" "}"
=> "int" main "(" "void" ")" "{" "return" 2 ";" "}"
```

Parsing is the *reverse* problem: given the tokens, find a derivation (or prove there isn't one,
which is a **syntax error**).

### Parse trees
Draw a derivation as a tree: each nonterminal is a node, and its children are what it was
replaced with. This is the **parse tree** (or *concrete syntax tree*):

```
                         <program>
                             |
                         <function>
     ________________________|_______________________________
    |    |      |   |    |   |   |          |                |
  "int" main   "(" "void" ")" "{"     <statement>           "}"
                                   _______|________
                                  |       |        |
                              "return"  <exp>     ";"
                                          |
                                        <int>
                                          |
                                          2
```

Every token appears as a leaf, in order. In 5.4 you'll see that compilers usually keep a slimmer
version, the AST, which drops the punctuation.

### Expressions, ambiguity and precedence
Now let expressions be richer. A first attempt:

```
<exp> ::= <exp> "+" <exp> | <exp> "*" <exp> | <int>
```

This grammar is **ambiguous**: some inputs have *two different* parse trees. `1 + 2 * 3`:

```
     Tree A: 1 + (2 * 3) = 7           Tree B: (1 + 2) * 3 = 9
            <exp>                              <exp>
          /   |   \                          /   |   \
      <exp>  "+"  <exp>                  <exp>  "*"  <exp>
        |        /  |  \                /  |  \        |
        1    <exp> "*" <exp>        <exp> "+" <exp>    3
               |         |            |         |
               2         3            1         2
```

Since the tree decides the meaning, an ambiguous grammar means an ambiguous language. We want
Tree A, because `*` has higher **precedence** than `+` (it "binds tighter"). The classic fix is to
give each precedence level its own nonterminal, lowest precedence at the top:

```
<exp>    ::= <exp> "+" <term>   | <exp> "-" <term>   | <term>
<term>   ::= <term> "*" <factor> | <term> "/" <factor> | <factor>
<factor> ::= <int> | "(" <exp> ")" | "-" <factor>
```

Now a `+` can only appear at the `<exp>` level, so `2 * 3` must be grouped into a `<term>` before
`+` sees it. Parentheses reset to the top (`"(" <exp> ")"`), which is how `(1 + 2) * 3` gets the
other meaning. `"-" <factor>` is **unary minus**, as in `-5`.

**Associativity** decides how *equal*-precedence operators group. `10 - 4 - 3` should mean
`(10 - 4) - 3 = 3`, not `10 - (4 - 3) = 9`. Subtraction is **left-associative**. The rule
`<exp> ::= <exp> "-" <term>` puts the recursion on the *left*, which builds exactly that left
grouping. (Assignment, `a = b = 0`, is right-associative; you'll handle it in Unit 10.)

### Recursive descent
**Recursive descent** is the most direct way to turn a grammar into a parser: write **one
function per nonterminal**. Each function looks at the next token, decides which rule applies,
and calls the functions for the nonterminals on the right-hand side, consuming terminals as it
goes. The call stack of your functions mirrors the parse tree.

Two helpers do most of the work: `peek()` looks at the next token without consuming it, and
`expect(kind)` consumes the next token, raising a syntax error if it is not `kind`. In Python-style
pseudocode, for the small grammar above:

```python
def parse_function():
    expect("int")
    name = expect_identifier()
    expect("("); expect("void"); expect(")"); expect("{")
    body = parse_statement()
    expect("}")
    return Function(name, body)

def parse_statement():
    expect("return")
    value = parse_exp()
    expect(";")
    return Return(value)
```

Each function *returns a tree node* for what it parsed. After `parse_program` returns, the parser
must also check that no tokens are left over: `int main(void) { return 2; } }` has an extra `}`.

**The left-recursion trap.** Translate `<exp> ::= <exp> "+" <term>` literally and `parse_exp`'s
first action is to call `parse_exp`, which calls `parse_exp`... forever, without consuming a
token. Recursive descent cannot handle **left recursion** directly. The fix is to rewrite the
rule with repetition, which describes the same strings:

```
<exp>    ::= <term> { ("+" | "-") <term> }
<term>   ::= <factor> { ("*" | "/") <factor> }
<factor> ::= <int> | "(" <exp> ")" | "-" <factor>
```

Now `parse_exp` parses one `<term>`, then *loops*: while the next token is `+` or `-`, consume it,
parse another `<term>`, and combine the tree so far (on the left) with the new term (on the
right). Building the tree in the loop this way restores left associativity.

### Tracing recursive descent by hand
Trace `1 + 2 * 3` with the rewritten grammar. Indentation shows the call stack:

```
parse_exp
  parse_term
    parse_factor          sees 1   -> consume, return Int(1)
    peek is "+", not * or /        -> return Int(1)
  left = Int(1); peek is "+"        -> consume "+"
  parse_term
    parse_factor          sees 2   -> consume, return Int(2)
    left = Int(2); peek is "*"     -> consume "*"
    parse_factor          sees 3   -> consume, return Int(3)
    left = Mul(Int(2), Int(3)); peek is end -> return it
  left = Add(Int(1), Mul(Int(2), Int(3))); peek is end -> return it
```

The result is Tree A. Precedence came "for free" from the grammar's layering: `parse_term`
grabbed `2 * 3` before `parse_exp` could see it.

Adding a new precedence level means adding a new function, which gets tedious for C's 15 or so
levels. In lesson 9.4 you'll replace the expression functions with **precedence climbing**, a
compact variant of the same idea driven by a table of operator precedences.

### How Python does it
CPython's parser is generated from a grammar file (`Grammar/python.gram`) written in a PEG
notation. PEG parsers are close cousins of recursive descent: ordered alternatives, tried top to
bottom. You can see the result with `python3 -m ast` (lesson 5.4). Python's grammar handles
precedence exactly as above, with one rule per level (`sum`, `term`, `factor`, `power`, ...).

   statements, and add a statement form `<identifier> "=" <exp> ";"`. Write it in EBNF.
2. **Derive.** Give a leftmost derivation of `int main(void) { return 2 + 3; }` using the
   grammar with `<exp>`, `<term>`, `<factor>` (the left-recursive version is fine for derivations).
3. **Ambiguity.** Using the ambiguous grammar, draw both parse trees for `8 - 4 - 2` and compute
   each value. Which one is correct C, and which grammar rule in the fixed version guarantees it?
4. **Draw parse trees** (fixed grammar) for: `1 * 2 + 3`, `(1 + 2) * 3`, `-4 * 5`, `2 - -3`.
5. **Trace recursive descent.** Write call-stack traces, in the style above, for `2 * (3 + 4)` and
   `10 - 4 - 3`. For the second, show how the loop builds `Sub(Sub(10, 4), 3)`.
6. **Find the syntax errors.** For each, say which function would detect the problem and what
   token it expected: `int main(void) { return 2 }` · `int main(void) { return ; }` ·
   `int main(void) return 2;` · `1 + * 2` · `(1 + 2`.
7. **Read Python's grammar.** Open https://docs.python.org/3/reference/grammar.html and find the
   rules for `sum` and `term`. Identify which operators each level handles and whether the rules
   are left-recursive.
8. **Add a level on paper.** Python has `**` (power), which binds tighter than unary minus on its
   left and is right-associative (`2 ** 3 ** 2` is `2 ** 9`). Add a `<power>` level to the
   grammar, and trace `2 ** 3 ** 2`.

## Common pitfalls
- Putting the *highest*-precedence operators at the top of the grammar. The top nonterminal holds
  the *lowest* precedence (the operator applied last).
- Building the tree right-to-left in the repetition loop, which silently makes `-` and `/`
  right-associative: `10 - 4 - 3` would give 9.
- Forgetting to check for leftover tokens at the end of the input.
- Mixing up `peek` and consuming: if a function consumes a token it then doesn't use, the next
  function gets a confusing error far from the real problem.
