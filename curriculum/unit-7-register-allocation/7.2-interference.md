# Lesson 7.2 — Interference
**Unit:** 7 — Register Allocation · **Type:** Builds interference-graph builder · **Est. time:** 6–8 h · **Tests:** ch. 20
**Prerequisites:** lessons 6.3, 6.4, 6.6, 7.1

## Learning goals
- Run liveness analysis over *assembly* instructions using your Unit 6 CFG and dataflow framework.
- Say exactly which registers and pseudos each assembly instruction reads and writes, including implicit ones (`idiv`, `cdq`, `call`, `ret`).
- Build an interference graph containing both pseudos and hard registers, with the `mov` exception.
- Decide which pseudos are allocation candidates at all.

## Key ideas
**Two values interfere** if one is written at a point where the other is live (and they might hold different values). Interfering values can't share a register. The interference graph has a node per candidate and an edge per interfering pair.

**Nodes.**
- Every *allocatable hard register* (the 12 from 7.1), pre-coloured. Hard registers all interfere with each other, so they will get distinct colours.
- Every pseudo that can live in a register: not static, not aliased (never the source of a `lea`/`GetAddress`), and a scalar (not an array or struct). Other pseudos keep going to memory exactly as before.
- With `double`: a separate graph for `xmm` registers and `double` pseudos. Integer and float nodes never interfere with each other.

**Reads and writes per instruction** (register/pseudo operands only; memory operands aren't nodes, but registers *inside* an address, like the base of `8(%rax)`, are reads):

| Instruction | Reads | Writes |
|---|---|---|
| `mov src, dst` | src | dst |
| `add/sub/imul src, dst`, `and/or/xor` | src, dst | dst |
| `neg/not dst` | dst | dst |
| `cmp a, b` | a, b | — |
| `setCC dst` | — (see pitfalls) | dst |
| `cdq` | ax | dx |
| `idiv op` (and `div`) | op, ax, dx | ax, dx |
| shifts by `%cl` | operand, cx | operand |
| `push op` | op | — |
| `call f` | the argument registers actually used by this call | every caller-saved register |
| `ret` | — (handled by the `Exit` boundary) | — |
| jumps, labels | — | — |

At `Exit`, `ax` is live if the function returns an integer (`xmm0` for `double`; more registers for struct returns).

**Liveness** is the same backward/union analysis as 6.6, over a CFG of assembly blocks (`jmp`, `jCC`, `ret` end blocks; labels start them). Transfer: `live_before = (live_after − writes) ∪ reads`.

**Interference rule.** For each instruction, for each register/pseudo `d` it writes, for each `l` live *after* it: add edge `d — l`, unless `l == d`, or the instruction is `mov src, d` and `l == src`. The `mov` exception is the whole point of coalescing later: after `mov a, c`, `a` and `c` hold the same value, so sharing a register is harmless.

**Call clobbers.** Because `call` writes every caller-saved register, any pseudo live across a call interferes with all of them, leaving only callee-saved registers (or a spill).

**Worked example.**

```
                        live after
1: movl $1, a           {a}
2: movl $2, b           {a, b}
3: movl a, c            {b, c}
4: addl b, c            {c}
5: movl c, %eax         {ax}
6: ret                  (Exit: {ax})
```

Edges: instruction 2 writes `b` while `a` is live → `a — b`. Instruction 3 writes `c` while `b` is live → `b — c` (`a` is the mov source, and isn't live anyway). Instructions 1, 4, 5 add nothing. Adjacency list (pseudos only; every hard register also neighbours every other):

```
a: b        b: a, c        c: b        ax: (all other hard registers)
```

With a call:

```
movl $5, x        ; x live across the call
call f            ; writes ax, cx, dx, di, si, r8, r9 while x is live
movl %eax, y
addl x, y
```

`x` gains edges to all seven caller-saved registers.

## Questions the tutor should ask you
1. Why does `mov a, c` not make `a` and `c` interfere, while `add a, c` would?
2. Why must hard registers be nodes in the graph instead of being handled separately?
3. Which pseudos are *not* nodes, and why can't they live in registers?
4. What does `idiv` read and write, and what goes wrong if you forget `dx`?
5. Why does a call only *read* the argument registers it actually uses?
6. Which register is live at `Exit` for a `void` function?

## What you build
- **Assembly CFG + liveness:** reuse your Unit 6 `Cfg` and framework, instantiated for assembly instructions. Boundary at `Exit` = the return-value register(s) for this function's return type.
- **Reads/writes helper:** a function from one assembly instruction to (registers/pseudos read, registers/pseudos written), covering every instruction your back end emits, including implicit operands. Test it instruction by instruction.
- **Interference graph:** nodes for allocatable hard registers and candidate pseudos; for each node, a set of neighbour node IDs, a spill cost slot (filled in 7.3), and a colour slot. Store nodes in a `Vec` or map keyed by a node ID that is either a hard register or a pseudo name; edges are symmetric, so always add both directions.
- **Candidate filter:** exclude statics, aliased variables and aggregates; use your backend symbol table.
- **Debug output:** a flag or test helper that prints the graph as adjacency lists (or Graphviz `dot`).
- Nothing changes in the emitted code yet; tests must still pass with no behaviour change.

## Rust focus
- A node ID enum that is either a hard register or a pseudo: `enum Node { Hard(Reg), Pseudo(Symbol) }`, deriving `Hash`/`Eq`/`Ord` ([Rust Book ch. 6](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)).
- Generic code reuse: instantiate the `Cfg<I>` and dataflow framework from Unit 6 with your assembly instruction type. If it doesn't fit, refactor the framework (generics with trait bounds, [ch. 10](https://doc.rust-lang.org/book/ch10-01-syntax.html)) rather than copying it.
- Adjacency as `HashMap<Node, BTreeSet<Node>>` or index-based `Vec<BTreeSet<usize>>`; [`HashMap::entry`](https://doc.rust-lang.org/std/collections/hash_map/struct.HashMap.html#method.entry) makes "insert neighbour, creating the set if needed" a one-liner.
- Interning pseudo names (mapping `String` to a small integer) is an optional speed-up; don't start there.

## Common pitfalls
- Missing implicit operands (`cdq`, `idiv`, shifts, `call`), producing allocations that silently clobber `ax`/`dx`/`cx`.
- `setCC` writes only the low byte of its operand; your codegen zeroes the register first with `mov $0`. Treating `setCC` as also *reading* its operand is the conservative, always-correct choice.
- Adding edges in one direction only.
- Applying the `mov` exception to other instructions, or applying it when the source is memory or a constant (it doesn't matter then, but be clear about why).
- Treating static or address-taken variables as candidates.
