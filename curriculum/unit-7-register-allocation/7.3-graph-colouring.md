# Lesson 7.3 — Graph colouring
**Unit:** 7 — Register Allocation · **Type:** Builds register allocator · **Est. time:** 12–18 h · **Tests:** ch. 20
**Prerequisites:** lessons 7.1–7.2

## Learning goals
- Colour an interference graph with *k* colours using Chaitin–Briggs simplify/select with optimistic spilling.
- Choose spill candidates with a cost/degree heuristic.
- Map colours to hardware registers, rewrite the assembly, and leave uncoloured pseudos to the existing stack-slot pass.
- Save and restore the callee-saved registers a function uses, keeping the stack 16-byte aligned.

## Key ideas
**Colouring = allocation.** Give each node one of *k* colours (k = 12 for integer registers, 14 for `xmm`) so that neighbours differ. Optimal colouring is NP-hard, so we use a heuristic that is fast and good in practice.

**Key fact.** A node with fewer than *k* neighbours can *always* be coloured, whatever colours its neighbours get. So remove it, colour the rest, and put it back last.

**Simplify** (build a stack):
1. While nodes remain: if some node has degree < k (counting only neighbours still in the graph), remove it and push it on a stack.
2. Otherwise every node has degree ≥ k. Pick a **spill candidate**: the node with the lowest `spill cost / degree`. Remove it and push it anyway (*optimistic*: it might still get a colour).

**Select** (pop the stack): for each node, look at the colours of its already-coloured neighbours and pick an unused colour. If none is free, the node becomes an **actual spill**: it stays a pseudo and gets a stack slot.

**Spill cost.** Count how many times a pseudo appears in the function's instructions (optionally weight occurrences inside loops more). Hard registers get infinite cost: they are never spill candidates. High degree makes a node a better candidate because removing it relieves more neighbours.

**Hard registers in the graph.** Hard-register nodes are coloured like any other node; because all 12 interfere, they receive 12 distinct colours. Afterwards, each colour *means* the register whose node got it. A pseudo that interferes with `%rdi` therefore can't get `%rdi`'s colour.

**Worked example 1 (k = 3, a spill).** Adjacency:

```
a: b, c, d      b: a, c, d      c: a, b, d      d: a, b, c, e      e: d
costs: a=6, b=5, c=4, d=2, e=3
```

Simplify: `e` has degree 1 → push `e`. Now a, b, c, d all have degree 3 = k. Ratios: a 6/3, b 5/3, c 4/3, d 2/3 → push `d` as spill candidate. Now a, b, c have degree 2 → push `a`, `b`, `c`. Stack (top first): c, b, a, d, e.
Select: c → 0, b → 1, a → 2, d: neighbours use 0, 1, 2 → **spill**. e: its only neighbour `d` has no colour → 0.

**Worked example 2 (k = 2, optimism pays).** A 4-cycle `a—b—c—d—a`, all costs 1. Every node has degree 2 = k: push `a` as a candidate. Then b, c, d form a path: push `b`, `c`, `d`. Select: d → 0, c → 1, b → 0, a: neighbours b and d both 0 → a gets 1. No spill: a pessimistic allocator would have spilled `a`.

**Choosing among free colours.** Using a callee-saved register costs a push/pop in the prologue/epilogue; using a caller-saved one is free (call clobbers are already edges). So when several colours are free for a pseudo, prefer one that maps to a caller-saved register. (Hard registers' colours are fixed by the graph, so this only needs care in how you order colours.)

**Rewriting.** Replace each coloured pseudo with its register at the operand's size (`%eax` vs. `%rax`, `%r8d` vs. `%r8`). Delete any `mov` whose source and destination are now the same register. Uncoloured pseudos flow into your existing pseudo-replacement and fix-up passes unchanged; that is why `%r10`/`%r11` stay reserved. (Classic Chaitin rebuilds the graph after inserting spill code; your fix-up pass makes that unnecessary.)

**Callee-saved registers.** Record which of `bx, r12–r15` were assigned to any pseudo. Push them in the prologue *after* `sub $N, %rsp` (so stack slots below `%rbp` don't move), and pop them in reverse order before `movq %rbp, %rsp; popq %rbp; ret` at every return. Stack alignment: choose `N` so that `N + 8 × (number pushed)` is a multiple of 16.

## Questions the tutor should ask you
1. Why can a node of degree < k always be coloured, no matter what happens to the others?
2. Why is removing a spill candidate and pushing it, instead of spilling immediately, safe?
3. Why divide spill cost by degree?
4. In worked example 2, what would a pessimistic allocator have done, and what did optimism save?
5. Why do the callee-saved pushes go after `sub $N, %rsp` and not before it?
6. With 3 callee-saved registers pushed and 20 bytes of stack slots, what `N` keeps calls aligned?

## What you build
- **Spill costs** for every node (hard registers infinite).
- **Colouring:** simplify with optimistic spill selection, then select, as above. Output: a map from pseudo to hard register for coloured pseudos; uncoloured pseudos are absent.
- **Colour→register mapping** via the hard-register nodes' colours.
- **Rewrite pass:** replaces allocated pseudos, removes self-moves, leaves the rest for pseudo replacement.
- **Prologue/epilogue changes:** the set of used callee-saved registers travels with each function (e.g. a field on the assembly function, or a backend symbol-table entry); emission pushes and pops them; stack size rounding accounts for them.
- **Pipeline:** per function, after assembly generation: liveness → interference → spill costs → colour → rewrite → pseudo replacement → fix-up. Separate runs for integer and `xmm` classes if you have `double`.
- **Edge cases:** functions with no pseudos; more than 12 simultaneously live values (forces real spills); values live across calls (must land in callee-saved registers or spill); a function that uses no callee-saved registers (prologue unchanged); multiple `ret`s.

## Rust focus
- A stack is just a `Vec` with `push`/`pop`; "degree among remaining nodes" can be tracked with a removed-flag per node or a counter you decrement ([`Vec`](https://doc.rust-lang.org/std/vec/struct.Vec.html)).
- `min_by` with floating-point ratios: `f64` isn't `Ord`, so use [`f64::total_cmp`](https://doc.rust-lang.org/std/primitive.f64.html#method.total_cmp) or compare by cross-multiplying integers.

  ```rust
  let best = xs.iter().min_by(|a, b| a.total_cmp(b));
  ```
- Infinite cost: `f64::INFINITY` or an `Option`/enum; pick whichever makes comparisons obviously correct.
- Keep allocation results as plain data (`HashMap<Symbol, Reg>`, `BTreeSet<Reg>`) passed between passes rather than mutating global state.

## Common pitfalls
- Counting degree against the original graph instead of remaining neighbours during simplify.
- Letting a hard register become a spill candidate.
- Forgetting the operand-size register names when rewriting (`%eax` vs. `%rax`), or forgetting byte names for `setCC` (`%al`, `%r8b`).
- Pushing callee-saved registers but popping them in the wrong order, or only before one of several `ret`s.
- Breaking 16-byte alignment at calls once registers are pushed.
