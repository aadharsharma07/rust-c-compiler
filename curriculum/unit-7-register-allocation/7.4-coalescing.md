# Lesson 7.4 — Coalescing
**Unit:** 7 — Register Allocation · **Type:** Builds coalescing · **Est. time:** 8–12 h · **Tests:** ch. 20
**Prerequisites:** lessons 7.1–7.3

## Learning goals
- Explain register coalescing: merging the source and destination of a `mov` so they share a register and the `mov` disappears.
- Explain why aggressive coalescing can make a colourable graph uncolourable.
- Apply the Briggs and George conservative tests correctly, and know when each fits.
- Iterate build → coalesce → rewrite until nothing coalesces, then colour.

## Key ideas
**Why.** Your TACKY and codegen are full of `mov`s: copying parameters out of `%rdi`, moving results into `%eax`, temporaries copied into variables. If `mov a, c` ends up with `a` and `c` in the same register, the `mov` is a no-op and is deleted. Coalescing *forces* that outcome by merging the two nodes before colouring.

**When it is legal.** Only if the two nodes don't interfere (thanks to the `mov` exception in 7.2, the move itself doesn't create an edge). Never merge two hard registers. If one side is a hard register, the merged node *is* that hard register.

**When it is wise.** The merged node has the union of both neighbour sets, so its degree can be large. Merge enough nodes and a graph that was k-colourable no longer is; you have traded a cheap `mov` for an expensive spill. *Conservative* coalescing only merges when a test proves colourability is not harmed:

- **Briggs test** (any pair `a`, `b`): count the neighbours of the merged node that have *significant degree* (≥ k), using each neighbour's degree *after* the merge (a node adjacent to both `a` and `b` loses one edge). If that count is < k, merge. Reason: during simplify, all the insignificant neighbours will be removed, leaving the merged node with < k neighbours, so it is still simplifiable.
- **George test** (pseudo `a` into hard register `r`): merge if every neighbour `t` of `a` either already interferes with `r` or has degree < k. Reason: merging adds no new constraints `r` couldn't already handle. This suits hard registers, whose huge neighbour lists make Briggs fail almost always; George only examines the pseudo's neighbours.

A common policy: for pseudo–pseudo pairs use Briggs; for pseudo–hard-register pairs use George (optionally accept if either test passes).

**Worked example** (k = 12; the graph from 7.2):

```
1: movl $1, a
2: movl $2, b
3: movl a, c
4: addl b, c
5: movl c, %eax
6: ret
```

Graph: `a — b`, `b — c`, hard registers all connected to each other.
- `mov a, c` (3): `a` and `c` don't interfere. Merged node `ac` has neighbour `b` (degree 2, insignificant). Significant neighbours: 0 < 12 → merge. Graph: `ac — b`.
- `mov c, %eax` (5): `ac` and `ax` don't interfere. George: `ac`'s only neighbour `b` has degree 1 < 12 → merge `ac` into `ax`.
- Rewrite and delete self-moves:

```
movl $1, %eax
movl $2, b
addl b, %eax
ret
```

Rebuild liveness and the graph; no more `mov`s between non-interfering nodes, so colour: `b` gets some free register, e.g. `%ecx`.

**Iteration.** Merging changes liveness and degrees, which can enable or block other merges. Loop: build liveness + interference graph → walk every `mov` whose source and destination are both nodes, testing and merging (update the graph's adjacency as you go, and track which node each name now maps to) → if anything merged, rewrite the instructions (rename every operand to its representative, delete `mov x, x`) and repeat → otherwise colour (7.3).

**Tracking merges.** A *union-find* (disjoint-set) structure maps each name to its representative. Find with path compression; when a hard register is involved, it must be the representative.

## Questions the tutor should ask you
1. Why can't you coalesce two nodes that interfere?
2. Give a small graph where aggressive coalescing turns a 2-colourable graph into one that needs 3 colours.
3. In the Briggs test, why do neighbours with degree < k not count?
4. Why does the George test work well for hard registers when Briggs mostly fails?
5. After merging, which names must be renamed in the instruction list, and which `mov`s disappear?
6. Why rebuild liveness instead of trusting the incrementally updated graph forever?

## What you build
- **Coalescing pass:** input the interference graph and the function's instructions; output a union-find (or rename map) of merged nodes. Considers each `mov` with node operands on both sides; skips pairs that interfere, pairs of two hard registers, and pairs failing the conservative test. Updates the graph in place after each merge (union of neighbour sets, neighbours repointed to the representative, degrees adjusted).
- **Rename pass:** rewrites every operand to its representative and deletes `mov`s whose source equals destination.
- **Driver loop:** build → coalesce → if changed, rename and rebuild; else colour → rewrite → pseudo replacement → fix-up, as in 7.3.
- **Correctness conditions:** merged nodes never interfere; hard registers keep their identity; the program's behaviour is unchanged; the result is at least as colourable as before (no new spills compared with `--no-coalescing` in normal cases).
- **Edge cases:** a `mov` whose source is a constant or memory (not a candidate); `mov a, a` already present; chains of moves (`a → b → c → %eax`); parameters copied out of argument registers; merged nodes that are later spilled anyway.

## Rust focus
- Union-find with path compression stored in a `Vec<usize>` or `HashMap<Node, Node>`; `find` is a short loop or recursion ([Rust Book ch. 8](https://doc.rust-lang.org/book/ch08-00-common-collections.html)).
- Mutating a graph in place while you hold references into it is a borrow-checker fight. Copy the small sets you need first (neighbour IDs), then mutate. [`std::mem::take`](https://doc.rust-lang.org/std/mem/fn.take.html) moves a set out of a struct, leaving an empty one:

  ```rust
  let old_neighbours = std::mem::take(&mut graph_entry.neighbours);
  ```
  (Illustrates `mem::take` only; the field name is up to you.)
- Keep tests for Briggs and George as separate small pure functions so you can unit-test them on hand-built graphs.

## Common pitfalls
- Forgetting the "neighbour of both" adjustment in Briggs, so the test is over-pessimistic or (worse, if you count wrongly the other way) unsafe.
- Making a pseudo the representative of a merge with a hard register, so the register's identity is lost.
- Leaving stale edges that still point at a merged-away node.
- Coalescing across register classes (integer with `xmm`).
- Infinite loops: re-merging the same pair each iteration because renaming wasn't applied before rebuilding.
