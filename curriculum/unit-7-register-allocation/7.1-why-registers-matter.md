# Lesson 7.1 — Why registers matter
**Unit:** 7 — Register Allocation · **Type:** Learning only · **Est. time:** 2–3 h · **Tests:** none
**Prerequisites:** lessons 6.1–6.6; 4.3 (System V calling convention)

## Learning goals
- Explain why keeping values in registers instead of stack slots makes code smaller and faster.
- Define spill, register pressure, live range, and caller- vs. callee-saved register.
- Count instructions in your own `rcc` output and compare with `clang -O1` for the same function.
- Name the registers `rcc` can allocate and the ones it must reserve.

## Key ideas
**Where `rcc` is today.** Every pseudoregister gets a stack slot. Because x86-64 instructions can't have two memory operands, the fix-up pass inserts scratch-register moves. For `int f(int a, int b) { int c = a + b; return c * 2; }` you emit something like:

```
movl %edi, -4(%rbp)        # copy parameters to their slots
movl %esi, -8(%rbp)
movl -4(%rbp), %r10d       # tmp = a   (fix-up: mem -> mem)
movl %r10d, -12(%rbp)
movl -8(%rbp), %r10d       # tmp += b
addl %r10d, -12(%rbp)
...
```

Every value takes a trip to memory and back. With registers the body shrinks to about three instructions before `ret`: something like `movl %edi, %eax; addl %esi, %eax; imull $2, %eax` from a simple allocator (clang -O1 does it in two, using `lea`; check on Godbolt). Memory accesses hit the cache, but they still cost more than register operands, and they add instructions, code size and dependency chains.

**Registers available.** x86-64 has 16 general-purpose registers, but `rcc` can't use all of them:
- `%rsp` and `%rbp` hold the stack frame.
- `%r10` and `%r11` are the fix-up pass's scratch registers (keep them reserved so fix-up still works after allocation).
- That leaves **12**: `ax, bx, cx, dx, di, si, r8, r9, r12, r13, r14, r15`.
- If you did `double`: `xmm0`–`xmm13` for floating point (keep `xmm14`/`xmm15` as scratch), allocated separately.

**Caller-saved vs. callee-saved (System V).**
- *Caller-saved* (`ax, cx, dx, di, si, r8, r9`, plus `r10, r11`, and all `xmm`): a call may overwrite them. A value that must survive a call can't live there.
- *Callee-saved* (`bx, r12–r15`, plus `rbp`): a function that uses one must save it on entry and restore it before returning. Using one costs a `push`/`pop` pair per function, but it survives calls.

**Live ranges and pressure.** A value is *live* from where it's written to its last read (6.6). Two values that are live at the same time can't share a register. **Register pressure** at a point is the number of live values there. If pressure exceeds 12 somewhere, at least one value must live in memory: it is **spilled**. A good allocator spills the value that costs least to keep in memory (used rarely, not inside a loop).

**What the allocator is, in one line.** Assign each pseudo a register such that no two simultaneously live pseudos share one; spill the ones you can't fit. That is graph colouring (7.3) on an interference graph (7.2).

## Questions the tutor should ask you
1. Why does your current compiler need `%r10` at all? What would happen if the allocator gave a pseudo `%r10`?
2. A value is live across a `call printf`. Which registers can hold it, and what does each choice cost?
3. What is the register pressure at `return a + b + c` if `a`, `b`, `c` are all live just before it?
4. Why is spilling a variable used once better than spilling a loop counter?
5. Static variables and address-taken locals can't go in registers. Why?
6. Why is minimising instruction count not the same as minimising run time?

## What you build
Nothing in code. Produce notes:
- Pick three functions from the chapter 19/20 tests (one with a loop, one with a call, one with many temporaries). For each, count instructions in `rcc --optimize -S` output and in `clang -O0` and `clang -O1` (Godbolt or local). Record the counts in a table.
- For the function with a call, mark which values are live across the call.
- For the function with many temporaries, find the point of maximum register pressure by hand.
- Write down the list of allocatable registers you will use, split into caller- and callee-saved, and the ones you reserve and why.

## Rust focus
- Plan a `Reg` (hard register) enum that already exists in your assembly AST: make sure it derives `Copy, Clone, PartialEq, Eq, Hash, PartialOrd, Ord, Debug` so it can be used as a graph node and set member ([derivable traits, Rust Book appendix C](https://doc.rust-lang.org/book/appendix-03-derivable-traits.html)).
- Think about a constant array listing allocatable registers in preference order: `const`/`static` arrays ([Rust reference: constant items](https://doc.rust-lang.org/reference/items/constant-items.html)).

## Common pitfalls
- Planning to allocate `%r10`/`%r11` and then discovering fix-up clobbers them.
- Forgetting that `%rax`, `%rdx`, `%rcx` have fixed jobs in some instructions (`idiv`, `cdq`, shifts, return value). The allocator must know.
- Assuming callee-saved registers are "free": each one used adds save/restore code.
- Counting instructions without checking the programs still produce the same output.
