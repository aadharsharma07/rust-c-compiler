# Lesson 4.6 — Modules, Testing and Tooling
**Part:** 1 — Learn Rust · **Unit:** 4 — Abstraction and Organisation · **Type:** Learning · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 1.1–3.5, 4.1–4.5

## Overview
Real programs don't live in one `main.rs`. This lesson shows how Rust organises code into modules
and crates, how privacy works, how to write unit tests, integration tests and doc tests, and how to
use the tools every Rust project runs constantly: `rustfmt`, `clippy` and `cargo doc`. Your compiler
will be a crate with a dozen modules (lexer, parser, code generator, ...) and hundreds of tests, so
the habits from this lesson are the ones you'll use every day in Part 3.

## The lesson

### Packages, crates and modules
Three words, from biggest to smallest:

| Rust | What it is | Nearest Python idea |
|---|---|---|
| **package** | a folder with a `Cargo.toml`; what `cargo new` makes | a project with `pyproject.toml` |
| **crate** | one unit the compiler builds: a *binary* (has `main`) or a *library* | an installable distribution |
| **module** | a named namespace inside a crate | a `.py` module or a package folder |

A package can contain one library crate (rooted at `src/lib.rs`) and any number of binary crates
(the main one rooted at `src/main.rs`). Each crate is a **tree of modules**, and the root file
(`main.rs` or `lib.rs`) is the top of the tree, called `crate`.

### Declaring modules: the big difference from Python
In Python, every `.py` file is a module automatically, and `import` finds it on disk. In Rust,
**a file is only part of your program if a parent module declares it** with `mod`:

```
src/
├── main.rs        contains:  mod inventory;      (look for inventory.rs or inventory/mod.rs)
├── inventory.rs   contains:  pub mod pricing;    (look for inventory/pricing.rs)
└── inventory/
    └── pricing.rs
```

```rust
// src/inventory.rs
pub mod pricing;                 // a child module, in src/inventory/pricing.rs

pub struct Item { pub name: String, price_pence: u32 }
```

`mod inventory;` with a semicolon means "the module's body is in another file". A forgotten `mod`
line is the classic beginner mistake: the file just sits there, never compiled, and nothing can
`use` it. You can also write a module inline with braces, `mod helpers { ... }`, which is how test
modules are usually written. (An older layout puts a module's file at `inventory/mod.rs` instead of
`inventory.rs`; both work, but don't mix them for one module.)

### Paths and `use`
Items are named by **paths**, with `::` between parts:
- `crate::inventory::Item` starts at the crate root (like an absolute import),
- `super::something` starts at the parent module (like `from .. import`),
- `self::something` starts at the current module.

`use` brings a path into scope so you can write the short name, like Python's `from x import y`:

```rust
use crate::inventory::{Item, pricing};
use std::collections::HashMap;
use std::fmt::Result as FmtResult;    // rename on import, like `import x as y`
```

`pub use` **re-exports** an item: `pub use pricing::discount;` inside `inventory` lets other code
write `inventory::discount`, hiding your internal layout.

### Privacy: private by default
Python has no real privacy. A leading underscore is a polite "please don't". Rust enforces it, and
everything starts **private**: visible only inside its own module and that module's children. Mark
items public with `pub`:

- `pub fn`, `pub struct`, `pub enum`, `pub mod`: visible to the parent and beyond.
- `pub(crate)`: visible anywhere in this crate, but not to other crates.
- **Struct fields are private separately**, even in a `pub struct`. Above, `name` is public but
  `price_pence` is not, so code outside `inventory` can't create an `Item` with a struct literal
  or change its price. It must go through functions you provide.
- **Enum variants** are public whenever the enum is.

Private fields are how you protect **invariants** (rules that must always hold). If a price must
never be zero, make the field private and provide `pub fn new(name: String, price: u32) -> Option<Item>`
that checks it. Now every `Item` anywhere in the program is valid.

### The library + binary pattern
A common and recommended layout: put almost all the logic in `src/lib.rs` (and its modules), and keep
`src/main.rs` tiny: read arguments, call the library, print errors, exit. The binary uses the library
like an external crate, by the **package name** (hyphens become underscores):

```rust
// src/main.rs of a package named "stock-check"
fn main() {
    if let Err(e) = stock_check::run() {
        eprintln!("error: {e}");          // eprintln! prints to stderr
        std::process::exit(1);
    }
}
```

Why? Library code can be tested directly (integration tests can only reach library crates), and
`main` stays too small to need tests.

### External crates
Other people's libraries are crates published on crates.io. `cargo add some_crate` adds a line under
`[dependencies]` in `Cargo.toml`; Cargo downloads and builds it, and records exact versions in
`Cargo.lock`. Every published crate's documentation is on docs.rs. You did this with `rand` in 1.5.

### Unit tests
Rust's test framework is built in, so there's nothing like pytest to install. A test is a function marked
`#[test]`. Unit tests live next to the code, in a child module that's only compiled when testing:

```rust
pub fn celsius_to_f(c: f64) -> f64 { c * 9.0 / 5.0 + 32.0 }

#[cfg(test)]                 // compile this module only for `cargo test`
mod tests {
    use super::*;            // bring the parent module's items (even private ones) into scope

    #[test]
    fn boiling_point() {
        assert_eq!(celsius_to_f(100.0), 212.0);
    }

    #[test]
    #[should_panic(expected = "index out of bounds")]
    fn out_of_range_panics() {
        let v: Vec<i32> = Vec::new();
        let _first = v[0];
    }

    #[test]
    fn parses() -> Result<(), std::num::ParseIntError> {
        let n: i32 = "42".parse()?;     // tests may return Result and use `?`
        assert!(n > 0, "expected positive, got {n}");
        Ok(())
    }
}
```

- `assert!(cond)`, `assert_eq!(a, b)` and `assert_ne!(a, b)` all accept an optional message with
  format arguments. `assert_eq!` needs `PartialEq` and `Debug` on the values, so it can compare them
  and print both on failure: one more reason to derive them.
- Because `tests` is a child module, it can test **private** functions. That's normal in Rust.
- `cargo test` runs everything; `cargo test boiling` runs tests whose names contain "boiling";
  `cargo test -- --nocapture` shows `println!` output, which is hidden for passing tests by default.

### Integration tests
Files in a top-level `tests/` folder (next to `src/`) are **integration tests**. Each file is
compiled as a separate crate that uses your library from the outside, exactly like a user would,
so it sees only the `pub` API:

```
stock-check/
├── Cargo.toml
├── src/lib.rs
└── tests/
    └── end_to_end.rs     contains:  use stock_check::Item;  and #[test] functions
```

No `#[cfg(test)]` is needed there. Shared helpers go in `tests/common/mod.rs` and are pulled in with
`mod common;`. Rule of thumb: unit tests check one piece in detail; integration tests check that the
pieces work together through the public interface.

### Doc comments and doc tests
`///` before an item writes its documentation, in Markdown. `//!` at the top of a file documents the
module or crate itself. Like a Python docstring, but with one more trick: code blocks in doc comments
are **compiled and run** by `cargo test` (for library crates), so examples can't silently go stale.

```rust
/// Converts degrees Celsius to Fahrenheit.
///
/// # Examples
/// ```
/// assert_eq!(stock_check::celsius_to_f(0.0), 32.0);
/// ```
pub fn celsius_to_f(c: f64) -> f64 { c * 9.0 / 5.0 + 32.0 }
```

`cargo doc --open` builds HTML docs for your crate and all its dependencies and opens them in a browser.

### Formatting and linting
- **`rustfmt`**, run with `cargo fmt`, rewrites your code into the one standard style, like `black`
  in Python. `cargo fmt --check` only reports differences. There's nothing to configure or argue about.
- **`clippy`**, run with `cargo clippy`, is a linter with hundreds of checks, like `ruff` or `pylint`.
  It catches un-idiomatic code (`return x;` at the end of a function, `if v.len() == 0` instead of
  `v.is_empty()`, needless `.clone()`s) and real bugs. Each warning links to an explanation;
  read them, they're a free Rust tutor. `cargo clippy -- -D warnings` turns warnings into errors,
  which is what CI (automated checks on every push) usually runs.
- Silence a lint only on purpose and locally: `#[allow(clippy::lint_name)]` on one item, with a
  comment saying why.

The routine before every commit, from now on: **`cargo fmt`, `cargo clippy`, `cargo test`.**

## Build
1. **Module playground.** `cargo new shop --lib`. Create modules `inventory` (in `inventory.rs`),
   `inventory::pricing` (in `inventory/pricing.rs`) and `orders`. Call across them with `crate::`,
   `super::` and `use`. Then trigger and read these errors: a file with no `mod` line, calling a
   private function from another module, and building a struct with a private field from outside.
2. **Protect an invariant.** Write a `Percent` type in its own module whose value must be 0–100,
   with a private field and `pub fn new(v: u8) -> Option<Percent>`. Show that code elsewhere can't
   create an invalid one. Add a `pub use` re-export and use the shorter path.
3. **Unit tests.** Add a `#[cfg(test)] mod tests` to each module with at least three tests each,
   including one `#[should_panic]`, one test returning `Result`, and one test of a private function.
   Practise `cargo test <filter>` and `-- --nocapture`.
4. **Restructure your todo CLI (3.5).** Split it into `lib.rs` plus modules (for example: the task
   model, storage, command parsing), with a thin `main.rs`. Add unit tests for parsing and task
   logic, and one integration test in `tests/` that drives the public API with a temporary file.
   Keep its behaviour exactly the same.
5. **Docs.** Write `///` docs with an `# Examples` doc test for three public functions and `//!`
   crate docs in `lib.rs`. Break one example on purpose and watch `cargo test` catch it. Run
   `cargo doc --open` and browse your crate.
6. **Tooling.** Run `cargo fmt` and fix every `cargo clippy` warning in this crate and the todo CLI.
   Optionally look (don't fix everything) at `cargo clippy -- -W clippy::pedantic`.
7. Rustlings: `10_modules`, `17_tests` and `22_clippy`.

## Common pitfalls
- Forgetting the `mod name;` line, or writing `mod` in two places for the same file. Declare each
  module exactly once, in its parent.
- Using `mod` where you meant `use`. `mod` *declares* a module; `use` only shortens a path to it.
- Making everything `pub` to silence errors. Expose the minimum; keep fields private.
- Putting integration tests in `src/`, or expecting `tests/` to see private items.
- Ignoring clippy warnings until there are fifty. Fix them as they appear.
