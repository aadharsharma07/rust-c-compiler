# Lesson 4.1 — Traits
**Part:** 1 — Learn Rust · **Unit:** 4 — Abstraction and Organisation · **Type:** Learning · **Est. time:** 3–5 h · **Tests:** none
**Prerequisites:** lessons 1.1–3.5

## Overview
A trait describes a set of behaviour ("can be printed", "can be compared", "has an area") that
many types can share. Traits are how Rust does what Python does with duck typing, abstract base
classes and dunder methods like `__str__` and `__eq__`, but checked completely before the program
runs. You'll meet traits everywhere from here on: `Display` for printing your compiler's errors,
`derive(Debug, PartialEq)` on every syntax-tree type, and `Iterator` in lesson 4.3.

## The lesson

### The problem traits solve
In Python you can write a function that works on "anything with an `area()` method":

```python
def total_area(shapes):
    return sum(s.area() for s in shapes)
```

This is **duck typing**: "if it has an `area` method, it's good enough". It's flexible, but if
you pass something without `area`, you find out only when that line runs, perhaps in production.

Python offers two ways to make this contract explicit:

- **Abstract base classes (ABCs).** `class Shape(ABC)` with an `@abstractmethod def area(self)`.
  Classes must *inherit* from `Shape` (this is called **nominal** typing: what matters is the
  declared name). Forgetting to implement `area` fails when you try to create an instance.
- **`typing.Protocol`.** `class HasArea(Protocol): def area(self) -> float: ...`. Any class with a
  matching method fits, without inheriting (this is **structural** typing: what matters is the
  shape). But only a type checker like mypy checks it; Python itself ignores it at runtime.

A Rust **trait** sits between the two. Like an ABC, a type has to *opt in* explicitly by writing
`impl Trait for Type`. Like a Protocol, it's checked statically (before running). Unlike both, the
check is done by the compiler and is not optional: a program that breaks a trait contract does not
compile.

### Defining and implementing a trait

```rust
trait Shape {
    fn area(&self) -> f64;                  // required: every implementor must write this
    fn describe(&self) -> String {          // provided: a default body implementors may override
        format!("a shape with area {:.2}", self.area())
    }
}

struct Circle { radius: f64 }
struct Rect { w: f64, h: f64 }

impl Shape for Circle {
    fn area(&self) -> f64 { std::f64::consts::PI * self.radius * self.radius }
}

impl Shape for Rect {
    fn area(&self) -> f64 { self.w * self.h }
    fn describe(&self) -> String { format!("a {}x{} rectangle", self.w, self.h) }
}
```

Things to notice:
- The trait lists method **signatures**. A signature ending in `;` is *required*; one with a body
  is a *default method*, like a concrete method on an ABC.
- `impl Shape for Circle` is a separate block from `impl Circle { ... }` (the inherent methods
  you wrote in 3.1). A type can have one inherent `impl` and any number of trait `impl`s.
- Default methods can call required ones (`describe` calls `self.area()`), exactly like a
  template method in a Python base class.
- There is no inheritance of *data*. Traits share behaviour only; structs never inherit fields.
  Rust prefers composition: put a struct inside another struct.

To call a trait method, the trait must be **in scope**: `use some_module::Shape;`. If you see
"no method named `area` found" for a type that clearly implements it, a missing `use` is the
usual cause.

### Using traits as parameter types
How do you write `total_area`? There are two ways.

```rust
fn print_it(s: &impl Shape) {           // "any type that implements Shape"
    println!("{}", s.describe());
}

fn total_area(shapes: &[Box<dyn Shape>]) -> f64 {
    shapes.iter().map(|s| s.area()).sum()   // .iter().map(...) is explained in 4.3
}
```

`&impl Shape` means "a reference to some single type that implements `Shape`". The compiler
generates a separate copy of `print_it` for each type you call it with (lesson 4.2 explains this,
called *monomorphisation*). It's fast, but every element must be the same type.

`dyn Shape` is a **trait object**: "some value implementing `Shape`, type decided at runtime".
That's what you need for a mixed list of circles and rectangles. Because different shapes have
different sizes, a `dyn Shape` must always live behind a pointer: `&dyn Shape` or `Box<dyn Shape>`
(`Box` puts a value on the heap; lesson 4.4 covers it fully). The pointer is a **fat pointer**,
two words wide:

```
Box<dyn Shape> on the stack          heap
+-----------------+            +----------------+
| data pointer  --+----------->| Circle {       |
| vtable pointer -+--+         |   radius: 2.0  |
+-----------------+  |         | }              |
                     |         +----------------+
                     |         vtable for Circle-as-Shape (static memory)
                     +-------->| area     -> Circle::area     |
                               | describe -> Shape::describe  |
                               +------------------------------+
```

A **vtable** ("virtual method table") is a small table of function pointers. Calling
`s.area()` on a trait object looks up the function in the table at runtime. This is **dynamic
dispatch**, which is how every Python method call works. Rust makes you choose it explicitly with
`dyn`, and it costs one pointer lookup per call.

### Standard traits: Rust's dunder methods
Much of Python's data model is dunder methods. Rust's equivalent is a set of standard traits:

| Python | Rust trait | Gives you |
|---|---|---|
| `__str__` | `std::fmt::Display` | `{}` in `println!`/`format!`, `.to_string()` |
| `__repr__` | `std::fmt::Debug` | `{:?}` and pretty `{:#?}` |
| `__eq__` | `PartialEq` (and `Eq`) | `==`, `!=`, `assert_eq!` |
| `__lt__` etc. | `PartialOrd` (and `Ord`) | `<`, `>`, `.sort()`, `.max()` |
| `__hash__` | `Hash` | use as a `HashMap` key or in a `HashSet` |
| `copy.copy` | `Clone` | `.clone()` |
| `__add__` | `std::ops::Add` | the `+` operator |
| `__iter__` | `IntoIterator` | `for x in thing` (lesson 4.3) |
| default `__init__` args | `Default` | `Type::default()` |

`Display` is the one you write by hand most often, because only you know how your type should look
to a user:

```rust
use std::fmt;

struct Money { pence: i64 }

impl fmt::Display for Money {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "£{}.{:02}", self.pence / 100, self.pence % 100)
    }
}
// println!("{}", Money { pence: 1234 });   prints £12.34
```

`write!` works like `format!` but writes into the formatter `f` and returns a `fmt::Result`
(success or failure), which is why there's no semicolon after it: it is the return value. The
`<'_>` is a *lifetime*, covered in 4.5; for now, copy it as written. Once you implement `Display`,
you get `.to_string()` for free, because the standard library has a blanket rule: "every type
that implements `Display` also implements `ToString`".

### `derive`: letting the compiler write the boring ones
`Debug`, `Clone`, `PartialEq` and friends have obvious implementations ("compare every field",
"clone every field"). Instead of writing them, ask the compiler:

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
enum Suit { Hearts, Spades }

#[derive(Debug, Clone, PartialEq)]
struct Card { suit: Suit, rank: u8 }
```

`#[derive(...)]` is an **attribute** that generates the `impl` blocks for you. It only works if
every field also implements that trait (a struct can't derive `Hash` if one field is an `f64`,
because floats don't implement `Hash`). Python's `@dataclass` does something similar: it writes
`__init__`, `__repr__` and `__eq__` from your fields. In the compiler, almost every type will start
with `#[derive(Debug, Clone, PartialEq)]` so you can print it and compare it in tests.

### Conversion traits: `From` and `Into`
`From<T>` says "I can be built from a `T`". Implementing `From` gives you `Into` for free in the
other direction:

```rust
struct Celsius(f64);
struct Fahrenheit(f64);

impl From<Celsius> for Fahrenheit {
    fn from(c: Celsius) -> Self { Fahrenheit(c.0 * 9.0 / 5.0 + 32.0) }
}
// let f: Fahrenheit = Celsius(100.0).into();
```

This matters for error handling: the `?` operator from 3.3 calls `From::from` on the error, so
`impl From<std::io::Error> for MyError` lets `?` turn I/O errors into your own error type
automatically. You'll rely on this in 4.7.

### Rules worth knowing early
- **The orphan rule.** You may write `impl Trait for Type` only if you defined the trait or the
  type (or both) in your crate. You can implement `Display` for your `Money`, or your own trait
  for `Vec<i32>`, but not `Display` for `Vec<i32>`: both belong to the standard library. This stops
  two libraries from giving conflicting implementations. The usual workaround is a *newtype*: wrap
  the foreign type in your own one-field struct, like `struct Lines(Vec<String>);`.
- **Traits as contracts, not hierarchies.** Rust has no class inheritance. A trait can require
  another (`trait Named: Display { ... }` means "to be `Named` you must also be `Display`"), but
  that's a requirement, not a parent class.

## Build
Make a new scratch crate (for example `cargo new traits_practice`) and do these in order.

1. **A trait with a default method.** Define a trait `Summary` with a required method
   `title(&self) -> String` and a default method `headline(&self) -> String` that returns the
   title in upper case with `"!"` added. Implement it for two structs, `Book` (title, author) and
   `Podcast` (name, episode number). Override `headline` for one of them only.
2. **Display by hand.** Implement `Display` for a `Duration` struct holding whole seconds so it
   prints as `1h 02m 05s` (hours only when non-zero). Use it with `println!("{}")` and
   `.to_string()`, and check both outputs match.
3. **Derive and compare.** Derive `Debug, Clone, PartialEq, Eq, Hash` on a small `Colour` enum and
   a struct containing it. Print one with `{:?}` and `{:#?}`, put several into a `HashSet`, and show
   that duplicates are dropped. Then add an `f64` field and read the error when deriving `Hash`.
4. **Static vs. dynamic.** Write `fn announce(item: &impl Summary)` and
   `fn announce_all(items: &[Box<dyn Summary>])`. Build a `Vec<Box<dyn Summary>>` holding both
   books and podcasts. Then try to put both types into a plain `Vec<Book>` and explain the error.
5. **Conversions.** Implement `From<u64>` for your `Duration` (from seconds) and use both
   `Duration::from(3725)` and `let d: Duration = 3725.into();`.
6. **Break the orphan rule on purpose.** Try `impl std::fmt::Display for Vec<String>`. Read the
   error, then fix it with a newtype `struct Shelf(Vec<String>);`.
7. Rustlings: `15_traits`, and `23_conversions` (only the `from_into` exercise for now).

## Common pitfalls
- Forgetting to `use` the trait, then getting "no method found" on a type that implements it.
- Adding a semicolon after `write!(...)` in `fmt`, which turns the return value into `()`.
- Reaching for `Box<dyn Trait>` everywhere out of Python habit. If all values have the same type,
  `impl Trait` or generics (4.2) are simpler and faster.
- Trying to model a class hierarchy with traits. Share behaviour with traits and data with
  composition (a struct inside a struct) or an enum.
- Confusing `Debug` (for developers, derivable) with `Display` (for users, always hand-written).
