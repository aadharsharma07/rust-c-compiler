# Lesson 4.7 — Project: File Search Tool
**Part:** 1 — Learn Rust · **Unit:** 4 — Abstraction and Organisation · **Type:** Project · **Est. time:** 6–8 h · **Tests:** none
**Prerequisites:** lessons 1.1–3.5, 4.1–4.6

## Overview
You'll build `seek`, a small version of the Unix `grep` command: it searches files for lines
containing a pattern and prints them. It's the capstone of Part 1, pulling together everything
from this unit: modules and a library/binary split (4.6), a custom error type (3.3, 4.1), a trait
with several implementations (4.1, 4.2), iterator pipelines (4.3), borrowed slices with lifetimes
(4.5) and a proper test suite. Its shape (read arguments, read files, process text, report errors,
exit with a status code) is exactly the shape of the compiler driver you'll write in Part 3.

## The lesson

### What the tool does
`grep` prints every line of a file that contains a pattern:

```
$ seek -n fox notes.txt
3:the quick brown fox
7:a fox in the henhouse
```

In Python, the heart of it might be a few lines:

```python
for i, line in enumerate(open(path), start=1):
    if pattern in line:
        print(f"{i}:{line}", end="")
```

The Rust version's core is just as short. The work in this project is everything around it: options,
several files, folders, errors that don't crash the program, a clean module structure and tests.
That surrounding work is what separates a script from a tool.

### Command-line arguments
`std::env::args()` returns an iterator of `String`s, like Python's `sys.argv`. The first item is the
program's own name, so you usually skip it. With Cargo, arguments after `--` go to your program:
`cargo run -- -n fox notes.txt`.

You'll parse arguments **by hand** in this project, because it's good practice with iterators,
`match` and errors. (Real projects often use the `clap` crate; that's a stretch goal.) An important
design choice: write your parser as a function that takes a *slice or iterator of strings* rather
than calling `env::args()` inside. Then tests can pass in `["-n", "fox", "a.txt"]` directly.

### Paths, files and folders
- `std::path::Path` and `PathBuf` are like Python's `pathlib.Path`. They relate as `&str` and
  `String` do: `&Path` is borrowed, `PathBuf` is owned. Paths aren't guaranteed to be valid UTF-8,
  so to print one, use `path.display()`.
- `std::fs::read_to_string(path)` reads a whole file into a `String` and returns `io::Result<String>`.
  If the file isn't valid UTF-8 (for example an image), it fails with an error whose `kind()` is
  `io::ErrorKind::InvalidData`. You'll use that to skip binary files.
- `std::fs::metadata(path)` tells you whether a path is a file or a directory (`is_dir()`).
- `std::fs::read_dir(path)` returns an iterator whose items are `io::Result<DirEntry>`: *each entry*
  can fail separately. Walking a folder tree is recursion (like your file-system tree in 4.4), but
  over the real disk. The order of entries is **not** guaranteed, so sort them if you want the same
  output every time (you do: your tests depend on it).

### Standard output, standard error and exit codes
A command-line tool talks through three channels:
- **stdout** (`println!`, or anything implementing `std::io::Write`): the results, for piping into
  other programs.
- **stderr** (`eprintln!`): warnings and errors, so they don't mix with results in a pipe.
- the **exit code**: a small number returned to the shell. 0 means success; anything else means some
  kind of failure. Scripts check it (`$?` in a shell, `subprocess.run(...).returncode` in Python).
  In Rust, `main` can return `std::process::ExitCode` (`ExitCode::SUCCESS`, `ExitCode::from(2)`),
  or you can call `std::process::exit(code)`.

`grep` uses a convention you'll copy: **0** if any line was selected, **1** if nothing was selected,
**2** if an error occurred.

### Designing for testability
The most useful idea in this project: keep **logic** and **I/O** apart.
- The *core* (does a line match? which lines of this text match? how is a result formatted?) works on
  `&str`s and returns values. No files, no printing. These are easy to unit test.
- The *shell* (read arguments, read files, walk folders, print, exit) is thin and calls the core.

Two concrete techniques:
1. Search functions take the file's text as `&str` and hand back **borrowed** lines (slices into that
   text, as in 4.5) together with line numbers, instead of copying each line into a new `String`.
2. The function that prints results takes a writer, `&mut impl std::io::Write`, instead of calling
   `println!`. In `main` you pass real stdout; in tests you pass a `Vec<u8>` (which implements
   `Write`) and check what was written.

### Errors: fatal vs. per-file
Some errors end the program immediately: a bad command line. Others concern one file (missing,
unreadable, a directory without `-r`): report them on stderr and **carry on** with the other files,
then exit with 2 at the end. Model this with your own error enum (3.3), give it a `Display` impl
(4.1) for the messages, and implement `From<io::Error>` (or wrap I/O errors with the path they came
from, since "No such file or directory" alone doesn't say *which* file). Decide which function
returns which kind.

## Build

### The behaviour to implement
```
seek [OPTIONS] PATTERN PATH...
```

| Option | Meaning |
|---|---|
| `-i` | ignore case (`Fox` matches `fox`) |
| `-n` | prefix each printed line with its 1-based line number |
| `-v` | invert: select lines that do **not** contain the pattern |
| `-c` | print only the count of selected lines per file, not the lines |
| `-r` | recurse into directories given as paths |
| `-h`, `--help` | print usage to stdout and exit 0 |

Rules:
1. Matching is plain substring matching (no regular expressions). An empty pattern matches every line.
2. Options may appear anywhere among the arguments. `--` ends option parsing, so
   `seek -- -v notes.txt` searches for the text `-v`. The first non-option argument is the pattern;
   the rest are paths. At least one path is required.
3. Unknown options, a missing pattern or a missing path: print an error and the usage line to stderr,
   exit 2, search nothing.
4. **Output prefix.** If more than one file could be searched (more than one path, or `-r` was given),
   prefix each output line with the file path and `:`. Combined with `-n`, the format is
   `path:line_number:text`. With one plain file, print no path.
5. **`-c`** prints `path:count` per file (or just `count` with one file), including files with a count of 0.
6. **Directories.** Without `-r`, a directory path is a per-file error: `seek: <path>: is a directory`.
   With `-r`, search every file under it, recursively, in sorted path order.
7. **Per-file errors** (missing file, permission denied, directory without `-r`) print
   `seek: <path>: <reason>` to stderr, and searching continues with the next path.
8. **Non-UTF-8 files** are skipped with a warning on stderr (`seek: <path>: binary file skipped`). This
   is not an error and doesn't affect the exit code.
9. **Exit code:** 2 if any error occurred (even if there were matches), otherwise 0 if at least one
   line was selected, otherwise 1. With `-c`, "selected" means any count above zero.
10. Print each selected line's text followed by a single newline (`str::lines` already strips `\n` and `\r\n`).

### Required structure
- A library crate (`src/lib.rs`) holding all the logic, and a `src/main.rs` of roughly ten lines that
  only calls into the library and turns the outcome into an exit code.
- At least these modules, each in its own file: argument parsing (producing a configuration struct),
  matching, searching, directory walking, and errors. Output formatting may be its own module.
- A **trait** that answers "does this line match?", with at least two implementations (for example,
  case-sensitive and case-insensitive), chosen at runtime from the options. Decide whether inversion
  is a third implementation, a wrapper around another matcher (generics practice!), or a flag
  applied elsewhere, and be ready to justify the choice.
- Search logic written with **iterator adapters** (no index-based `for i in 0..len` loops), returning
  borrowed line slices rather than copies.
- Your own error enum with `Display`. No `unwrap()` or `expect()` outside tests, unless a comment
  explains why it can never fail.

### Suggested order
1. `cargo new seek`, add `src/lib.rs`, create the empty module files and the `mod` lines. Make sure it builds.
2. **Matching and searching first, test-first.** Write unit tests for matching (plain, ignore-case,
   empty pattern, pattern at the start/end of a line) and for searching a multi-line `&str` (line
   numbers start at 1, inverted selection, counting, text with no matches, empty text, a last line
   with no trailing newline). Then make them pass.
3. **Argument parsing**, tested with slices of strings: each option, options after the pattern, `--`,
   repeated options, each usage error. The result is either your config struct or your error.
4. **One file end to end**: read, search, format, print through a writer, return a result `main` can
   turn into an exit code. Try it by hand with `cargo run -- ...`.
5. **Several files**: the path prefix, `-c` per file, per-file errors that don't stop the run, the
   exit-code rules.
6. **Recursion** with `-r`: walk directories, sort, skip binary files with a warning.
7. **Integration tests** in `tests/`: build a small folder tree in a fresh directory under
   `std::env::temp_dir()` (with a unique name, created at the start of the test and removed at the end),
   containing text files, a nested folder and one non-UTF-8 file. Test through the library's public API
   with a `Vec<u8>` writer, and at least once by running the real binary with `std::process::Command`
   (Cargo gives integration tests its path as `env!("CARGO_BIN_EXE_seek")`), checking stdout, stderr
   and the exit code.
8. **Polish**: `--help` text, `///` docs on every public item, a doc test on one function, `cargo fmt`, `cargo clippy`.

### Stretch goals (pick any)
- `-l`: print only the names of files with at least one selected line.
- `-w`: match whole words only. Decide what counts as a word boundary, and test it.
- Read from standard input when no path is given, so `cat notes.txt | seek fox` works.
- `-C N`: print N lines of context around each match, with `--` between separate groups.
- Combined short flags (`-in` meaning `-i -n`).
- Swap your hand-written parser for the `clap` crate, or substring matching for the `regex` crate,
  and notice how little the rest of your code needs to change if the trait boundary is right.

## Check your understanding
1. Why does your search function take `&str` and return borrowed slices? What would change if it returned `Vec<String>`?
2. Which errors in `seek` are fatal and which are per-file? How does your error type show the difference?
3. Why does printing go through a writer parameter instead of `println!`? How did that help your tests?
4. Walk through what happens, module by module, for `seek -r -n fox docs/`.
5. How did you handle `-v`, and what are the trade-offs of the alternatives?
6. Why must directory entries be sorted, and what would break in your tests if they weren't?

## Common pitfalls
- Calling `std::process::exit` deep inside the library. It skips destructors and makes code untestable;
  return errors and let `main` decide the exit code.
- Stopping at the first unreadable file because `?` propagated a per-file error all the way up.
- Lower-casing only the line and not the pattern for `-i` (or lower-casing them again for every line).
- Integration tests that depend on the real file system's ordering or on files outside the test's own temp folder.
- Printing errors to stdout, which corrupts output piped into another program.
- Writing the whole program in `main.rs` "for now". Start with the module layout.
