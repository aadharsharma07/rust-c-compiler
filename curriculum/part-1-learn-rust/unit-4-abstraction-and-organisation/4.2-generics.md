# Lesson 4.2 — Generics
**Part:** 1 — Learn Rust · **Unit:** 4 — Abstraction and Organisation · **Type:** Learning · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 1.1–3.5, 4.1

## Overview
Generics let you write one function or type that works for many types, such as a `Vec<T>` that
can hold integers, strings or tokens. Combined with trait bounds from 4.1 ("any `T` that can be
compared"), they give you Python's flexibility with none of its runtime surprises, and with no
runtime cost. You have already been using generics (`Vec<T>`, `Option<T>`, `Result<T, E>`,
`HashMap<K, V>`); this lesson shows you how to write your own.

## The lesson

### The problem: the same code for different types
Suppose you want "the index of the first element equal to a target" for a list of `i32`, and then
the same thing for a list of `String`. Without generics you'd write two identical functions that
differ only in the type name. In Python you'd never notice the problem, because a Python function
accepts anything:

```python
def index_of(items, target):
    for i, x in enumerate(items):
        if x == target:
            return i
    return None
```

Python can do this because it checks `x == target` at runtime, every time, for whatever objects
turn up. Rust checks types at compile time, so it needs a way to say "this works for any type,
as long as that type supports `==`".

### Generic functions
```rust
fn index_of<T: PartialEq>(items: &[T], target: &T) -> Option<usize> {
    for (i, x) in items.iter().enumerate() {
        if x == target {
            return Some(i);
        }
    }
    None
}

// index_of(&[3, 1, 4], &4)              -> Some(2)
// index_of(&["a", "b"], &"z")            -> None
```

Read `<T: PartialEq>` as: "this function has a **type parameter** called `T`, and `T` must
implement `PartialEq`". The part after the colon is a **trait bound**. Inside the function you may
use only what the bounds promise: `==` works because of `PartialEq`, but `x > target` would be a
compile error ("binary operation `>` cannot be applied to type `T`"), because nothing promised
that `T` can be ordered. The compiler checks the *body* once, against the bounds, not against
each concrete type. That's the key difference from Python: the contract is written down.

Python's type hints have a similar idea, `TypeVar`:

```python
T = TypeVar("T")
def first(items: list[T]) -> T: ...
```

But Python hints are only checked by external tools like mypy, and the interpreter ignores them.
Rust's type parameters are part of the language, and the program won't compile if they're wrong.

### Several bounds, and `where`
Join bounds with `+`. When the list gets long, move it into a `where` clause after the
signature. These two are identical:

```rust
fn show_twice<T: std::fmt::Display + Clone>(x: T) -> String { format!("{x} {x}") }

fn show_twice_w<T>(x: T) -> String
where
    T: std::fmt::Display + Clone,
{
    format!("{x} {x}")
}
```

(`{x}` inside a format string is shorthand for `{}` with `x` as the argument.)

`fn f(x: &impl Display)` from 4.1 is simply shorter syntax for `fn f<T: Display>(x: &T)`.

### Generic structs, enums and `impl` blocks
Types can have parameters too:

```rust
struct Pair<T> {
    left: T,
    right: T,
}

impl<T> Pair<T> {                         // methods for every Pair<T>
    fn new(left: T, right: T) -> Self { Pair { left, right } }
    fn swap(self) -> Self { Pair { left: self.right, right: self.left } }
}

impl<T: PartialOrd + Copy> Pair<T> {      // extra methods only when T can be compared and copied
    fn larger(&self) -> T {
        if self.left > self.right { self.left } else { self.right }
    }
}
```

`impl<T> Pair<T>` reads as "for any type `T`, here are methods for `Pair<T>`". The second block is
a **conditional implementation**: `Pair<i32>` has a `larger` method, but a `Pair<Vec<u8>>` does
not, because `Vec<u8>` isn't `Copy`. Python has nothing like this: a method either exists on a
class or it doesn't.

Now look again at types you already know. They are ordinary generic enums from the standard
library:

```rust
enum Option<T> { Some(T), None }
enum Result<T, E> { Ok(T), Err(E) }
```

Nothing magic: you could have written them yourself after this lesson.

### How it works: monomorphisation
When you call `index_of` with `&[i32]` and later with `&[&str]`, the compiler writes two
specialised copies of the function behind the scenes, one per concrete type. This is called
**monomorphisation** ("making single-shaped"):

```
your source                      what the compiler actually generates
fn index_of<T: PartialEq>  --->  fn index_of_i32(items: &[i32], target: &i32) -> ...
                           --->  fn index_of_str(items: &[&str], target: &&str) -> ...
```

Each copy knows its exact types, so `==` compiles to a direct machine comparison: no lookups at
runtime. The costs are a slightly bigger binary and longer compile times. Contrast this with the
trait objects from 4.1 (`dyn Trait`), which keep one copy of the code and look up methods through
a vtable at runtime.

| | Generics / `impl Trait` | Trait objects (`dyn Trait`) |
|---|---|---|
| Decided | at compile time (static dispatch) | at runtime (dynamic dispatch) |
| Mixed types in one `Vec` | no, one `T` per `Vec<T>` | yes, `Vec<Box<dyn Trait>>` |
| Speed | fastest, calls can be inlined | one pointer lookup per call |
| Code size | one copy per type used | one copy |

Rule of thumb: use generics by default, and `dyn` when you genuinely need a mixed collection or
want to pick an implementation at runtime.

### Helping inference: the turbofish
Usually Rust infers `T` from the arguments. Sometimes there's nothing to infer from, for example
when the type only appears in the *return* value. Then either annotate the variable or use the
**turbofish** syntax `::<>`:

```rust
let n: i32 = "42".parse().unwrap();       // annotate the variable...
let m = "42".parse::<i32>().unwrap();     // ...or use the turbofish
```

You'll see the turbofish most with `collect::<Vec<_>>()` in 4.3. The `_` means "you work this
part out, compiler".

### `impl Trait` in return position
A function can promise "I return *some* type implementing this trait" without naming it:

```rust
fn evens_up_to(n: u32) -> impl Iterator<Item = u32> {
    (0..=n).filter(|x| x % 2 == 0)
}
```

There is still exactly one concrete type, chosen by the function; the caller just doesn't get to
know its name. This is essential for returning iterators and closures, whose real type names are
long or impossible to write. Lesson 4.3 explains the body.

### Associated types (a preview)
Some traits have a type "slot" filled in by the implementor rather than a type parameter. The
`Iterator` trait says `type Item;`, and each iterator chooses what its `Item` is. That's why the
return type above is written `Iterator<Item = u32>`. You'll implement one yourself in 4.3.

## Build
Use a new scratch crate (for example `cargo new generics_practice`).

1. **A generic function.** Write `count_matching<T: PartialEq>(items: &[T], target: &T) -> usize`.
   Call it with integers, `&str`s and a `#[derive(PartialEq)]` enum of your own.
2. **Read the bound error.** Write `fn biggest<T>(items: &[T]) -> Option<&T>` with *no* bounds,
   using `>` inside. Read the error carefully, then add the smallest bound that fixes it.
3. **A generic container.** Write `Stack<T>` backed by a `Vec<T>`, with `new`, `push`,
   `pop -> Option<T>`, `peek -> Option<&T>`, `len` and `is_empty`. Use it with two element types.
4. **A conditional method.** Add an `impl<T: std::fmt::Display> Stack<T>` block with a method
   `render(&self) -> String` that shows the stack as `[1, 2, 3]`. Confirm that a stack of a type
   without `Display` doesn't have `render` (the error message will tell you).
5. **Two type parameters.** Write `Labelled<L, V> { label: L, value: V }` with a method
   `map_value` that takes the struct by value and a new value of a *different* type, and returns
   `Labelled<L, W>`. (The method itself introduces `W`: `fn map_value<W>(self, ...)`.)
6. **A counter with bounds.** Write `Tally<K>` wrapping a `HashMap<K, usize>` with `add(&mut self, key: K)`
   and `count(&self, key: &K) -> usize`. Work out which bounds `K` needs (hint: what does a
   `HashMap` key need?) and put them in a `where` clause.
7. Rustlings: `14_generics`.

## Check your understanding
1. What does the bound in `fn f<T: PartialEq>(...)` allow inside the body, and what does it forbid?
2. Explain monomorphisation. What does it cost, and what does it buy you?
3. When would you choose `Vec<Box<dyn Trait>>` over a generic `Vec<T>`?
4. What is a conditional `impl` block, and why might a method exist on `Pair<i32>` but not on `Pair<String>`?
5. Why does `"42".parse()` sometimes need a turbofish or a type annotation?
6. How are Rust's type parameters different from Python's `TypeVar`?

## Common pitfalls
- Adding bounds to the struct definition (`struct Stack<T: Display>`). Put bounds on the `impl`
  blocks or functions that need them, and keep the struct itself unbounded.
- Forgetting the `<T>` after `impl`: write `impl<T> Stack<T>`, not `impl Stack<T>`.
- Over-generalising. If a function is only ever called with one type, write it for that type.
- Reading `impl Trait` in return position as "any type the caller wants". It means one specific
  type, chosen by the function.
