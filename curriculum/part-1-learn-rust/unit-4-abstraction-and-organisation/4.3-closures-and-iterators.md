# Lesson 4.3 — Closures and Iterators
**Part:** 1 — Learn Rust · **Unit:** 4 — Abstraction and Organisation · **Type:** Learning · **Est. time:** 4–5 h · **Tests:** none
**Prerequisites:** lessons 1.1–3.5, 4.1, 4.2

## Overview
Closures are Rust's lambdas: small anonymous functions that can use variables from around them.
Iterators are Rust's version of Python's iterator protocol, generators and comprehensions all
at once. Together they let you write data processing as short pipelines like
`lines.filter(...).map(...).collect()`. This lesson matters a lot for the compiler: a lexer walks
through its input one character at a time with an iterator, and `peekable` (covered at the end) is
the tool it uses to look one character ahead before deciding what to do.

## The lesson

### Closures: lambdas that can do more
A Python lambda (`lambda x: x * x`) is limited to one expression. A Rust closure is written
with the parameters between pipes:

```rust
let square = |x: i32| x * x;               // one expression
let describe = |x: i32| {                  // or a whole block
    let kind = if x % 2 == 0 { "even" } else { "odd" };
    format!("{x} is {kind}")
};
println!("{} {}", square(4), describe(7)); // 16 7 is odd
```

Parameter and return types are usually inferred, so `|x| x * x` is common.

### Capturing the environment
A closure can use variables from the scope where it was created. That's what makes it a
*closure* (it "closes over" its surroundings). After `let threshold = 10;`, the closure
`let is_big = |x: i32| x > threshold;` borrows `threshold`, and `is_big(12)` is `true`.

Python closures capture *variables*, looked up when the function runs. That causes the
famous loop surprise:

```python
fs = [lambda: i for i in range(3)]
[f() for f in fs]   # [2, 2, 2], not [0, 1, 2]
```

Rust closures capture in one of three ways, chosen by what the body does, and the borrow rules
from 2.3 apply to them like any other borrow:

| Body does | Captures as | Closure implements |
|---|---|---|
| only reads the variable | shared borrow `&` | `Fn` (can be called many times) |
| modifies the variable | mutable borrow `&mut` | `FnMut` (many times, needs `mut`) |
| moves the variable out (e.g. returns it, drops it) | by value | `FnOnce` (called at most once) |

```rust
let mut count = 0;
let mut tick = || count += 1;   // FnMut: mutably borrows `count`
tick(); tick();
// println!("{count}") here *between* the calls would fail: `count` is mutably borrowed by `tick`
println!("{count}");            // 2: fine, `tick` is no longer used
```

The `move` keyword forces every captured variable to be moved (or copied) into the closure. You
need it when the closure must outlive the current function, for example when returning one:

```rust
fn make_greeter(name: String) -> impl Fn() -> String {
    move || format!("Hello, {name}!")      // the closure now owns `name`
}
```
Without `move`, the closure would borrow `name`, which dies when `make_greeter` returns.

### Passing closures to functions
`Fn`, `FnMut` and `FnOnce` are traits, so you accept closures with generics (4.2):

```rust
fn apply_twice<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 { f(f(x)) }
// apply_twice(|n| n + 3, 1) == 7
```

Ask for the most permissive trait you can: `FnOnce` if you call it once, `FnMut` if you call it
repeatedly and it may change state, `Fn` only if you need shared, read-only calls. Ordinary
functions can be passed too: `apply_twice(double, 1)` works if `fn double(n: i32) -> i32` exists.

### The `Iterator` trait
Python's iterator protocol is `__next__`, which returns the next item or raises `StopIteration`.
Rust's is one trait with one required method:

```rust
trait Iterator {
    type Item;                                     // the associated type from 4.2
    fn next(&mut self) -> Option<Self::Item>;      // Some(item), or None when finished
    // ...plus about 70 default methods: map, filter, sum, collect, ...
}
```

No exceptions: the end is just `None`. And because every adapter is a *default method* (4.1),
anything that implements `next` gets `map`, `filter`, `zip` and the rest for free.

A `for x in it` loop is sugar for `while let Some(x) = it.next() { ... }`.

### Three ways to iterate a collection
This is where ownership (unit 2) shows up:

| Call | Yields | Afterwards the `Vec` is |
|---|---|---|
| `v.iter()` | `&T` (shared references) | still usable |
| `v.iter_mut()` | `&mut T` (so you can modify elements) | still usable, modified |
| `v.into_iter()` | `T` (owned values) | gone: moved into the loop |

`for x in &v` means `v.iter()`, `for x in &mut v` means `v.iter_mut()`, and `for x in v` means
`v.into_iter()`. If you get "value used after move" after a loop, you probably wrote `for x in v`
when you meant `for x in &v`.

### Lazy adapters and consumers
An **adapter** takes an iterator and returns a new one: `map`, `filter`, `enumerate`, `zip`,
`take`, `skip`, `take_while`, `skip_while`, `chain`, `rev`, `flat_map`, `copied`, `cloned`.
A **consumer** drives the iterator and produces a result: `collect`, `sum`, `count`, `min`, `max`,
`fold`, `any`, `all`, `find`, `position`, `last`, `for_each`.

Adapters are **lazy**, like a Python generator expression: building the chain does no work at
all. Nothing happens until a consumer pulls items through. That's why
`v.iter().map(|x| x * 2);` on its own triggers the warning "unused `Map` that must be used".

Here is how Python idioms translate (assume `nums: Vec<i32>` and `words: Vec<String>`):

| Python | Rust |
|---|---|
| `[x * x for x in nums if x % 2 == 0]` | `nums.iter().filter(\|x\| *x % 2 == 0).map(\|x\| x * x).collect::<Vec<_>>()` |
| `sum(nums)` | `nums.iter().sum::<i32>()` |
| `any(x < 0 for x in nums)` | `nums.iter().any(\|&x\| x < 0)` |
| `for i, w in enumerate(words)` | `for (i, w) in words.iter().enumerate()` |
| `list(zip(a, b))` | `a.iter().zip(b.iter()).collect::<Vec<_>>()` |
| `{w: len(w) for w in words}` | `words.iter().map(\|w\| (w.clone(), w.len())).collect::<HashMap<_, _>>()` |
| `next((w for w in words if w.startswith("a")), None)` | `words.iter().find(\|w\| w.starts_with('a'))` |
| `itertools.takewhile(lambda x: x > 0, nums)` | `nums.iter().take_while(\|x\| **x > 0)` |

The stars and ampersands are the one fiddly part. `nums.iter()` yields `&i32`, and `filter` hands
its closure a reference *to* each item, so inside `filter` you hold a `&&i32`. You can dereference
with `*`, or destructure in the parameter: `|&x|` means "take the reference apart and give me the
value inside". When in doubt, add `.copied()` after `.iter()` to turn `&i32` into `i32` early.

`collect` can build many collections (`Vec`, `String`, `HashMap`, `HashSet`), so it needs to know
which: annotate the variable or use the turbofish (4.2). A useful trick: an iterator of
`Result<T, E>` can be collected into a `Result<Vec<T>, E>`, which stops at the first error:

```rust
let parsed: Result<Vec<i32>, _> = ["1", "2", "x"].iter().map(|s| s.parse::<i32>()).collect();
// Err(ParseIntError { .. }) because "x" failed
```

Iterator chains are a **zero-cost abstraction**: they compile to code as fast as a hand-written loop.

### Writing your own iterator (Rust's generators)
In Python you'd write a generator function with `yield`:

```python
def countdown(n):
    while n > 0:
        yield n; n -= 1
```

Stable Rust has no `yield`. Instead you store the generator's "paused" state in a struct and write
`next`, which runs until the next `yield` would have happened:

```rust
struct Countdown { n: u32 }

impl Iterator for Countdown {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.n == 0 { return None; }
        self.n -= 1;
        Some(self.n + 1)
    }
}
// Countdown { n: 3 }.collect::<Vec<_>>() == vec![3, 2, 1]
// Countdown { n: 5 }.filter(|x| x % 2 == 1).sum::<u32>() == 9
```

The Python generator keeps its state in local variables that are frozen between `yield`s; the
Rust struct keeps the same state in fields. Once you implement `next`, all the adapters work.

### Looking ahead with `peekable`
Sometimes you need to see the next item *without* taking it. Python iterators can't do this:
calling `next()` consumes the item, so people keep an index into a list or use a helper library.
Rust provides an adapter. `.peekable()` wraps any iterator in a `Peekable`, which adds `peek()`
(returns `Option<&Item>` for the next item without consuming it), `next_if(|item| condition)`
(consumes and returns the next item only if the condition holds) and `next_if_eq(&value)` (the
same, for "only if it equals this").

Toy example: report words that appear twice in a row ("the the cat").

```rust
let text = "the the cat sat sat sat down";
let mut words = text.split_whitespace().peekable();
while let Some(word) = words.next() {
    if words.peek() == Some(&word) {
        println!("doubled word: {word}");
        while words.next_if_eq(&word).is_some() {}   // skip all the repeats
    }
}
// prints: doubled word: the
//         doubled word: sat
```

Step through it: `next` takes `"the"`; `peek` shows `"the"` without moving, so we report it and
`next_if_eq` swallows the copy; `next` takes `"cat"`; `peek` shows `"sat"`, which differs, so
nothing happens; and so on. Note the shapes: `peek()` returns `Option<&&str>` here (a reference to
the item, which is itself a `&str`), which is why we compare with `Some(&word)`.

Why it matters: a lexer reading `=` must look at the next character to decide whether the token is
`=` or `==`, and a lexer reading a digit keeps taking characters *while* they're digits. "Look,
then decide whether to consume" is exactly what `peek` and `next_if` give you.
`text.chars().peekable()` is the usual starting point when working character by character.

## Common pitfalls
- Building an adapter chain and never consuming it (the "must be used" warning). Nothing ran.
- Getting lost in `&&x`: use `|&x|` patterns, `*x`, or `.copied()` to get back to plain values.
- Holding the result of `peek()` (a reference into the iterator) while calling `next()`. Copy or
  compare the peeked value first, then advance.
- `collect()` with no type to aim for: "type annotations needed". Annotate or use `::<Vec<_>>`.
- Using `for x in v` when you still need `v` later.
