# Lesson 4.5 — Lifetimes
**Part:** 1 — Learn Rust · **Unit:** 4 — Abstraction and Organisation · **Type:** Learning · **Est. time:** 4–6 h · **Tests:** none
**Prerequisites:** lessons 1.1–3.5, 4.1–4.4 (especially 2.3 references and 2.4 slices)

## Overview
A lifetime is the stretch of a program during which a reference is valid. Rust tracks lifetimes so
that a reference can never outlive the data it points to, which is the cause of a whole family of
crashes in C. Most of the time the compiler works lifetimes out silently; this lesson explains what
it's doing, the few places you must write them yourself (`'a`), and what `'static` means. You'll
need this later when a struct holds a slice of a larger string, such as a lexer reading from source
text without copying it.

## The lesson

### The problem: dangling references
In Python, a reference keeps its object alive. As long as some variable refers to a list, the
reference count is above zero and the list exists. You can't end up pointing at freed memory.

Rust references (`&T`) do **not** keep anything alive. The owner decides when a value is dropped
(unit 2), and a reference is just a borrowed pointer. So the compiler has to prove that every
reference is used only while its value still exists. Here's a program it rejects:

```rust
let r;
{
    let s = String::from("hello");
    r = &s;
}                  // `s` is dropped here; its heap memory is freed
println!("{r}");   // error[E0597]: `s` does not live long enough
```

Draw each value's life as a bar:

```
line:    1    2    3    4    5    6
s:                 [==========]           s exists from line 3 to the end of the block (line 5)
r:       [=========================]      r exists from line 1 and is used at line 6
                        ^ line 4: r starts pointing into s
                                   ^ line 6: s is already gone, so r would dangle
```

In C this compiles and reads freed memory: sometimes it prints garbage, sometimes it crashes,
sometimes it seems to work. Rust makes it a compile error instead.

### What a lifetime is
A **lifetime** is the region of code over which a reference is valid. Every reference has one.
The part of the compiler that checks them is the **borrow checker**, which you've been meeting
since 2.3. Most lifetimes are inferred, just like most types are.

When you *do* write a lifetime, it looks like `'a` (an apostrophe and a short name), and it goes
right after the `&`: `&'a str` means "a reference to a `str` that is valid for the region `'a`".

The most important idea in this lesson: **lifetime annotations never change how long anything
lives.** They are labels that describe relationships ("this output borrows from that input") so
the compiler can check them. Like type annotations, they describe; they don't do.

### Why functions sometimes need annotations
Try writing a function that returns the longer of two strings:

```rust
fn longer(a: &str, b: &str) -> &str {      // error[E0106]: missing lifetime specifier
    if a.len() >= b.len() { a } else { b }
}
```

The compiler checks each function using only its **signature**, never the bodies of the functions
it calls. That keeps checking fast and means changing a function's body can't break its callers. So
from the signature alone, a caller needs to know: the returned reference borrows from *what*? From
`a`? From `b`? The answer decides how long the caller may keep using the result. Here it could be
either, so you must say so:

```rust
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}
```

`<'a>` declares a **lifetime parameter**, just like `<T>` declares a type parameter (4.2). Read the
signature as: "for some region `'a` where both `a` and `b` are valid, the result is valid for `'a`
too". In practice `'a` becomes the *shorter* of the two inputs' lifetimes. Now the compiler can
check callers:

```rust
let outer = String::from("a long string");
let result;
{
    let inner = String::from("short");
    result = longer(&outer, &inner);
}                          // `inner` dropped here
println!("{result}");      // error: `inner` does not live long enough
```

Even though `result` would actually be `outer` at runtime, the signature promised only "valid while
both are valid", and the compiler trusts the signature.

Not every input needs to be connected to the output. If the result only ever comes from the first
argument, say so, and the second argument is free:

```rust
fn first_of<'a, 'b>(a: &'a str, _b: &'b str) -> &'a str { a }
```

### Lifetime elision: why you rarely write them
Many functions you've written already return references without any `'a`, such as a function
taking `&str` and returning a word from it. That works because of three **elision rules** ("elide"
means "leave out"), which the compiler applies to signatures:

1. Each reference parameter gets its own lifetime.
2. If there is exactly one input lifetime, every output reference gets it.
3. If one of the parameters is `&self` or `&mut self` (a method), every output reference gets the
   lifetime of `self`.

If, after these rules, an output still has no lifetime, you get E0106 and must write it yourself.

```rust
fn first_word(s: &str) -> &str { ... }             // rule 2: output borrows from s. Fine.
fn longer(a: &str, b: &str) -> &str { ... }        // two inputs, not a method: must annotate.
impl Library { fn title(&self, i: usize) -> &str { ... } }   // rule 3: borrows from self.
```

If a function creates a new string, it can't return a reference to it at all: the local `String`
is dropped when the function returns. Return the owned `String` instead. Lifetimes describe
borrowing; they can't stretch a local's life.

### Structs that hold references
A struct can store a reference, but then it must carry a lifetime parameter, because the struct
must not outlive the data it borrows:

```rust
struct Document<'a> {
    text: &'a str,          // borrows text owned by someone else
}

impl<'a> Document<'a> {
    fn first_line(&self) -> &'a str {
        self.text.lines().next().unwrap_or("")
    }
}
```

Read `Document<'a>` as "a document that borrows something valid for `'a`". The `impl<'a>` mirrors
the `impl<T>` syntax from 4.2.

Notice the return type `&'a str`, not plain `&str`. With plain `&str`, rule 3 would tie the
result to `&self`, meaning "valid only while this `Document` value exists". But the line really
points into the original text, which lives longer than the `Document`. Writing `'a` tells the truth,
so this works:

```rust
let book = String::from("Chapter 1\nIt was a dark night.");
let line;
{
    let doc = Document { text: &book };
    line = doc.first_line();
}                         // doc is gone, but book (which line points into) is still alive
println!("{line}");       // fine with -> &'a str; an error with the elided -> &str
```

```
book (String, owner) ................................ alive throughout
  ^ borrowed by
doc: Document<'a> { text: &'a str }  ... short-lived view
line: &'a str ................................. points into book, not into doc
```

Why bother with borrowing structs at all? Because they let you work on a large piece of text
without copying it: you hand out slices that point into one owned `String`. The cost is that the
borrowing struct is tied to the owner. If that gets painful, a struct that owns its data (a `String`
field) has no lifetime parameter and is always an acceptable choice, especially while learning.

### `'static`
One lifetime has a reserved name: `'static`, meaning "valid for the entire run of the program".
String literals are `&'static str`, because the text is stored inside the compiled program itself
and never freed:

```rust
fn weekday(n: u8) -> &'static str {
    match n { 0 => "Mon", 1 => "Tue", _ => "other" }   // literals, so returning them is fine
}
```

You'll also see `T: 'static` as a bound, for example on thread functions. It doesn't mean "lives
forever"; it means "contains no borrowed references that could expire". A `String` or `Vec<i32>`
satisfies it because it owns everything.

When the compiler suggests adding `'static` to fix an error, be suspicious: usually the real fix is
to own the data or to shorten how long you keep the reference.

### The anonymous lifetime `'_`
In 4.1 you wrote `fmt::Formatter<'_>`. `'_` means "there's a lifetime here; infer it, I don't need
to name it". It's common in `impl` blocks and type names where a lifetime exists but isn't
interesting.

## Build
Use a new scratch crate (for example `cargo new lifetimes_practice`). For each error, read the
whole message before fixing; the arrows in it show you the lifetimes.

1. **Dangling on purpose.** Reproduce the "does not live long enough" example. Draw the lifetime
   bars on paper, then fix it in two ways: by moving the declaration, and by making `r` own a
   `String`.
2. **Annotate a function.** Write `shorter(a: &str, b: &str) -> &str`. Read E0106, add lifetimes,
   then write one caller that compiles and one that doesn't. Explain the failing one with the
   signature, not the body.
3. **Elision in practice.** Write `first_sentence(text: &str) -> &str` (up to the first `.`) and
   `longest_word(text: &str) -> &str`, with no annotations. For each, say which elision rule
   applies.
4. **Unconnected inputs.** Write `strip_prefix_or_self(text: &str, prefix: &str) -> &str` that
   returns `text` without `prefix` if it starts with it, otherwise `text`. Which input does the
   result borrow from? Annotate so that `prefix` can be a short-lived temporary `String`, and prove
   it with a caller.
5. **A borrowing struct.** Write `Book<'a> { text: &'a str }` with methods `chapters(&self) -> Vec<&'a str>`
   (split on lines starting with `"Chapter"`) and `word_count(&self) -> usize`. Show that the
   chapters can outlive the `Book` but not the `String`. Then change the return type to `Vec<&str>`
   and find the caller that breaks.
6. **Owned alternative.** Write `OwnedBook { text: String }` with the same methods. Write down two
   advantages and one cost compared with exercise 5.
7. **`'static`.** Write `weekday(n: u8) -> &'static str`. Then try to return `&format!(...)` from a
   function and read the error.
8. Rustlings: `16_lifetimes`.

## Check your understanding
1. Why can't a Rust reference keep its value alive the way a Python reference does?
2. "Lifetime annotations don't change how long anything lives." What do they do instead?
3. Why does the compiler need an annotation on `longer` but not on `first_word`?
4. In `Document<'a>`, why might `first_line` return `&'a str` rather than `&str`? What's the difference for a caller?
5. What does `'static` mean on a reference? What does `T: 'static` mean as a bound?
6. When would you choose a struct holding `String` over one holding `&'a str`?

## Common pitfalls
- Thinking an annotation can make a value live longer. If the owner is dropped, no `'a` can save
  the reference: restructure, or own the data.
- Adding `'static` to make an error disappear. It usually moves the problem somewhere worse.
- Trying to return a reference to a local variable. Return the owned value.
- Giving every parameter the same `'a` by reflex, which ties outputs to inputs they don't borrow from.
- Putting references in structs too early. Start with owned fields; borrow when you have a reason.
