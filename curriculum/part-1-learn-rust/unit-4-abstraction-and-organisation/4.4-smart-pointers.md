# Lesson 4.4 — Smart Pointers and Recursive Types
**Part:** 1 — Learn Rust · **Unit:** 4 — Abstraction and Organisation · **Type:** Learning · **Est. time:** 4–6 h · **Tests:** none
**Prerequisites:** lessons 1.1–3.5, 4.1–4.3 (especially 2.1 the stack and the heap)

## Overview
Some data is naturally recursive: a folder contains folders, a person has parents who are people.
In Python you build such structures without thinking. In Rust, a type that contains itself won't
compile until you add a pointer, and this lesson explains exactly why. You'll learn `Box` (one
owner, on the heap), `Rc` (shared ownership, like Python's reference counting) and `RefCell`
(mutation checked at runtime), and when each is worth its cost. Every syntax tree in your compiler
will be built from the `Box` and recursive-enum ideas in this lesson.

## The lesson

### Every type has a size known at compile time
Recall from 2.1: Python puts every object on the heap, and a variable is just a reference (a
pointer) to it. Rust stores values *directly*, inline, wherever they're declared: in a stack frame,
inside a struct, inside a `Vec`'s buffer. To lay out a stack frame or a struct, the compiler must
know how many bytes each type takes **before the program runs**.

For a struct, the size is (roughly) the sum of its fields. For an enum, it is the size of the
largest variant plus a small **tag** saying which variant is present. On a 64-bit machine:

```
struct Point { x: i32, y: i32 }        8 bytes:  [ x: 4 | y: 4 ]
String                                 24 bytes: [ ptr: 8 | len: 8 | capacity: 8 ]  (text on heap)
enum Shape { Dot, Circle(f64) }        16 bytes: [ tag | padding | f64: 8 ]
```
You can check any of these with `std::mem::size_of::<Point>()`.

### Why a type can't contain itself
Let's model a family tree, where each person may have a known mother:

```rust
struct Person {
    name: String,
    mother: Option<Person>,      // error[E0072]: recursive type `Person` has infinite size
}
```

Try computing the size. A `Person` holds a `String` (24 bytes) plus an `Option<Person>`, which
holds a whole `Person`, which holds another `Option<Person>`, which holds a whole `Person`...

```
size(Person) = 24 + size(Option<Person>)
             = 24 + tag + size(Person)
             = 24 + tag + 24 + tag + size(Person) = ... forever
```

There's no finite answer, so the compiler refuses. Python never hits this because `self.mother`
is a *reference* to another object somewhere on the heap: always 8 bytes, however big the mother
is. The fix in Rust is the same idea, made explicit: store a pointer instead of the value.

### `Box<T>`: a single owner on the heap
`Box<T>` is the simplest **smart pointer**: a pointer that also owns what it points to and does
extra work (here, freeing memory). `Box::new(value)` moves `value` onto the heap and gives you a
box, which is just one 8-byte pointer on the stack:

```rust
struct Person {
    name: String,
    mother: Option<Box<Person>>,   // fixed size: a box is always one pointer
}

let gran = Person { name: "Edith".into(), mother: None };
let mum  = Person { name: "Rose".into(),  mother: Some(Box::new(gran)) };
let me   = Person { name: "Ada".into(),   mother: Some(Box::new(mum)) };
```

```
stack                  heap
me: Person             +---------------------+      +----------------------+
 name: "Ada"           | Person              |      | Person               |
 mother: Some(ptr) --->|  name: "Rose"       |      |  name: "Edith"       |
                       |  mother: Some(ptr) -+----->|  mother: None        |
                       +---------------------+      +----------------------+
```

Now `size(Person) = 24 + 8 = 32` bytes. (The `Option` adds no tag here: a box can never be null,
so Rust uses the null value itself to mean `None`.)

What a `Box` gives you:
- **Ownership.** The box owns its contents. `me` owns Rose, who owns Edith. When `me` goes out of
  scope, Rust drops `me`, which drops Rose's box, which drops Edith's box: the whole chain is
  freed, in order, with no garbage collector. (This behaviour comes from the `Drop` trait.)
- **Transparent use.** `Box` implements the `Deref` trait, so `*b` gives the value inside, and
  method calls and field access see straight through it: `boxed_person.name` just works.

Walking the chain uses `Option` tools from 3.3. `as_deref()` turns an `&Option<Box<Person>>` into
an `Option<&Person>` (borrow the person, don't move it):

```rust
let mut current = Some(&me);
while let Some(p) = current {
    println!("{}", p.name);              // Ada, Rose, Edith
    current = p.mother.as_deref();
}
```

### Recursive enums: a file-system tree
Trees are usually enums: "this node is either a leaf or a branch with children". A file system:

```rust
enum Entry {
    File { name: String, bytes: u64 },
    Dir  { name: String, children: Vec<Entry> },
}
```

There's no `Box` here, and it compiles. Why? A `Vec<Entry>` is itself just pointer + length +
capacity (24 bytes); the entries live in a heap buffer. The `Vec` already provides the indirection.
You need `Box` only when the recursive field holds the type *directly* or in an `Option`, as in
`Person`, or in an enum variant like `Pair(Box<Node>, Box<Node>)`.

A tree like this is processed with recursion that mirrors its shape: one `match` arm per variant.
Leaf arms answer directly; branch arms recurse into the children and combine the answers:

```rust
fn count_dirs(e: &Entry) -> usize {
    match e {
        Entry::File { .. } => 0,
        Entry::Dir { children, .. } => 1 + children.iter().map(count_dirs).sum::<usize>(),
    }
}
```

The function takes `&Entry` because it only *looks* at the tree (taking `Entry` would consume it).
Matching on a reference gives references to the fields (`children` is a `&Vec<Entry>`), so nothing
is moved out. `{ .. }` means "ignore the other fields".

Trees built from `Box` and `Vec` have a simple, strict shape: every node has **exactly one owner**,
its parent. There's no sharing and there are no cycles. That fits a syntax tree perfectly, which
is why your compiler will need nothing more.

### When one owner isn't enough: `Rc<T>`
Back to the family tree. Two siblings have the *same* mother. With `Box`, each sibling would have
to own its own copy of her. What we want is **shared ownership**: the mother stays alive as long as
*anyone* still refers to her. That is exactly how Python manages every object (reference counting),
and Rust offers it opt-in as `Rc<T>` ("reference counted"):

```rust
use std::rc::Rc;

let rose = Rc::new(String::from("Rose"));
let ada_mum = Rc::clone(&rose);     // no copy of the string: just count += 1
let tom_mum = Rc::clone(&rose);
println!("{}", Rc::strong_count(&rose));   // 3
drop(tom_mum);                             // count -= 1  -> 2
```

```
stack                     heap (one allocation)
rose    --+          +--------------------------+
ada_mum --+--------->| strong count: 3          |
tom_mum --+          | value: "Rose"            |
                     +--------------------------+
```

When the count reaches zero, the value is dropped. Write `Rc::clone(&x)` rather than `x.clone()`
so readers can see it's a cheap count bump, not a deep copy. An `Rc` gives only **shared
(read-only)** access, since mutating would break the borrow rules while others might be reading.
`Rc` is also not thread-safe; its thread-safe twin is `Arc` (atomic reference count).

### Mutation behind shared pointers: `RefCell<T>`
The borrow rules (2.3) say: many readers *or* one writer. Usually the compiler proves this at
compile time. `RefCell<T>` moves the check to **runtime**: it keeps a counter of active borrows,
and `borrow()` / `borrow_mut()` check it each time. Breaking the rule doesn't fail to compile;
it **panics** (crashes with an error) while running:

```rust
use std::cell::RefCell;

let notes = RefCell::new(vec![String::from("first")]);
notes.borrow_mut().push(String::from("second"));   // fine: borrow ends at the semicolon
let reader = notes.borrow();
// notes.borrow_mut();  // would panic: "already borrowed: BorrowMutError"
println!("{}", reader.len());
```

This is called **interior mutability**: you can change the contents through a shared reference.
Combine the two and you get `Rc<RefCell<T>>`: shared *and* mutable. That's what every Python object
effectively is, with the safety checks done while the program runs:

```rust
let log = Rc::new(RefCell::new(Vec::<String>::new()));
Rc::clone(&log).borrow_mut().push("from a clone".into());   // any handle can write...
println!("{:?}", log.borrow());                             // ...and all see it: ["from a clone"]
```

### Cycles and `Weak<T>`
Suppose each person also lists their children with `Rc`, and each child points back to the parent
with `Rc`. Parent and child now keep each other's count above zero forever: a **reference cycle**,
and the memory is never freed (a leak). Python has an extra cycle-detecting garbage collector to
clean these up; Rust does not. The fix is `Weak<T>`: a pointer that doesn't count as ownership.
Make the "owning" direction (parent to child) `Rc`, and the back-pointer (child to parent) `Weak`.
`Rc::downgrade(&rc)` creates one; `weak.upgrade()` returns `Option<Rc<T>>`, which is `None` if the
value has already been dropped.

### Choosing: the trade-offs

| Tool | Owners | Mutation | Checked | Cost |
|---|---|---|---|---|
| plain value / `Vec` | one | via `&mut` | compile time | none |
| `Box<T>` | one | via `&mut` | compile time | one heap allocation |
| `Rc<T>` | many | none | compile time | allocation + count updates |
| `RefCell<T>` | one | through `&` | **runtime** (panics) | a borrow counter check per access |
| `Rc<RefCell<T>>` | many | yes | **runtime** | all of the above, and possible cycles |
| `Weak<T>` | none (observer) | via `upgrade` | runtime (`Option`) | as `Rc` |

Prefer the top of the table. `Rc<RefCell<T>>` everywhere feels comfortable after Python, but it
gives up the compile-time guarantees that are Rust's main benefit, and turns bugs into runtime
panics. Another common Rust approach for graphs is an **arena**: store all nodes in one `Vec` and
refer to them by index (`usize`), so there are no pointers to fight over at all.

## Build
Use a new scratch crate (for example `cargo new trees_practice`).

1. **Infinite size on purpose.** Write the `Person` struct with `mother: Option<Person>`. Read
   the error and run `rustc --explain E0072`. Fix it with `Box`. Print `size_of` for `String`,
   `Box<Person>`, `Option<Box<Person>>` and `Person`, and explain each number.
2. **Family tree with `Box`.** Build three or four generations by hand. Write `maternal_line(&Person) -> Vec<String>`
   and `generations(&Person) -> usize`. Then add an optional `father` too, and write
   `ancestor_count` (it becomes a real two-way tree, so recursion beats a loop).
3. **File-system tree.** Using the `Entry` enum (add whatever fields you like), build a small tree
   by hand and write: `total_bytes`, `count_files`, `depth`, `largest_file -> Option<(&str, u64)>`
   and `render`, which returns an indented listing like the `tree` command. Use `match` and
   iterators, and take `&Entry` everywhere.
4. **Sharing with `Rc`.** Two siblings share a mother. First try it with `Box` and see why it
   doesn't work without `.clone()`. Then switch the mother field to `Option<Rc<Person>>`. Print
   `Rc::strong_count` as siblings are created and dropped, and predict each number first.
5. **`RefCell`.** Make a guestbook, `Rc<RefCell<Vec<String>>>`, and give a handle to two `Visitor`
   structs, each with a `sign(&self, msg)` method. Note `&self`, not `&mut self`: explain why that
   compiles. Then cause a `BorrowMutError` panic on purpose and read the message.
6. *(Stretch)* Give each `Entry::Dir` a `Weak` link to its parent (you'll need `Rc<RefCell<...>>`
   for the children) and write `full_path`. Compare its complexity to exercise 3.
7. Rustlings: `19_smart_pointers`.

## Check your understanding
1. Why must Rust know every type's size at compile time, when Python doesn't care?
2. Why does `Option<Person>` inside `Person` fail, while `Vec<Entry>` inside `Entry` compiles?
3. Who frees the nodes of a `Box` tree, and when? What does Python do instead?
4. What problem does `Rc` solve that `Box` can't? Why is an `Rc` read-only?
5. What does `RefCell` check, when, and what happens if the check fails?
6. Why does a cycle of `Rc`s leak in Rust but not in Python, and how does `Weak` prevent it?

## Common pitfalls
- Boxing everything. Only the recursive link needs indirection, and `Vec` already provides it.
- Moving out of a borrowed tree ("cannot move out of ... which is behind a shared reference"):
  match on `&node` or use `as_ref()` / `as_deref()` instead of taking ownership.
- Confusing `Option<Box<T>>` ("maybe a child") with `Box<Option<T>>` (a heap allocation that may be empty).
- Holding a `borrow()` alive (for example, in a variable) while calling `borrow_mut()`: runtime panic.
- Reaching for `Rc<RefCell<T>>` when a plain owned tree would do.
