# Lesson 1.5 — Project: guessing game
**Part:** 1 — Learn Rust · **Unit:** 1 — Rust Basics for Python Programmers · **Type:** Project · **Est. time:** 4–6 h · **Tests:** none
**Prerequisites:** lessons 1.1–1.4

## Overview
Your first real Rust program: a number-guessing game. The computer picks a secret number, you
type guesses, and it tells you "too high" or "too low" until you get it. To build it you need
four new things, all taught below: reading a line from the keyboard, turning text into a number
(and handling text that isn't a number), using an external **crate** (a Rust library), and
comparing values. A compiler is, at heart, a program that reads input, parses it, and reacts to
bad input without crashing; this is that, in miniature.

## The lesson

### 1. Bringing names into scope with `use`
Rust's standard library (`std`) is organised into **modules**, like Python packages. To refer to
something you either write its full path or import it with `use`:
```rust
use std::io;              // like Python's `from std import io`

fn main() {
    let stdin = io::stdin();          // short name, thanks to `use`
    let also = std::io::stdin();      // full path works without `use`
}
```
`::` separates path segments, where Python uses `.` (`os.path.join` would be `os::path::join`).

### 2. Strings you can grow: `String`
So far your strings were **literals** (`"hello"`), which are fixed text baked into the program.
To hold text that arrives at run time, you need a `String`, an owned, growable piece of text:
```rust
let mut name = String::new();        // an empty String; `mut` because we'll add to it
name.push_str("Ada");
name.push('!');
println!("{}", name);                // Ada!
```
`String::new()` calls an **associated function** named `new` that belongs to the `String` type
(like a Python classmethod, `String.new()`). Exactly how `String` differs from a literal (`&str`),
and why, is the subject of 2.4. For now: user input goes into a `String`.

### 3. Reading a line from the keyboard
In Python, `input()` returns the line. In Rust:
```rust
use std::io;

fn main() {
    println!("What's your name?");
    let mut name = String::new();
    io::stdin()
        .read_line(&mut name)
        .expect("failed to read line");
    println!("Hello, {}!", name.trim());
}
```
Step by step:
- `io::stdin()` gets a handle to **standard input** (the keyboard, unless input is redirected).
- `.read_line(&mut name)` reads one line and **appends** it to `name`, *including the newline
  character* at the end. The `&mut` means "let `read_line` modify my `name` without taking it
  away from me". That's a **mutable reference**, explained fully in 2.3. For now, recognise the
  pattern.
- Reading can fail (say, the input isn't valid text). `read_line` returns a value of type
  `Result` that is either *success* or *an error*. `.expect("msg")` says: if it's an error,
  crash the program with this message; otherwise carry on. Crashing on purpose is called a
  **panic**. Fine for now; 3.3 teaches proper error handling.
- `.trim()` removes leading and trailing whitespace, including that newline (like Python's
  `.strip()`).

One gotcha: because `read_line` *appends*, reusing the same `String` in a loop without clearing
it (`name.clear()`) makes it accumulate every line typed. Creating a fresh `String` inside the
loop body also works.

### 4. Turning text into a number with `parse`
Python's `int("42")` either returns `42` or raises `ValueError`. Rust's equivalent is
`.parse()`, and it returns a `Result` instead of raising:
```rust
let text = "42";
let n: u32 = text.parse().expect("not a number");   // n == 42
```
`parse` can produce many types (`i32`, `f64`, `u8`, …), so you must tell it which, either with
an annotation on the variable (`n: u32`) or with the "turbofish" syntax `text.parse::<u32>()`.

`expect` would crash on bad input. To *handle* it instead, `match` on the `Result`. A `Result`
has two variants: `Ok(value)` for success and `Err(error)` for failure. You can match on them
like the patterns in 1.4, binding the inner value to a name:
```rust
let text = "12x";
match text.trim().parse::<i32>() {
    Ok(n) => println!("got the number {}", n),
    Err(_) => println!("'{}' isn't a whole number", text),
}
```
Here `parse` fails, so the `Err(_)` arm runs (`_` ignores the error details). Because `match` is
an expression, you can also use it to produce a value, and an arm can `continue` or `break` out
of an enclosing loop instead of producing one. Full treatment of `Result` is in 3.3; this much
is all you need now.

### 5. External crates and `Cargo.toml`
Rust's standard library deliberately has no random-number generator. Instead you use a
**crate** (Rust's word for a package or library) from <https://crates.io>, like using `pip` to
install from PyPI. The standard one is `rand`.

Add it from your project folder:
```
$ cargo add rand
```
This edits `Cargo.toml`, adding a line under `[dependencies]` like `rand = "0.9.x"`. The next
`cargo build` downloads it, compiles it, and records the exact version in `Cargo.lock` (like a
pinned `requirements.txt`) so builds are reproducible.

How do you learn a crate's API? Every crate has documentation on <https://docs.rs>. Open
`docs.rs/rand`, check that the version matches what's in your `Cargo.toml`, and look for a
function that produces a random number **in a range**. The API changed between versions 0.8 and
0.9 (function names differ), so read the docs for *your* version rather than copying an old blog
post. Running `cargo doc --open` builds docs for all your dependencies locally, too. Learning to
read docs.rs is a skill you'll use for the rest of the course.

### 6. Comparing values
You can compare with `<`, `>` and `==` in an `if`/`else if` chain. Rust also offers a neater
way: every number has a `.cmp(&other)` method that returns a value of type
`std::cmp::Ordering`, which is one of `Ordering::Less`, `Ordering::Greater` or `Ordering::Equal`.
Because there are exactly three possibilities, it's perfect for an exhaustive `match`:
```rust
use std::cmp::Ordering;

let age = 20;
match age.cmp(&18) {
    Ordering::Less => println!("minor"),
    Ordering::Equal => println!("just turned adult"),
    Ordering::Greater => println!("adult"),
}
```
No `_` arm needed: the compiler knows these three cover everything. (The `&` in `&18` is a
reference; 2.3 explains it.) Note that both sides of a comparison must have the same type: you
can't compare a `u32` with an `i64` without converting.

### 7. Program structure: think before typing
Before writing the game, sketch it in plain words or Python-like pseudocode: what happens once
at the start, what repeats, what ends the loop, and what happens on bad input. Then write the
Rust in small steps, running it after each. That habit (small steps, run often, let the compiler
guide you) is exactly how you'll build the compiler in Part 3.

## Build
Create the project with `cargo new guessing-game`. Write all the code yourself; ask the tutor
for hints (concept → docs → approach in words), not code.

**Specification**
1. On start, print a welcome line explaining the game and the range: **1 to 100 inclusive**.
2. Pick a secret random whole number in that range using the `rand` crate.
3. Repeatedly:
   - prompt for a guess and read one line from standard input;
   - ignore leading/trailing whitespace;
   - if the input is not a whole number, print a friendly message (including what was typed)
     and ask again, **without** counting it as a guess and **without** crashing;
   - if the number is outside 1–100, say so and ask again, also not counted;
   - otherwise compare it to the secret: print `Too small!`, `Too big!`, or on a match, print
     `You win!` with the number of valid guesses it took, and end the program.
4. If the user types `quit` (any capitalisation), print the secret number and exit.
5. If standard input ends (Ctrl-D, or `read_line` reads 0 bytes), exit politely instead of looping forever.

**Suggested order of small steps**
1. Read one line and echo it back, trimmed.
2. Parse it as a number, crashing on bad input with `expect`. Then replace that with a `match` that handles both cases.
3. Hard-code a secret (e.g. 42) and compare with a `match` on `Ordering`. Wrap it in a `loop`.
4. Add the guess counter, the range check and `quit`.
5. Only now add `rand` and replace the hard-coded secret. Check the docs.rs page for your version.
6. Handle end of input (hint: `read_line` returns how many bytes it read).

**Stretch goals (optional)**
- After winning, ask "Play again? (y/n)".
- Let the user choose the range's upper bound at start (validate it).
- Track the best score across rounds in one session.

## Check your understanding
1. Why does `read_line` take `&mut` your `String` rather than returning a new one? What would go wrong if you reused the `String` without clearing it?
2. Why does `"42\n".parse::<u32>()` fail, and what fixes it?
3. What does `.expect()` do, and why is it the wrong tool for a user typing "abc"?
4. What's the difference between `Cargo.toml` and `Cargo.lock`?
5. Why doesn't your `match` on `Ordering` need a `_` arm?

## Common pitfalls
- **Forgetting `.trim()`**: the trailing newline makes every `parse` fail.
- **Accumulating input** in one `String` across loop iterations without `clear()`.
- **Type mismatches** between the guess and the secret (e.g. `u32` vs. `i32`). Pick one type.
- **Copying old `rand` examples**: `thread_rng`/`gen_range` are from 0.8; check the docs for your version.
- **Counting invalid input as a guess.** Re-read the spec.
