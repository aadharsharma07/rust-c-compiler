# Lesson 1.1 — How Rust differs from Python
**Part:** 1 — Learn Rust · **Unit:** 1 — Rust Basics for Python Programmers · **Type:** Learning · **Est. time:** 2–3 h · **Tests:** none
**Prerequisites:** none (comfortable Python)

## Overview
Before writing much Rust, you need a mental model of what is different about it. This lesson
explains three big ideas (compiling ahead of time, static typing, and memory management without
a garbage collector), then installs the Rust toolchain and walks you through creating, building
and running your first program, and reading your first compiler error. It matters for the road
ahead because you are about to spend months *using* a compiler (`rustc`) before you *write* one.

## The lesson

### 1. Running Python vs. compiling Rust
When you type `python hello.py`, a program called the **interpreter** (CPython) starts up, reads
your source file, and runs it right then. Under the hood CPython first turns your text into
**bytecode** (simple instructions for CPython's own virtual machine; you'll look at it in Part 2),
then a loop inside CPython executes that bytecode one instruction at a time. Your `.py` file is
never turned into something the CPU can run directly. The interpreter has to be present every
time, and errors like a misspelled variable are only found when that line actually runs.

Rust works differently. A **compiler** (`rustc`) reads your whole program *ahead of time* and
translates it into **machine code**: the raw numeric instructions your CPU executes directly.
The result is an **executable** file, a standalone program.

```
Python:   hello.py ──► python (reads + runs, every time) ──► output

Rust:     main.rs  ──► rustc (once) ──► hello (executable)
                                         │
                       ./hello  ─────────┘ ──► output   (no rustc needed to run it)
```

Two consequences you will feel immediately:
- **Errors move earlier.** Many mistakes Python reports at runtime (or never) are rejected by
  `rustc` before the program exists. The compiler is strict, but every error it catches is a bug
  your users never see.
- **Speed.** No interpreter loop sits between your program and the CPU, so Rust typically runs
  10–100× faster than equivalent Python. (Your C compiler will make executables the same way.)

The words to remember: **compile time** is when `rustc` runs; **run time** is when your
executable runs. Keep asking yourself "is this checked at compile time or run time?".

### 2. Static typing vs. dynamic typing
In Python, *values* have types, but *names* don't. This is legal:

```python
x = 5          # x refers to an int
x = "five"     # now x refers to a str; Python doesn't mind
def double(n):
    return n * 2
double("ab")   # "abab" -- works, maybe by accident
```

Python checks types **dynamically**: only when an operation runs does it look at the value and
decide whether `*` makes sense. That's flexible, but a wrong type is only discovered when that
exact line runs with that exact value.

Rust is **statically typed**: every variable and expression has one type, fixed and known at
compile time. The compiler checks every operation against those types before the program runs.

```rust
fn double(n: i32) -> i32 {   // n must be an i32 (32-bit integer); result is an i32
    n * 2
}

fn main() {
    let x = 5;               // Rust infers x: i32
    println!("{}", double(x));
    // double("ab");         // would not compile: expected `i32`, found `&str`
}
```

Notice you didn't have to write the type of `x`: Rust **infers** it. Static typing doesn't mean
writing types everywhere; it means the compiler always knows them. If you've used Python type
hints with `mypy`, it's similar, except in Rust the check is mandatory and the compiler uses the
types to generate fast machine code (it knows `x` is exactly 4 bytes holding an integer).

### 3. Memory without a garbage collector
Every value your program creates (a list, a string, an object) needs some memory, and that
memory must be given back when the value is no longer needed, or the program slowly eats all
your RAM (a **memory leak**).

Python handles this for you. Every object carries a **reference count**: how many names or
containers point at it. When the count drops to zero, CPython frees it. A separate **garbage
collector** (GC) runs occasionally to find groups of objects that point at each other but that
nothing else can reach. You never think about it, at the cost of some speed and memory, and of
not knowing exactly *when* memory is freed.

Languages like C go the other way: the programmer frees memory by hand. That's fast, but humans
make mistakes: freeing too early (then using it: a **use-after-free**), freeing twice, or
forgetting. These bugs cause crashes and a large share of real-world security holes.

Rust takes a third path. It has **no garbage collector and no manual freeing**. Instead, the
compiler tracks which variable **owns** each value, and inserts the "free this" step at exactly
the point where the owner goes away. Rules checked at compile time guarantee you can never use
memory after it's freed. You get C's speed and predictability with Python's safety. The price is
learning those rules, which is what Unit 2 is about. For now, just know that when the compiler
complains about "moved" or "borrowed" values, this is the system at work.

### 4. Installing the toolchain
Rust is installed with **rustup**, a tool that installs and updates Rust versions. It gives you:
- `rustc`: the compiler itself.
- `cargo`: Rust's build tool and package manager (think `pip` + a project runner in one).
- `rustup`: the installer/updater.

On macOS or Linux, run the command shown on <https://rustup.rs> (it is
`curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh`) and accept the defaults. On
macOS, `rustc` needs a **linker** (the tool that glues compiled pieces into an executable), which
comes with Apple's command-line tools: run `xcode-select --install` if you haven't already.
Open a new terminal and check:

```
$ rustc --version
rustc 1.xx.0 (...)
$ cargo --version
cargo 1.xx.0 (...)
```

### 5. Your first project with cargo
You will almost never call `rustc` directly. Cargo calls it for you.

```
$ cargo new hello
    Creating binary (application) `hello` package
$ cd hello
```

Cargo created:
```
hello/
├── Cargo.toml      # project settings: name, version, edition, dependencies
├── .gitignore      # ignores target/
└── src/
    └── main.rs     # your program's source code
```

`src/main.rs` contains:
```rust
fn main() {
    println!("Hello, world!");
}
```
- `fn main()` defines a function named `main`. Every Rust executable starts running at `main`
  (Python just runs the file top to bottom; Rust needs this entry point).
- The curly braces `{ }` mark the body. Rust uses braces, not indentation, for blocks
  (indent anyway; `cargo fmt` will do it for you).
- `println!` prints a line. The `!` means it's a **macro**, not a function: code that expands
  into more code at compile time. For now just treat `println!` as "Rust's `print`".
- Statements end with `;`.

The four cargo commands you'll use constantly:

| Command | What it does | Python analogy |
|---|---|---|
| `cargo check` | Type-checks your code, reports errors, produces **no** executable. Fastest. | running `mypy` |
| `cargo build` | Compiles to `target/debug/hello`. | (none) |
| `cargo run` | Builds if anything changed, then runs it. | `python hello.py` |
| `cargo build --release` | Compiles with optimisations into `target/release/`. Slower build, faster program. | (none) |

Try `cargo run`, then run the executable directly with `./target/debug/hello`. That second step
is the point: the executable exists on its own, no cargo or rustc involved.

### 6. Reading your first compiler error
Change `main.rs` to:
```rust
fn main() {
    let count: i32 = "three";
    println!("{}", count);
}
```
`cargo check` prints something like:
```
error[E0308]: mismatched types
 --> src/main.rs:2:22
  |
2 |     let count: i32 = "three";
  |                ---   ^^^^^^^ expected `i32`, found `&str`
  |                |
  |                expected due to this
```
Read it top to bottom:
1. **`error[E0308]: mismatched types`**: the kind of error and its code. Run
   `rustc --explain E0308` for a full explanation with examples.
2. **`--> src/main.rs:2:22`**: file, line 2, column 22.
3. **The snippet**: `^^^^^^^` underlines the problem ("found `&str`", a string literal) and
   `---` underlines the *reason* ("expected due to this": you said `i32`).

Rust's errors are famously helpful; they often end with a `help:` line suggesting a fix. Get in
the habit of reading the *whole* message, not just the first line. The tutor will help you
translate each new error into "which rule did I break?".

## Build
Work in a folder of scratch projects, e.g. `~/projects/rust-scratch/`.
1. Install Rust with rustup. Record the output of `rustc --version` and `cargo --version`.
2. `cargo new hello`, then `cargo run`. Find the executable under `target/debug/` and run it directly.
3. Run `cargo build --release` and compare the sizes of `target/debug/hello` and
   `target/release/hello` (`ls -lh`). Note which is smaller.
4. Change the message to print three lines: your name, the language you know, and why you're
   learning Rust. Use three `println!` calls.
5. `println!` can insert values: `println!("{} + {} = {}", 2, 3, 2 + 3);`. Print a line that
   uses `{}` at least twice.
6. **Break it on purpose**, one at a time, run `cargo check` after each, and read the full error:
   - delete a semicolon;
   - misspell `println!` as `printn!`;
   - remove the `!` from `println!`;
   - assign a string literal to a variable annotated `: i32` (as above).
   For each, write one sentence in your notes: what the error said, and what rule it enforced.
   Look up one error code with `rustc --explain`.
7. Write `hello.py` with a deliberate type error on a line that only runs inside an `if` that is
   false (e.g. `if False: print(1 + "a")`). Run it: no error. Now explain in your notes why the
   equivalent mistake can't sneak past `rustc`.

## Check your understanding
1. What exactly does `rustc` produce, and why don't you need Rust installed to *run* it?
2. What's the difference between `cargo check`, `cargo build` and `cargo run`? When would you use each?
3. In your own words: what does "statically typed" mean, and how is type inference different from dynamic typing?
4. Python, C and Rust each free memory differently. Describe all three in one sentence each.
5. In an error message, what do the `^^^` and `---` markers point at?

## Common pitfalls
- **Ignoring the rest of the error message.** The first line says *what*; the snippet and
  `help:` lines say *where* and *how to fix it*.
- **Running `rustc main.rs` by hand** inside a cargo project. Use cargo; it handles dependencies and flags.
- **Expecting indentation to matter.** Braces and semicolons define structure in Rust.
- **Forgetting the `!`** on `println!`. It's a macro, not a function.
- **Missing linker on macOS** (`linker 'cc' not found`): install the Xcode command-line tools.
