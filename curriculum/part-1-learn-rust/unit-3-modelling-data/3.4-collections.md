# Lesson 3.4 — Collections
**Part:** 1 — Learn Rust · **Unit:** 3 — Modelling Data · **Type:** Learning · **Est. time:** 3–5 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.5, 3.1–3.3

## Overview
Python's `list`, `dict` and `set` have Rust counterparts: `Vec<T>`, `HashMap<K, V>` and
`HashSet<T>`. They do the same jobs, but every element has one fixed type, ownership decides
who may change the collection, and "this key might not be there" is an `Option` rather than a
`KeyError`. You'll also meet the **entry API**, Rust's tidy answer to "insert if missing, else
update". A compiler leans on these constantly: a `Vec` of tokens, a `Vec` of instructions, a
`HashMap` from variable names to their information, a `HashSet` of names already used.

## The lesson

### `Vec<T>`: Python's list, with one element type
```rust
let mut scores: Vec<u32> = Vec::new();
scores.push(90);
scores.push(72);
let primes = vec![2, 3, 5, 7];        // the vec! macro, like a list literal
println!("{} items, first {}", primes.len(), primes[0]);
```

The `<u32>` says every element is a `u32`. Python's `[1, "two", 3.0]` has no direct equivalent;
when you genuinely need mixed kinds, use a `Vec` of an enum from 3.2 (`Vec<Event>`), which is
usually a clearer design anyway.

In memory, a `Vec` is the same three-word header as a `String` (2.4), because a `String` *is* a
`Vec<u8>` underneath:

```
 a Vec holding 2, 3, 5, 7 with room for 6 (e.g. built with Vec::with_capacity(6) + 4 pushes)

 stack                             heap
 +-----------------+               +---+---+---+---+---+---+
 | ptr  ---------- | ------------> | 2 | 3 | 5 | 7 | . | . |
 | len      = 4    |               +---+---+---+---+---+---+
 | capacity = 6    |                 elements stored inline, one after another
 +-----------------+
```

The elements are stored directly, side by side. A Python list instead holds an array of
*pointers* to separate integer objects on the heap. When `push` runs out of capacity, the `Vec`
allocates a bigger block (roughly double), copies the elements over and frees the old block, just
as a Python list does internally. `Vec::with_capacity(n)` pre-allocates if you know the size.

### Reading elements: indexing panics, `get` doesn't
```rust
let v = vec![10, 20, 30];
let a = v[1];          // 20
let b = v[99];         // panics: index out of bounds (like Python's IndexError, but a crash)
let c = v.get(99);     // None: an Option<&i32>, no crash
if let Some(x) = v.get(1) { println!("{x}"); }
```

Use `v[i]` when an out-of-range index would be a bug in your code; use `v.get(i)` when the index
comes from outside (user input, a file) and might be wrong. That's the panic-vs-`Result` rule from
3.3 again. Negative indices don't exist (indices are `usize`, which can't be negative); use
`v.last()` for Python's `v[-1]`, and slices `&v[1..3]` for `v[1:3]` (recall slices from 2.4).

Other everyday methods: `pop()` (returns `Option<T>`), `insert(i, x)`, `remove(i)`,
`contains(&x)`, `sort()`, `reverse()`, `is_empty()`, `extend(…)`, `clear()`. Floats can't be
sorted with plain `sort()`, because `NaN` breaks ordering; that's a known Rust surprise.

### Ownership meets collections
A collection **owns** its elements. Pushing a value moves it in:

```rust
let name = String::from("Ada");
let mut names = Vec::new();
names.push(name);
// println!("{name}");   // error: `name` was moved into the vector
```

There are three ways to loop over a `Vec`, matching `&self`, `&mut self` and `self` from 3.1:

```rust
for n in &names { println!("{n}"); }          // borrow each element: n is &String
for n in &mut names { n.push('!'); }          // mutably borrow each: n is &mut String
for n in names { consume(n); }                // move each element out; `names` is gone afterwards
```

`for n in names` (without `&`) is a common beginner surprise: it consumes the vector. Default to
`&names`.

The borrow rules (2.3) also stop a classic bug. This compiles in Python and misbehaves:

```python
for x in items:
    if x < 0:
        items.append(0)    # mutating a list while iterating over it
```

In Rust, the loop holds a shared borrow of `items` while `push` needs an exclusive one, so the
compiler rejects it. Similarly, holding `let first = &v[0];` and then calling `v.push(…)` is an
error: the push might reallocate the buffer and leave `first` pointing at freed memory. Python
doesn't have that danger (it keeps the object alive); C has it and doesn't check; Rust has it and
checks.

### `HashMap<K, V>`: Python's dict
```rust
use std::collections::HashMap;   // not in scope by default, unlike Vec

let mut capitals: HashMap<String, String> = HashMap::new();
capitals.insert(String::from("France"), String::from("Paris"));
capitals.insert(String::from("Japan"), String::from("Tokyo"));

match capitals.get("France") {          // returns Option<&String>
    Some(city) => println!("{city}"),
    None => println!("unknown"),
}
```

Differences from Python's `dict` worth remembering:
- **Lookups return `Option`.** `map.get(&k)` gives `Option<&V>`; there's no `KeyError`.
  `map[&k]` exists but panics on a missing key, like `v[99]`.
- **`insert` returns the old value** as `Option<V>`, so you can tell whether you overwrote something.
- **No guaranteed order.** Python dicts remember insertion order; a Rust `HashMap` iterates in an
  arbitrary order that can change between runs. If you need sorted keys, use
  `std::collections::BTreeMap` (same API, kept sorted), or collect and sort the keys.
- **Ownership of keys and values.** Inserting a `String` key moves it into the map. You can look
  up with a `&str` even though keys are `String`, which is why `get("France")` works.
- **Key types** must be hashable and comparable. Strings, integers, `char`, `bool` and tuples of
  them work. For your own struct or enum, add `#[derive(PartialEq, Eq, Hash)]`. Floats can't be
  keys, for the same `NaN` reason.

Other methods: `contains_key(&k)`, `remove(&k)` (returns `Option<V>`), `len()`, `keys()`,
`values()`, and iteration: `for (country, city) in &capitals { … }`.

### The entry API: insert-or-update in one step
A frequent pattern is "if the key is missing, insert a starting value; then update it". In Python
you'd use `dict.setdefault` or `collections.defaultdict`:

```python
by_team = {}
for name, team in players:
    by_team.setdefault(team, []).append(name)
```

The naive Rust translation (check `contains_key`, then `insert`, then `get_mut`) looks the key up
three times and fights the borrow checker. The **entry API** does it in one lookup:

```rust
let mut by_team: HashMap<&str, Vec<&str>> = HashMap::new();
for (name, team) in [("Ana", "red"), ("Bo", "blue"), ("Cy", "red")] {
    by_team.entry(team).or_insert(Vec::new()).push(name);
}
// {"red": ["Ana", "Cy"], "blue": ["Bo"]}   (in some order)
```

Step by step:
1. `by_team.entry(team)` finds the slot for that key and returns an `Entry`, which is (you guessed
   it) an enum: `Occupied` or `Vacant`.
2. `.or_insert(Vec::new())` inserts the value if vacant, then in both cases returns a
   `&mut Vec<&str>`: a mutable reference to the value now in the map.
3. `.push(name)` modifies that value in place.

For numbers, you change the value through the reference with `*` (the **dereference** operator:
"the thing this reference points at"), for example `*map.entry(k).or_insert(0) += 5;`. Related
methods: `.or_default()` inserts the type's default (`0`, empty `Vec`, empty `String`), and
`.or_insert_with(|| …)` builds the value only when needed. You can also `match` on the `Entry`
directly when the two cases need different logic.

### `HashSet<T>`: Python's set
```rust
use std::collections::HashSet;

let mut seen: HashSet<String> = HashSet::new();
let first_time = seen.insert(String::from("x"));    // true: newly added
let again = seen.insert(String::from("x"));         // false: already there
println!("{}", seen.contains("x"));                 // true
```

`insert` returning a `bool` makes "have I seen this before?" a one-liner. Set operations exist as
methods: `a.union(&b)`, `a.intersection(&b)`, `a.difference(&b)`, `a.is_subset(&b)`. They return
iterators (4.3); for now, loop over them with `for`. Like `HashMap`, a `HashSet` has no order;
`BTreeSet` is the sorted version.

### Which one?
| Need | Python | Rust |
|---|---|---|
| Ordered sequence, index access, push to the end | `list` | `Vec<T>` |
| Push/pop at both ends (a queue) | `collections.deque` | `VecDeque<T>` |
| Key → value lookup | `dict` | `HashMap<K, V>` (`BTreeMap` if you need sorted keys) |
| Membership, no duplicates | `set` | `HashSet<T>` (`BTreeSet` if sorted) |

When unsure, start with `Vec`. For small sizes, a linear search through a `Vec` is often as fast
as a hash map.

## Build
Make a scratch crate (`cargo new collections_practice`). Test everything; for maps, test by
looking up specific keys, not by printing the whole map (its order isn't fixed).

1. **Vec warm-up.** Write `fn stats(nums: &[i64]) -> Option<(i64, i64, f64)>` returning min, max
   and mean, or `None` for an empty slice. Don't use iterator adapters yet; use a `for` loop.
2. **Remove duplicates, keep order.** Write `fn dedup_keep_order(words: &[&str]) -> Vec<String>`
   using a `HashSet` to remember what you've seen. `["b","a","b","c","a"]` → `["b","a","c"]`.
3. **Letter frequencies.** Write `fn letter_counts(text: &str) -> HashMap<char, usize>` counting
   only alphabetic characters, case-insensitively, using the entry API. Then write a function
   returning the top 3 letters, ties broken alphabetically (collect into a `Vec` and sort).
4. **Invert a map.** Given a `HashMap<String, String>` of student → house, build a
   `HashMap<String, Vec<String>>` of house → sorted list of students.
5. **Inventory.** A `HashMap<String, u32>` of item → quantity. Write `add(&mut map, item, n)` and
   `remove(&mut map, item, n) -> Result<(), StockError>` where `StockError` (an enum, as in 3.3)
   distinguishes "unknown item" from "not enough stock" (carry how many there are). Removing the
   last unit should delete the key.
6. **Borrow-checker tour.** Write the "push while iterating" loop and the "hold `&v[0]` then
   push" code. Read both errors and explain to your tutor what bug each one prevents.
7. Rustlings: `05_vecs`, `11_hashmaps`.

## Check your understanding
1. Why does `v.get(i)` return an `Option` while `v[i]` can panic? When would you choose each?
2. What's the difference between `for x in v`, `for x in &v` and `for x in &mut v`?
3. Why won't Rust let you push to a `Vec` while holding a reference to one of its elements? What
   could go wrong in memory?
4. What does `entry(k).or_insert(0)` return, and why can you modify the map through it?
5. Your program prints a `HashMap` and the order changes between runs. Is that a bug? What would
   you use if order mattered?

## Common pitfalls
- Forgetting `use std::collections::HashMap;` (or `HashSet`). `Vec` is always in scope; they aren't.
- Looping with `for x in v` and then finding `v` has been moved.
- Writing tests that depend on `HashMap` iteration order.
- Indexing with an `i32` (`v[i]` needs a `usize`). Convert carefully, or use `usize` from the start.
- Forgetting the `*` when updating a number through `or_insert`'s `&mut`.
