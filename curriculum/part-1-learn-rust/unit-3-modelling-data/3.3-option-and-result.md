# Lesson 3.3 — Option, Result and error handling
**Part:** 1 — Learn Rust · **Unit:** 3 — Modelling Data · **Type:** Learning · **Est. time:** 4–6 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.5, 3.1, 3.2

## Overview
Python has two ways of saying "there's no answer": returning `None`, and raising an exception.
Both are invisible in a function's signature, so you find out about them at runtime, usually in a
traceback. Rust has neither. Instead it uses two ordinary enums from lesson 3.2: `Option` for
"maybe a value" and `Result` for "a value, or the reason it failed". This lesson shows how to use
them, how the `?` operator keeps them tidy, how to design your own error types, and when crashing
with `panic!` is the right call. A compiler mostly processes *wrong* programs, so clear, typed
errors are part of its job.

## The lesson

### Two Python problems
**The `None` surprise.** In Python, any variable might be `None`:

```python
user = find_user("ada")       # returns a User... or None
print(user.email)             # AttributeError: 'NoneType' object has no attribute 'email'
```

Nothing in `find_user`'s signature forced you to check. Tony Hoare, who invented the null
reference, later called it his "billion-dollar mistake".

**The invisible exception.** `int("abc")` raises `ValueError`. `open(path)` raises
`FileNotFoundError`. Neither fact appears where you call them. To know what can go wrong you read
documentation, or wait for a crash. Exceptions also jump: an exception raised five calls deep
skips every function in between, so reading a function doesn't tell you where its control flow
can leave.

Rust's approach: **absence and failure are values, and their possibility is part of the type.**

### `Option<T>`: maybe a value
`Option` is defined in the standard library as a plain enum:

```rust
enum Option<T> {
    Some(T),   // there is a value, of type T
    None,      // there isn't
}
```

The `<T>` makes it **generic**: `T` is a placeholder for any type, so `Option<i32>` is "maybe an
`i32`" and `Option<String>` is "maybe a `String`". (Unit 4.2 covers generics; for now read
`Option<T>` as "Option of T".) `Option`, `Some` and `None` are always in scope; you don't import
them.

The key fact: **an `Option<i32>` is not an `i32`.** You cannot add one to a number, or call
`String` methods on an `Option<String>`. The compiler forces you to handle `None` first:

```rust
fn first_even(nums: &[i32]) -> Option<i32> {
    for &n in nums {
        if n % 2 == 0 { return Some(n); }
    }
    None
}

match first_even(&[3, 5, 8]) {
    Some(n) => println!("found {n}"),
    None => println!("no even numbers"),
}
```

And since a plain `i32` can never be `None`, you never need to check it. Rust has no null at all:
if a type doesn't say `Option`, the value is always there.

Many standard methods return `Option`: `vec.get(i)` (index may be out of range), `vec.first()`,
`s.find('x')`, `iter.next()`, `map.get(&key)` (3.4).

### `Result<T, E>`: a value or a reason
For operations that can *fail* (rather than just come up empty), Rust uses:

```rust
enum Result<T, E> {
    Ok(T),     // success, carrying the value
    Err(E),    // failure, carrying an error value of type E
}
```

`str::parse` is a good example:

```rust
let r: Result<i32, std::num::ParseIntError> = "42".parse();
match "4x2".parse::<i32>() {
    Ok(n) => println!("number {n}"),
    Err(e) => println!("bad number: {e}"),   // "invalid digit found in string"
}
```

(`::<i32>` is called the "turbofish"; it tells `parse` which type to produce, when nothing else
does.)

Compare with Python's `int("4x2")`. Same information, but here the failure is in the type:
`parse` *says* it can fail, and you cannot get at the `i32` without deciding what to do about
`Err`. If you call a function returning `Result` and ignore the value completely, the compiler
warns you ("unused `Result` that must be used").

### Getting the value out: the toolbox
`match` always works, but writing it every time is heavy. Common shortcuts, on both types:

| Method | On `Some(v)` / `Ok(v)` | On `None` / `Err(e)` |
|---|---|---|
| `.unwrap()` | gives `v` | **panics** (crashes) |
| `.expect("msg")` | gives `v` | panics with your message |
| `.unwrap_or(default)` | gives `v` | gives `default` |
| `.is_some()` / `.is_ok()` | `true` | `false` |
| `.ok_or(err)` (Option only) | `Ok(v)` | `Err(err)`: turns absence into failure |
| `.ok()` (Result only) | `Some(v)` | `None`: throws the error away |

Methods like `.map(…)`, `.map_err(…)` and `.unwrap_or_else(…)` take a **closure** (a small inline
function, like a Python `lambda`). Their syntax is `|arg| expression`, for example
`r.map_err(|e| e.to_string())`. Closures are covered properly in 4.3; this one form is all you need now.

### The `?` operator: propagating failure
Often a function can't sensibly handle an error itself and should pass it up to its caller. In
Python, that happens automatically: you don't catch the exception, and it flies upward. In Rust
you do it explicitly, but with one character:

```rust
fn add_strings(a: &str, b: &str) -> Result<i32, std::num::ParseIntError> {
    let x = a.parse::<i32>()?;
    let y = b.parse::<i32>()?;
    Ok(x + y)
}
```

`expr?` means: "if this is `Ok(v)`, give me `v` and carry on; if it's `Err(e)`, **return**
`Err(e)` from the current function right now". So `a.parse::<i32>()?` is shorthand for:

```rust
match a.parse::<i32>() {
    Ok(v) => v,
    Err(e) => return Err(e.into()),   // .into() converts the error type if needed (see below)
}
```

This gives you the convenience of exceptions (errors bubble up with almost no code) while keeping
them visible: every place that can fail is marked with `?`, and the signature says
`Result`. Reading the function, you can see every exit.

Rules:
- `?` only works inside a function whose return type is a `Result` (or `Option`, for `?` on
  `Option`, where it returns `None` early). Using it in a function returning `()` is an error.
- `main` can return a `Result`: `fn main() -> Result<(), String> { … }`. If it returns `Err`,
  Rust prints the error and exits with a non-zero status.

### Designing your own error type
A function that can fail in several different ways needs an error type that says *which* way. A
`String` works for quick experiments (`Err(format!("bad port: {s}"))`), but callers can't
distinguish errors except by comparing text, and tests become fragile. The Rust way is an
**error enum**, exactly the tool from 3.2:

```rust
#[derive(Debug, PartialEq)]
enum PortError {
    Empty,
    NotANumber(String),     // carries the offending text
    OutOfRange(u32),        // carries the bad value
}

fn parse_port(s: &str) -> Result<u16, PortError> {
    let s = s.trim();
    if s.is_empty() {
        return Err(PortError::Empty);
    }
    let n: u32 = s.parse().map_err(|_| PortError::NotANumber(s.to_string()))?;
    if n == 0 || n > 65535 {
        return Err(PortError::OutOfRange(n));
    }
    Ok(n as u16)
}
```

Now a caller can `match` on the error to react differently to each case, and a test can say
`assert_eq!(parse_port("99999"), Err(PortError::OutOfRange(99999)))`. Errors carry **data**
(the bad text, the bad value) so the message shown to a human can be precise. Later, your
compiler's errors will carry the line and column of the problem in the same way.

To turn an error into a human message, write a method such as `fn message(&self) -> String` that
`match`es on `self`. (In 4.1 you'll implement the `Display` trait instead, which lets `{}` print
it. The idea is the same.)

**Converting between error types.** If your function returns `Result<_, PortError>` and calls
something returning `Result<_, ParseIntError>`, the error types don't match. Two fixes:
- `.map_err(|e| …)?` converts this one call, as shown above. Simple and explicit.
- Teach Rust a general conversion with `impl From<ParseIntError> for PortError { … }`. Then plain
  `?` converts automatically, because it calls `.into()`. This uses traits (4.1); `map_err` is
  enough for this unit.

### Option or Result?
- `Option` when absence is a normal, unsurprising outcome and needs no explanation: "the first
  even number" (maybe there isn't one), "look up this key".
- `Result` when something *went wrong* and the caller might want to know why: parsing, reading a
  file, validating input.
- Converting is easy: `.ok_or(MyError::Missing)` when absence becomes an error at a higher level.

### `panic!`: when crashing is correct
`panic!("message")` stops the program (more exactly, the current thread): it prints the message
and location and unwinds the stack, dropping values as it goes. `unwrap`, `expect`, out-of-range
indexing like `v[99]`, and integer division by zero all panic. It's the closest thing Rust has to
an uncaught Python exception, but you are not meant to catch it.

The rule of thumb:
- **`Result`** for things that can go wrong because of the outside world or the user: bad input,
  missing files, network failures. These are *expected* and the program should report them
  nicely.
- **`panic!`** for **bugs**: situations that would mean your own code is wrong, where continuing
  could only produce nonsense. For example, an internal function called with a value that every
  caller has already checked. Python's `assert` plays this role.

Where `unwrap`/`expect` is fine:
- In **tests**, where a panic is exactly a test failure.
- In quick experiments and prototypes.
- When you can prove it can't fail; then prefer `expect("why this can't fail")` so the reason is
  written down. `"42".parse::<i32>().expect("literal is a valid number")`.

Where it's a bug: anywhere user input or file contents decide whether it fails. A todo app (3.5)
that crashes with a panic message because the user typed `todo done abc` is broken; it should
print "not a number: abc" and exit cleanly. A compiler that panics on a malformed C file is
broken too; it should report a syntax error.

## Build
Make a scratch crate (`cargo new errors_practice`). Test every success *and* every error case.

1. **`Option` basics.** Write `fn longest_word(text: &str) -> Option<&str>` (`None` for empty or
   all-whitespace text; use `split_whitespace`). Test both outcomes.
2. **Safe division.** Write `fn checked_div(a: i32, b: i32) -> Option<i32>` without using the
   standard `checked_div` method. Then write a function that divides three numbers in a chain,
   using `?` on `Option`.
3. **`Result` with `?`.** Write `fn sum_numbers(text: &str) -> Result<i64, String>` where
   `"3 14 15"` gives `Ok(32)` and `"3 x 4"` gives an `Err` saying which word failed and its
   position (word index is fine). Use `parse` and `?`.
4. **A custom error enum.** Write `fn parse_time(s: &str) -> Result<(u8, u8), TimeError>` for
   24-hour `"HH:MM"` strings. Give `TimeError` distinct variants for: missing colon, non-numeric
   part (carry the text), hour out of range, minute out of range (carry the value). Add a
   `message(&self) -> String` method. Test each variant with `assert_eq!`.
5. **`main` that reports, not crashes.** Write a `main` that reads one command-line argument
   (`std::env::args().nth(1)`, which returns an `Option<String>`), runs `parse_time` on it and
   prints either the time or the error message. Missing argument must be a friendly message too.
   No `unwrap` in `main`.
6. **Panic or not?** For each, decide `Result` or `panic!` and write one sentence why: a config file
   missing a required key; a function `fn nth_prime(n)` called with `n = 0` by your own code; a
   user typing a negative quantity; an index your code computed one line earlier from the same
   vector's length.
7. Rustlings: `12_options`, `13_error_handling`.

## Common pitfalls
- Using `.unwrap()` everywhere to make errors go away. Each one is a possible crash; reserve it
  for tests and true invariants.
- Using `?` in a function that returns `()`, including a plain `fn main()`.
- Mismatched error types with `?` ("the trait `From<…>` is not implemented"). Convert with
  `map_err`.
- `Result<T, String>` everywhere in code that grows. Callers end up matching on message text.
- Forgetting the turbofish or a type annotation on `parse`, so Rust can't infer the target type.
