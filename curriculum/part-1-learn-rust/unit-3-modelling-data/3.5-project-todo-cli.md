# Lesson 3.5 — Project: todo CLI
**Part:** 1 — Learn Rust · **Unit:** 3 — Modelling Data · **Type:** Project · **Est. time:** 6–8 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.5, 3.1–3.4

## Overview
You'll build `todo`, a command-line to-do list that saves its tasks to a text file. It's small, but
it uses everything from this unit: a struct for a task, an enum for the commands, `Result` and a
custom error enum for everything that can go wrong, and a `Vec` (and maybe a `HashMap`) to hold
the data. It's also shaped like a tiny compiler: read text in, turn it into well-typed data, act
on it, write text out, and report bad input clearly instead of crashing.

## The lesson
The unit taught the data-modelling tools. This section covers the few new pieces of the standard
library the project needs, plus a way of structuring a CLI program. The examples use unrelated toy
programs; designing `todo` itself is your job.

### Reading command-line arguments
`std::env::args()` gives the program's arguments, like Python's `sys.argv`. Element 0 is the
program's own name. Collecting them into a `Vec<String>` is the easiest way to work with them:

```rust
let args: Vec<String> = std::env::args().collect();
// running `greet hello world` gives ["greet", "hello", "world"]
```

`collect()` turns the arguments into a `Vec`; you'll learn how it works in 4.3. Once you have a
`Vec<String>`, you can match on a slice of `&str`s. This works because patterns can match slices:

```rust
let words: Vec<&str> = args.iter().skip(1).map(|s| s.as_str()).collect();
match words.as_slice() {
    [] => println!("no arguments"),
    ["hello"] => println!("hi!"),
    ["repeat", word] => println!("{word} {word}"),
    ["sum", rest @ ..] => println!("{} numbers to add", rest.len()),
    _ => println!("didn't understand"),
}
```

`rest @ ..` binds "all the remaining elements" to `rest` as a slice. Slice patterns are a natural
fit for parsing command lines. (If the `iter().skip(1).map(…)` line looks mysterious, it's
"skip the program name and borrow each `String` as a `&str`"; 4.3 explains it.)

**Design tip:** keep the parsing in a function that takes the words as a parameter (a slice), not
one that calls `std::env::args()` itself. Then tests can call it with any made-up input.

### Reading and writing files
`std::fs` has whole-file helpers, the equivalent of Python's `open(p).read()` and
`open(p, "w").write(s)`:

```rust
use std::fs;

let text: Result<String, std::io::Error> = fs::read_to_string("notes.txt");
fs::write("notes.txt", "first line\nsecond line\n")?;   // creates or replaces the file
```

Both return `Result<_, std::io::Error>`. An `io::Error` has a **kind**, which is (of course) an
enum, so you can treat "file doesn't exist" differently from other failures:

```rust
use std::io::ErrorKind;

let text = match fs::read_to_string("scores.txt") {
    Ok(t) => t,
    Err(e) if e.kind() == ErrorKind::NotFound => String::new(),  // first run: nothing saved yet
    Err(e) => return Err(e),                                    // anything else is a real error
};
```

Notice the guard (from 3.2) choosing between two `Err` cases.

To split a file into lines, use `text.lines()` in a `for` loop. To split one line on a separator,
`line.split('\t')` or `line.split_once('\t')` (which returns `Option<(&str, &str)>`).

### Choosing a file format
You decide how tasks are stored. Good properties for a hand-made format:
- **Human-readable**, so you can open the file and see what's there.
- **One record per line**, so reading is "for each line, parse it".
- **A separator that can't appear inside a field**, or a rule for what happens if it does. A tab is
  a common choice. Task text containing a tab or newline must either be rejected or escaped;
  whichever you choose, it must never corrupt the file.
- **Reading and writing are exact inverses.** Writing a list, then reading it back, must give the
  same list. That makes a great test (a "round-trip" test).

Treat the file as untrusted input: someone may edit it by hand and break it. A malformed line must
produce an error that names the line number, not a panic.

### Wrapping other errors in your own error enum
Your program can fail for its own reasons (bad command, bad task number) and because of the
operating system (file unreadable). One error enum can hold both, with a variant that *wraps* the
`io::Error`. Toy example:

```rust
#[derive(Debug)]
enum ConfigError {
    Io(std::io::Error),                 // wraps the OS error
    BadLine { line: usize, text: String },
}

fn load(path: &str) -> Result<String, ConfigError> {
    let text = std::fs::read_to_string(path).map_err(ConfigError::Io)?;
    Ok(text)
}
```

`map_err(ConfigError::Io)` works because a tuple-like variant's name can be used as a function
that builds the variant: `ConfigError::Io(e)`. (Note: `io::Error` doesn't implement `PartialEq`,
so an enum wrapping it can't derive `PartialEq`. In tests, check variants with `matches!`
instead of `assert_eq!`.)

### Structuring a CLI: `run` returns `Result`, `main` reports
A clean shape for small programs is: put all the work in a function returning `Result`, and keep
`main` tiny. `main` prints any error to **standard error** with `eprintln!` (like `println!`, but
to stderr, as `print(..., file=sys.stderr)` does) and exits with a non-zero status, the shell's
convention for "failed":

```rust
fn main() {
    if let Err(e) = run() {
        eprintln!("error: {}", e.message());
        std::process::exit(1);
    }
}
```

Inside `run`, every fallible step uses `?`. The flow then reads as a pipeline:

```
 command-line words ──parse──▶ a command value (enum) ──┐
 data file ──────────read───▶ the task list (Vec)  ─────┤
                                                        ▼
                                              apply the command
                                                        │
                        print output ◀──────────────────┤
                        write file   ◀──────────────────┘   (only if something changed)
       any step fails ──▶ Err(…) bubbles up via ? ──▶ main prints it, exit code 1
```

Parsing the arguments into an enum *first*, before touching any data, is the same idea as a
compiler turning source text into tokens and a tree before doing any work on it: once you hold a
well-typed value, the rest of the program can't see malformed input.

## Build
Create a new binary crate: `cargo new todo`. Run it with `cargo run -- <args>` (everything after
`--` goes to your program) or install it with `cargo install --path .`.

### Specification
**Commands** (`<…>` is a required argument):

| Command | Behaviour |
|---|---|
| `todo add <text…>` | Adds a pending task. All remaining words are joined with spaces as the text. Prints the new task's id. |
| `todo list` | Prints every task, one per line: id, a done marker (`[ ]` / `[x]`) and text, in id order. Prints a friendly message if there are none. |
| `todo list --pending` | As `list`, but only tasks not yet done. |
| `todo done <id>` | Marks the task done. |
| `todo undo <id>` | Marks a done task as pending again. |
| `todo remove <id>` | Deletes the task. |
| `todo clear` | Deletes all done tasks and prints how many were removed. |
| `todo help` (or no arguments) | Prints a usage summary. |

**Ids.** Positive whole numbers. A task's id never changes, even after other tasks are removed
(so `done 3` always means the same task). A new task gets one more than the highest id ever
stored, or 1 for the first task.

**Storage.** Tasks are saved to `todo.txt` in the current directory. If the environment variable
`TODO_FILE` is set, use that path instead (`std::env::var("TODO_FILE")` returns a `Result`); this
lets you test without touching your real list. A missing file means an empty list, not an error.
The file is written only by commands that change something.

**Errors.** Each of these must print a clear one-line message to stderr starting with `error:`,
exit with status 1, and leave the data file unchanged:
- unknown command (name it), and a missing or extra argument (say which command expects what);
- `add` with empty text, or text containing a tab or newline (or escape them, if your format allows);
- an id that isn't a positive number (`done abc`, `done -2`, `done 0`);
- an id that doesn't exist;
- `done` on a task already done, `undo` on one that's pending;
- an unreadable data file (permission denied, etc.), including the OS's reason;
- a malformed line in the data file, with its line number.

The program must never panic on any input or any file contents.

### Design requirements
- A `Task` struct and a `Command` enum (one variant per command, carrying its arguments, already
  parsed into the right types).
- One custom error enum covering every error above, with a method (or `Display`, if you've read
  ahead) producing the message. No `String` errors.
- No `unwrap()` or `expect()` outside tests, unless you write a comment proving it can't fail.
- Parsing (words → `Command`), the file format (text ↔ tasks) and applying a command (tasks +
  command → updated tasks) are separate functions that don't do I/O, so they can be tested
  directly.

### Suggested order
1. On paper, write the `Task` fields, the `Command` variants and the error variants. Show your
   tutor before coding.
2. Write the argument parser and its tests (every command, every argument error). No files yet.
3. Write the file format: tasks → text, text → tasks. Test the round trip, an empty file, and each
   kind of malformed line.
4. Write the functions that apply each command to an in-memory list, with tests (including ids
   staying stable after a removal).
5. Wire it together in `run` and `main`: read the file, parse, apply, print, write.
6. Try it by hand with `TODO_FILE=/tmp/t.txt cargo run -- …`, including every error in the spec.
   Check exit codes with `echo $?` straight after a run. Corrupt the file by hand and see what happens.

**Stretch goals** (optional): a priority per task (an enum: low/normal/high) settable with
`add --high <text…>` and shown by `list`; `todo edit <id> <text…>`; a `stats` command showing
counts using a `HashMap`.

## Check your understanding
1. Why parse the arguments into a `Command` enum before reading the data file, instead of matching
   on strings throughout the program?
2. How did your error enum handle `io::Error`? Why can't that enum derive `PartialEq`?
3. What would happen to your data file if the program crashed halfway through writing it? (Think
   about it; no need to fix it.)
4. Which of your functions are pure (no I/O), and why did that make testing easier?
5. Where in your program could a panic still happen, and how do you know it can't?

## Common pitfalls
- Forgetting that `args[0]` is the program name, and treating it as the command.
- Calling `.unwrap()` on `parse::<u32>()` for an id: `todo done abc` then crashes.
- Renumbering tasks on removal, so `done 3` suddenly means a different task.
- Writing the file before validating the command, so a failed command corrupts or rewrites data.
- Tests that write to the real `todo.txt`. Keep I/O out of the tested functions, or use `TODO_FILE`.
- Printing errors with `println!` (stdout) and exiting with status 0.

## Done when
