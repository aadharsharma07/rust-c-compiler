# Lesson 3.1 — Structs and methods
**Part:** 1 — Learn Rust · **Unit:** 3 — Modelling Data · **Type:** Learning · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.5

## Overview
A `struct` groups several named values into one new type, the way a Python class or dataclass
does. An `impl` block attaches functions (methods) to it. This lesson shows how Rust's version
differs from Python's: the fields are fixed when you write the code, there is no inheritance, and
every method says exactly how it uses `self` (read it, change it, or consume it), which ties
straight back to the ownership rules from Unit 2. Later, every compiler stage passes structs
around: a token with its position, a function with its name and body, an assembly program.

## The lesson

### From a Python class to a Rust struct
In Python you might write:

```python
from dataclasses import dataclass

@dataclass
class Song:
    title: str
    artist: str
    seconds: int
```

The type hints are only hints. Python will happily let you write `song.seconds = "long"` or
`song.rating = 5`, adding a brand-new attribute at runtime, because a Python object is really a
dictionary of attributes behind the scenes.

The Rust version:

```rust
struct Song {
    title: String,
    artist: String,
    seconds: u32,
}
```

A **struct** (short for "structure") is a type made of named **fields**, each with a fixed type.
The set of fields is fixed at compile time: you cannot add `rating` later, and `seconds` can
only ever hold a `u32`. In return, the compiler knows exactly how big a `Song` is and where each
field lives, and it catches typos like `song.secnds` before the program runs.

### Creating and using a struct value
You build a value by naming the struct and giving *every* field a value (there are no default
arguments):

```rust
let mut s = Song {
    title: String::from("Blue in Green"),
    artist: String::from("Miles Davis"),
    seconds: 337,
};
println!("{} by {}", s.title, s.artist); // field access with a dot, as in Python
s.seconds += 1;                          // allowed only because `s` is `mut`
```

Mutability belongs to the **binding** (the variable), not to individual fields. If `s` were
declared with plain `let`, no field could change. Rust has no "mutable field, frozen object"
mix; you decide per variable.

Two shortcuts. **Field init shorthand**: if a local variable has the same name as a field, write
it once. **Struct update syntax**: copy the remaining fields from another value.

```rust
let title = String::from("So What");
let s2 = Song { title, ..s };   // title: title, and artist + seconds taken from s
```

Careful: `..s` *moves* any non-`Copy` fields (here `artist`, a `String`) out of `s`, so `s` can't
be fully used afterwards. Recall moves from 2.2.

### What a struct looks like in memory
A struct is just its fields laid out side by side. There is no hidden dictionary and no per-object
type pointer. For `Song` on a 64-bit machine (the compiler may reorder fields to save space):

```
 stack: s (a Song, 56 bytes)                         heap
 +------------------------------+
 | title:  ptr | len | capacity | --------------->  "Blue in Green"
 | artist: ptr | len | capacity | --------------->  "Miles Davis"
 | seconds: 337 (4 bytes + pad) |
 +------------------------------+
```

Each `String` is the three-word header you saw in 2.4, pointing at heap bytes. Compare Python,
where `s` would be a pointer to a heap object containing a pointer to an attribute dict containing
pointers to three more heap objects. Rust's version is flatter and needs no garbage collector:
when `s` goes out of scope, it is dropped, which drops its two `String`s, which frees their heap
bytes.

### Methods: `impl` blocks and the three kinds of `self`
In Python, methods live inside the class body and take `self` as their first parameter. In Rust,
the data (`struct`) and the behaviour (`impl`) are written separately:

```rust
impl Song {
    fn minutes(&self) -> u32 {          // borrows the Song read-only
        self.seconds / 60
    }
    fn rename(&mut self, new: &str) {   // borrows the Song mutably
        self.title = new.to_string();
    }
    fn into_title(self) -> String {     // takes ownership; the Song is consumed
        self.title
    }
}
```

The first parameter says *how the method uses the value*, using the borrowing rules from 2.3:

| You write | Means | Python analogy | Caller's value afterwards |
|---|---|---|---|
| `&self` | shared borrow: read only | an ordinary method that doesn't modify | still usable |
| `&mut self` | exclusive borrow: may modify | a method that mutates attributes | still usable; caller needs `let mut` |
| `self` | takes ownership | no real analogy | moved, can't be used again |

You call all three with the dot, and Rust inserts the `&` or `&mut` for you
(`s.minutes()` is really `Song::minutes(&s)`). This explicitness is a gift: reading a method
signature tells you whether calling it can change your data or use it up. In Python you have to
read the method body to know.

`self` (by value) is less common, but useful when a method turns the value into something else,
like `into_title` above, or `String::into_bytes` in the standard library. The naming convention
`into_…` signals "this consumes".

### Associated functions: Rust's constructors
A function in an `impl` block that does **not** take `self` is an **associated function**. You
call it with `::` on the type name. Rust has no `__init__` and no special constructor syntax; by
convention, a constructor is an associated function called `new`:

```rust
impl Song {
    fn new(title: &str, artist: &str, seconds: u32) -> Self {
        Self { title: title.to_string(), artist: artist.to_string(), seconds }
    }
}
let s = Song::new("Naima", "John Coltrane", 261);
```

`Self` (capital S) means "the type this `impl` is for", here `Song`. Associated functions play
the role of Python's `@classmethod` and `@staticmethod`: `Song::new(…)`, `Song::from_line(…)`
and `String::from(…)` are all associated functions. You can have several named constructors,
which Python can only fake with classmethods.

You may write several `impl` blocks for one type; they all add to the same type.

### Tuple structs and unit structs
Sometimes field names are noise. A **tuple struct** has positional fields, accessed with `.0`,
`.1`:

```rust
struct Celsius(f64);
struct Rgb(u8, u8, u8);
let boiling = Celsius(100.0);
println!("{}", boiling.0);
```

A one-field tuple struct is called a **newtype**. It costs nothing at runtime (a `Celsius` is just
an `f64` in memory), but `Celsius` and `Fahrenheit(f64)` are different types, so the compiler
stops you passing one where the other is expected. Python's `typing.NewType` is the same idea,
except Python only checks it if you run a type checker.

A **unit struct** has no fields at all (`struct Marker;`). It's rare for now; it becomes useful
with traits in Unit 4.

### Printing a struct: `#[derive(Debug)]`
`println!("{}", s)` doesn't compile for a struct: Rust refuses to guess how your type should look.
For debugging output, put this line above the struct:

```rust
#[derive(Debug)]
struct Song { /* ... */ }
println!("{:?}", s);   // Song { title: "Blue in Green", artist: "Miles Davis", seconds: 337 }
println!("{:#?}", s);  // the same, pretty-printed over several lines
```

`derive` asks the compiler to write some code for you, much as `@dataclass` writes `__repr__` and
`__eq__`. You'll see what's really being generated (traits) in 4.1. For now, add
`#[derive(Debug)]` to every struct you write, and `#[derive(Debug, PartialEq)]` when you want to
compare two values with `==` or `assert_eq!`.

### No inheritance
Rust structs cannot inherit from each other. Where Python uses a base class to share fields, Rust
uses **composition**: put one struct inside another as a field.

```rust
struct Address { city: String, postcode: String }
struct Customer { name: String, address: Address }
// customer.address.city
```

Where Python uses a base class to share *behaviour* or to treat different classes alike, Rust uses
enums (3.2) or traits (4.1). Most Python inheritance hierarchies you've seen are one of those two.

### Owned fields vs. borrowed fields
Give struct fields owned types (`String`, not `&str`) for now. A struct holding a reference needs
a lifetime annotation (4.5), and the compiler will tell you so if you try. Owned fields mean the
struct is self-contained: it owns its data and frees it when dropped.

### A small testing reminder
Each exercise below asks for tests. A test is a function marked `#[test]`, usually inside a
`tests` module at the bottom of the file, run with `cargo test`:

```rust
#[cfg(test)]
mod tests {
    use super::*;   // see the items in the rest of this file
    #[test]
    fn celsius_holds_value() {
        assert_eq!(Celsius(21.5).0, 21.5);
    }
}
```

`assert_eq!(a, b)` fails the test if `a != b`. Unit 4.6 covers testing properly.

## Build
Make a scratch crate (`cargo new structs_practice`). Derive `Debug` everywhere and write tests for
every method.

1. **`Point`.** A struct with `x: f64` and `y: f64`. Add an associated function `origin()`, a
   method `distance_to(&self, other: &Point) -> f64`, and a method `translate(&mut self, dx, dy)`.
   Test that the distance from (0,0) to (3,4) is 5.0 and that `translate` changes the point.
2. **`Counter`.** A struct with a name and a count. Methods: `new(name)`, `increment(&mut self)`,
   `reset(&mut self)`, `count(&self)`. Write one test calling them in sequence.
3. **Consuming method.** Give `Counter` a method `finish(self) -> String` returning something
   like `"clicks: 3"`. In `main`, call it, then try to use the counter again. Read the compiler
   error and explain to your tutor, in words, which rule it enforces.
4. **Newtypes.** Define `Meters(f64)` and `Feet(f64)`, and a function
   `meters_to_feet(m: Meters) -> Feet` (1 m = 3.28084 ft). Try passing a `Feet` to it and read the
   error.
5. **Composition.** Define a `Rect` built from two `Point`s (top-left and bottom-right) with
   `width`, `height` and `area` methods, and a `contains(&self, p: &Point) -> bool` method.
6. **Struct update.** Create a `Counter`, then a second one using `..` syntax with a new name.
   Check which original fields you can still use afterwards, and why.
7. Rustlings: `07_structs`.

## Check your understanding
1. In Python you can add a new attribute to an object at runtime. Why can't you in Rust, and what
   does the compiler gain from that?
2. Given only a method's signature, how can you tell whether calling it might change the value,
   or use it up?
3. What is the difference between a method and an associated function, and how do you call each?
4. Why is `struct UserId(u64)` better than passing a bare `u64` around? What does it cost at runtime?
5. Draw the memory of a struct with one `u32` field and one `String` field. What happens to the
   heap bytes when the struct goes out of scope?

## Common pitfalls
- Forgetting `mut` on the variable, then being puzzled that `&mut self` methods won't compile.
- Writing `self.field` as a plain `field` inside a method. Rust never looks up fields implicitly.
- Using `&str` fields and hitting "missing lifetime specifier". Use `String` until 4.5.
- Calling a `self` method and then trying to use the value. It's been moved.
- Expecting `println!("{}", value)` to work on your struct. Use `{:?}` with `#[derive(Debug)]`.
