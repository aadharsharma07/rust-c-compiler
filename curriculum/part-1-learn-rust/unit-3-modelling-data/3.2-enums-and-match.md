# Lesson 3.2 — Enums and pattern matching
**Part:** 1 — Learn Rust · **Unit:** 3 — Modelling Data · **Type:** Learning · **Est. time:** 4–5 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.5, 3.1

## Overview
A struct says "a value has *all* of these fields". An enum says "a value is *exactly one* of these
alternatives, and each alternative can carry its own data". Python has no direct equivalent, so
this lesson builds the idea slowly, starting from the Python workarounds you already know. Then
comes `match`, which takes an enum apart safely, and which the compiler checks for missing cases.
This pairing is the single most important tool for the compiler you'll build: tokens, syntax trees
and assembly instructions are all enums, processed with `match`.

## The lesson

### The problem: "one of several shapes"
Imagine a drawing app that receives input events. An event is *one of*: a key press (which key?),
a mouse click (where?), a window resize (new width and height?), or quit (no data). Each kind
carries *different* data. How do you model that in Python?

**Attempt 1: a kind string plus optional fields.**

```python
event = {"kind": "click", "x": 10, "y": 20}
if event["kind"] == "click":
    handle_click(event["x"], event["y"])
elif event["kind"] == "key":
    handle_key(event["key"])
```

Nothing stops you writing `"kind": "clik"`, or a click with no `"y"`, or a resize event that also
has a `"key"`. Every check happens at runtime, if at all.

**Attempt 2: a class hierarchy plus `isinstance` chains.**

```python
class Event: pass
class KeyPress(Event):
    def __init__(self, key): self.key = key
class Click(Event):
    def __init__(self, x, y): self.x, self.y = x, y
class Quit(Event): pass

def describe(e: Event) -> str:
    if isinstance(e, KeyPress):
        return f"key {e.key}"
    elif isinstance(e, Click):
        return f"click at {e.x},{e.y}"
    # forgot Quit! Python returns None silently.
```

Better: each kind has its own fields. But the set of kinds is *open* (anyone can add a subclass
anywhere), so nothing can tell you that `describe` forgot `Quit`. Add a `Resize` class next month
and every `isinstance` chain in the codebase is now silently incomplete.

**Attempt 3: Python 3.10 `match`.**

```python
match e:
    case KeyPress(key=k): return f"key {k}"
    case Click(x=x, y=y): return f"click at {x},{y}"
```

This *looks* like what we want, and it's where Python borrowed the idea from (languages like ML,
Haskell and Rust). But Python's `match` is not checked: an unmatched value just falls through and
nothing happens. Static checkers like mypy can approximate exhaustiveness with extra work
(`typing.assert_never`), but the language itself doesn't care.

What we want: a **closed** set of alternatives, each with its own data, and a language that refuses
to compile code that forgets one. That's a Rust enum.

### Enums without data
Start simple. An **enum** (short for "enumeration") defines a type by listing its possible values,
called **variants**:

```rust
#[derive(Debug, Clone, Copy, PartialEq)]
enum Direction { North, East, South, West }

let d = Direction::North;     // variants are named Type::Variant
```

So far this is Python's `enum.Enum`. A `Direction` value is always exactly one of the four; there
is no fifth, and no "unset".

### Enums whose variants carry data
Here is where Rust goes further than Python's `Enum`. Each variant can hold data, and different
variants can hold different data. There are three styles of variant, mirroring the three kinds of
struct from 3.1:

```rust
#[derive(Debug)]
enum Event {
    KeyPress(char),                     // tuple-like: positional data
    Click { x: i32, y: i32 },           // struct-like: named fields
    Resize(u32, u32),                   // tuple-like, two values
    Quit,                               // unit-like: no data
}

let a = Event::KeyPress('q');
let b = Event::Click { x: 10, y: 20 };
let c = Event::Quit;
```

`a`, `b` and `c` all have the **same type**, `Event`. You can put them in one `Vec<Event>`, pass
any of them to a function taking `Event`, and return any of them from a function. But a `Click`
*always* has an `x` and a `y`, and a `Quit` *never* has a key. The bad states from Attempt 1 are
not just discouraged; they can't be written.

Think of it as Attempt 2 with the hierarchy **closed**: the enum definition is the complete,
final list of subclasses, all in one place. Another name you'll meet is **sum type** (a struct is
a *product type*: all fields together; an enum is a *sum type*: one alternative out of several).
Some books say "tagged union" or "algebraic data type"; they mean the same thing.

### What an enum looks like in memory
An enum value is stored as a small hidden number called the **tag** (or discriminant), saying
which variant it is, followed by room for the **largest** variant's data:

```
 Event value (12 bytes here; the compiler decides the exact layout)
 +-------+---------------------------+
 |  tag  |  payload                  |
 +-------+---------------------------+
   0       'q'                          KeyPress('q')
   1       x=10      | y=20             Click { x: 10, y: 20 }
   2       w=800     | h=600            Resize(800, 600)
   3       (unused)                     Quit
```

Every `Event` is the same size, so they sit happily side by side in a `Vec`. Checking the variant
is just reading the tag, which is cheap. Compare Python, where each event is a separate heap
object and `isinstance` follows a pointer to the object's class.

### `match`: taking an enum apart
To use an enum's data you **match** on it. A `match` compares a value against a list of
**patterns** (shapes to try), top to bottom, and runs the first arm whose pattern fits:

```rust
fn describe(e: &Event) -> String {
    match e {
        Event::KeyPress(c) => format!("key {c}"),
        Event::Click { x, y } => format!("click at {x},{y}"),
        Event::Resize(w, h) => format!("resize to {w}x{h}"),
        Event::Quit => String::from("quit"),
    }
}
```

Read each arm as "if `e` is this variant, **bind** its data to these names, then evaluate the
right-hand side". In the `Click` arm, `x` and `y` are new variables holding the click's fields.
Because `e` is a reference (`&Event`), those bindings are references too (`c: &char`,
`x: &i32`); Rust handles this automatically, and `format!` prints them the same way.

Two things to notice:
- `match` is an **expression** (recall 1.3: blocks and `if` have values). The whole `match`
  evaluates to the chosen arm's value, so every arm must produce the same type. Here, `String`.
- An arm's right side can be a block: `Event::Quit => { log(); String::from("quit") }`.

### Exhaustiveness: the compiler checks you covered every case
Delete the `Quit` arm and try to compile:

```
error[E0004]: non-exhaustive patterns: `&Event::Quit` not covered
  |
  |     match e {
  |           ^ pattern `&Event::Quit` not covered
```

This is the heart of the lesson. Rust checks that **every possible value** is handled by some arm.
This is the guarantee Python can't give you. When you add a new variant to `Event` next month,
*every* `match` on `Event` in your whole program that doesn't handle it becomes a compile error,
with its line number. The compiler hands you a complete to-do list of the places to update.

On a big program (like a compiler with dozens of node types and a dozen passes over them) this
turns "I hope I updated everything" into "it compiles, so I updated everything".

### More pattern forms
Patterns can do much more than name a variant:

```rust
fn classify(n: i32) -> &'static str {
    match n {
        0 => "zero",                        // a literal
        1 | 2 | 3 => "small",               // several alternatives with |
        4..=9 => "medium",                  // an inclusive range
        x if x < 0 => "negative",           // a binding plus a guard
        _ => "large",                       // wildcard: matches anything
    }
}
```

(`&'static str` is a string literal type; you'll learn what `'static` means in 4.5.)

- A **guard** (`if …` after a pattern) adds an extra condition. The compiler can't see inside
  guards, so they don't count towards exhaustiveness. That's why the `_` arm is still needed.
- `_` matches anything and binds nothing. Use `..` to ignore the rest of a variant's fields:
  `Event::Click { x, .. } => …`.
- Patterns nest: `Some(Event::Click { x: 0, .. })` matches an optional event that is a click on
  the left edge. You can match on tuples too: `match (a, b) { (0, 0) => …, (_, 0) => …, _ => … }`.

### The danger of `_` on enums
A wildcard arm is convenient, but on your own enums it switches off the to-do list:

```rust
match e {
    Event::Quit => stop(),
    _ => {}            // every other variant, including ones you add later
}
```

Add a `Scroll` variant and this compiles without complaint, silently ignoring scrolls. That's
sometimes what you want. But when each variant *should* be considered, list them all explicitly,
even the ones that do nothing: `Event::KeyPress(_) | Event::Resize(..) => {}`.

### `if let`, `let … else` and `matches!`: when you care about one variant
A full `match` is noisy when you only care about one case. **`if let`** runs a block only if the
pattern fits:

```rust
if let Event::KeyPress(c) = e {
    println!("pressed {c}");
}   // you can add `else { ... }`
```

**`let … else`** binds a variant's data or leaves the function (the `else` block must exit with
`return`, `break` or similar):

```rust
let Event::Resize(w, h) = e else {
    return;   // not a resize: give up
};
// w and h are usable from here on
```

**`matches!`** gives a `bool`: `matches!(e, Event::Quit | Event::KeyPress('q'))`.

These are not exhaustive, by design. Use them for "is it this one?" and `match` for "which one is
it?".

### Methods on enums
Enums get `impl` blocks exactly like structs. A method usually starts with `match self`:

```rust
impl Direction {
    fn turn_right(self) -> Direction {
        match self {
            Direction::North => Direction::East,
            Direction::East => Direction::South,
            Direction::South => Direction::West,
            Direction::West => Direction::North,
        }
    }
}
```

(`Direction` is `Copy`, so taking `self` by value is fine; it's just a small tag.)

### Why this matters for the compiler (motivation only)
A compiler reads source text like `x = 7 + y;` and first breaks it into **tokens**: an identifier
`x`, an equals sign, the number 7, a plus, an identifier `y`, a semicolon. Each token is *one of*
a fixed set of kinds, and only some kinds carry data. That's an enum, shaped like this:

```rust
enum Tok { Number(i64), Name(String), Plus, Semicolon /* ... */ }
```

Next, the compiler builds a **syntax tree**: an expression is *one of* a number, a variable, or a
binary operation that contains two smaller expressions. That's an enum too, one whose variants
contain more of itself (which needs `Box`, coming in 4.4). Every later stage of the compiler is
then a function that `match`es on these enums. When you add a new operator in Part 3, the
compiler will point at every stage you still need to update. You'll design those types in Part 3;
for now, just notice the shape.

## Build
Make a scratch crate (`cargo new enums_practice`). Derive `Debug` (and `PartialEq` where you
compare) and test every function.

1. **Shapes.** An enum `Shape` with `Circle { radius: f64 }`, `Rectangle { width: f64, height: f64 }`
   and `Triangle(f64, f64, f64)` (three side lengths). Add `area(&self)` and `perimeter(&self)`
   methods using `match`. (Hint for the triangle area: look up Heron's formula.) Test each variant.
2. **Break it on purpose.** Add a `Square(f64)` variant. Before fixing anything, run
   `cargo build` and read every error. Count them and say what each one is pointing at. Then fix them.
3. **Playing cards.** Model a card: a `Suit` enum (four suits, no data) and a `Rank` enum with
   `Number(u8)` for 2–10 plus `Jack`, `Queen`, `King`, `Ace`. Put them in a `Card` struct. Write
   `value(&self) -> u8` (number cards are their number, face cards 10, ace 11) and
   `is_face(&self) -> bool` using `matches!`.
4. **Patterns.** Write `fn temperature_word(c: i32) -> &'static str` returning `"freezing"` below
   0, `"cold"` for 0–10, `"mild"` for 11–20, `"hot"` above 20, using ranges and guards. Test the
   boundary values.
5. **Un-stringly-type it.** Here is Python-style Rust:
   `fn traffic(colour: &str) -> &str { if colour == "red" { "stop" } else if colour == "green" { "go" } else { "slow" } }`.
   Rewrite it with a `Light` enum and a `next(self) -> Light` method (red → green → amber → red).
   Write down, in a comment, two bugs the string version allows and the enum version doesn't.
6. **`if let` / `let else`.** Write `fn circle_radius(s: &Shape) -> f64` that returns the radius
   for a circle and `0.0` otherwise, once with `if let` and once with `let … else`.
7. Rustlings: `08_enums`.

## Check your understanding
1. Why is "an event is one of these kinds" better modelled as an enum than a struct with a
   `kind: String` field and several optional fields?
2. What does the compiler do when you add a variant and forget a `match` arm? Why does that matter
   more as a program grows?
3. How does a Python class hierarchy with `isinstance` checks differ from a Rust enum, in terms
   of who can add new cases and who checks they're all handled?
4. Why don't guarded arms count towards exhaustiveness? When is a `_` arm a mistake?
5. Sketch the memory of an enum value. Why are all values of one enum type the same size?
6. When would you use `if let` instead of `match`?

## Common pitfalls
- Forgetting the type prefix: writing `Quit` instead of `Event::Quit` in a pattern. (A bare name in
  a pattern is a *new variable* that matches anything, which can silently catch every case. Rust
  usually warns you about it.)
- Arms that return different types. Every arm of a `match` used as a value must produce the same type.
- Reaching for `_ =>` out of habit and losing the exhaustiveness check on your own enums.
- Trying to read a variant's field directly (`e.x`). You must match first; the compiler doesn't
  know `e` is a `Click`.
- Putting a guarded arm *after* a pattern that already catches everything. Arms are tried top to
  bottom, so order specific arms before general ones.
