# Lesson 2.4 — Slices and strings
**Part:** 1 — Learn Rust · **Unit:** 2 — Ownership and Memory · **Type:** Learning · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.3

## Overview
Rust has two main string types where Python has one: the owned, growable `String` and the
borrowed view `&str`. This lesson explains both using what you now know about ownership and
borrowing, introduces **slices** (borrowed views into part of a sequence), and explains UTF-8,
the byte encoding behind every Rust string, which is why you can't write `s[0]`. Your compiler's
lexer will spend its whole life walking through a `&str` of C source, slicing out pieces like
`return` and `42`, so this lesson is directly on the road to Part 3.

## The lesson

### 1. Slices: a view into part of a sequence
A **slice** is a reference to a contiguous run of elements inside some collection, without
owning or copying them. For an array or `Vec` of `i32`, its type is `&[i32]`:
```rust
let nums = [10, 20, 30, 40, 50];
let middle: &[i32] = &nums[1..4];    // elements at indexes 1, 2, 3: [20, 30, 40]
let all: &[i32] = &nums[..];         // the whole thing
let head = &nums[..2];               // [10, 20]
let tail = &nums[3..];               // [40, 50]
println!("{:?} has {} items", middle, middle.len());
```
Python's `nums[1:4]` looks similar but **copies** into a new list. A Rust slice copies nothing.
It's a **fat pointer**: two 8-byte fields, a pointer to the first element and a length.
```
 nums (stack array):  [ 10 | 20 | 30 | 40 | 50 ]
                             ▲
 middle: &[i32]       ptr ───┘
                      len = 3
```
Because a slice is a borrow, all the 2.3 rules apply: you can't modify `nums` while `middle` is
alive. Slicing past the end (`&nums[2..9]`) panics at run time.

Slices make functions flexible. A function taking `&[i32]` accepts a whole array, a whole `Vec`,
or any part of either:
```rust
fn total(xs: &[i32]) -> i32 {
    let mut sum = 0;
    for x in xs { sum += x; }
    sum
}
let v = vec![1, 2, 3, 4];
total(&v);          // &Vec<i32> converts to &[i32] automatically
total(&v[1..3]);    // just [2, 3]
```

### 2. `String` and `&str`
- **`String`**: owns a growable heap buffer of text (pointer, length, capacity; recall 2.1). You
  can push to it. Dropped when its owner goes out of scope.
- **`&str`** (say "string slice"): a borrowed view of some text owned by someone else. A fat
  pointer: address + length. Read-only.

`&str` is to `String` what `&[i32]` is to `Vec<i32>`.
```rust
let owned: String = String::from("hello world");
let word: &str = &owned[0..5];       // "hello": borrows part of owned's buffer
let whole: &str = &owned;            // &String converts to &str automatically
```
```
 owned: String   ptr ──────► [h e l l o   w o r l d]   (heap)
                 len 11          ▲
                 cap 11          │
 word: &str      ptr ────────────┘
                 len 5
```

**String literals are `&str`.** When you write `"hello"`, the text is stored inside your compiled
executable (in a read-only data section), and the literal gives you a `&str` pointing at it. That
text lives for the whole run of the program, which is why its full type is `&'static str`
(you saw this in 1.4; `'static` means "valid forever", more in 4.5).

Converting between them:
```rust
let s: String = "hi".to_string();     // &str -> String (allocates)
let s2: String = String::from("hi");  // same
let r: &str = &s;                     // String -> &str (free, just borrows)
let r2: &str = s.as_str();            // same, explicitly
```

### 3. Which one to use?
- **Function parameters**: take `&str`. It accepts literals, `&String` and slices of either.
  Taking `&String` would reject literals and slices for no benefit.
- **Return values and struct fields**: use `String` when the value should own its text (e.g. you
  built it with `format!`, or it must outlive the input). Return `&str` only when it's a slice of
  an input (4.5 explains the rules).
- **Building text**: `String` with `push_str`, `push`, or `format!`.

```rust
fn shout(s: &str) -> String {
    s.to_uppercase()             // produces a new owned String
}
shout("hey");                    // literal: fine
shout(&String::from("hey"));     // &String -> &str: fine
```

### 4. How Python's `str` compares
A Python `str` is an immutable sequence of Unicode **code points** (characters). CPython stores
it so that every character takes the same number of bytes (1, 2 or 4, depending on the widest
character in the string), which makes `s[5]` and `len(s)` constant-time and character-based.
Slicing copies. Strings are immutable, so "modifying" one builds a new one.

Rust made different choices: text is always **UTF-8** bytes, `String` is mutable, and slicing
borrows. To see why `s[0]` is a problem, you need UTF-8.

### 5. UTF-8 in five minutes
Text is stored as bytes. **Unicode** assigns every character a number (a **code point**): `A` is
65, `é` is 233, `€` is 8364, `🦀` is 129408. **UTF-8** is a way to encode those numbers as bytes
using a *variable* number of bytes per character:

| Character | Code point | UTF-8 bytes | Count |
|---|---|---|---|
| `A` | 65 | `41` | 1 |
| `é` | 233 | `C3 A9` | 2 |
| `€` | 8364 | `E2 82 AC` | 3 |
| `🦀` | 129408 | `F0 9F A6 80` | 4 |

ASCII characters (English letters, digits, punctuation, and all of C's syntax) take 1 byte, so
ASCII text is valid UTF-8 unchanged. Consequences in Rust:
- **`len()` counts bytes, not characters.** `"héllo".len()` is 6. `"héllo".chars().count()` is 5.
- **Indexing is by byte offset**, and `s[i]` is not allowed at all: a single byte might be half a
  character, and finding the *n*th character means scanning from the start. Rust refuses to hide
  that cost behind `[]`:
  ```
  error[E0277]: the type `str` cannot be indexed by `{integer}`
  ```
- **Slicing uses byte ranges** and **panics if a boundary falls inside a character**:
  `&"héllo"[0..2]` panics ("byte index 2 is not a char boundary"), because bytes 1–2 are `é`.
  `&"héllo"[0..3]` is `"hé"`.

### 6. Walking through a string
Since you can't index by character, you iterate:
```rust
let s = "naïve";
for c in s.chars() {            // each char (a Unicode scalar value, 4 bytes)
    print!("[{}]", c);          // [n][a][ï][v][e]
}
for b in s.bytes() { }          // each raw u8 byte: 110, 97, 195, 175, 118, 101
for (i, c) in s.char_indices() {   // byte offset + char: (0,'n') (1,'a') (2,'ï') (4,'v') (5,'e')
}
```
`char_indices` is the bridge between characters and byte offsets: it tells you exactly where
each character starts, so you can slice safely. A lexer is essentially a loop over
`char_indices`, which you'll write yourself in Part 3. You can also get the *n*th char with
`s.chars().nth(n)` (an `Option`, covered in 3.3), knowing it scans from the start.

### 7. Useful `str` methods (and their Python names)
| Rust | Python | Notes |
|---|---|---|
| `s.trim()` | `s.strip()` | returns a `&str` slice of `s`; no allocation |
| `s.split_whitespace()` | `s.split()` | yields `&str` pieces |
| `s.split(',')` | `s.split(',')` | |
| `s.lines()` | `s.splitlines()` | |
| `s.to_lowercase()` | `s.lower()` | returns a new `String` |
| `s.contains("ab")` | `"ab" in s` | |
| `s.starts_with("x")` | `s.startswith("x")` | |
| `s.replace("a", "b")` | `s.replace("a", "b")` | returns a new `String` |
| `c.is_alphabetic()`, `c.is_ascii_digit()` | `c.isalpha()`, `c.isdigit()` | methods on `char` |
| `format!("{}-{}", a, b)` | `f"{a}-{b}"` | builds a `String` |
| `s1 + &s2` | `s1 + s2` | moves `s1`, borrows `s2` |

Notice which methods return slices (`trim`, `split`, `lines`: cheap views into the original) and
which return a new `String` (`to_lowercase`, `replace`: they must allocate because the text
changes). The slice-returning ones borrow the original, so the original must outlive them:
```rust
let first_piece;
{
    let text = String::from("alpha beta");
    first_piece = text.split_whitespace().next();   // borrows text...
}   // ...text is dropped here
// println!("{:?}", first_piece);   // error[E0597]: `text` does not live long enough
```

## Common pitfalls
- **Taking `&String` or `String` parameters** when `&str` would do.
- **Assuming `len()` counts characters.** It counts bytes.
- **Slicing at arbitrary byte offsets** in non-ASCII text, causing a panic. Use `char_indices`.
- **Returning a slice of a local `String`.** The `String` dies at the end of the function; return a `String`.
- **Using `+` and being surprised `s1` is gone.** `+` moves its left operand; use `format!` when unsure.
