# Lesson 2.1 — The stack and the heap
**Part:** 1 — Learn Rust · **Unit:** 2 — Ownership and Memory · **Type:** Learning · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 1.1–1.5

## Overview
Every value in a running program lives somewhere in memory. This lesson builds, from scratch, a
picture of the two main regions a program uses (the **stack** and the **heap**), then shows how
Python manages memory for you (heap objects, names as references, reference counting and a
garbage collector) and how Rust does it differently (values stored directly, with heap memory
freed at a point the compiler decides). Ownership (2.2) and borrowing (2.3) only make sense with
this picture in your head. You'll also need it again in Part 2 and Part 3, where your compiler
manages the stack itself.

## The lesson

### 1. Memory is a giant numbered array of bytes
To a running program, memory (RAM) looks like one enormous row of bytes, each with a number
called its **address**. An address is just an integer, usually written in hexadecimal
(`0x7ff7_b2c0`). A value that takes 4 bytes, like an `i32`, occupies 4 consecutive addresses.
A **pointer** is simply a value that holds an address: "the thing you want is over *there*". On
a 64-bit machine, a pointer is 8 bytes.

```
address:  ...  1000   1001   1002   1003   1004   1005  ...
contents: ...  0x2A   0x00   0x00   0x00   0x07   ...         <- bytes 1000..1003 hold the i32 42
```

The operating system gives each program its own region of addresses, split into areas. Two
matter for us: the **stack** and the **heap**.

### 2. The stack: fast, automatic, fixed-size
Every time a function is called, the program needs room for that call's local variables. It
gets it from the **stack**, a region used like a stack of plates: you only add to or remove from
the top.

- **Calling** a function pushes a **stack frame** (a block of memory for its locals) on top.
- **Returning** pops that frame off. Its memory is instantly available for the next call.

The CPU keeps the address of the top of the stack in a special register (the **stack pointer**;
on x86-64 it's called `rsp`, and you'll meet it in 6.4). Making room is a single subtraction
from that register, so allocating on the stack is essentially free. Freeing is equally cheap.

Walk through this program:
```rust
fn square(n: i32) -> i32 {
    let result = n * n;
    result
}

fn main() {
    let a = 3;
    let b = square(a);
    println!("{}", b);
}
```
```
 1) main starts            2) main calls square(3)     3) square returns 9
 ┌──────────────┐          ┌──────────────┐            ┌──────────────┐
 │ main         │          │ main         │            │ main         │
 │  a = 3       │          │  a = 3       │            │  a = 3       │
 │  b = ?       │          │  b = ?       │            │  b = 9       │
 └──────────────┘ <- top   ├──────────────┤            └──────────────┘ <- top
                           │ square       │
                           │  n = 3       │            (square's frame is gone;
                           │  result = 9  │             its memory will be reused)
                           └──────────────┘ <- top
```
(Real stacks grow *downward*, toward lower addresses; it's drawn growing down the page here to
match. Details in 6.4.)

The catch: **the compiler must know the size of every stack value at compile time**, because
it lays out each frame in advance ("`a` is at offset 0, `b` at offset 4"). An `i32` is always
4 bytes, a `bool` is 1, an `[i32; 5]` array is 20. Fine. But how big is a line the user types?
A list that grows? Unknown until run time. And a stack value dies when its function returns,
so it can't outlive the call. For both problems we need the heap.

### 3. The heap: flexible, manual-ish, slower
The **heap** is a large pool of memory for data whose size is only known at run time, or that
must outlive the function that created it. A piece of code called the **allocator** manages it:
- You ask: "I need 37 bytes." The allocator finds a free spot, marks it used, and gives back its
  address (a pointer). That's an **allocation**.
- When you're done, you hand it back so it can be reused: you **free** (or **deallocate**) it.

The heap is slower than the stack (the allocator has to search and keep records), and someone
has to remember to free each allocation exactly once, at the right moment. *Who* does that is
the big difference between languages:

| Who frees heap memory? | Language | Risk |
|---|---|---|
| The programmer, by hand (`malloc`/`free`) | C | forget → leak; too early → use-after-free; twice → crash or worse |
| A runtime system, automatically | Python, Java, Go | slower, unpredictable timing, extra memory |
| The compiler, at a statically known point | **Rust** | you must follow the ownership rules |

Usually a heap value is reached through a pointer that lives on the stack:
```
     STACK                         HEAP
 ┌───────────────┐            ┌─────────────────────┐
 │ main          │            │                     │
 │  ptr ─────────┼───────────►│ [ 37 bytes of data ]│
 └───────────────┘            └─────────────────────┘
```

### 4. How Python manages memory
In CPython, **every value is an object on the heap**, even the integer `5`. Each object has a
header containing a **reference count** and a pointer to its type, then its data. Variables
(names) never contain values; they contain **references** (pointers) to objects.

```python
a = [1, 2, 3]
b = a          # no copy: b refers to the SAME list
b.append(4)
print(a)       # [1, 2, 3, 4]
```
```
 names (in the frame)            HEAP
 ┌────────┐                ┌──────────────────────────┐
 │ a ─────┼───────┐        │ list object              │
 │ b ─────┼───────┴───────►│  refcount = 2            │
 └────────┘                │  type → list             │
                           │  items → [1, 2, 3, 4]    │
                           └──────────────────────────┘
```
That's why `b = a` doesn't copy and why changing `b` "changes" `a`: there is only one list.

**Reference counting.** Each time a new reference is made (`b = a`, putting it in a list,
passing it to a function), CPython increments the count; each time one goes away (a name is
reassigned or deleted, a function returns), it decrements it. When the count hits **zero**, the
object is freed immediately. You can watch it with `sys.getrefcount(obj)` (it reports one extra,
for its own argument).

**The cycle collector.** Reference counting can't free objects that point at each other:
```python
x = []
x.append(x)    # x refers to itself: its count never reaches 0
del x          # unreachable, but count is still 1
```
So CPython also runs a **garbage collector** (the `gc` module) every so often, which hunts for
groups of objects unreachable from your program and frees them.

The trade-offs: every object carries extra bookkeeping (a Python `int` is about 28 bytes; the
raw number needs 8), every assignment updates counts, and the program pauses occasionally for
the GC. You never write a `free`, and you can't get a use-after-free. This is the convenience
Rust wants to keep without the costs.

### 5. How Rust lays out values
Rust stores values **directly**, not behind a pointer, unless you ask for the heap.

```rust
let x: i32 = 5;          // 4 bytes, right there in main's stack frame
let p: (i32, i32) = (1, 2);  // 8 bytes, in the frame
let arr = [0u8; 16];     // 16 bytes, in the frame
```
No header, no reference count, no heap: `x` *is* those 4 bytes. That's a big part of Rust's speed.

Types that need to grow use the heap, and the clearest example is `String`, which you used in
1.5. A `String` is a small fixed-size value on the stack (three 8-byte fields: a pointer to a
heap buffer, the buffer's **capacity**, and the current **length**) plus the text in that buffer:
```rust
let mut s = String::from("hi");
s.push_str(" there");
```
```
     STACK (main's frame)                    HEAP
 ┌──────────────────────────┐          ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
 │ s: String                │          │ h │ i │   │ t │ h │ e │ r │ e │ . │ . │ . │
 │   ptr ───────────────────┼─────────►└───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
 │   len = 8                │            (capacity = 11 bytes: room to grow
 │   cap = 11               │             before needing a bigger allocation)
 └──────────────────────────┘
```
(The exact capacity varies; it's at least the length.) When the text outgrows the capacity,
`String` allocates a bigger buffer, copies the bytes over and frees the old one, as Python lists do.

You can also put any single value on the heap explicitly with `Box`:
```rust
let b = Box::new(5);     // the 5 lives on the heap; b (a pointer) lives on the stack
println!("{}", b);       // 5
```
You won't need `Box` until 4.4 (for trees).

### 6. When does Rust free heap memory?
Here's the key idea. Each heap allocation in Rust has exactly one variable responsible for it,
its **owner**. When the owner goes **out of scope** (the closing `}` of the block it was
declared in), Rust automatically runs cleanup code for it, called **dropping** it, which frees
the heap buffer.
```rust
fn main() {
    let a = 1;
    {
        let s = String::from("temporary");   // heap allocation happens here
        println!("{}", s);
    }                                        // s goes out of scope: buffer freed HERE
    println!("{}", a);
}                                            // a goes away (stack only; nothing to free)
```
No runtime counting, no collector: the compiler sees the `}` and inserts the free right there,
as cheap as C's manual `free`, but you never write it and can't forget it.

This raises an obvious question. What if two variables point at the same heap buffer, like `b = a`
in Python? If both "owned" it, both would free it at their `}`: a **double free**. Rust's answer
is ownership and moves, the subject of 2.2.

### 7. Measuring sizes
`std::mem::size_of::<T>()` returns how many bytes a type takes *in place* (on the stack, or
inside another value). It does not count heap data the value points to:
```rust
use std::mem::size_of;
println!("{}", size_of::<i32>());     // 4
println!("{}", size_of::<char>());    // 4
println!("{}", size_of::<Box<i32>>()); // 8: just the pointer
```
Print an address with `{:p}` and a reference: `println!("{:p}", &x);`.

## Common pitfalls
- **Thinking "stack = small values, heap = big values."** It's about whether the size is known at
  compile time and how long the value must live, not raw size.
- **Thinking `size_of::<String>()` includes the text.** It's always 24 bytes on 64-bit machines; the text is on the heap.
- **Assuming Rust has reference counting by default.** It doesn't. (Opt-in `Rc` exists; see 4.4.)
- **Expecting addresses to be the same every run.** The OS randomises them for security (ASLR); compare relative positions.
