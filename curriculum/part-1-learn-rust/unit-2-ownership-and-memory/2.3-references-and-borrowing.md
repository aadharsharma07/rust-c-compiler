# Lesson 2.3 — References and borrowing
**Part:** 1 — Learn Rust · **Unit:** 2 — Ownership and Memory · **Type:** Learning · **Est. time:** 4–6 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.2

## Overview
Moving ownership into every function that just wants to *look at* a value is clumsy, as you saw
in 2.2. This lesson introduces **references**: a way to let code use a value without owning it,
called **borrowing**. You'll learn shared references `&T`, mutable references `&mut T`, the two
borrowing rules the compiler enforces, and how to read the borrow checker's errors. Your compiler
will borrow constantly: the lexer reads the source text without owning it, and every pass walks
the syntax tree by reference.

## The lesson

### 1. A reference is a pointer that doesn't own
```rust
fn length(s: &String) -> usize {   // s is a reference to a String
    s.len()
}

fn main() {
    let name = String::from("Grace");
    let n = length(&name);          // &name creates a reference: "borrow name"
    println!("{} has {} letters", name, n);   // name is still valid!
}
```
`&name` creates a **reference**: a value holding the address of `name`. The type `&String` reads
"reference to a `String`". Because a reference doesn't own what it points at, nothing is dropped
when the reference goes away. Ownership never moved, so `name` is still usable afterwards.
```
       STACK                                       HEAP
 ┌─────────────────────────┐
 │ main                    │
 │  name: ptr ─────────────┼──────────────► [G r a c e]
 │        len 5, cap 5     │◄───┐
 ├─────────────────────────┤    │
 │ length                  │    │
 │  s: &String ────────────┼────┘   (s points at name, which points at the heap)
 └─────────────────────────┘
```
Creating a reference is called **borrowing**: like borrowing a book, you can use it, but you must
give it back, and the owner keeps it. Under the hood a reference is just an 8-byte address, so
it's as cheap as Python passing a reference to an object.

How is this different from Python, where everything is a reference? In Python, any reference
keeps the object alive (the count goes up). A Rust reference does **not** keep anything alive:
the owner decides when the value dies. So the compiler must prove that no reference is ever used
after its owner is gone. That's the job of the **borrow checker**.

### 2. Using a reference: auto-deref and `*`
Method calls work straight through references: `s.len()` works whether `s` is a `String` or a
`&String`, because Rust automatically follows (**dereferences**) the pointer for method calls.
To get at the value explicitly, use the **dereference operator** `*`:
```rust
let x = 10;
let r = &x;          // r: &i32
let y = *r + 1;      // *r is "the i32 that r points at": 10
println!("{} {}", r, y);   // println! also follows references for you: prints 10 11
```

### 3. Mutable references: `&mut T`
A plain `&` reference is **shared** and read-only: you can't change the value through it. To
change a borrowed value, you need a **mutable reference**, `&mut`:
```rust
fn add_exclaim(s: &mut String) {
    s.push('!');
}

fn main() {
    let mut msg = String::from("hello");   // the variable itself must be `mut`
    add_exclaim(&mut msg);                 // lend it out mutably
    println!("{}", msg);                   // hello!
}
```
Three places say `mut`: the variable (`let mut`), the borrow (`&mut msg`) and the parameter type
(`&mut String`). That's on purpose: mutation is always visible at the call site. In Python,
passing a list to a function might or might not modify it, and you can't tell without reading
the function. In Rust, `f(&x)` cannot modify `x`; `f(&mut x)` might. You saw this pattern in 1.5
with `read_line(&mut input)`.

To modify a `Copy` value through a mutable reference, dereference it: `*count += 1;`.

### 4. The borrowing rules
At any moment, for a given value, you may have **either**:
- **any number of shared references (`&T`)**, **or**
- **exactly one mutable reference (`&mut T`)**,

but not both. And:
- **every reference must always point at a valid value** (it can't outlive the owner).

The short version: **many readers, or one writer**. Why this rule? Consider what could go wrong if
you could read and write at the same time. A `Vec` (growable list) stores its items in a heap
buffer. Pushing an item may need a bigger buffer: allocate new, copy, **free the old one** (like
`String` in 2.1). Now:
```rust
let mut v = vec![1, 2, 3];     // vec! makes a Vec, like a Python list literal
let first = &v[0];             // a reference INTO v's heap buffer
v.push(4);                     // might move the buffer and free the old one...
println!("{}", first);         // ...so `first` could point at freed memory!
```
In C, this compiles and reads garbage, or crashes, sometimes. In Python it can't happen because
`first` would reference the `int` object, not a slot in the list's buffer. Rust refuses to
compile it:
```
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let first = &v[0];
  |                  - immutable borrow occurs here
4 |     v.push(4);
  |     ^^^^^^^^^ mutable borrow occurs here
5 |     println!("{}", first);
  |                    ----- immutable borrow later used here
```
(`push` needs `&mut v`, because it changes the vector.) Read the three labels: where the shared
borrow starts, where the conflicting mutable borrow happens, and where the shared borrow is still
needed. That last label is what makes it a conflict.

### 5. Borrows last until their last use
A borrow doesn't last until the end of the block; it lasts until the reference is **last used**.
(The compiler's analysis for this is called **non-lexical lifetimes**, NLL.) So this is fine:
```rust
let mut v = vec![1, 2, 3];
let first = &v[0];
println!("{}", first);   // last use of `first`: the shared borrow ends here
v.push(4);               // no conflict now
```
Often the fix for a borrow error is just to reorder: finish using the reference before
mutating, or copy out the value you need (`let first = v[0];` copies the `i32`, no borrow at all).

### 6. Two mutable borrows at once
```rust
let mut s = String::from("x");
let a = &mut s;
let b = &mut s;
a.push('1');
```
```
error[E0499]: cannot borrow `s` as mutable more than once at a time
```
If two `&mut` could exist at once, two pieces of code could change the same value without
knowing about each other. With one writer at a time, whoever holds the `&mut` knows nothing else
can see or touch the value. (This same rule is what lets Rust prevent data races between threads
at compile time.)

### 7. Dangling references are impossible
A **dangling reference** points at memory that has been freed. Try to return a reference to a
local variable:
```rust
fn make() -> &String {
    let s = String::from("temp");
    &s
}   // s is dropped here, so the reference would dangle
```
Rust rejects it with `error[E0106]: missing lifetime specifier`, and the help text suggests
returning the owned `String` instead. The fix is to return `String` (move ownership out, as in
2.2). "Lifetime" means how long a reference is valid; you'll study lifetimes in 4.5. For now,
remember: **you can't return a reference to something created inside the function**.

### 8. Borrowing while looping
`for x in &v` iterates by shared reference (`x: &i32`), leaving `v` usable afterwards.
`for x in &mut v` gives `x: &mut i32`, letting you modify each element with `*x += 1`.
`for x in v` (no `&`) moves `v` (2.2). Inside a `for x in &v` loop you can't `v.push(...)`:
same rule as section 4.

### 9. Choosing a parameter type
| You want to... | Take | Caller writes |
|---|---|---|
| read the value | `&T` | `f(&x)` |
| modify it in place | `&mut T` | `f(&mut x)` |
| keep it, store it, or consume it | `T` (ownership) | `f(x)` (moves) |

Default to `&T`. Take ownership only when the function needs to keep the value. (For strings
specifically, 2.4 shows that `&str` is better than `&String`.)

### 10. Reading a borrow-checker error: a method
1. Read the error code and title (`E0502: cannot borrow ... as mutable because ... immutable`).
2. Find the **three places** in the snippet: where the first borrow starts, where the conflicting
   action happens, and where the first borrow is used later.
3. Ask: which rule? (one writer XOR many readers; no use after move; no dangling).
4. Fix by: shortening the first borrow (reorder, finish using it first), copying/cloning the small
   bit you need, or restructuring so ownership is clearer. Use `rustc --explain` for examples.

## Common pitfalls
- **Forgetting `mut` in one of the three places** (`let mut`, `&mut x`, `&mut T`).
- **Holding a reference across a mutation** of the same collection. Finish with the reference first, or copy the value out.
- **Trying to return a reference to a local.** Return the owned value.
- **Cloning to escape every borrow error.** Usually reordering or narrowing the borrow is the real fix.
- **Confusing `&mut x` (a mutable borrow) with `let mut x` (a mutable variable).** They're related but different.
