# Lesson 2.2 — Ownership and moves
**Part:** 1 — Learn Rust · **Unit:** 2 — Ownership and Memory · **Type:** Learning · **Est. time:** 4–5 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.1

## Overview
Lesson 2.1 ended with a problem: if Rust frees a heap buffer when its owner goes out of scope,
what happens when two variables refer to the same buffer? This lesson answers it with Rust's
**ownership rules**: every value has exactly one owner, assigning or passing a value **moves**
ownership, simple values are **copied** instead, you can **clone** deliberately, and the owner
**drops** the value at the end of its scope. Your compiler's data (source text, tokens, trees)
will be passed between stages constantly, so knowing when a value moves is a daily skill.

## The lesson

### 1. The three ownership rules
1. **Each value in Rust has an owner** (a variable, or a field of another value).
2. **There can be only one owner at a time.**
3. **When the owner goes out of scope, the value is dropped** (its resources, such as heap memory, are freed).

Everything in this lesson follows from these three sentences.

### 2. Moves: what `let b = a;` does to a `String`
Recall the layout of a `String` from 2.1: a 24-byte stack part (pointer, length, capacity) plus a
heap buffer. Now:
```rust
let a = String::from("hello");
let b = a;
```
Rust copies the **24-byte stack part** from `a` to `b`. It does *not* copy the heap buffer (that
could be huge and slow). So for a moment, two pointers aim at one buffer:
```
     STACK                                HEAP
 ┌──────────────────┐
 │ a: ptr ──────────┼──────┐         ┌───┬───┬───┬───┬───┐
 │    len 5, cap 5  │      ├────────►│ h │ e │ l │ l │ o │
 ├──────────────────┤      │         └───┴───┴───┴───┴───┘
 │ b: ptr ──────────┼──────┘
 │    len 5, cap 5  │
 └──────────────────┘
```
If both `a` and `b` were owners, both would free the buffer at the end of `main`: a **double
free**, which corrupts the allocator. Python avoids it by counting references at run time. Rust
avoids it at compile time: after `let b = a;`, **`a` is no longer valid**. Ownership has
**moved** to `b`. Only `b` will free the buffer.

Try to use `a` afterwards:
```rust
let a = String::from("hello");
let b = a;
println!("{}", a);
```
```
error[E0382]: borrow of moved value: `a`
 --> src/main.rs:3:20
  |
1 |     let a = String::from("hello");
  |         - move occurs because `a` has type `String`, which does not implement the `Copy` trait
2 |     let b = a;
  |             - value moved here
3 |     println!("{}", a);
  |                    ^ value borrowed here after move
```
Read it as a story: *where* the value was created, *where* it moved, and *where* you used it
after the move. This is the single most common error for new Rust programmers. (`println!` uses
the value by **borrowing** it, which is why it says "borrow"; borrowing is 2.3.)

Compare with Python: `b = a` gives you two names for one object, both usable, with the count at
2. In Rust, `let b = a;` *transfers* the object: one name, one owner, count always effectively 1,
so no count is needed.

### 3. Moves happen on function calls and returns too
Passing a value to a function moves it into the parameter, exactly like assignment:
```rust
fn shout(text: String) {
    println!("{}!", text.to_uppercase());
}   // text goes out of scope here: the String is dropped (freed)

fn main() {
    let greeting = String::from("hi");
    shout(greeting);              // ownership moves into `shout`
    // println!("{}", greeting);  // error[E0382]: value used after move
}
```
Returning a value moves it **out** to the caller:
```rust
fn make_label(n: u32) -> String {
    let s = format!("item-{}", n);   // format! builds a String, like Python's f-string
    s                                // ownership moves out to the caller; not dropped here
}

fn main() {
    let label = make_label(7);       // label now owns it
    println!("{}", label);
}                                    // dropped here
```
You *could* pass ownership in and hand it back out again (`fn f(s: String) -> String`) to keep
using a value, but that's clumsy. In 2.3 you'll learn to **borrow** instead.

A `for` loop over a `Vec` (a growable list; full lesson in 3.4) also moves: `for s in names { }`
moves each element out, and `names` can't be used afterwards. (`for s in &names` borrows instead;
see 2.3.)

### 4. `Copy`: simple values are copied, not moved
Why didn't any of this happen in Unit 1?
```rust
let x = 5;
let y = x;
println!("{} {}", x, y);   // fine!
```
An `i32` lives entirely on the stack and owns no heap memory. Copying its 4 bytes produces a
completely independent value, and nothing needs freeing, so there's no double-free risk. Types
like this implement the **`Copy` trait** (a **trait** is a capability a type has; full lesson
in 4.1). For a `Copy` type, assignment and passing **copy** the value and the original stays valid.

`Copy` types include: all integers and floats, `bool`, `char`, shared references `&T` (2.3), and
tuples and arrays made only of `Copy` types, like `(i32, f64)` or `[u8; 4]`. `String`, `Vec` and
`Box` are **not** `Copy`, because they own heap memory. Rule of thumb: *if it owns something on the
heap, it moves; if it's plain bits, it copies*.

### 5. `Clone`: a deliberate deep copy
When you really do want two independent `String`s, ask for it explicitly with `.clone()`:
```rust
let a = String::from("hello");
let b = a.clone();         // allocates a NEW heap buffer and copies the bytes into it
println!("{} {}", a, b);   // both valid, both owners of their own buffer
```
```
 a: ptr ──────► [h e l l o]
 b: ptr ──────► [h e l l o]      (a separate allocation)
```
This is like Python's `copy.deepcopy` (or `list(xs)` for a flat list). Rust makes the expensive
operation visible in the code: when you see `.clone()`, you know memory is being allocated and
copied. That's deliberate. Python's `b = a` is cheap but shares; Rust's `let b = a` is cheap and
moves; only `.clone()` is expensive.

`clone()` is the right answer sometimes, but beginners often sprinkle it everywhere to silence the
compiler. Before cloning, ask: "do I actually need a second copy, or do I just need to *look at*
the value?" Looking is borrowing (2.3).

### 6. Drop: what happens at the end of scope
When an owner goes out of scope, Rust calls the value's **drop** logic. For a `String`, that
frees its buffer. For a `Vec<String>`, it drops each `String`, then frees the vector's own
buffer. Values in a scope are dropped in **reverse order** of declaration.

You can watch it by giving a type custom drop behaviour with the `Drop` trait. (The `struct` and
`impl` syntax here is taught properly in 3.1; just read it as "a type called `Noisy` that prints
when it's dropped".)
```rust
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("dropping {}", self.0);
    }
}

fn main() {
    let _a = Noisy("a");
    {
        let _b = Noisy("b");
        println!("end of inner block");
    }                                  // prints "dropping b"
    let c = Noisy("c");
    let d = c;                         // move: no drop happens here
    println!("end of main");
}                                      // prints "dropping c" (owned by d), then "dropping a"
```
Notice the move from `c` to `d` didn't drop anything: the value just has a new owner, and it's
dropped once, when `d` goes out of scope. You can also drop a value early with `drop(value)`,
which simply moves it into a function that does nothing, so it's dropped there.

This deterministic, scope-based cleanup is sometimes called **RAII**. It frees not just memory
but files (closed when dropped), locks and network connections. Python's `with` statement is the
closest analogue, but Rust applies it to every value automatically.

### 7. Moves out of a variable are tracked across branches
The compiler tracks moves through control flow:
```rust
let s = String::from("x");
if some_condition {
    shout(s);          // moved in this branch
}
// println!("{}", s);  // error[E0382]: value used after *possibly* being moved
```
And inside a loop, moving the same value twice is caught, because the second iteration would
use a value that was moved in the first:
```rust
let s = String::from("x");
for _ in 0..2 {
    shout(s);          // error[E0382]: value moved here, in previous iteration of loop
}
```

### 8. Reassigning after a move
A moved-from variable can be given a new value, if it's `mut`:
```rust
let mut s = String::from("one");
let t = s;                     // s is now moved-out
s = String::from("two");       // s owns a fresh value; fine
println!("{} {}", s, t);
```

## Common pitfalls
- **Using a value after passing it to a function.** Passing moves it unless the type is `Copy`.
- **Cloning to make errors go away.** It works, but costs memory and hides design problems; borrow instead (2.3).
- **Thinking a move copies the heap data.** Only the small stack part is copied; the buffer stays put.
- **Forgetting that `for x in vec` consumes the vector.**
- **Expecting a value to be dropped when it's moved.** It's dropped once, by its final owner.
