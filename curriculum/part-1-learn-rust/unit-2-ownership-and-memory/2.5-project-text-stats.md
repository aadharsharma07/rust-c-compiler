# Lesson 2.5 — Project: text statistics tool
**Part:** 1 — Learn Rust · **Unit:** 2 — Ownership and Memory · **Type:** Project · **Est. time:** 4–6 h · **Tests:** none
**Prerequisites:** lessons 1.1–2.4

## Overview
You'll build `textstats`, a command-line tool that reads a text file and reports how many lines,
words and characters it has, plus its most frequent words (a small cousin of the Unix `wc`
command). It exercises everything from this unit: one owned `String` holding the whole file,
borrowed `&str` slices for lines and words, functions that take `&str`, and careful thinking
about who owns what. That shape (read a file into one `String`, then walk it by reference) is
exactly how your C compiler will start.

## The lesson
This section teaches the few new pieces of standard library you need. Ownership, borrowing and
string methods come straight from 2.2–2.4.

### 1. Command-line arguments
In Python you'd read `sys.argv`. In Rust, `std::env::args()` gives you the arguments one at a
time, as owned `String`s. Element 0 is the program's own path, as in Python.
```rust
use std::env;

fn main() {
    let args: Vec<String> = env::args().collect();   // gather them into a Vec<String>
    println!("program: {}", args[0]);
    println!("got {} extra argument(s)", args.len() - 1);
    for (i, a) in args.iter().enumerate().skip(1) {
        println!("arg {}: {}", i, a);
    }
}
```
`.collect()` turns a sequence of items into a collection (it's like `list(...)` in Python); the
`Vec<String>` annotation tells it which collection to build. Iterators get their own lesson in 4.3.

When running through cargo, put your program's arguments after `--` so cargo doesn't treat them
as its own: `cargo run -- notes.txt --top 5`. `args[1]` panics if there is no argument, so check
`args.len()` first.

### 2. Reading a whole file
Python's `open(path).read()` becomes:
```rust
use std::fs;

let contents: String = fs::read_to_string("poem.txt").expect("could not read poem.txt");
```
`read_to_string` returns a `Result` (as in 1.5): success with the file's text as an owned
`String`, or an error (file missing, no permission, not valid UTF-8). For now, handle it with a
`match` that prints a helpful message and exits, rather than `expect` crashing with an ugly panic:
```rust
use std::process;

let text = match fs::read_to_string(path) {
    Ok(t) => t,
    Err(e) => {
        eprintln!("error: cannot read {}: {}", path, e);   // eprintln! prints to stderr
        process::exit(1);                                   // exit status 1 = failure
    }
};
```
`process::exit` never returns, so the `Err` arm doesn't need to produce a `String`; the compiler
knows. Note the ownership story: `text` **owns** the file's contents. Everything else in your
program should **borrow** from it with `&str`. You'll do this properly with `?` in 3.3.

### 3. A first look at `HashMap`
A Python `dict` is Rust's `HashMap` (full lesson in 3.4). The basics:
```rust
use std::collections::HashMap;

let mut capitals: HashMap<String, String> = HashMap::new();
capitals.insert("France".to_string(), "Paris".to_string());
capitals.insert("Japan".to_string(), "Tokyo".to_string());

match capitals.get("Japan") {          // get returns an Option: Some(&value) or None
    Some(city) => println!("{}", city),
    None => println!("unknown"),
}
println!("{}", capitals.contains_key("Peru"));   // false
for (country, city) in &capitals {               // iterate by reference; order is arbitrary
    println!("{} -> {}", country, city);
}
```
- `Option` is like `Result` but for "maybe there's a value": `Some(x)` or `None`. Match on it
  like `Ok`/`Err`. (3.3 covers it.)
- Like a Python `dict`, iteration order is **not** sorted or insertion-ordered. If you need an
  order, collect the entries into a `Vec` and sort it.
- Keys can be owned (`String`) or borrowed (`&str`). A `HashMap<&str, u32>` whose keys are slices
  of your file's `String` avoids allocating a `String` per key. The compiler will make sure the map
  doesn't outlive the text it borrows from (2.3).
- To update a value in place, look at the `get_mut` method and the `entry` API in the
  [`HashMap` docs](https://doc.rust-lang.org/std/collections/struct.HashMap.html). Reading the docs
  and choosing between them is part of this project.

### 4. Sorting a `Vec`
`v.sort()` sorts in place when the elements have a natural order. To sort by a custom rule, use
`sort_by` with a small **closure** (an inline function, like a Python `lambda`; 4.3 covers them).
Toy example: sort people by age, oldest first, then by name:
```rust
let mut people = vec![("Bo", 31), ("Al", 45), ("Cy", 31)];
people.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0)));
// [("Al", 45), ("Bo", 31), ("Cy", 31)]
```
`a.cmp(&b)` returns an `Ordering` (you met it in 1.5). Swapping `a` and `b` reverses the order,
and `.then(...)` breaks ties. Python's equivalent is `sorted(people, key=lambda p: (-p[1], p[0]))`.
Sorting with a tie-breaker matters: without one, the output order of equal items can vary, and
your tool's output wouldn't be reproducible.

### 5. Designing for ownership
Before coding, decide the shape:
- `main` owns the arguments and the file's `String`.
- Each statistic is a function that **borrows** the text (`&str`) and returns a number, or a
  collection whose keys may borrow from the text.
- Nothing needs `clone()`. If you find yourself cloning the whole text, stop and rethink who
  needs to own what.

Write each function so you can test it on a short literal like `"the cat\nthe hat\n"` before
pointing it at a real file. Think about the definitions, too: what is a "word"? Is `"Cat,"` the
same word as `"cat"`? Pinning down definitions before coding is a big part of compiler work
(the C standard is a long list of such definitions).

## Build
Create `cargo new textstats`. Write all the code yourself.

**Specification**
1. Usage: `textstats <FILE> [--top N]`. `N` defaults to 10.
2. With no file argument, print a usage line to stderr and exit with status 1. If `--top` is
   given without a valid positive whole number, do the same with a clear message.
3. If the file can't be read, print `error: cannot read <FILE>: <reason>` to stderr and exit with status 1. Never panic.
4. Print, in this order:
   - `lines:` the number of lines (as `str::lines` counts them);
   - `words:` the number of words, where words are separated by whitespace;
   - `chars:` the number of Unicode characters (not bytes);
   - `bytes:` the number of bytes;
   - `longest line:` the 1-based line number and its length in characters (first one if tied);
   - `top N words:` the N most frequent words with their counts, one per line, most frequent
     first, ties broken alphabetically. For counting, a word is **lower-cased** and has leading and
     trailing non-alphanumeric characters stripped (so `"Cat,"`, `"cat"` and `"(CAT)"` all count
     as `cat`); skip pieces that become empty (like a lone `"--"`).
5. An empty file prints zeros, `longest line: none`, and an empty top-words list.
6. The file's text must be read into **one** `String` and everything else must borrow from it.

**Suggested order of small steps**
1. Read and print the arguments; handle the missing-file case.
2. Read the file with a `match`; handle the error case. Print the byte count.
3. Add line, word and char counts, each as a separate function taking `&str`. Check them against
   a tiny file you can count by hand, and against `wc -l -w -m -c` (note: `wc` counts newline
   characters, so a file without a final newline may differ by one line; explain any difference).
4. Add the longest-line report.
5. Write the word-normalising function (hint: look at `trim_matches` with a closure or
   `char::is_alphanumeric` in the `str` docs). Test it on tricky inputs.
6. Count frequencies in a `HashMap`, then move the entries into a `Vec`, sort, and print the top N.
7. Add `--top N` parsing.

**Test files to make**: an empty file; a one-line file without a trailing newline; a file with
accents and an emoji (so chars ≠ bytes); a long public-domain text (e.g. a book from Project
Gutenberg, which you download yourself).

**Stretch goals (optional)**
- Accept several files and print stats for each plus a total.
- Read from standard input if no file is given (look at `std::io::read_to_string`).
- A `--stopwords` flag that ignores common words such as "the" and "and".

## Check your understanding
1. Which variable owns the file's text in your program? Which values borrow from it, and what stops them outliving it?
2. Why did you take `&str` (not `String` or `&String`) as the parameter of your counting functions?
3. Why do `chars` and `bytes` differ for some files? Which of your test files shows it?
4. If your `HashMap` keys are `&str`, what would go wrong if you tried to return the map from a function that also read the file itself? What would you change?
5. Why does sorting need a tie-breaker for reproducible output?

## Common pitfalls
- **Using `len()` for the character count.** It counts bytes.
- **Allocating a `String` per word by habit** when a slice would do (fine for correctness, but know which you chose and why).
- **Panicking with `expect` or `args[1]`** on bad input. The spec says exit cleanly with a message.
- **Forgetting `--` with `cargo run`**: `cargo run --top 5` passes `--top` to cargo.
- **Unsorted output** from iterating a `HashMap` directly.
