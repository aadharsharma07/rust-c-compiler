# Lesson 1.3 — Lexing C
**Unit:** 1 — The Whole Pipeline for `return 2;` · **Type:** Builds lexer · **Est. time:** 4–6 h · **Tests:** ch. 1 (`--stage lex`)
**Prerequisites:** lessons 0.5, 1.2

## Learning goals
- Define token, lexeme and token kind, and list the chapter-1 C tokens.
- Apply the longest-match rule and the word-boundary rule (why `123abc` is an error, not two tokens).
- Distinguish keywords from identifiers with a lookup *after* matching an identifier.
- Decide between tokens that own their text (`String`) and tokens that borrow it (`&'a str`), and meet lifetime annotations.
- Report lexical errors as values, so `rcc --lex` exits non-zero on bad input.

## Key ideas
**Tokens for chapter 1.** After preprocessing, the input is plain text with no comments or
`#` lines. The lexer needs:

| Kind | Pattern (informal) | Examples |
|---|---|---|
| Identifier | letter or `_`, then letters/digits/`_` | `main`, `_x1` |
| Constant | one or more digits, *not followed by* a letter, digit or `_` | `2`, `100` |
| Keywords | identifiers that are reserved | `int`, `void`, `return` |
| Punctuation | single characters | `(` `)` `{` `}` `;` |

Whitespace (spaces, tabs, newlines) separates tokens and is discarded. Anything else
(`@`, `\`, `` ` ``, `$`) is a lexical error.

**Longest match.** At each position, take the longest prefix that forms a token. `returnx` is one
identifier, not `return` + `x`. Later you'll have `-` vs. `--` and `<` vs. `<=`, where the same rule
decides. **Keywords:** lex an identifier, then check whether its text is a keyword; this avoids
`int1` being lexed as `int` followed by `1`.

**Word boundary.** C requires a constant to end at a word boundary. `1foo` is not `1` then `foo`;
it is an invalid token, and chapter 1's `invalid_lex` tests check exactly this.

**Worked example.** Input `int main(void) { return 2; }` becomes
```
Int  Identifier("main")  OpenParen  Void  CloseParen  OpenBrace
Return  Constant(2)  Semicolon  CloseBrace
```
Input `int main(void) { return 0@; }` fails at `@`; input `return 1foo;` fails at `1foo`.

**Owned vs. borrowed lexemes.** An identifier token can store its own `String` (simple, a copy),
or a `&'a str` slice of the source (no copy, but the tokens can't outlive the source text, which
Rust expresses with a lifetime parameter `'a` on the token type). Either works for this course;
the borrowed version is a good first contact with lifetimes. Constants can be parsed to an integer
now or kept as text until the parser; choose one and justify it.

**Lexing approach.** Two common designs: (a) walk the characters with a peekable iterator or byte
index and dispatch on the first character; (b) try a list of regular expressions at the current
position and take the longest match (the `regex` crate, anchored with `^`). (a) is dependency-free
and teaches more Rust; (b) is closer to a formal description. Either is fine.

## Questions the tutor should ask you
- Your lexer sees `r`. How does it decide between keyword `return` and an identifier like `result`?
- What should happen at `123abc`? Where in your design does that check live?
- If tokens borrow from the source string, who owns the source, and how long must it live?
- What information would make an error message useful (`unexpected character '@' at line 3`)? Is it worth storing now?
- How will you test the lexer independently of the driver?

## What you build
A `lexer` module with one public entry point: given the preprocessed source text, return either
a list of tokens or a lexical error.
- **Token type:** an enum with one variant per kind: identifiers and constants carry data, keywords
  and punctuation are dataless variants. Derive `Debug`, `PartialEq` and `Clone` so tests can compare tokens.
- **Error type:** carries at least the offending character or text; a position (byte offset or
  line/column) is recommended.
- **Behaviour:** skip whitespace; lex identifiers/keywords, constants, and the five punctuation
  characters; reject anything else; reject constants immediately followed by a word character.
  Empty input yields an empty token list (the parser will reject it).
- **Driver:** the compile step now lexes. With `--lex`, stop after lexing and exit 0 on success.
  On error, print it to stderr and exit non-zero. Later stages stay stubbed.
- **Unit tests** (`#[cfg(test)]`): the worked example, `1foo`, `@`, `int1` (identifier),
  extra whitespace/newlines, and an empty file.

## Rust focus
- Iterating characters: `str::chars`, `char_indices`, and `Peekable::peek`: https://doc.rust-lang.org/std/iter/struct.Peekable.html
- `char` classification: `is_ascii_alphabetic`, `is_ascii_digit`, `is_ascii_whitespace`: https://doc.rust-lang.org/std/primitive.char.html
- String slicing by byte range: https://doc.rust-lang.org/book/ch08-02-strings.html#slicing-strings
- Lifetimes in structs and enums: https://doc.rust-lang.org/book/ch10-03-lifetime-syntax.html
- Parsing digits: `str::parse`: https://doc.rust-lang.org/std/primitive.str.html#method.parse
- Unit tests: https://doc.rust-lang.org/book/ch11-01-writing-tests.html

A lifetime annotation only names a relationship, it doesn't change how long anything lives:
`enum Token<'a> { Identifier(&'a str), /* … */ }` reads "an identifier token can't outlive the text it points into".

## Common pitfalls
- Matching keywords by prefix, so `returnValue` lexes as `return` + `Value`.
- Accepting `1foo` as two tokens: the most common chapter-1 lex failure.
- Slicing a `&str` by character count instead of byte index (fine for ASCII, a panic waiting to happen elsewhere).
- Forgetting tabs and `\r` as whitespace.
- Infinite loops when no rule matches and the position never advances.
