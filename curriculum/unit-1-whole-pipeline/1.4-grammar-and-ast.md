# Lesson 1.4 — Grammar & AST
**Unit:** 1 — The Whole Pipeline for `return 2;` · **Type:** Builds AST + recursive-descent parser · **Est. time:** 5–8 h · **Tests:** ch. 1 (`--stage parse`)
**Prerequisites:** lessons 0.4, 0.6, 1.3

## Learning goals
- Read and write a grammar in EBNF, distinguishing terminals (tokens) from non-terminals.
- Explain the difference between concrete syntax (parse tree, every token) and abstract syntax (AST, only meaning).
- Translate a grammar into a recursive-descent parser: one function per non-terminal.
- Model the AST with Rust structs and enums so invalid trees are hard to represent.
- Produce precise parse errors and reject trailing junk after a complete program.

## Key ideas
**The chapter-1 grammar.** Quoted strings are terminals (tokens), `<angle>` names are non-terminals:
```
<program>    ::= <function>
<function>   ::= "int" <identifier> "(" "void" ")" "{" <statement> "}"
<statement>  ::= "return" <exp> ";"
<exp>        ::= <int>
<identifier> ::= an Identifier token
<int>        ::= a Constant token
```
This tiny grammar fixes a lot: exactly one function, returning `int`, taking `void`, with exactly
one `return` statement whose expression is a constant.

**Abstract syntax.** The AST keeps only what later stages need. Written in a compact ASDL-like
notation:
```
program   = Program(function_definition)
function_definition = Function(identifier name, statement body)
statement = Return(exp)
exp       = Constant(int)
```
Parentheses, braces, `int`, `void` and `;` vanish: they guided parsing but carry no meaning yet.
Note the AST is *not* a mirror of the grammar; it will diverge more as the language grows
(e.g. parentheses in expressions never become nodes).

**Worked example.** Tokens `Int Identifier("main") ( Void ) { Return Constant(2) ; }` parse to
```
Program(
    Function(
        name = "main",
        body = Return(Constant(2))))
```

**Recursive descent.** Each non-terminal becomes a function that consumes tokens and returns an
AST node (or an error). Terminals are consumed with a helper such as "expect the next token to be
X, else fail". Parsing `<function>` is just a sequence: expect `int`, parse identifier, expect
`(`, expect `void`, expect `)`, expect `{`, parse statement, expect `}`. When there are
alternatives (from Unit 2 on), the function peeks at the next token to choose.

**End of input.** After parsing `<program>`, the token stream must be empty. `int main(void)
{ return 2; } foo` is invalid even though a valid program is a prefix of it.

## Questions the tutor should ask you
- Which tokens in `int main(void) { return 2; }` show up in the AST, and which don't? Why?
- What should the parser do when the input ends in the middle of a function?
- How does your parser keep track of its position: an index, an iterator, or by consuming a `Vec`? What does each cost?
- Should the AST store the function name as `String` or borrow it from the tokens? What does each choice mean for lifetimes later?
- Why does a parser function return `Result<Node, Error>` instead of panicking?

## What you build
- An `ast` module: one type per AST node kind above (a struct for program and function, enums for
  statement and expression so they can grow new variants). Derive `Debug`, `Clone`, `PartialEq`.
- A `parser` module with a public entry point: tokens in, `Program` or parse error out. Internally,
  one function per non-terminal and a small "expect token" helper.
- **Parse errors:** say what was expected and what was found (or "end of input"). Cover:
  missing tokens, wrong keyword, a non-constant expression, missing `;`, mismatched braces,
  and extra tokens after the function.
- **Driver:** `--parse` now lexes and parses, then stops. Valid input exits 0; invalid exits non-zero.
- **Pretty-printing:** a readable dump of the AST (via `{:#?}` or your own `Display`) behind a debug
  flag or used in tests; it will save you hours later.
- **Unit tests:** the worked example, plus at least four invalid token sequences.

## Common pitfalls
- Not checking for leftover tokens after the program; the "extra junk" invalid test will catch you.
- Returning a placeholder node on error instead of an `Err`, then getting confusing failures downstream.
- Mirroring the concrete syntax in the AST (nodes for parentheses or keywords).
- Indexing past the end of the token vector and panicking instead of returning "unexpected end of input".
- Fighting the borrow checker by holding a reference into the token list while also advancing a mutable position; consider returning owned data or cloning cheap tokens.
