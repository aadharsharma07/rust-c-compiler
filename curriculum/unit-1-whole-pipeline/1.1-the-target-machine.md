# Lesson 1.1 — The Target Machine
**Unit:** 1 — The Whole Pipeline for `return 2;` · **Type:** Learning only · **Est. time:** 3–4 h · **Tests:** none
**Prerequisites:** lessons 0.1–0.7

## Learning goals
- Name the x86-64 general-purpose registers, their 32-bit sub-registers, and the special roles of `%rax`, `%rsp`, `%rbp` and `%rip`.
- Read and write simple AT&T-syntax assembly: `mov`, `ret`, size suffixes, `$` immediates, `%` registers.
- Explain what the preprocessor, compiler, assembler and linker each do, and what file each produces.
- Get an x86-64 toolchain and the test suite working on your machine (including Apple Silicon).
- Use `clang -S` and Godbolt to see what a real compiler emits, and know which parts to ignore.

## Key ideas
**Registers.** x86-64 has 16 general-purpose 64-bit registers: `rax rbx rcx rdx rsi rdi rbp rsp r8–r15`.
Each has a 32-bit lower half: `eax ebx ecx edx esi edi ebp esp r8d–r15d`. Writing a 32-bit
register zeroes the upper 32 bits of the 64-bit register. C `int` is 32 bits, so for now you
will mostly use the `l` (long word = 32-bit) instruction forms. `%rsp` is the stack pointer,
`%rbp` the frame (base) pointer, `%rip` the instruction pointer; `RFLAGS` holds condition flags.

**The return value.** Under the System V ABI (Linux and macOS on x86-64) an `int` result is
returned in `%eax`. When `main` returns, the C runtime passes that value to `exit`. The shell's
`$?` shows only the low 8 bits, so `return 258;` shows `2`.

**AT&T syntax** (what `gcc`/`clang` emit and the test suite expects): `op source, destination`.
Immediates start with `$`, registers with `%`, and the mnemonic carries a size suffix
(`b`=8, `w`=16, `l`=32, `q`=64 bits). Memory operands look like `-4(%rbp)` (address `rbp - 4`).
Intel syntax (`mov eax, 2`) reverses the operand order; don't mix the two up when reading docs.

**Worked example.** The whole program `int main(void) { return 2; }` on macOS:
```
	.globl	_main        # make the symbol visible to the linker
_main:                   # label = address of the next instruction
	movl	$2, %eax     # put the constant 2 in the return register
	ret                  # pop the return address and jump to it
```
On Linux the symbol is `main` (no underscore), and you add `.section .note.GNU-stack,"",@progbits`
at the end so the linker doesn't mark the stack executable.

**The toolchain.**

| Step | Tool | In → out |
|---|---|---|
| Preprocess | `gcc -E -P` | `prog.c` → `prog.i` (macros expanded, comments gone, no line markers) |
| Compile | **your `rcc`** | `prog.i` → `prog.s` (assembly text) |
| Assemble | `as` (via `gcc`) | `prog.s` → `prog.o` (machine code + symbol table) |
| Link | `ld` (via `gcc`) | `prog.o` + C runtime startup → `prog` executable |

The assembler only encodes instructions; the linker resolves symbols (like `main`, later
`printf`) and adds startup code that calls `main`. That is why `.globl` matters.

**Apple Silicon.** Your Mac's CPU runs arm64, but the course targets x86-64. Two options:
1. **Rosetta 2:** install with `softwareupdate --install-rosetta`, then start an x86-64 shell
   with `arch -x86_64 zsh` (`uname -m` should print `x86_64`). Pass `-arch x86_64` to
   `clang`/`gcc` when assembling and linking: `clang -arch x86_64 prog.s -o prog`. The resulting
   binary runs transparently under Rosetta. (Your `rcc` itself can stay a native arm64 binary; it
   only writes text and calls `gcc`, which is why the explicit `-arch x86_64` is the robust choice.)
2. **Docker:** `docker run --platform linux/amd64 -it -v "$PWD":/work -w /work rust bash` gives
   an emulated x86-64 Linux with `gcc`. Then you target Linux conventions (no `_`, GNU-stack note).

**Setting up the test suite.** Clone `https://github.com/nlsandler/writing-a-c-compiler-tests`
next to your project (it needs Python 3.8+). Run `./test_compiler --check-setup` from the x86-64
shell or container. Later you will run `./test_compiler /path/to/rcc --chapter 1`, optionally with
`--stage lex|parse|tacky|codegen`. Browse `tests/chapter_1/` to see valid and invalid inputs.

**Reading real compiler output.** `clang -S -O0 -arch x86_64 -fno-asynchronous-unwind-tables return_2.c`
produces extra noise: `.section __TEXT,__text`, `.build_version`, `.p2align`, maybe `.cfi_*`
directives, a `pushq %rbp`/`movq %rsp, %rbp` prologue, and at `-O0` a spare `movl $0, -4(%rbp)`.
Try `-O2`: it shrinks to the `movl $2, %eax` / `ret` pair above (older clang prints `retq`).
On https://godbolt.org choose "x86-64 gcc" or "x86-64 clang" — AT&T syntax is the default output.

## Questions the tutor should ask you
- Why does `main` put its result in `%eax` rather than `%rax`, and what happens to the upper half of `%rax`?
- If you run a program that does `return 300;`, what will `echo $?` print and why?
- What does the linker know that the assembler doesn't? What would go wrong without `.globl`?
- In `movl $2, %eax`, which operand is the source? How would Intel syntax write it?
- On your machine, which process actually executes x86-64 instructions, and how do you know?

## Common pitfalls
- Reading Intel-syntax tutorials and getting operand order backwards.
- Forgetting the `_main` prefix on macOS (linker error: `Undefined symbols ... _main`) or adding it on Linux.
- Running the test suite in a native arm64 shell on Apple Silicon: executables fail to run or link as arm64.
- Treating `.cfi_*` and `.build_version` directives as something you must reproduce; you don't.
- Expecting `$?` to show values above 255.
