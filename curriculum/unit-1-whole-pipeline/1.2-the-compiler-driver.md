# Lesson 1.2 — The Compiler Driver
**Unit:** 1 — The Whole Pipeline for `return 2;` · **Type:** Builds `rcc` CLI + stage flags · **Est. time:** 3–5 h · **Tests:** none (manual smoke test; ch. 1 stages start passing from 1.3)
**Prerequisites:** lessons 0.7, 1.1

## Learning goals
- Explain what a compiler *driver* is and why `gcc`/`clang` are drivers, not just compilers.
- Design the `rcc` command-line interface the test suite expects, including stage-stopping flags.
- Run external programs from Rust, check their exit status, and propagate failure as a non-zero exit code.
- Work with file paths (changing extensions) and temporary files, cleaning up after yourself.
- Structure `main` so that every error flows to one place via `Result` and `?`.

## Key ideas
**A driver orchestrates tools.** When you type `gcc prog.c`, the `gcc` binary runs the
preprocessor, the real compiler (`cc1`), the assembler and the linker in turn. Your `rcc` does
the same, but only the middle step is yours:
```
prog.c --(gcc -E -P)--> prog.i --(rcc's compiler)--> prog.s --(gcc)--> prog
```
`-E` means "preprocess only"; `-P` suppresses `# 1 "prog.c"` line markers, so your lexer never
sees them. `gcc prog.s -o prog` both assembles and links. On macOS (Rosetta setup) add
`-arch x86_64` to that last command so you link an x86-64 binary even if `rcc` itself is arm64.

**Stage flags let the test suite probe partial compilers.** The test script invokes your binary
as `rcc [flag] path/to/prog.c` and only checks the exit code for partial stages:

| Flag | Run up to and including | Writes files? |
|---|---|---|
| `--lex` | lexer | no |
| `--parse` | lexer + parser | no |
| `--codegen` | … + assembly generation (no emission) | no |
| `-S` | … + emission | leaves `prog.s`, no executable |
| *(none)* | everything | executable `prog` next to `prog.c` |

Unit 2 adds `--tacky` (stop after IR generation) and Unit 3 adds `--validate`. Design for
growth: a new stage should be one new variant, not a rewrite.

**Exit codes are the interface.** For a valid program every stage exits `0`. For an invalid
program (bad token, bad syntax) `rcc` must exit non-zero; the message on stderr is for you,
the test suite ignores it. A crash via `panic!` also exits non-zero, but it's sloppy: return
errors instead.

**Worked example.** `rcc --parse tests/chapter_1/valid/return_2.c` should: run
`gcc -E -P return_2.c -o return_2.i`, read `return_2.i`, lex, parse, delete `return_2.i`, and exit 0
with no output files left. `rcc return_2.c` should leave exactly one new file, `return_2`.

## Questions the tutor should ask you
- What should happen if `gcc -E` fails (for example, the file doesn't exist)? How will your driver know?
- Where do the intermediate files live, and who deletes them if the compile step fails halfway?
- How will you represent "which stage to stop after" so that adding `--tacky` later is a one-line change?
- What is the difference between a `String` from `env::args()` and a `&Path`? When do you need each?
- Why is it better to return a `Result` from a `run()` function than to call `process::exit` deep inside it?

## What you build
A `rcc` binary crate (`cargo new rcc`) whose `main` is only a thin wrapper:
- **Argument parsing.** Accept exactly one input path and at most one of `--lex`, `--parse`,
  `--codegen`, `-S`. Unknown flags, a missing path, or two paths → usage message on stderr, exit 1.
  Model the chosen stage as an enum (in prose: one variant per stopping point, ordered so that
  "did we get past stage X?" is easy to ask). Hand-parse `env::args()`; a crate like `clap` is
  optional and arguably hides what you are meant to learn.
- **Preprocess.** Run `gcc -E -P <input> -o <input with .i>`; on non-zero status, fail.
- **Compile.** A function that takes the preprocessed source text and the stage, and returns
  either assembly text (or nothing, for early stages) or an error. For now it is a stub: for a
  full compile, return a hard-coded `return 2` assembly program for your platform so you can test
  the rest of the driver. Lessons 1.3–1.6 replace the stub piece by piece.
- **Clean up.** Delete the `.i` file whether compilation succeeded or not.
- **Assemble + link.** For `-S`, write `<input>.s` and stop. Otherwise write the `.s`, run
  `gcc [-arch x86_64] <input>.s -o <input without extension>`, then delete the `.s`.
- **Errors.** One error type (an enum or a boxed error; your choice) that `main` prints to stderr
  before exiting with status 1.
- Put the driver in `main.rs` (or `driver.rs`) and leave room for `lexer`, `parser`, `codegen`
  and `emit` modules.

Smoke test by hand: `cargo build`, then `./target/debug/rcc path/to/return_2.c && ./path/to/return_2; echo $?`
prints `2`; `rcc --lex nonexistent.c` exits non-zero.

- `std::env::args` and iterating over arguments: https://doc.rust-lang.org/std/env/fn.args.html
- `std::process::Command`, `.status()`, `ExitStatus::success`: https://doc.rust-lang.org/std/process/struct.Command.html
- `std::process::exit` and exit codes: https://doc.rust-lang.org/std/process/fn.exit.html
- `std::fs::read_to_string`, `fs::write`, `fs::remove_file`: https://doc.rust-lang.org/std/fs/index.html
- `Path`/`PathBuf` and `with_extension`: https://doc.rust-lang.org/std/path/struct.Path.html
- Error handling with `Result` and `?`: https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html
- The Book's CLI project (separating `main` from logic): https://doc.rust-lang.org/book/ch12-03-improving-error-handling-and-modularity.html
- Conditional platform logic: `std::env::consts::OS` or `cfg!(target_os = "macos")`: https://doc.rust-lang.org/std/macro.cfg.html

A `Command` is a builder: each call returns the builder so you can chain, for example
`Command::new("gcc").arg("-E").arg(path)`.

## Common pitfalls
- Ignoring the `ExitStatus` of `gcc`: `Command::status()` returning `Ok` only means the process *ran*.
- Using `cfg!(target_os = ...)` and forgetting that inside Docker the target is Linux, which is exactly what you want.
- Leaving `.i`/`.s` files behind after errors; the test suite's directories fill with junk.
- Building output paths with string concatenation and breaking on paths containing dots (`my.dir/prog.c`).
- Writing files for `--lex`/`--parse`/`--codegen`; those stages must produce no output files.
- Printing errors to stdout instead of stderr.

## Done when
- [ ] `rcc prog.c` produces a runnable `prog` (from the stub) and leaves no `.i` or `.s` behind.
- [ ] `rcc -S prog.c` leaves `prog.s` and no executable.
- [ ] `--lex`, `--parse`, `--codegen` are accepted, produce no files, and exit 0 on valid input.
- [ ] Bad arguments and a missing input file exit non-zero with a message on stderr.
- [ ] `cargo clippy` is clean and `main` contains no business logic beyond calling `run()` and reporting errors.
- [ ] You can explain, without notes, what each of the four toolchain steps does and which flag stops where.
